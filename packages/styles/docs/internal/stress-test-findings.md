# Stress-test findings

## Purpose

[Roadmap](./roadmap.md)'s stress-test pass composes non-trivial, real-world screens against the published package and records where the model holds up and where it does not. This is that record: friction points, missing primitives, combinations that read wrong, and classes or tokens nothing exercises.

This document is a working list, not a design. Nothing here is a decision -- the roadmap's next planned step, feeding findings back into the contract, is where a finding turns into a versioned change to [Model](./model.md), `registry.json`, or the public docs, and each entry below stays until that happens or it is deliberately dropped.

**Method.** A screen's own CSS composes what the package has no opinion on -- page-level layout, a sidebar's grid, spacing between sections, sizing a full-width-by-default field for a toolbar it was never meant to fill. It does not correct what the package gets wrong. A local override that makes a confirmed defect look fine would mean the screen was no longer testing the package, and every fix here started as exactly that temptation -- a low-contrast progress track, a dialog rendering open on load -- restated to look right in the fixture until it was pointed out that a consumer restates nothing before finding the problem themselves. The screens render the real, broken behavior; the write-up below is where the correction belongs.

## `app-shell/`

A sidebar nav, a header, a toolbar (search, two filters, bulk actions), a data table with row actions, a selection-count/rows-per-page/page pagination footer, and a delete-confirmation dialog. Read under all five aesthetics and both themes.

### `.pixel`'s numerals are hard to tell apart at UI sizes

Pagination page numbers and the small "Showing 1-4 of 23" count are legible in the page's actual text content but visually ambiguous under `.pixel` at the sizes a real toolbar or pagination control uses -- `2`/`8` and `3`/`9` read alike at a glance. The existing playground pages mostly show `.pixel` at heading size or in generous matrix cells, which does not surface this; a dense screen does. Confirmed by reading the rendered text (correct) against the screenshot (visually ambiguous), not a rendering bug -- a legibility question about the bundled preview face at small sizes.

Not a code fix: the package ships no font binary for `.pixel` by design (`Not Planned` in the roadmap gives the reasons -- no bundled bitmap face clears the distinct-case, real-weight bar a substitute would need), and the playground's own CDN face is preview scaffolding, not something a consumer gets. There is nothing in `src/` to change. Left open as a documentation question: whether the aesthetic's own docs should carry a caveat about numeral legibility at small sizes, for whoever picks a real face to pair it with.

### Aesthetics own `border-radius` by design -- considered and not changed

Per [Model](./model.md)'s axis table. Tested whether that forecloses a consumer's own choice: `--ui-radius` overridden on a single `.btn` under `.pixel` (`0px` resting) took immediately (`8px` after `element.style.setProperty("--ui-radius", "0.5rem")`). A per-element override works the same way every other token override in this package does; there is no named escape hatch the way `.pill` is one for full roundness, but "unable to" is not accurate. Not disputed.

### `.soft`'s ground reads closer to `.solid` than intended -- landed for `.card` and `data-table`, `.panel`/`.alert` deliberately left alone

Measured before touching anything: swapping which token `.soft` grounds on barely moves a neutral card's result (12% ink onto `--color-background`, `--color-foreground`, or `--color-surface` land within 5-18 units of each other, since a near-black ink dominates regardless of which near-white ground it mixes onto). What actually reads as quiet is removing the tint at rest entirely.

`.card.soft` now composes `--color-foreground` untinted, with the intent tint and a `--color-surface` ground both arriving together on `.interactive`/`.hoverable` `:hover` (`src/components/surface.css`). The first attempt at this wrote `--ui-fill: 0%` directly on `.card.soft` and silently did nothing: `presentation.css`'s `.soft` is unlayered CSS, `@utility card` compiles into Tailwind's `utilities` cascade layer, and an unlayered declaration beats a layered one for the same property at any specificity -- so `.soft`'s `12%` always won regardless of selector. `src/box.css` now carries a `--_fill-cap` slot in its fill formula for exactly this, a token `.soft` never touches, and `.card.soft` sets that instead. A browser test now pins the numeric rest value so this cannot silently regress again.

**Corrected in the form/settings pass**, once the settings screen's danger-zone panel needed to become a card (see the write-up under `settings/` below) and no `.card.soft.destructive` reproduced its warm-pink rest: the untint above shipped unconditionally, for every intent, and that turned out to be broader than the measurement justified. Only a neutral `.card.soft` mixes near-black ink (the "reads as a slab" problem); a named intent's own hue at the same 12% already reads fine, measured against `.panel.destructive`'s identical `249, 225, 225`. `&.soft` now excludes every named intent (`:not(.primary, .secondary, .success, .warning, .destructive, .danger, .error, .info)`), so a named-intent `.card.soft` rests at its ordinary 12% wash again and deepens further on hover through the same generic `box-hover` step (12% to 26%) -- no ground shift needed, since it was never moved off a page-adjacent tone to begin with. `tests/browser/surfaces.spec.ts`'s assertions already read `-success`/`-primary` fills as "some distance greater than 2 from the page," which holds more strongly now than before, so nothing needed to change there.

`data-table`'s head has no hover or interaction state to move a reveal to, so its `.soft` head is untinted the same way, permanently, for every intent (`src/utilities/content.css`). The head-only version of this fix shipped first and created a new problem, caught by direct measurement rather than assumed away: an untinted head (`--color-foreground`, five units off the page background) sitting above a body still carrying the ordinary 12% tint (twenty-four units past the head) read backwards -- the seam that should mark one table read instead as the head belonging to the page and the body being the odd piece out. The table's own base fill now rests the same untinted way as the head, through the same `--_fill-cap` mechanism `.card.soft` uses. `.ghost` is unaffected and stays fully transparent, so `.soft` now differs from it by keeping an opaque, untinted plate and a head label strip, not by how much ink either carries. No hover-reveal was added to the table body -- row hover-to-highlight is a real, separate feature, left for later rather than folded into this fix.

`.panel` and `.alert` were considered for the same treatment and deliberately left alone. `.alert`'s whole job is status signaling, and it is never interactive -- an `.alert.soft.destructive` with the same fix would show no red anywhere, ever, which is a real regression in legibility rather than a quieter version of the same component. `.panel` carries the same tension at lower stakes (a `.panel.success` sidebar-of-the-day would flatten to grey-with-a-border). Both keep mixing `12%` at rest, unchanged.

Revisited once more against the live app-shell screen, after the fixes above made the bulk-actions bar (`.panel.primary.soft`) the one visibly strong-tinted surface left on the page. A narrower version was considered -- untint only a panel carrying no named intent (`none`/`.neutral`), leaving `.panel.primary`/`.success`/etc. tinted -- but not built: every other carve-out in this pass keys on _component_ and _presentation state_, never on _which intent_ is present, and this would be the first place fill amount depends on intent identity, needing a selector that lists which intents count as "loud" and stays in sync as intents are added. `.panel` stays unchanged; worth reopening if the same friction keeps surfacing.

It did, in the `form/`/`settings/` pass, and this time it landed -- see the write-up under `settings/` below rather than repeating it here. The intent-identity carve-out this section set aside turned out not to need "a selector that lists which intents count as loud": it is a single binary (named intent or not), the same bucket `--intent-fill-max` already carves out for exactly this "neutral ink reads louder" reason, not a per-intent list that grows as intents do.

### `.icon` ghost buttons read cramped at `.dense` in a real table's row-actions column

The app-shell members table's row actions (edit/remove/resend, `.btn.icon.ghost.dense`) looked visually undersized once seen next to the row's own badges and checkbox at real density -- `.compact` reads better there. Not a code change: `.dense` and `.compact` both work exactly as specified (this is the same floor-drop fix from the table above), it is a matter of which size tier suits a dense table's click targets. Fixture updated to `.compact` in `playground/app-shell/index.html`; left here in case the same preference shows up again and is worth a documented recommendation for table row-actions specifically.

## `form/`

A "create project" form: sectioned fields (project details, visibility, team access, billing), a validation-summary alert at the top, and several fields carrying `aria-invalid`/`.hint.error` together rather than one isolated invalid cell. Read under all five aesthetics and both themes.

### `.alert.soft.edged`'s border misses 3:1 for some intents, and which ones flips with the theme

The form's own validation-summary alert (`.alert.destructive.icon`) is the component's shipped default (`soft edged`, per the registry), not a chosen combination. Measured its border against its own fill -- the comparison [P3](./model.md#what-presentation-may-not-do)'s edge blend makes the right one -- across every intent on `.alert.soft.edged`, then reconfirmed the same numbers on the existing `feedback/` matrix so this is the shipped model, not something this fixture's markup did differently:

| Intent            | Dark theme | Light theme |
| ----------------- | ---------- | ----------- |
| none / `.neutral` | 1.46:1     | 1.70:1      |
| `.primary`        | 11.86:1    | 11.81:1     |
| `.secondary`      | 5.44:1     | 4.80:1      |
| `.success`        | 2.89:1     | 3.61:1      |
| `.warning`        | 4.51:1     | 2.38:1      |
| `.destructive`    | 2.56:1     | 4.09:1      |
| `.info`           | 2.48:1     | 4.09:1      |

Below 3:1 in dark theme: none, success, destructive, info. Below 3:1 in light theme: none, warning. `.panel.edged` composes the same seam and reproduces the same numbers -- confirmed against `settings/`'s destructive danger zone below (a panel when this was first measured; a card since the fix to `.card.soft` below, at identical numbers).

The mechanism is the one `model.md` already documents (P3: an edge blends toward the component's own fill by the fill amount) and the fix that shipped for `.card.soft.edged`'s border in the app-shell pass touched the same token, `--color-border`, one step in light theme only. That fix was tuned against a neutral card; it was never checked against all seven intents, and an intent's own hue plus a 12% fill lands at a different distance from `--color-border` depending on the intent and the theme, which is why the failing set is not the same set in both themes. Not fixed here: `--color-border`/`--intent-border` is what every soft-or-partial-fill component's edge blends toward, so a change reaches `.alert`, `.panel`, `.badge`, `.kbd`, `.pre`/`.code`, and any consumer composition using the same seam, across all seven intents and both themes -- a wider blast radius than the single-token nudge that fixed the card. Left open; see [Open threads](#open-threads).

### `.input-group` with a text affix instead of an icon -- landed

Every documented and shipped `.input-group` example is an icon child (`docs/usage/forms.md`, `forms/index.html`). The URL-slug field here uses a plain `<span>` of text (`codenhub.dev/`) as the leading child instead, to see whether the wrapper's fixed `gap-2` assumes an icon's footprint. First read as "considered, works" -- it renders without breaking, flush and vertically centered the same way an icon sits -- until a closer look at the actual screen showed the 8px gap between the prefix and the field read as a stray space: `codenhub.dev/` `acme-labs` rather than one glued path. Measured: the gap is exactly `.input-group`'s `gap-2`, the same fixed value an icon uses, with nothing else contributing (no extra letter-spacing bleed, no affix-specific rule). An icon reads that gap as normal breathing room for a distinct glyph; a text affix meant to glue onto the value does not.

Landed as a token rather than a new class: `--input-group-gap: 0.5rem` in `src/components/form.css`, read where `gap-2` used to be hardcoded. Icon compositions are unchanged -- the default is the same value they always had -- and a text affix sets `--input-group-gap: 0` on its own `.input-group` for the flush look. `docs/usage/forms.md` documents the pattern under Icons.

### `.pixel`'s numeral legibility reappears here

The counter ("57 / 240") and the alert's "3 fields" reproduce the same small-numeral ambiguity already recorded against the app-shell pagination controls. Same open documentation question, not a new one -- see the app-shell section above.

### Unchecked toggles read as disabled next to a checked one that varied by presentation -- landed

A real screen surfaced something the matrix pages never would: three radios and a switch, all unchecked, all reading as a pale, washed-out box barely distinguishable from the page -- close enough to `disabled`'s look (measured: `disabled` is the _same_ resting colors at `opacity: 0.58`, no separate palette) that an ordinary, enabled, unchecked control in a real form read as though it might not be interactive. Measured against the shipped model rather than assumed: a checkbox's resting fill was capped at `20%` regardless of which presentation class was on it -- `.checkbox.primary.solid` unchecked painted the identical `rgb(202 202 202)` a class-less checkbox did, because the cap won regardless of what `--ui-fill` asked for. Presentation was supposed to be the axis that differentiates the unchecked box and was not doing that job.

Meanwhile the _checked_ state was where presentation actually had room to act, and that room was a cost rather than a benefit on a real screen: `:checked` used to lift the fill cap and floor the result at `12%`, so `.solid` reached 100% and `.soft` stayed a pale tint with just the mark at full strength -- the classic ring-and-dot radio. A checkbox, a radio, and a switch each ended up with three different "on" identities to learn depending on which presentation class happened to be nearby, while the side of the axis that needed differentiating (unchecked) had none.

The fix moves the axis to the side that needed it. `:checked` now pins the fill by setting the floor equal to the cap (`100%`/`100%` instead of `100%`/`12%`), so `clamp()` returns exactly `100%` whatever `--ui-fill` asks -- one checked plate, whatever presentation is on the element. `checkbox`/`radio` raise their own resting cap from `20%` to `40%`, matching `.switch`'s already-measured value, so `.ghost` (0%), `.soft` (12%), and `.solid` (the cap) read as three distinct resting plates instead of three shades of one wash. Neutral toggles -- the common case, since most controls carry no intent class -- now lift `--intent-fill-max` unconditionally rather than only at `:checked`, so a plain `.checkbox` reaches the raised cap instead of being held at the 20% ceiling a neutral badge or card stays under.

One bug surfaced measuring the fix rather than guessing it worked: pinning the fill alone left a checked `.ghost`/`.soft` toggle with an opaque plate but a mark that still asked for `--ui-fg-on-fill: 0%` (no contrast ink, what `.ghost`/`.soft` declare) -- fill and mark within about 13 sRGB steps of each other, nearly invisible. Writing `--ui-fg-on-fill: 100%` directly into `:checked` did nothing, for the reason already on file for `--_fill-cap`: `.ghost`/`.soft` are unlayered CSS and `:checked` compiles into Tailwind's `utilities` layer, so the layered write loses to the unlayered one regardless of specificity. `--_on-fill`'s formula gained the same seam `--_fill-cap`/`--_fill-floor` already use -- a private `--_fg-on-fill-floor` nothing unlayered touches -- and `:checked` pins that instead.

`.ghost` is no longer unsupported on any toggle. It used to be: a checked one was a mark on nothing, a tick floating on the page, which is why the registry floored a cascaded `.ghost` at `12%` rather than publishing it. Pinning the checked fill removes the reason -- a checked `.ghost` toggle now renders the exact plate every other checked toggle does -- so its unchecked silhouette (0% fill, full edge) is a real, published look: `.edged`, no background, which is the look this pass's own read of the screen preferred. `registry.json`, `model.md`, `docs/usage/forms.md` and `docs/usage/composing.md`, and the `checkbox`/`radio`/`switch` matrices in `playground/forms/index.html` are all updated; `tests/browser/axes.spec.ts` and `tests/browser/forms.spec.ts` assert the new behavior (one checked plate regardless of presentation, three separated resting plates) in place of the old ones.

Approved as landed, a further look at the same screens moved which of the three resting plates is unclassed. All three toggles used to default to `.solid` -- `--_d-fill`/`--_d-fg-on-fill` in `form.css` named the same pair `.solid` does -- which put a bare, no-intent checkbox or switch at the loudest of the three plates the fix above exists to separate, next to fields and buttons that all default quieter. `.soft` is the default now: those two tokens name `.soft`'s pair (`12%`/`0%`) instead, so an unclassed toggle rests at the quiet tint and `.solid` is what a consumer writes to ask for the louder plate explicitly. Checked is unaffected either way -- the pin composes the same plate regardless of which presentation an element rests at. `registry.json`'s `default.fill` for `checkbox`/`radio`/`switch`, `model.md`'s defaults table, and the toggle tables in `docs/usage/forms.md`/`composing.md` are updated to match; `tests/browser/forms.spec.ts`'s switch test, which asserted the unclassed element matched `.solid`, now asserts it matches `.soft`.

## `settings/`

An account-settings page: profile, plan/usage, an API-keys table, a security card, and a destructive danger-zone section, stacked in `.sect-inn.narrow` (768px) -- a size between a component-matrix cell and the full app-shell width. Read under all five aesthetics and both themes.

### Danger zone reproduces the `form/` border finding

Measured as `.panel.destructive.edged` (the danger zone's markup at the time): 2.56:1 (dark) / 4.09:1 (light) border-against-fill, the same numbers `.alert.destructive.soft.edged` measured in `form/` -- see [that finding](#alertsoftedgeds-border-misses-31-for-some-intents-and-which-ones-flips-with-the-theme) rather than repeating the table. Confirms the issue is the shared edge-blend seam, not something specific to alerts. Re-measured as `.card.soft.destructive` after the danger zone changed component below: identical numbers, since both compose the same `--intent-border`/fill blend.

### Neutral panels, key caps, and code chips read as a slab -- landed

The same danger zone that reproduces the border finding above also read, once its warning color is set aside, like the strongest surface on either screen when it was still a panel -- and it was not alone: the API-keys table's `kbd` cells, the plain (`none`/`.neutral`) rows of `surfaces/`'s own panel matrix, and every neutral `code`/`pre` chip carry the same look. Measured before deciding anything: `.panel` (no intent) is `217, 217, 217` on a `250, 250, 250` page, and `.kbd`/`.code` (no intent) is `199, 199, 199` against a `229, 229, 229` `--color-surface` step -- both notably heavier than `.card.soft`'s already-fixed rest of `245, 245, 245`. Dark theme is the same shape, more exaggerated: neutral `kbd` measures `60, 60, 60`, overshooting even its own `--color-surface` ground (`38, 38, 38`).

The reason it is these three and not, say, `.alert`: 12% of `--color-text` (near-black) mixed onto a ground is a much more assertive move than 12% of an actual hue -- measured, a resting `.panel.destructive` is a gentle `249, 225, 225` warm wash, and `.kbd.destructive` a legible `252, 205, 208` chip, neither anything like the neutral numbers above. The complaint was never "soft is too strong," it is "neutral ink at 12% reads as a slab, colored ink at 12% doesn't" -- already a recognized distinction in the model (`--intent-fill-max: 20%` exists for exactly this reason on every component), just never applied to `--_fill-cap` before.

That is the shape of the fix: unlike `data-table`, which untints unconditionally for every intent because its head has nothing to reveal a tint into, `.panel`'s carve-out is scoped to no named intent, because neither a panel nor a key cap/code chip has a hover state to reveal a colored intent back into either, and `.panel` is edgeless by default, so the fill is the only channel a `.primary` bulk-actions bar or the destructive danger zone has to say what it is. This is the intent-identity carve-out the app-shell pass considered and set aside above -- reopened because the same friction surfaced again independently, and because it turns out to need only a single binary (named intent or not), the same bucket `--intent-fill-max` already keys on, not a per-intent list.

`.card.soft` needed the identical correction, caught by the very next thing this pass did: the settings screen's danger-zone panel (`.panel.destructive.edged`) reads well by color but sits at panel's padding scale, one tier below card's, so it misaligns against the sibling `.card`s around it on the page. The obvious fix -- make it a `.card.destructive` -- ran into `.card.soft`'s app-shell-era fix head-on: that fix untinted every intent unconditionally, so no `.card` variant reproduced the panel's warm-pink rest (`.card.destructive` is a plain, unfilled card with a red border; `.card.soft.destructive` was, until this correction, the same untinted `245, 245, 245` every other `.card.soft` rests at). `.card.soft` now carries the identical no-named-intent guard `.panel` does, so `.card.soft.destructive` rests at `249, 225, 225` -- pixel-identical to `.panel.destructive`, because both now compose the same ground and the same 12% formula for a named intent. The danger zone is `.card.soft.destructive` in `playground/settings/index.html` now, unchanged in color and aligned in padding.

`.panel` (`src/components/surface.css`) grounds on `--color-foreground` through the public `--ui-surface-ground` escape hatch -- the same token and value `.card.soft` already rests at -- and caps its fill to `0%`, permanently rather than hover-revealed, the same way `data-table`'s own base fill is. `.kbd`/`.code`/`.pre` (`src/utilities/content.css`) only drop the extra `--_fill-cap`; their ground stays `--intent-subtle`, which already resolves to a real, visible `--color-surface` step for neutral and needs no shift. Both carve-outs exclude `.solid`/`.ghost` (and every named intent) so an explicit presentation is never clamped to a cap it did not ask for -- the same guard `data-table`'s `:not(.solid, .ghost)` already uses.

One cost carries over from `.card.soft` rather than being introduced fresh: an own declaration always beats an inherited one, so `.panel`'s ground override also beats `.glass` setting the same public token on an ancestor for its translucent surface -- a neutral panel under `.glass` is quiet but opaque rather than blurred. `.card.soft` has shipped with this exact trade-off since the app-shell pass; nothing exercised it because the glass test suite only ever checked a default (ghost) card. `tests/browser/aesthetics.spec.ts`'s "reaches every surface" test used `panel-default-none` and now uses `panel-default-destructive` instead, for the same reason -- a named-intent panel proves glass reaches the component without hitting the new carve-out.

`.alert` and `.badge` share the identical formula and measure identically once composited (`alert-none` is `217, 217, 217` too; `badge`'s fill is alpha-based rather than grounded, but composites to about the same value against the page) -- left alone because neither was flagged, and an alert is rarely used with no intent in practice. `registry.json` is unaffected -- the published default for all four stays `soft`, only what a no-intent instance of `soft` composes to has changed, the same kind of change `.card.soft` made without a registry update either.
