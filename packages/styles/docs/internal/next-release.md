# Next release (draft)

Working title `0.2.0`. This is scratch space for the changelog text as fixes land, not a commitment to the version number, the scope, or the release date -- see [Stress-test findings](./stress-test-findings.md) for what is still open and why. Nothing here ships until it is copied into a real `docs/changelog/<version>.md` and the manifest version is raised in the same change that merges it.

## Landed so far

- **`.visually-hidden`**, a utility that hides content from sighted users while keeping it in the accessibility tree. It ships wherever the layout utilities do (`.`, `./native`, `./tw`, `./tw/native`, `./tw/utilities`), including the vanilla, ready-to-import ones (`.`, `/native`) that have no Tailwind utility layer of their own to supply `.sr-only` from; it is not part of `./components` or the narrower `/tw/*` component slices. Not named `.sr-only` itself: on a `/tw` entry, where the consumer's own Tailwind build already ships that name, a same-named utility of this package's own would silently collide with it -- the same reason `.data-table` is not named `.table`.
- **`dialog:not([open])`/`dialog[open]` restated in author origin.** The user agent already hides a `<dialog>` without `open` and centers it via `margin: auto` when shown, but both are user-agent origin, so `.card`'s own `display: block` and a global margin reset (Tailwind's Preflight, on the entries that carry it) silently beat them. A `<dialog class="card">` now hides until opened and centers when it is, without a dialog/modal component of its own -- `.card` stays the primitive a consumer composes it from.
- **`.icon` in `registry.json`.** The button's icon-only shape modifier was real, shipped, and documented (`docs/usage/buttons.md`) but absent from the machine-readable contract. Added under `modifiers.shape`.
- **`.icon` kept the wrong `min-width` floor under `.compact`/`.spacious`.** Only `.p-xs`/`.dense` used to drop `--control-height`'s floor for `.icon`; `.compact` and `.spacious` cut padding the same way but left the floor in place, so the glyph sat in a box far bigger than it needed. All three tiers now size `.icon` to its own padding.
- **`.chunky-tile`'s offset shadow read as a fill on a small `.icon` button.** The tile bar is a flat 4px offset at every size; on a ~20px `.btn.icon.dense`/`.p-xs` it sat close enough to the glyph's own footprint to read as a solid circle behind a `.ghost` button. Halved to 2px for that combination only.
- **`.progress`'s track failed WCAG 1.4.11 in both themes.** Measured under 1.2:1 against both the page and a `.soft` card, in light and dark. `--progress-surface` now mixes `--color-text-secondary`, which clears 3:1 (3.63-4.26:1 measured) against both, in both themes.
- **`.card.soft.edged`'s border was nearly invisible against its own fill in light theme.** `--color-border`'s light value moved one step, from neutral-300 to neutral-400. Dark theme, which already separated, is unchanged. Re-verified against `.card.soft`'s new untinted rest below: 2.37:1, better than the original fix's 1.70:1.
- **Table row rules stayed a 1px hairline under `.chunky-tile`'s 2px frame.** Row and boundary rule width now tracks `--_width` -- the same token the table's own outer frame uses -- instead of a fixed `1px`.
- **Elevation cascaded onto unclassed descendants.** A `.floating` dialog's ambient ×2 reached its own unclassed "Cancel"/"Remove member" buttons, doubling their shadow with nothing asking for that. `--ui-elevation`, `--elevation-y`, and `--elevation-blur` are now registered non-inheriting (`@property`, `inherits: false`): an elevation class lifts the element it is written on only. There is no longer a way to lift a whole unclassed subtree in one class -- each element that wants depth needs its own elevation class. `.tooltip.raised`/`.floating` needed a fix of their own alongside this: the bubble is a `::after` pseudo-element of a wrapper the classes are actually written on, and host-to-pseudo-element inheritance is exactly what `inherits: false` also cuts, even though wrapper and bubble are one component. `tooltip.css` carries the three tokens back across that gap through ordinary, still-inheriting proxies.
- **`.card.soft` read as assertive, close to `.solid`.** Measured first: swapping which token it grounds on (`--color-background` → `--color-foreground` → `--color-surface`) barely moves a neutral card's result, 5-18 units, because 12% of near-black ink dominates regardless of the near-white ground it lands on. `.card.soft` now rests fully untinted -- `--color-foreground`, effectively `--ui-fill: 0%` -- with the intent tint and a `--color-surface` ground both appearing together on `.interactive`/`.hoverable` `:hover`. `.solid` and `.ghost` are unaffected, and a non-interactive `.card.soft` (neither class) has no hover state to reveal into and stays at the quiet rest permanently.

  The first attempt at this wrote `--ui-fill: 0%` directly on `.card.soft` and silently did nothing: `presentation.css`'s `.soft` is unlayered CSS and `@utility card` compiles into Tailwind's `utilities` cascade layer, and an unlayered declaration beats a layered one for the same property at any specificity, so `.soft`'s `12%` always won regardless of how the override was written. `box.css` now carries a `--_fill-cap` slot in its fill formula for exactly this -- a token `.soft` never touches, so nothing contests it -- and `.card.soft` sets that instead. A browser test (`surfaces.spec.ts`) now pins the numeric rest value so this cannot silently stop working again.

- **`data-table`'s `.soft` read closer to `.solid` than `.card.soft` does, on both the head and the body.** The head-only fix below shipped first and created a new problem: an untinted head (`--color-foreground`, five units off the page) sitting directly above a body still carrying the ordinary 12% tint (twenty-four units past the head) read backwards -- the seam that should mark one table read instead as the head belonging to the page and the body being the odd piece out. The table's own base fill now rests the same way the head does, through the same `--_fill-cap` slot `.card.soft` uses (plus `--_d-ground`, box's own private ground slot, set to `--color-foreground` here): a `.soft` table -- including the common case of a bare `<table class="data-table">`, since `soft` is the published resting fill -- is an opaque, untinted `--color-foreground` plate throughout, head and body alike, for every intent. `.ghost` is unaffected (still box's default fully-transparent ground), so `.soft` now differs from it by keeping that quiet plate and a head label strip, not by how much ink either carries. No hover-reveal was added to the body -- a table has no single element to reveal a tint on the way a card's `.interactive`/`.hoverable` does, and giving rows their own hover-to-highlight behavior is a real feature in its own right, left for a later pass rather than folded into this fix.
- **A badge sitting inside the now-untinted table lost its own fill entirely** -- coloured text with no chip behind it. `--_fill-cap` inherits like any custom property, so `.data-table`'s `0%` cap was reaching every box nested inside it, not just the table itself, the same class of bug `--_d-ground` was already guarded against. `box.css`'s `@utility box` now restates `--_fill-cap: 100%` on every element that uses it, the same way it already restates `--_d-ground: transparent` -- an own declaration beats an inherited one at any specificity, so a nested badge, button, or chip always reads its own presentation regardless of what container it sits in.
- **`.input-group`'s gap read as a stray space next to a text affix.** `codenhub.dev/` followed by `acme-labs` in the form stress-test screen read as two pieces rather than one glued path -- measured as exactly the wrapper's fixed `gap-2`, tuned for an icon's breathing room and too much for text meant to sit flush. `--input-group-gap: 0.5rem` in `form.css` replaces the hardcoded value; icon compositions are unchanged, and a text affix sets `--input-group-gap: 0` on its own `.input-group` for the flush look.
- **A checked toggle varied by presentation into three different "on" identities, while every unchecked toggle read the same washed-out plate regardless of presentation** -- close enough to the disabled treatment (the same colors at a lower opacity, nothing else) that a real form full of ordinary, unchecked controls read as half-disabled. `:checked` now pins the fill (floor raised to equal the cap, `100%`/`100%` instead of `100%`/`12%`) so every presentation composes the same checked plate, the way a checked `.solid` already did. Presentation instead separates the _unchecked_ plate: `.checkbox`/`.radio` raise their own resting cap from `20%` to `40%`, matching `.switch`'s already-measured value, so `.ghost` (0%), `.soft` (12%), and `.solid`/default (the cap) read as three distinct plates. Neutral toggles -- the common case, since most controls carry no intent class -- now lift `--intent-fill-max` unconditionally rather than only at `:checked`, so a plain, unchecked `.checkbox` reaches the raised cap instead of the 20% ceiling a neutral badge or card stays under.

  Pinning the fill alone left the ink behind: `.ghost`/`.soft` ask for `--ui-fg-on-fill: 0%` (no contrast ink), so a checked one had an opaque plate and a mark that still read as though the plate were quiet. Writing `--ui-fg-on-fill: 100%` into `:checked` did nothing -- `.ghost`/`.soft` are unlayered CSS and `:checked` compiles into Tailwind's `utilities` layer, the same trap `--_fill-cap` already routes around for the fill itself -- so `--_on-fill`'s formula gained the same kind of seam, a private `--_fg-on-fill-floor` nothing unlayered touches, and `:checked` pins that instead.

  `.ghost` is no longer unsupported on any toggle: a checked one used to be a mark on nothing, and pinning the checked fill removes that, so its unchecked silhouette (no background, full edge) is a real, published look now. `registry.json`, `model.md`, `docs/usage/forms.md`, `docs/usage/composing.md`, the toggle matrices in `playground/forms/index.html`, and `tests/browser/axes.spec.ts`/`forms.spec.ts` are all updated.

  A further look at the same screens moved which plate is unclassed. All three toggles used to default to `.solid` -- the loudest of the three resting plates the fix above separates -- so a bare, no-intent checkbox or switch sat at the strongest tint on the page while every field and button around it defaulted quieter. `.soft` is the default now: `--_d-fill`/`--_d-fg-on-fill` in `form.css` name the same pair `.soft` does (`12%`/`0%`) instead of `.solid`'s, so an unclassed toggle rests at the quiet tint and a consumer reaches for `.solid` itself to ask for the louder plate. Checked is unaffected -- the pin composes the same plate regardless of which presentation an element rests at. `registry.json`'s `default.fill` for all three, `model.md`'s defaults table and the bounds-that-survive entry, and the toggle tables in `docs/usage/forms.md`/`composing.md` are updated to match; `tests/browser/forms.spec.ts`'s switch test, which asserted the unclassed element matched `.solid`, now asserts it matches `.soft`.

- **A neutral `.panel`, `.kbd`, `.code`, or `.pre` mixed 12% of near-black ink at rest and read as a grey slab, while the same 12% of an actual hue on a named intent already read fine.** Measured: neutral `.panel` was `217, 217, 217` on a `250, 250, 250` page (heavier than `.card.soft`'s already-fixed `245, 245, 245`), and neutral `.kbd`/`.code` was `199, 199, 199` against their own `229, 229, 229` `--color-surface` ground -- both notably softer once the extra wash is dropped, and neither problem shows up on a named intent (`.panel.destructive` is a gentle `249, 225, 225`, `.kbd.destructive` a legible `252, 205, 208`).

  Unlike `data-table`, which untints unconditionally for every intent because its head has nothing to reveal a tint into, this fix is scoped to the no-named-intent case only: neither a panel nor a key cap/code chip has a hover state to reveal a colored intent back into either, and `.panel` is edgeless by default, so its fill is the only channel a `.primary` bulk-actions bar or a `.destructive` danger zone has to say what it is -- untinting those unconditionally would silence them, not quiet them. `.panel` (`surface.css`) steps its ground to `--color-foreground` and caps its fill at `0%` for that case, permanently rather than hover-revealed, the same plate `.card.soft` already rests at; `.kbd`/`.code`/`.pre` (`content.css`) keep their existing `--intent-subtle` ground and only drop the extra wash. `.solid`/`.ghost` and every named intent are excluded from the guard, so an explicit presentation is never clamped to a cap it did not ask for. `.alert` and `.badge` measure identically at rest but are addressed separately, below.

  This is the intent-identity carve-out the app-shell pass considered and set aside below, reopened because the same friction surfaced again independently. It turns out to need only a single binary (named intent or not) -- the same bucket `--intent-fill-max` already keys on for exactly this "neutral ink reads louder" reason -- not the per-intent list that was the original worry. One cost carries over unchanged from `.card.soft`: an own declaration beats an inherited one, so the ground override also beats `.glass` setting the same public `--ui-surface-ground` token on an ancestor, meaning a neutral panel under `.glass` is quiet but opaque rather than blurred -- `.card.soft` has shipped with this trade-off since the app-shell pass, just never exercised by a test until now.

- **`.card.soft`'s own untint turned out to be broader than the measurement justified, caught fixing the danger-zone panel's padding above.** It shipped unconditional -- untinted for every intent, tint revealed on hover -- so no `.card` variant reproduced `.panel.destructive`'s warm-pink rest when the settings danger zone needed to become a card for its padding to line up with its sibling cards. `.card.soft` now carries the identical no-named-intent guard `.panel` does: a named intent rests at its ordinary 12% wash again and deepens further on hover through the same generic step (12% to 26%), while the no-intent case is unchanged. `.card.soft.destructive` now measures `249, 225, 225`, pixel-identical to `.panel.destructive` -- the danger zone is `.card.soft.destructive` now, same color, aligned padding.

- **A neutral `.alert` measured the identical `217, 217, 217` slab as the neutral `.panel`/`.kbd`/`.code`/`.pre` fix above, and got the same carve-out** (`feedback.css`): `--_fill-cap: 0%` plus the `--ui-surface-ground` step to `--color-foreground`, scoped to no named intent. It differs from `.badge` in one load-bearing way -- `.alert` keeps a border at rest whatever the fill (`--_d-border: 100%`, unconditional), so untinting it still leaves a framed box, just a quiet one instead of a grey slab. `.badge` was left alone for exactly that reason: it has no border to fall back on (`--_d-border: 0%`), so the identical fix was tried and measured live -- a neutral badge lands at `245, 245, 245`, and with no border that reads as bare text, not a chip. That is a real regression, the same failure mode the earlier, unconditional version of this fix caused for `.alert.soft.destructive`'s red -- so `.badge` keeps its 12% wash at rest, unchanged.

## Considered and left alone

- **`.badge`** was considered for the same no-named-intent carve-out `.alert` just got and set aside: it has no border at rest, so its fill is the only thing marking it as a chip at all. Measured live in the browser -- dropping the fill and regrounding to `--color-foreground`, the same treatment `.alert`/`.panel` use, lands a neutral badge at `245, 245, 245` with nothing to frame it, which reads as plain text rather than a quieter chip. A different fix (e.g. giving the no-intent case a border) might solve this properly, but that is a new mechanism, not a copy of this carve-out, and is left as its own open question rather than bundled in here.

- **`.panel` and `.alert`** were considered for the same untinted-at-rest treatment as `.card`/`data-table` and deliberately left out, in an earlier pass. Back then the fix under consideration was unconditional -- every intent, not just the neutral case -- and `.alert`'s whole job is status signaling: an `.alert.soft.destructive` untinted unconditionally would show no red anywhere, ever, a real regression rather than a quieter version of the same component. `.panel` carried the same tension at lower stakes. Both landed since, scoped to the no-named-intent case only -- `.panel` in the form/settings pass above, `.alert` in this one -- which was never the combination the original objection was about.

## Documented, not fixed

- **`.alert`/`.panel`'s soft-edged border misses 3:1 against its own fill for some intents, and which ones flips between themes.** Measured on the shipped default, not a chosen combination: any change reaches `--color-border`/`--intent-border`, the seam every soft-or-partial-fill component's edge blends toward (`.alert`, `.panel`, `.badge`, `.kbd`, `.pre`/`.code`), across all seven intents and both themes -- a wider blast radius than the single-token nudge that already fixed `.card.soft.edged`'s border. Raised with the maintainer and decided: recorded as a known characteristic in [Accessibility → Color and contrast](../accessibility.md#color-and-contrast) instead of chasing the token through every affected component. See [Stress-test findings](./stress-test-findings.md#form).
