# Build command

## Purpose

`chs build` lets a project that does not run Tailwind, with a JavaScript build or without one, get a stylesheet trimmed to the classes its templates use, as a bundler's Tailwind plugin gives a Tailwind project. It is the package's one route to a trimmed stylesheet outside Tailwind: the package publishes no compiled file per component family. Every such file would carry the theme, the reset, and the shared base, which the command writes for any content: 30,314 bytes minified of the 42,028 it writes for a page with one `.btn.primary`, measured on 0.11.0 before its release. A page that uses two families would load that floor twice from two files, where the command writes it once. A buttons file would also have to ship every intent, fill, edge, and modifier a button takes, 46,094 bytes through the command, or 107,299 with their ten variants, where a page pays only for the ones it names. It is deliberately thin: one `build` command that tree-shakes a stylesheet this package compiled, improved as real consumers need more. The source is `src/cli/`, bundled to `dist/cli.js` by `pnpm build:cli`, the last step of `pnpm build`; the tests are `tests/integration/cli.test.ts` and `tests/integration/purge.test.ts`. Public usage is in [Without a bundler](../integrating/without-a-bundler.md#build-only-the-classes-you-use).

## One package

The command ships inside `@codenhub/styles` as its `bin`, named `chs`, so a consumer runs it from a `package.json` script as `chs build …`, or as `npx @codenhub/styles build …`, which runs the package's only `bin`. `chs help` prints the usage and exits 0, as `--help` does; before 0.11.0's release it failed with `unknown command "help"`, though `help` is the first word a reader tries.

The public documentation never shows `npx chs`. An unrelated package named `chs` exists on npm, and `npx chs` runs it wherever this package is not installed. Checked against a packed tarball under npm 11.12 on Windows 11: with the package installed, both the script form and `npx @codenhub/styles build` build, and `npx @codenhub/styles --version` prints this package's version.

Rejected: an alias under the earlier `bin` name, `codenhub-styles`. The rename is a breaking change of a 0.x package, which the changelog records, and an alias would be a second name to document and remove later.

Rejected: a separate `@codenhub/styles-cli` package. A second package is only harder to use: a second name to find and install, a second version that has to be matched to the StyleKit version it builds, and a release order to get right, since the CLI cannot be published until the StyleKit release it depends on is out.

## The command tree-shakes; it does not compile

The command compiles nothing. `scripts/build-purge.mjs` runs Tailwind at this package's build and writes `dist/purge/`:

- `index.css`: the complete stylesheet, as `dist/index.css`, plus each intent, presentation, and modifier class under each of ten variants, such as `md:lg` and `hover:primary`.
- `classes.json`: the class names the command may drop.

`src/cli/purge.ts` parses `index.css` and drops each rule whose selectors cannot match the classes found in the content. Any other class in the stylesheet is one Tailwind always emits, so the command keeps it: `.dark`, `.theme-dark`, and `.theme-light`, which switch the theme, and `.disabled`. Any other class a script adds at run time, such as `.active` or `.indeterminate` on a progress bar, is a candidate like the rest, kept only when a file the command reads names it, which is why the guide's examples read the project's scripts too. Before 0.11.0 the guide said the output kept "the classes a page gets at run time", which a reader took to cover those two, and the bar lost its state. Rejected: keeping every class the documentation tells a script to add, which would be a second list of classes to keep in step with the documentation, and would ship the rules of every one of them to a page that uses none. Purged to every class, the output is `dist/index.css` byte for byte, which `tests/integration/purge.test.ts` holds.

Rejected: running Tailwind in the consumer's project, loading the `@tailwindcss/cli` and `tailwindcss` the consumer installs as optional peers, compiling `/tw` against their templates, and writing what Tailwind writes. It loses for three reasons:

- **It makes the consumer install Tailwind.** Two peers, `@tailwindcss/cli` and `tailwindcss`, kept within `>=4.3.2 <5`, for a consumer who otherwise has no JavaScript build at all; `npx @codenhub/styles build` in an empty folder cannot work, since no package manager installs an optional peer.
- **Its output varies with the consumer's Tailwind.** The same templates and the same StyleKit version can write a different stylesheet under a different 4.x patch, which this package can neither test nor pin.
- **It calls API Tailwind does not document.** To turn off the polyfills the CLI always writes, the command has to call `compile`, `Scanner`, and `optimize` from `@tailwindcss/node` and `@tailwindcss/oxide` in its own process, the API Tailwind's own integrations use but its documentation does not promise.

The command imports nothing beyond Node.js built-ins, which `tests/integration/cli.test.ts` checks of the bundle, and its output depends only on the package version and the content.

Cost accepted: every consumer installs `dist/purge/`, about 346 KB (29 KB gzipped) for `index.css` and 7 KB for `classes.json`, measured on 0.11.0 before its release, whether or not they run the command. That is far less than the 19 MB that `@tailwindcss/cli` and `tailwindcss` as regular `dependencies` would cost every consumer to make the bare `npx` work, which is rejected for that size.

Rejected: a fork of Tailwind's compiler or scanner inside the package. It would make this package maintain a CSS compiler to keep Tailwind's output, utilities included, for consumers who can run Tailwind themselves through `/tw`. Since 0.10.0, [a build of this package's own](./roadmap.md#a-build-the-package-owns-with-tailwind-as-an-adapter) compiles its source, and Tailwind is the `/tw` integration and the compiler of the variants in `dist/purge/`, and nothing else. That build is not the fork rejected here: it compiles this package's source and no Tailwind utility.

## No Tailwind utilities, ten variants

The command emits StyleKit classes only. A Tailwind utility such as `flex` or `mt-4` is not in `dist/purge/index.css`, so it is never found. Shipping utilities would mean shipping a fixed subset of Tailwind compiled in advance, and any subset is the wrong one for some project; a project that wants them runs Tailwind and imports `/tw`, which gives every utility and every variant. [Roadmap → Possible](./roadmap.md#possible) keeps open a command that generates a closed set of utilities instead of trimming a compiled one; this decision stands until that one is made.

The variants are a fixed list in `scripts/build-purge.mjs`: `sm`, `md`, `lg`, `xl`, `2xl`, `hover`, `focus`, `focus-visible`, `active`, and `dark`, on the intent, presentation (fill and edge), and modifier classes from `registry.json`, except `disabled`, which the documentation tells consumers to write as the attribute or the class. Each variant costs its copy of every class it applies to, about 3 KB minified for the axis classes alone, and a page pays only for the ones it uses, but every install carries them all.

Rejected: all of Tailwind's variants. 52 of them measured 197 KB in the source, and stacking the breakpoints on the states another 845 KB, for combinations few pages use. Rejected too: component classes, such as `btn` or `card`, under a variant; a component switched on at a breakpoint is better written as two elements or a layout helper, and doubling the components would double the source.

## Which classes the command may drop

A class may be dropped when it is a Tailwind candidate: naming it adds CSS to the build. `scripts/build-purge.mjs` finds them by adding each class of `dist/index.css` to a compiler one at a time and comparing the output's length, since the compiler keeps every candidate it was given. Reading them from the selectors of an empty build was rejected: those name component classes inside rules Tailwind always emits.

## Node.js version

The command supports Node.js 24 and newer, the line `.node-floor` names, and the package declares `engines.node` as `>=24`, as `docs/specs/packages-lifecycle.md` requires of a package with a CLI. The floor matters most to consumers who never run the command: a consumer below it is warned on install by npm, stopped by Yarn 1 and by npm or pnpm with `engine-strict`, and told nothing by plain pnpm 11, even when they only link the CSS. Until 0.11.0 it was `>=26`, the pinned major, and the audit of 0.11.0 found what that cost: on Node.js 24.11.0, pnpm with `engine-strict` refused the install with "Expected version: >=26", and on Node.js 22, `yarn add` failed with "The engine \"node\" is incompatible with this module", for a package whose stylesheets need no Node.js at all. So the floor is the lowest line CI tests, as that specification's rule for a package whose main deliverable runs without Node.js records, and the package's unit and integration suites run in the `floor` job of `docs/ci.md`. It is not the oldest release the code runs on: the newest API the command uses is `globSync` from `node:fs`, which Node.js 22 has, but no CI job runs 22. The command also checks the version itself when `build` runs, against the same major, and names both versions; the test "rejects a Node.js older than the engines floor" reads the floor from `package.json`, so the two cannot drift. The inlined scanner takes `globSync` from the default export of `node:fs` so that an older Node.js reaches that check: a named import of a missing export fails at load, before any code runs. Rejected: declaring no `engines.node`, as a browser-only package does, with the run-time check alone guarding the command; it would turn away no one, but it breaks the specification's rule for a package that runs on Node.js, and a consumer would learn the command's floor only from a failed build.

## Finding the package root

The command resolves everything from this package's own files, never through its package name: a package resolving itself by name depends on self-reference and on how it was installed. The running file is `src/cli/run.ts` in the tests and `dist/cli.js` once built, two different depths below the package root, so `findPackageRoot` walks up from the running file to the nearest folder holding a `package.json`. No folder between either file and the root holds one. `tests/integration/cli.test.ts` covers the walk, and its `--version` test checks the root it finds in practice is this package's.

The aesthetic names are read from the keys of the same manifest's `exports` (`./aesthetics/<name>`, less `./aesthetics/tw`, which is the Tailwind source of all of them), and each `--aesthetic` reads the file that subpath names under the `import` condition, so a new aesthetic needs no change to the command. An aesthetic is added only when asked for, since no template names which one a project wants, and is purged against the same classes as the stylesheet: its solo class is not in `classes.json`, so it is kept, and its rules for unused components are dropped.

## How classes are found

Content is read as text and never run, as Tailwind reads it. A file is UTF-8 unless it starts with a UTF-16 byte order mark, as Windows PowerShell 5.1's `"card" > safelist.txt` writes, which before 0.11.0 was read as UTF-8 and lost every class in it. Every run of characters a class name can hold is a word, and a word counts when it is in `classes.json`. A word that is not one is read again by its parts around each colon, so Svelte's `class:primary={isPrimary}` and a Ruby `btn: true` are found. The parts are taken one at a time: a word is as long as the run of class characters, which can be the whole file, and `split(":")` made an array of every part, so before 0.11.0 a 160 MB content file of colons aborted Node.js with no `chs:` line, and a 192 MB file of `a:` peaked at 1.6 GB; the test "reads the parts of a word one at a time" holds it. Only the `--content` globs are read: nothing of the consumer's other files or of this package adds a class, and nothing is written but the output. The output file is left out even when a glob matches it: it names every class the last build kept, so read back it would keep them, and the stylesheet would grow with each build instead of following the templates. Files are read one at a time and each is dropped once its classes are counted, so memory follows the largest file, not the sum of them. The tests hold it: a class only in an unlisted file in the working directory stays out, and a build whose glob matches its output writes the same stylesheet twice.

Resolving the globs, reading the files, and splitting them into words are done by `@codenhub/scan`, a private package this package and `@codenhub/icons` inline; which words count stays here. A `--content` entry is tried as a literal path before it is read as a glob, so `app/[id]/page.tsx` is found, where `fs.glob` alone reads `[id]` as a set of letters and matches nothing. A glob that matches a link to a file reads the file, as `scanFiles` in `@codenhub/icons` does. The icons [Build command](../../../icons/docs/internal/cli.md#the-shared-scanner) records the split.

A wildcard does not enter a `node_modules` folder unless the entry names `node_modules`, as in `node_modules/some-ui/**/*.html`; a literal path is read wherever it is. Run from the root of a project without a bundler, `**/*.html` read every dependency's demo pages, and `**/*` reached this package's own `dist/purge/classes.json`, which names every class, so the whole stylesheet shipped with no sign of why. Since 0.11.0 the scanner's `skipNodeModules` keeps it out, as Tailwind's scan does. Rejected: an `--exclude` option, which adds a flag every project would have to know to pass, and only a warning in the guide, which leaves the trap set. The cost is a project that relied on a wildcard reaching `node_modules`, which now names it; an entry whose only matches were there fails saying a wildcard does not enter `node_modules`. `@codenhub/icons` does not turn the option on; that is its own decision. The test is "keeps a wildcard out of node_modules unless the glob names it" in `tests/integration/cli.test.ts`.

A copy of the package's own files is not read for classes, since each names every class and kept the whole stylesheet: Django's `collectstatic` copies `dist/` into `STATIC_ROOT`, and with `-c "**/*"` from the project root a page with one button got the whole stylesheet, 323,521 bytes where it needed 32,485 then, and two builds over one folder read each other's output. Since 0.11.0 a content file is skipped when it starts with the package's `/*! @codenhub/styles` notice, the same `WRITTEN_HEAD` the [output check](#failure-modes) reads, which every stylesheet the command writes and each complete compiled stylesheet carries; when it is a JSON list of strings holding at least half of this version's `classes.json`, as a copy of that file from this or a nearby version is and a safelist written as JSON is not; and when it is, byte for byte, a file this version ships under `dist/`, compared only with the files of its size, which catches the aesthetics, `theme.css`, `palette.css`, and `cli.js`, none of which carries the notice. The test is "does not read a copy of the package's stylesheets, class list, or another build's output". Rejected: skipping by name, which misses a copy `ManifestStaticFilesStorage` renamed with a hash and skips a template that happens to be named `index.css`. The gap is a copy from another version of a file without the notice, such as an earlier deploy's aesthetic left in `STATIC_ROOT`; the guide tells readers to keep their globs to templates and scripts. Closing it means stamping the notice on every file `dist/` ships, which changes their bytes and the output check's reading of a copy of `/theme` or an aesthetic, so it is left open.

A folder a glob has to list and cannot, for want of permission, fails the build with Node.js's `EACCES` or `EPERM` naming it, since 0.11.0. `fs.globSync` skips such a folder without a word, so `-c "views/**/*.html"` built without the classes of a `views/locked/` and exited 0, and `-c "views/locked/*.html"` was told the path matched nothing, though it was right. The scanner's `failOnUnreadable`, which the command turns on, finds the folders the entry would list with a second glob per segment of the entry and opens each that holds no match. That glob asks for `withFileTypes` and keeps the folders, since a `**` matches every file below it too, and before 0.11.0's release each of those was opened as well, which made the check about three times slower on a tree of many assets; the scanner's test "opens only folders to check" holds it, by the paths `fs.opendirSync` is given, not by a timing. Its `exclude` callback is then given a `Dirent`, not a path, which the `node_modules` test reads by its name. A folder the entry never enters, as `views/*.html` never enters `views/locked/`, is not checked. The second walk costs a build that succeeds a little time, which a failure that names the folder is worth. The tests are "fails on a folder a --content glob cannot list, naming it" here and "a folder it cannot list" in `@codenhub/scan`; Windows denies the listing through an ACL, POSIX through the mode, skipped as root.

Two findings print a `chs: warning:` line to stderr after the output is written, and leave the exit status 0:

- **Content that names no StyleKit class.** The build writes the theme and the reset, 30,314 bytes on 0.11.0, and names the globs. That is the outcome a [glob that matches nothing](#content-globs-that-match-nothing) fails to prevent, but here the files exist and were read, and a page may use the tokens and the reset alone under a stylesheet of its own. Rejected: failing, which would leave such a page no way to build, since the command takes no flag to allow it.
- **An aesthetic's class without its `--aesthetic`.** An aesthetic's classes are those its stylesheet names that the complete stylesheet does not, under its name or a name that starts with it, such as `glass-liquid` and `glass-solo`, read from the build. A class found without its aesthetic requested is named, with the `--aesthetic` to add. Rejected: adding the aesthetic on its own, which a word in prose such as "pixel" or "sketch" would trigger, shipping an aesthetic no page asked for, and which would make the output depend on more than the `--aesthetic` options. The cost of the warning is the same word in prose printing it for nothing.

## Content globs that match nothing

Each `--content` entry has to name at least one file, and each file it names has to be readable; the scanner fails on either, in the strict modes this command turns on. A build from no content would write a stylesheet without component classes, which on a deploy is a site that silently loses its styling. The output is left out of an entry's matches before the entry is checked, so an entry that matched only the output fails too: after a build into `public/s.css`, `-c "public/*.css"` read nothing, and before 0.11.0 wrote a stylesheet without component classes and exited 0. A file named as the [temporary file](#replacing-the-output) of the output, `<output>.<16 hex digits>.tmp`, is left out the same way: a build killed between creating it and renaming it leaves it behind, and read as content it held the last build's classes, which `-c "public/*"` then kept. Its name is random, so a template named that way is not a realistic loss.

"Check the path" sends a reader to fix a path that may be right, so the scanner's `UnmatchedEntryError` names a likelier cause when it finds one, as its `reason`: an entry naming a folder, which gets a glob for its files, as in `app/views/**/*`; a wildcard whose only matches were in a `node_modules` it skipped; and an entry holding a `[`, which a glob reads as the start of a set of characters, so `app/[locale]/**/*.tsx` matches a folder named with one of those letters. That one shows `[[]`, a set holding only `[`, which matches a bracket on every system, where `\[` escapes it on POSIX alone, since Windows reads the backslash as a separator. It is named only when the entry, with each `[` not already written `[[]` written so, matches a file; before that check, a missing `src/pages/[slug].astro` was told to write `[[]slug]`, which failed again and was then told `[[][[]]slug]`. An entry that matches nothing either way gets the advice to check the path. The causes are looked for only once an entry has failed, so the second walk the `node_modules` check takes costs a build that succeeds nothing.

## Replacing the output

The stylesheet is written to a temporary file beside the output, `<output>.<random>.tmp`, and renamed over it, so a write that fails partway, on a full disk say, leaves the previous stylesheet whole rather than a truncated one a deploy would ship. The file is created with `wx`, which fails on any entry already at that name, a link included, and a taken name is retried with another; the write, owner, and mode then go through the file's handle, never its name, and a failed build removes only a file it created. Before 0.11.0 the name was `<output>.<pid>.tmp`, which anyone can guess, and the write followed a link planted there, so whoever could write to the output's folder could make a build overwrite any file the runner can write, and on POSIX give it another owner and mode, past the check that refuses a file the command did not write. `tests/integration/cli-write.test.ts` holds the exclusive open, the retry, and the cleanup, through a mocked `fs.open`, and `tests/integration/cli.test.ts` holds that a link at the old name is not followed, where the system lets it create one. A rename puts a new file in place, so on POSIX the temporary file first takes the permission bits, owner, and group of the file it replaces: a `0640` stylesheet of the web server's group used to come back `0644` and the runner's, readable by everyone and perhaps no longer by the server. `tests/integration/cli.test.ts` holds the mode on every POSIX run, the owner as root, and the group where the runner is in a second group.

Only root can give a file to another user, and a user can give a file only to a group they are in. A runner without that right does not fail a build that wrote the stylesheet, since the output itself is right: it keeps the group when it can, keeps the mode, and prints one `chs: warning:` line to stderr naming the owner, and the group when that changed too, or the group alone when the runner owned the file already, as for a `0640` file of a group the runner is not in, before the usual line on stdout, and exits with status 0. The warning is printed after the rename, so a build that fails still prints its one line. The mode is kept as it was, so when the owner changed and the mode lets no one read the file but its owner, through the group bits while the group is kept and the others bits after that, as `0600` does, the previous owner, often the web server's user, may no longer be able to read the stylesheet, and the warning says so. The same holds for the group: when it changed and the mode lets only the owner and the group read the file, as `0640` does, the previous group's members, often the web server, may no longer read it, and the warning names them too, also when the runner owned the file already and only the group changed. Rejected: failing the build in that case, which would add a failure mode for a stylesheet that was written correctly, and widening the mode, which would loosen a permission the user chose. Any other failure to set the owner, group, or mode fails the build as a failed write. A test cannot make a file of another user without root, so `tests/integration/cli.test.ts` runs `keepOwnership` on a file whose calls are recorded and refused as a user's are; the warning was also checked under WSL Arch with Node.js 26.13.1 on 2026-11-19, as a user replacing a root-owned stylesheet in a folder that user owns, once with the group kept and once without.

Windows keeps neither, and needs neither kept: a new file takes its folder's permissions, and the only mode Node.js reads there is the read-only attribute. Windows refuses to rename over a read-only file, so a read-only `--output` fails as a write the user may not make, with `EPERM`, after the brief retries the rename gets on Windows for a file another process holds open; `tests/integration/cli.test.ts` holds it. POSIX replaces a read-only file, since the rename needs only the folder's permission, and keeps it read-only. Rejected: clearing the attribute to replace the file and setting it again, which would change a file the user marked read-only before knowing the write succeeds.

## Limits

- **Classes are found as words.** A class assembled at render time, such as `class="btn <%= kind %>"`, is never found. The public page documents the two workarounds: write class names whole in a file the build reads, or list them in a safelist file passed as another `--content`.
- **No Tailwind utilities, no other variants, no stacked variants.** As [No Tailwind utilities, ten variants](#no-tailwind-utilities-ten-variants) records. A consumer who needs them has outgrown the command and imports `@codenhub/styles/tw` from their own Tailwind input.
- **No watch mode or other commands.** `build` and `help` are the commands; the rest are left out until a consumer needs them.
- **A glob's braces stand for at most 1,024 patterns.** `fs.globSync` walks once per pattern a brace expands to, and its time grows faster than their number: in an empty folder on Node.js 26.13, 1,024 patterns took 0.06 to 0.2 seconds, 4,096 took 0.3, 16,384 took 2.7 to 8.7, and 32,768 took 41, so 18 groups of two would take minutes, with nothing said. The scanner counts the patterns without expanding them, adding a list's choices, counting a range's steps, and multiplying the groups, and fails an entry past `MAX_BRACE_EXPANSIONS`, naming the count and the limit; the limit is the largest power of two measured well under a second, and no glob a project writes for its templates comes near it. Rejected: a limit on the number of groups, which lets one range of a million steps through.
- **No configuration file or custom CSS input.** A project changes the look with tokens and container classes, and resizes controls with `--ui-scale`; [Roadmap → Not Planned](./roadmap.md#not-planned) records why a configuration file was dropped.
- **Node.js 24 or newer.** The floor is the oldest line CI tests, and the command checks the version itself before it reads a file, as [Node.js version](#nodejs-version) describes. The stylesheets themselves need no Node.js.

## Failure modes

Every failure the command handles prints one line, `chs: <reason>`, to stderr and exits with status 1 without writing the output file. `tests/integration/cli.test.ts` runs the command into most of the reasons below. Two it does not: a content file that cannot be read, which `@codenhub/scan`'s own tests cover where its `readFiles` reports it; and a flag given a value it does not take. Some run only where the system allows the case: the links where it lets the test create one, so not on a Windows account without developer mode; an existing `--output` it cannot read, a folder it cannot write to, and the pipe and device outputs on POSIX alone, the first two as a user other than root, who reads and writes anything; and a read-only `--output` on Windows alone. The reasons: a missing `--content` or `--output` (a `--content` or `--output` that is empty or only spaces counts as missing: an unset variable in `-c "$TEMPLATES"` read the working directory as a folder, and the advice for a folder named `"/**/*"`, the root of the disk); a folder a `--content` glob has to list and cannot, with Node.js's `EACCES` or `EPERM` naming it; a `--content` glob that matches no file, naming the glob and the folder, and a likelier cause when [one is known](#content-globs-that-match-nothing), or that matches only the `--output`; an extra positional argument, almost always an unquoted glob the shell expanded; an unknown flag, or a flag missing its value or given one it does not take, worded from `parseArgs`'s error rather than passed through, since Node words those for programmers, with `parseArgs`'s advice kept for a value that starts with a dash, which it reads as another flag, as in `-o -app.css`, so the line says to write `--output=-app.css`, unless the next argument is one of the command's own options, short or long, alone or with its value attached, as in `-c -o out.css` or `-c -oout.css`, where the value was left out and the line says only that it is missing; an `--output` given more than once, of which `parseArgs` would keep the last without a word; an unknown aesthetic, listing the valid ones; a missing or unknown command, naming `build` and `help`; a `--content` glob whose braces expand past [the limit](#limits), naming the count; a Node.js older than 24, naming both versions; an `--output` of `-`, which Tailwind's CLI reads as standard output and this command would write as a file named `-`; an `--output` that a `--content` entry names, or an existing file that holds more than whitespace and does not start, within its first 1,024 bytes, with the package's `/*! @codenhub/styles` notice, optionally after Tailwind's banner, which the command did not write and would replace whole, so a template or a hand-written stylesheet named by mistake is kept; an existing `--output` it cannot read, since a folder can allow a file to be renamed over without allowing it to be read; an `--output` that ends with a folder separator, `/`, or `\` on Windows too, which `path.resolve` dropped, so `-o newdir/` wrote a file named `newdir`, or whose last segment is `.` or `..`, which it resolves to a folder above, so `-o newdir/.` did the same; on Windows, an `--output` that breaks Windows' rules for a name, from Microsoft's "Naming Files, Paths, and Namespaces", in any segment, since the folders above the output are created first, and checked before anything is: a name Windows keeps for a device in every folder, `CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `COM¹` to `COM³`, `LPT0` to `LPT9`, `LPT¹` to `LPT³`, `CONIN$`, or `CONOUT$`, in any case and with any extension, which `fs.stat` reports missing there and the rename turned into a file `del` cannot remove; a name that ends with a dot or a space, other than `.` and `..`, which Windows drops, so `-o app.css.`, `-o "pub./a.css"`, and `-o "dir/..."` left files and folders `del` cannot remove; and a character Windows allows in no name, `<`, `>`, `"`, `|`, `?`, `*`, a control character, or a `:` past a leading drive, so `-o fresh.css:s`, which names a stream of `fresh.css`, no longer leaves an empty `fresh.css` beside its error, and `-o NUL::$DATA` no longer writes the device's name; each line names the segment or the character. The rules are Windows' own, so the test runs each form as a table: every device name in each case, with an extension, after a space, and as a folder, every reserved and control character, and the names that end with a dot or a space; a `\\?\` path is refused for its `?`; an `--output` that is, after any link, a folder, a device, a pipe, or a socket, named by kind, since the rename that replaces the output would replace a pipe with a file, and as root a device too, so `-o /dev/null` turned `/dev/null` into a stylesheet, and a folder failed with a raw `EISDIR`, or `EPERM` on Windows. Every stylesheet the command has written since 0.9.0 starts with that notice, and so does each compiled stylesheet, so a copy of one is replaced. Rejected: taking any `/*!` banner or `@layer` at the head as a stylesheet built to be replaced, which 0.11.0 did before its release, because a stylesheet written by hand opens with a layer order as often as not, as the essential-motion example in the accessibility page does, and a vendor's opens with its own banner, and nothing the command writes needs either. An `--output` that is a link is written through: the file it leads to is replaced and the link stays, and a content file that leads to the output is not read; a file that cannot be read, with Node.js's own message, or with its path added when Node.js leaves it out, as for a file too large for a string; and a failed write, naming the `--output` as given, with Node.js's reason and code and what to do, a read-only `--output` on Windows among them, as [Replacing the output](#replacing-the-output) records. The write goes to a temporary file beside the output that is then renamed over it, and Node.js's message names whichever path its call failed on, mostly that temporary file, which the user never gave; so the paths are dropped from the message, and `--output` is named instead.
