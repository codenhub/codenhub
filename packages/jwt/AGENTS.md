# packages/jwt

## Traps

- **Linux WebKit fails some Ed25519 key generations.** `crypto.subtle.generateKey({ name: "Ed25519" })` rejects with `OperationError` whenever the new key's `d` or `x` starts with a zero byte, about 1 call in 128, so `generateKeyPair` with `EdDSA` or `Ed25519` fails at random on that engine and a browser test that generates such a key flakes. Keys like that import, sign, verify and export correctly, and so does every key the engine does generate. Held under Playwright 1.61.1 (webkit-2311) in the `v1.61.1-noble` image: 451 of 60,000 generations failed, every one with that error and none with another ([probe run 38956681761](https://github.com/codenhub/codenhub/actions/runs/38956681761)); in a second run 394 of 50,000 failed, and each of the other 49,606 keys was exported as a JWK, imported, used to sign by both the generated and the imported key, and verified without a failure ([probe run 39231643599](https://github.com/codenhub/codenhub/actions/runs/39231643599)). The cause is WebKit's libgcrypt backend, fixed upstream in WebKit 323215@main ([bug 307095](https://bugs.webkit.org/show_bug.cgi?id=307095)). `generateKeyPair` and `generateJweKeyPair` therefore retry that one error, for OKP keys only, up to three times (`generatePair` in `src/keys/web-crypto.ts`, scope.md decision 46), and the leading-zero JWK scenarios in `tests/scenarios.ts` cover the import path. Remove the retry and this trap once released WebKit builds carry the fix: when Playwright ships one, a probe that calls `crypto.subtle.generateKey` directly a few thousand times should succeed every time.
- **WebKit exports a short `d` for EC and Ed25519 keys.** `crypto.subtle.exportKey("jwk", key)` drops the leading zero bytes of `d`, which RFC 7518 §6.2.2.1 says must be as long as the coordinates, so the JWK checks refuse the package's own export when it reads it back: `ES512 key pair import from one private JWK` failed in about half of runs on WebKit. Held under Playwright 1.61.1's WebKit on Windows: 98 of 200 P-521 keys, 21 of 4000 P-256 keys and 10 of 2000 P-384 keys came out short, `x` and `y` never did, and every short `d` padded back to full length imported and signed. Chromium and Firefox gave full length every time. Prefer `exportWebCryptoJwk` in `src/keys/exported-jwk.ts`, or `padPrivateScalar` there for a JWE key, over calling `exportKey("jwk")` directly; `exported-jwk.test.ts` simulates the engine.
- **workerd refuses `cache: "no-cache"` before compatibility date 2025-08-07.** `fetch(url, { cache: "no-cache" })` rejects: with `Error: The 'cache' field on 'RequestInitializerDict' is not implemented.` before 2024-11-11, and with `TypeError: Unsupported cache mode: no-cache` from then until 2025-08-07, when it starts answering; `no-store` is accepted from 2024-11-11 and `reload` still rejects. The call does not throw synchronously; the promise rejects. Held under workerd 1.20261023.1 as Miniflare 5.20261023.3-beta runs it, probed with compatibility dates from 2024-01-01 through 2026-07-01 against an `outboundService` stub; `tests/integration/workerd.test.ts` uses 2026-07-01 and a stub `fetch`, so it never exercises the refusal. That is why `send` in `src/keysets/remote.ts` retries without `cache`, and drops the member for good, only when the rejection's message names `cache`: a network failure also rejects with a `TypeError`, and is not retried. The unit tests in `remote.test.ts` ("cache mode") simulate both messages. Drop the fallback and this trap once the package no longer supports compatibility dates before 2025-08-07.
