# `@codenhub/jwt`: package scope

> **How to read this document.** This is not a final spec. Section 3 lists the **invariants**: security and design commitments that hold unless there is a strong, explained reason to break them. Sections 1, 2, 4 and 6 are the agreed scope of 0.1. The API sketch in section 5 was a **proposal**; the shipped API answers it differently in places, as section 5 notes. Section 7 records the decisions taken while building the package: all of them approved by the maintainer. If you find a better API shape, better behavior, or a better-established practice, propose it and explain why, as `docs/guidelines/documentation.md` asks for reversing a decision. The goal is the best possible package, not faithfulness to this document.
>
> The package is published as `@codenhub/jwt` (decision 9). The display name is `JwtKit` (section 7).
>
> How the package is built, and why, is in [architecture.md](architecture.md). What remains before 0.1 is in [roadmap.md](roadmap.md).

---

## 1. Context

This package is the first building block of a larger effort:

1. **`@codenhub/jwt`** (this package): JWS, JWE and JWK primitives on Web Crypto.
2. **`@codenhub/oidc`**: OpenID Connect, both **client** (relying party) and **provider** (OpenID Provider), built on top of this package.
3. **An SSO application**: a self-hosted, 100% free and open-source identity provider with an admin dashboard (users, roles, registered apps). Its differentiator is that user data belongs to the user's account, not to individual apps.
4. Later, and only if needed: `xml`, `xmldsig`, and `saml`.

`oidc` will be designed against this package's public API, so it should be stable enough to build on by 0.1.

### Why build it instead of depending on an existing library

`panva/jose` is excellent: zero dependencies, runtime-agnostic, and well scrutinized. We are not building this because it's bad. We're building it because:

- The SSO project must not depend on a core it doesn't own. The project has to stay free and open indefinitely, and its consumers shouldn't inherit someone else's maintenance decisions.
- The required scope is much smaller than a full JOSE implementation (see section 2).
- It should follow codenhub's conventions and its "trust no input" posture, matching `@codenhub/validation` and `@codenhub/error`.

**Use `panva/jose` as a reference.** Reading how it handles edge cases is encouraged, and it is a good **devDependency** for interop tests. It must never become a runtime dependency.

## 2. Scope

### In scope (0.1)

- **JWS compact serialization**: sign and verify.
- **Algorithms**: `ES256`, `ES384`, `ES512`, `EdDSA` and `Ed25519` (both Ed25519), `RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`, `HS256`, `HS384` and `HS512` (decision 27).
- **JWK**: import and export, public and private, for the supported key types; PEM import (decisions 31 and 48); Web Crypto `CryptoKey` import (decision 49); RFC 7638 thumbprints (decision 30).
- **Key generation** for the supported algorithms.
- **Key sets**: a local key set, plus a remote JWKS key set (fetch, cache, rotation), a verifier that chooses one by the token's issuer (decision 47), and an issuer's key ring for rotating its signing keys (decision 61).
- **Claim validation**: `exp`, `nbf`, `iat`, `iss`, `aud`, `typ`, max age, required claims, and optional custom claim validation via Standard Schema.
- **Header-only inspection**, used to route by `kid`.
- **DPoP proofs** (RFC 9449): creating them, and verifying them with their method, URL, access token hash, nonce, replay and key binding checks (decisions 30 and 62).
- **JWE compact serialization**: encrypt and decrypt, with the algorithms of decision 63, separate encryption keys (decision 64), signed tokens nested inside (decision 66), and recipient encryption key sets (decision 67).

### Out of scope (0.1)

- JWE JSON serialization, multiple recipients, compression (`zip`), `RSA1_5`, `PBES2-*`, and the 192-bit AES algorithms (decision 55).
- JWS JSON serialization (general and flattened).
- Unencoded payloads (`b64: false`, RFC 7797).
- Algorithms beyond those listed above, such as `ES256K` and `Ed448`.
- Anything OIDC-specific, such as `nonce`, `at_hash`, `c_hash`, or `azp` semantics. These belong in `@codenhub/oidc`, though this package should make them easy to implement there.

### Open question (resolved)

**HMAC (`HS256`)?** OIDC's `client_secret_jwt` and HS-signed ID tokens use it, so `oidc` may need it eventually. If it's included, symmetric keys must be a distinct key type that can never be confused with an asymmetric public key. Decide whether it belongs in 0.1 or later.

Resolved: `HS256` is in 0.1, as the distinct `SecretKey` kind. See decision 1 in section 7. `PS256` is in 0.1 too (decision 13).

## 3. Invariants

These are the commitments that should hold.

1. **The algorithm comes from the key, never from the token.** A key is bound to exactly one algorithm when it's imported or generated. If the token header's `alg` doesn't match the key's algorithm, verification fails. This closes off `alg: none` and the RS/HS confusion attack class.
2. **`none` is never supported**, in any form.
3. **No unverified payload access.** There is no `decode()` that returns claims. The only unverified reads are the header, for key selection, and, when `keys` is a function, the payload's `iss`, which only routes the token to a key set and is passed to nothing else (decision 47).
4. **Untrusted input never throws.** Verification and import of untrusted data return results. Programmer errors, such as invalid options or signing with a verify-only key, throw `TypeError`, ideally when the verifier or key is created rather than when it's used. Exceptions from the caller's own code, such as a `claims` schema that throws or rejects, propagate rather than becoming results (decision 10).
5. **Bounded cost.** Token length is capped before any decoding happens. JSON depth and size are bounded. Remote JWKS responses are size-capped and time-bounded. Failing input must be cheap.
6. **Issues never contain input values.** No token content, claim values, or key material appears in issues, error messages, or logs. Issues can name _which_ check failed (`wrong_audience`); they don't echo what the token said. The one exception the package makes is a `claims` schema's issue paths, which are kept (decision 11) and may name keys chosen by the signed payload. A custom key set's failure issues are passed through as the caller's key set wrote them (decision 16).
7. **Strict parsing.**
   - Base64url only: no padding, no `+`/`/`, no non-canonical trailing bits.
   - Exactly three segments.
   - Header and payload must be JSON objects. **Duplicate keys must be rejected**, because `JSON.parse` silently keeps the last one.
   - Reject `crit` headers this package doesn't understand. In 0.1 that means any `crit`.
   - Numeric date claims must be finite numbers.
8. **Key hygiene.**
   - Enforce minimum RSA modulus length (2048).
   - Importing a key for verification must not quietly accept private parameters.
   - Validate the curve and key type against the declared algorithm.
   - Exporting private key material is a separate, explicitly named operation.
9. **Frozen results.** Returned headers, payloads, keys, and key sets are immutable.
10. **Runtime-agnostic.** Use only Web Crypto and standard globals. It must run on Node 26+, Cloudflare Workers, Deno, Bun, and modern browsers. `fetch` must be injectable wherever it's used.
11. **Zero runtime dependencies.**
12. **Codenhub conventions.** Result shape `{ ok: true, value } | { ok: false, error: { issues } }`, consistent with `@codenhub/validation`. ESM only, `sideEffects: false`, tree-shakable named exports. Follow the repository's docs, tooling, and contribution standards (`AGENTS.md`, `docs/`).

## 4. Behavior details worth getting right

- **Key selection.** If the header has a `kid`, select by `kid`. Without a `kid`:
  - If the key set holds one compatible key, use it.
  - Otherwise fail.

  Never try every key in turn. Selection should also filter by algorithm and `use`/`key_ops`.

- **Remote JWKS.**
  - HTTPS only, except `http:` on a loopback host (decision 29).
  - Cache with a TTL.
  - On an unknown `kid`, refetch once, subject to a **cooldown**, so attackers can't force a fetch on every request.
  - Concurrent misses share a single in-flight request.
  - Response size cap and timeout.
  - Optionally serve stale keys while a refetch fails; decide on and document the policy.
- **Time.** Configurable clock tolerance with a sane default and an upper bound. An injectable clock, for tests.
- **`aud`.** Handle both string and array forms. Decide on and document the behavior for multi-audience tokens.
- **`typ`.** Allow requiring a specific `typ`, for example `at+jwt` from RFC 9068 versus `JWT`. This lets `oidc` prevent token-type confusion.
- **Comparisons.** Signature verification goes through Web Crypto. Any other secret-dependent comparison must be constant-time.

## 5. API sketch (a proposal, change freely)

> The shipped API is `src/index.ts`. It differs from this sketch where building it found a better shape: `importKey` became `importPublicKey`, `importPrivateKey` and `importSecretKey`, so the kind of key is in the function name and its return type rather than in a `use` option; `exportJwk` became `exportPublicJwk`, with `exportSecretJwk` beside `exportPrivateJwk`; `sign` takes one `{ payload, key, header }` object; and a verified result also carries the `key` that matched. The questions at the end of this section are answered in section 7: `sign` takes a single object (decision 20), the verifier has one stage (decision 7), and `at_hash`/`c_hash` stayed in `@codenhub/oidc` until decision 14 brought `tokenHash` here. The sketch is kept as the record of what was proposed.

```ts
// Keys: algorithm bound at import/generation
const key = await importKey(jwk, { alg: "ES256", use: "verify" }); // Result<Key>
const pair = await generateKeyPair({ alg: "EdDSA" }); // { privateKey, publicKey }
exportJwk(pair.publicKey); // public JWK
exportPrivateJwk(pair.privateKey); // explicit, separate

// Signing: the caller's own data, so bad input is a programmer error (throws)
const token = await sign({ kid: "2026-10", typ: "JWT" }, payload, pair.privateKey);

// Key sets
const local = createKeySet([keyA, keyB]);
const remote = createRemoteKeySet({
  url: "https://sso.example/jwks",
  cacheTtl: 600,
  cooldown: 30,
  fetch, // optional
});

// Verification: a configured verifier, called like a validator
const verify = createVerifier({
  keys: remote,
  issuer: "https://sso.example",
  audience: "app123",
  type: "JWT",
  clockTolerance: 30,
  maxAge: 3600,
  maxLength: 8_192,
  requiredClaims: ["sub"],
  claims: someStandardSchema, // optional
});

const result = await verify(token);
// ok    → { ok: true, value: { header, payload, key } }  (frozen)
// error → { ok: false, error: { issues: [{ code, ... }] } }

// Unverified header read, for kid routing only
readHeader(token); // Result<Header>
```

**Candidate issue codes:** `malformed`, `too_large`, `duplicate_key`, `unsupported_crit`, `unknown_kid`, `no_matching_key`, `alg_mismatch`, `bad_signature`, `expired`, `not_yet_valid`, `issued_in_future`, `too_old`, `wrong_issuer`, `wrong_audience`, `wrong_type`, `missing_claim`, `schema_failed`, `key_fetch_failed`.

**Questions worth reconsidering:**

- Should `sign` take `(header, payload, key)`, or a single options object?
- Should verifier configuration be split into "signature" and "claims" stages, so `oidc` can compose its own claim checks?
- How should `oidc` derive `at_hash` and `c_hash`? Should this package expose a small hashing helper tied to the key's algorithm?

## 6. Testing and acceptance

- **Official vectors.** RFC 7515 appendices, RFC 7520 (JOSE Cookbook) for the supported algorithms, and RFC 8037 for EdDSA.
- **Interop.** Tokens signed here verify with `panva/jose`, and the reverse, as a devDependency-only test suite.
- **Hostile-input suite**, in the spirit of `@codenhub/validation`'s README. Each case asserts the exact result:
  - `alg: none`, including case variants.
  - `alg` swapped (RS256 ↔ HS256, ES256 ↔ RS256).
  - Duplicate JSON keys.
  - Non-canonical base64url.
  - Oversized tokens and deeply nested JSON.
  - Unknown `crit`.
  - Wrong `kid`.
  - Expired, not-yet-valid, and future-`iat` tokens.
  - Audience arrays.
  - A JWKS endpoint that is slow, huge, or flapping.
  - Kid-miss floods hitting the cooldown.
- **Leak checks.** Serialized failures never contain token or key contents.
- **Runtime matrix.** Tests run on Node and in a Workers-compatible environment (for example, workerd/Miniflare), plus a browser if the tooling allows.
- **Docs.** A README and `docs/` written to codenhub standards, including a short "what hostile input gets" section.

**0.1 is done when:**

- Everything in scope above works.
- Every invariant holds and has a test.
- The public types are stable enough for `@codenhub/oidc` to build against.

## 7. Decisions

### Approved by the maintainer

These were asked explicitly and approved. They bind work while they stand; reversing one follows "Recording decisions" in `docs/guidelines/documentation.md`.

1. **`HS256` is in 0.1, as a distinct `SecretKey` kind.** `@codenhub/oidc` needs it for `client_secret_jwt` and HS-signed ID tokens, and adding it after 0.1 would widen the key unions (`SigningKey`, `VerificationKey`) and the `KeySet` contract that `oidc` builds against, which is a breaking change for it. A secret key has its own `kind`, is never selected for an asymmetric `alg`, is never imported from a JWKS, and must be at least 32 bytes. Rejected: deferring it to a later minor, for the breaking change above.
2. **Both `EdDSA` and `Ed25519` are supported, and each key is bound to one of them.** RFC 9864 deprecates the curve-agnostic `EdDSA` identifier in favor of `Ed25519`, but deployed issuers still publish `EdDSA`. Binding each key to one identifier keeps invariant 1 literal: a key verifies under exactly one `alg`. A JWKS entry without `alg` is imported as two keys, one bound to each identifier, so each key still verifies under exactly one `alg` (decision 12). Rejected: only `Ed25519`, which cannot verify tokens from those issuers; treating the two as aliases of one key, which makes a key answer to two `alg` values.
3. **Runtime matrix: Node.js, browsers (Playwright: Chromium, Firefox, WebKit), and workerd.** These are the runtimes invariant 10 names that differ in their Web Crypto and `fetch`. Deno and Bun are expected to work through the same standard globals but are not tested.
4. **Display name `JwtKit`.** `jwt` is an acronym, not a word that reads as a name, so the package-naming guideline's neutral, fused pattern applies with the `kit` descriptor. Recorded in `docs/guidelines/package-naming.md`.
5. **A remote key set serves stale keys for a bounded `maxStale` (default 3600 seconds) after its TTL while refetching fails.** Without it, a short outage at the issuer takes down every service that verifies its tokens, once their caches expire. The bound means a key the issuer has removed, possibly because it was compromised, stops being trusted at most `cacheTtl` plus `maxStale` after the last successful fetch, whether or not the issuer is reachable. A cache fetched up to a minute "in the future" counts as just fetched, which loosens the bound by that minute: the 0.1 full audit found that expiring it on any backward step, as an NTP correction of a second makes, threw away a fresh cache and every seed saved on a host whose clock ran ahead. Rejected: never serving stale keys, which turns an issuer outage into an outage of every consumer; serving them without a bound, which keeps a removed key trusted indefinitely while the issuer is unreachable.
6. **Default clock tolerance is 0 seconds, at most 300.** Decision 26 gives `nbf` and `iat` a floor of 60 seconds. Skew is something a consumer opts into, so a default never silently extends a token's life. The cap keeps a misconfiguration from turning short-lived tokens into long-lived ones. Rejected: a default of 30 or 60 seconds, as several libraries use, which widens every token's validity for consumers that never asked for it.
7. **The verifier has a single stage.** `createVerifier(options)` checks structure, signature and claims in one call, and `@codenhub/oidc` adds its own per-request checks (`nonce`, `azp`, `at_hash`) on the frozen result. Rejected: separate signature and claims stages, which double the API surface and make it possible to run claim checks on a payload whose signature was never checked, against invariant 3.
8. **This document is kept as `docs/internal/scope.md`**, conformed to the internal documentation rules, with its decisions recorded here; the design and its rationale are in [architecture.md](architecture.md).
9. **The npm name is `@codenhub/jwt`.** The first publish fixes the name, and renaming later would cost every consumer a migration, so it is settled before 0.0.1 is published.
10. **A throwing or rejecting `claims` schema propagates**: the verifier's promise rejects. The schema is caller code, and a bug in it should surface rather than be hidden, as `@codenhub/validation` treats callbacks. Rejected: mapping the throw to a `schema_failed` issue at `["payload"]`, which hides caller bugs as token failures; the cost of rejecting is that an HTTP handler that does not catch the rejection answers 500 instead of 401.
11. **A `claims` schema only checks.** The returned payload is the token's own frozen payload, typed by the schema's input type, and the schema's output is discarded. Schema messages are dropped from issues; their paths are kept. A transforming schema would return an unfrozen value the package did not parse, against invariant 9, and a message is the most likely place for an input value to leak, against invariant 6. Rejected: returning the schema's output, for invariant 9; forwarding messages, for invariant 6.
12. **JWKS binding.** In `importKeySet` and `createRemoteKeySet`, a JWK without `alg` is bound to every allowed algorithm its `kty`/`crv` fit (an RSA key becomes `RS256` and `PS256`); `algorithms` defaults to every asymmetric algorithm; `oct` keys and `HS256` are never imported from a JWKS; unusable entries are skipped rather than failing the import; a JWKS may list at most 100 keys. Many issuers omit `alg` in their JWKS, and the token's `alg` still picks exactly one binding, so invariant 1 holds; skipping lets an issuer's JWKS hold encryption keys without breaking verification. Rejected: refusing entries without `alg`, which cannot verify those issuers' tokens; failing the whole import on one unusable entry, which lets one unrelated key take verification down.
13. **`PS256` is included.** It costs one entry in the algorithm table on Web Crypto, and section 2 allowed it "if it's nearly free".
14. **`tokenHash` computes `at_hash` and `c_hash`, and the algorithm lists, their guards and base64url are exported.** The left half of the hash an `alg` uses is a property of the JWS algorithm table this package owns; every issuer and relying party needs it, and `@codenhub/oidc`'s own copy maps only `ES256`, `RS256`, `PS256`, `HS256` and EdDSA, so an ID token signed with `ES384`, `RS512` or any other algorithm this package signs with gets no `at_hash` there. One table here keeps the two from drifting. The algorithm lists and guards answer "may I pass this `alg`?" for values from configuration or discovery, which callers otherwise copy and let fall behind when an algorithm is added (decision 27). base64url is exported because `ath`, `x5t#S256` and similar members need it. Rejected: leaving the helper to `@codenhub/oidc` because OpenID Connect defines it, the earlier form of this decision, which did not weigh that the hash follows from the `alg` table and that the copy had already fallen behind it.
15. **`importSecretKey` details.** The `kid` option names raw bytes, and a JWK as decision 51 describes; an empty-string `kid` is accepted everywhere; a secret JWK's `key_ops` passes when it includes `sign` or `verify` and nothing else (decision 52), and does not restrict the key: a secret imported from a JWK with `key_ops: ["verify"]` can still sign. Anyone holding an HMAC secret can compute the same MAC, so a verify-only secret protects nothing, and enforcing it would need a visible marker on `SecretKey`. Rejected: honoring `key_ops` as a verify-only secret key, which adds public surface for no security gain; refusing `key_ops` without `sign`, which breaks a verifier that is handed a verify-only JWK.
16. **A custom `KeySet` that throws, rejects, returns something that is not a result, returns a failed result without issues, or returns a successful result whose value is not a public or secret key this package created** gives `key_fetch_failed` with `{ reason: "key_set_error" }`. A failed result with issues, such as `unknown_kid`, is passed through with its issue list re-frozen. The verifier must not throw for a token (invariant 4), and must not verify with a key it cannot vouch for. Rejected: propagating the key set's exception, which lets one bad token reject the verifier's promise.
17. **Remote key set details.** The default `cooldown` is `min(30, cacheTtl)`; URLs with a user name or password are refused; the TTL counts from when a fetch completes; a `select` call starts at most one fetch; a header without `kid` never triggers a refetch. Together they limit the fetches tokens can cause (invariant 5): with a positive `cooldown`, a stream of hostile tokens costs the issuer at most one request per window. `cooldown: 0` is allowed and gives up that limit, leaving only one fetch in flight at a time. The cost: after an issuer rotates keys, tokens without `kid` signed by the new key fail until the cache expires.
18. **Header handling.** A `b64` header is `malformed` (RFC 7797 is out of scope, and ignoring `b64` without `crit` would verify a different payload than the signer meant); `jwk`, `jku`, `x5u` and `x5c` headers are ignored and never used for key selection, and `sign` refuses them in `header` along with `crit` and `b64`; decision 30 lets `sign` write `jwk` from `embedKey`. A token must never choose its own key (invariant 1). Rejected: honoring embedded or linked keys, the attack class invariant 1 closes.
19. **Units.** Durations in options are seconds, matching the claims they are compared with; `now` returns milliseconds, matching `Date.now`, so `now: Date.now` and test clocks need no wrapper. Rejected: one unit for both, which forces a wrapper on either the clock or every duration.
20. **`sign` input.** `sign` takes one `{ payload, key, header }` object rather than positional arguments; it rejects `undefined` values and every other value JSON cannot carry exactly, and checks registered claim types. On verification, an ill-typed registered claim is one `invalid_claim` issue and the later checks of that claim are skipped. Dropping a value silently, as `JSON.stringify` does, can sign a different token than the caller wrote: `{ aud: undefined }` becomes a token with no audience. Rejected: `JSON.stringify` semantics, for that case; positional arguments, which make `header` an easy argument to misplace.
21. **Result type.** A package-local `JwtResult` mirrors `@codenhub/validation`'s shape, with no runtime dependency on `@codenhub/error` or `@codenhub/validation`, per the error-propagation pattern in `docs/specs/errors.md` and invariant 11.
22. **Unknown options throw.** `createVerifier` and `createRemoteKeySet` throw a `TypeError` for an own enumerable string key that is not a documented option, such as `audiance` or `issuers`, naming the member (the caller's own option name, cut at 64 characters) and even when its value is `undefined`; symbol keys are ignored. Decision 28 extends the rule to every function that takes options. A typo silently turned off the audience or issuer check, and TypeScript catches it only for inline object literals. Rejected: ignoring unknown options, as most libraries do, which lets a typo turn off a check.
23. **A non-finite `now()` rejects.** When `options.now` returns anything but a finite number, the verifier's promise rejects with a `TypeError`, checked once per verification when it reads the time, and a remote key set's `select` rejects the same way. A verifier that calls such a key set reports `key_fetch_failed` with `{ reason: "key_set_error" }` by decision 16, which fails closed. `now: () => NaN`, such as `Date.parse` of an unset variable, otherwise disabled every time check and kept a remote cache from ever expiring. The clock is caller code, so it propagates as a throwing `claims` schema does (decision 10). Rejected: failing the token with an issue, which hides a caller bug as a token failure, as decision 10 reasoned; leaving it, which fails open.
24. **`importSecretKey` takes `Uint8Array | object`.** A string is a compile error, while runtime behavior is unchanged: untrusted input still never throws (invariant 4), and a string at runtime still returns `invalid_key`. Rejected: `unknown`, which hides a string secret until runtime.
25. **`importKeyPair` loads a key pair from one private JWK.** It runs `importPrivateKey`'s checks, derives the public key from the same JWK's public members, and returns `invalid_key` unless the public key verifies a fixed message the private key signed. An application that stores its signing key with `exportPrivateJwk` otherwise had to store a second, public JWK and pair the two halves itself, as `@codenhub/oidc`'s provider docs show, with nothing to check they belong together: a mismatched pair issues ID tokens nobody can verify. Node.js rejects mismatched halves at import already; the probe covers engines that do not. Rejected: letting `importPublicKey` strip private members, against invariant 8; leaving the pairing to the application, for the mismatch above.
26. **`nbf` and `iat` get at least 60 seconds of future leeway; `exp` and `maxAge` keep `clockTolerance`.** A token is refused as not yet valid only when `nbf` or `iat` is more than `max(clockTolerance, 60)` seconds ahead of the verifier's clock. Decision 6 weighed the default tolerance as something that extends a token's life, which holds for `exp` and `maxAge`; it did not weigh that an issuer stamps `iat` and `nbf` from its own clock, so a token checked the moment it is issued fails whenever the verifier's clock is a fraction of a second behind, as two hosts' clocks routinely are. Accepting a token up to 60 seconds early does not lengthen a life `exp` bounds. `maxAge` counts from `iat`, so a token stamped up to `max(clockTolerance, 60)` seconds ahead is accepted until `iat + maxAge + clockTolerance` inclusive, that much past `maxAge` by the verifier's clock; the 0.1 full audit found this was not recorded, and a replay store must keep each `jti` until that time has passed. It stands: counting `maxAge` from `min(iat, now)` accepts the same token for `maxAge` from whenever it is first seen, and refusing an `iat` ahead of the clock when `maxAge` is set brings back the fresh-token failures this decision fixes. Decision 6 stands for `exp` and `maxAge`. The floor is fixed, with no option: a caller who wants less has no case it protects. Rejected: a default tolerance above 0 for every claim, which decision 6 rejected; a separate `futureTolerance` option, which adds surface for a value nobody needs to tune; leaving it, which fails fresh tokens at random.
27. **Every JWS algorithm Web Crypto signs with is supported, and the algorithm unions may widen in a minor release.** `ES384`, `ES512`, `RS384`, `RS512`, `PS384`, `PS512`, `HS384` and `HS512` join decisions 1, 2 and 13; each is one row of the algorithm table plus vectors and interop tests. The roadmap deferred them because adding one widens `AsymmetricAlgorithm` and what every key set accepts, which is a breaking change for `@codenhub/oidc`. That weighed the cost of each widening but not the alternative: an issuer or client that signs with `ES384` or `RS512` cannot be verified at all, and OpenID providers and `private_key_jwt` clients do use them. Adding them all before 0.1.0 pays the widening once. From 0.1.0 on, `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm`, the JWK and header types and the default `algorithms` of a key set may gain members in a minor release, and the package documents that, so a consumer's exhaustive `switch` over them needs a default branch. Rejected: adding algorithms one at a time on demand, which makes each a breaking change; keeping only the four, for the issuers above.
28. **Unknown options throw in every function that takes options.** Decision 22's rule now covers `generateKeyPair`, `generateSecretKey`, `importPublicKey`, `importPrivateKey`, `importKeyPair`, `importSecretKey`, `importKeySet`, `readHeader` and `sign`'s input as well as `createVerifier` and `createRemoteKeySet`, with the same message and the same handling of `undefined` values and symbol keys. Decision 22 limited the rule to the two functions where a typo turned a check off, and left other functions unchanged; it did not weigh that a typo elsewhere also falls back to a default silently, such as `{ extractible: true }` giving a key that cannot be exported until the day it must be, or `{ maxLenght: 512 }` reading a header of the default length, and that two rules for one kind of mistake are harder to learn than one. Rejected: keeping the rule to the two functions, for those cases.
29. **A remote key set accepts an `http:` URL on a loopback host.** The host must be `localhost`, an address in `127.0.0.0/8` or `[::1]`, as the WHATWG URL parser normalizes them; every other `http:` URL is still refused. Section 4's "HTTPS only" did not weigh local development and integration tests, where an identity provider such as the SSO application runs on `http://localhost` and a consumer otherwise has to replace the whole key set to point at it. Traffic to a loopback address does not leave the host, so TLS protects nothing there. Rejected: an `allowHttp` option, which can be left on in production; keeping HTTPS only, for local development.
30. **`sign` embeds a public key for DPoP, and `jwkThumbprint` computes RFC 7638 thumbprints.** `sign({ ..., embedKey })` writes the public JWK of `embedKey` as the `jwk` header, only from a public key this package created, with the same `alg` as the private signing key and proven to be its pair. `jwkThumbprint(publicKey)` returns the SHA-256 thumbprint that `cnf.jkt` binds a token to. This partly reverses decision 18: `sign` still refuses a `jwk` member in `header`, and the verifier still never selects a key from a token. Decision 18 did not weigh DPoP (RFC 9449), which a client holding sender-constrained tokens needs, and so does a server that issues or accepts them: a DPoP proof must carry its public key in `jwk`, so a client could not sign one, and a server could not compute the `jkt` an access token binds to. A server verifies a proof by reading the header with `readHeader`, importing `header.jwk` with `importPublicKey` for the header's `alg`, and verifying with a key set of that one key: the caller chooses to trust the key, which is what DPoP means. The roadmap's note that a thumbprint helper is not needed considered only `kid` values. When this was recorded, its reason named the SSO application as a DPoP server and `@codenhub/oidc` as a client; both have since put DPoP out of scope, and the 0.1 full audit found the decision stands on the general need above, which no consumer of this package could meet without it. Rejected: a `jwk` header member written by the caller, which lets a private member or a key of another algorithm reach a token; a verifier option that trusts the embedded key, which reopens what invariant 1 closes for every caller who sets it by mistake.
31. **`importPublicKey`, `importPrivateKey` and `importKeyPair` also take a PEM string, with a `kid` option for it.** A `PUBLIC KEY` (SPKI) or `PRIVATE KEY` (PKCS#8) block, at most 16384 characters with only whitespace around it, is read by Web Crypto into the JWK of its material, and every JWK check then runs on that JWK; anything else is `invalid_key`, and a `PRIVATE KEY` given for a public key is `unexpected_private_key`. A PEM has no place for a `kid`, so the `kid` option names it; decision 51 extends the option to a JWK. Section 2 named only JWK import; it did not weigh that keys are often handed over as PEM, from OpenSSL, a cloud KMS, or a secret store, and a consumer had to convert them with a second library. Rejected: separate `importPublicPem`-style functions, which double the import surface for one input type; accepting PKCS#1 (`RSA PRIVATE KEY`) and SEC 1 (`EC PRIVATE KEY`), which Web Crypto does not read and would need a DER parser here, against invariant 11's spirit of a small trusted base; encrypted PEM, which needs a password-based KDF. Decision 48 widens "only whitespace around it" to whitespace inside the block too.
32. **A verifier requires `exp` unless `maxAge` is set, and refuses a token with `aud` when it names no audience.** `requireExpiration: false` waives the first, for tokens that carry no `exp` by design; `audience: false` waives the second, for a verifier that accepts every audience on purpose. The 0.1 release audit found that the defaults accepted a token for another service: with no `audience` option, `{ aud: "other-api" }` verified, though RFC 7519 §4.1.3 says a recipient not named in `aud` must reject the token, and an issuer that mints tokens for several clients, as the SSO application does, made each service accept the others' tokens. A token without `exp` verified forever unless `requiredClaims` listed it, so an issuer bug that dropped `exp` produced tokens that never expire. Decision 6's reasoning, that a default never silently widens what a token is good for, applies to both. `maxAge` waives `exp` because it bounds a token's life on its own, as for DPoP proofs. Rejected: keeping the defaults and documenting them, for the cases above; requiring `audience`, which refuses a verifier whose tokens never carry `aud`; no waiver for `exp`, which leaves tokens without `exp` by design, such as API keys revoked by `jti`, unverifiable.
33. **`allowExpired` accepts a token whose `exp` has passed, with every other check still run.** An OpenID Provider must accept an expired ID token as `id_token_hint` at RP-initiated logout, the SSO application's first roadmap item, and `@codenhub/oidc` worked around the missing option by parsing the payload itself and verifying again with the clock set to `iat`. Rejected: a per-call `now`, which still makes the caller read `iat` from a payload it has not verified; a larger `clockTolerance`, which decision 6 caps for a reason.
34. **`type` takes an array of accepted values, and `null` in it accepts a token without `typ`.** A single value could not say "absent, or `at+jwt`", the common case while an issuer moves to RFC 9068 access tokens, nor accept two token types in one verifier. Rejected: a separate option for an optional `typ`, which adds surface for one case of the list.
35. **A key without a `kid` stands in for a header `kid` that no key in the set has.** Exactly one key without a `kid` must have the header's `alg`; several is `ambiguous_key`, none `unknown_kid`. Keys handed out as PEM, as Clerk and Supabase do for their session tokens, have no `kid`, while the tokens name one, so `createKeySet([await importPublicKey(pem, { alg: "RS256" })])` refused every token with `unknown_kid` unless the caller knew the issuer's `kid` ahead of time. The caller chose to trust that key for its algorithm, and the signature still has to verify, so the fallback trusts nothing new. A remote set refetches first, under the same cooldown as an unknown `kid`, and lets the key without a `kid` stand in only when the refetched JWKS still lacks the `kid` or the refetch fails; selecting it straight from the cache would make a rotated-in `kid` fail with `bad_signature` until the cache expired. The cost: such a set refetches once per cooldown while tokens name a `kid` it never lists. Rejected: a `createVerifier({ key })` form, which adds a second way to give keys; trying every key, against the rule that keys are never tried in turn.
36. **`sign` is generic over its payload type.** `SignInput<TPayload>` accepts any object type whose registered claims have their RFC 7519 types (`JwtRegisteredClaims`) and whose members are all JSON values (`JsonCompatible`); the default stays `JwtPayload`. Typing the payload as `JwtPayload`, whose index signature an `interface` does not satisfy, made `sign({ payload: claims })` a compile error for claims declared as an `interface`, the usual way to declare them, while a type alias holding a `Date` compiled and then threw. Rejected: `payload: object`, which drops the registered claim types; `Record<string, unknown>`, which has the same index-signature problem.
37. **A remote key set answers from an expired JWKS at once and refetches in the background.** Within `maxStale` after `cacheTtl`, a `select` uses the cached JWKS without waiting and starts a fetch; only a key the cache lacks waits for it. Before, the first token after expiry waited for the fetch, up to `timeout` when the issuer hung, once per cooldown window, which put the issuer's latency on the request path for no gain in safety: decision 5 already accepts these keys for `maxStale`. The cost: a key the issuer removed is accepted for the duration of one more fetch after `cacheTtl`; decision 5's bound of `cacheTtl` plus `maxStale` still holds. A fetch that has not settled a second past `timeout` and past the cooldown no longer blocks a new one, and a fetch that settles after being replaced changes nothing, because on Workers a fetch started by a request that ended may never settle. Rejected: an option to choose waiting, which no consumer has asked for.
38. **A remote key set takes a `seed` and reports fetches through `onFetch` and `onFetchError`.** A serverless process, Symbolon's Workers among them, starts each isolate with an empty cache and fetches the JWKS on the first token; `onFetch` hands out `{ url, jwks, fetchedAt }` to store (the `url` since decision 59), and `seed` starts a set from it with the same TTL and `maxStale` rules as a fetch. An invalid seed is ignored rather than thrown, because it comes from storage an earlier version may have written. `onFetchError` gives an operator the failures that `maxStale` otherwise hides until it runs out. Callbacks' errors are swallowed so a broken store or logger never fails a token, and a promise a callback returns goes to `waitUntil` (decision 42), since on Workers a save the request does not await is otherwise cancelled with it. Rejected: exposing the cache as a method, which adds state a caller must synchronize; a cache-store interface, which is more surface than one value in and one out.
39. **`createKeySet` and `importKeySet` return a `LocalKeySet`, which lists its keys.** An issuer such as Symbolon verifies its own tokens with a set and publishes the same keys at its `jwks_uri`; with `select` alone it had to keep a second list beside the set, and the two could disagree after a rotation. The list is the set's own frozen array, so reading it costs nothing and cannot change the set. A remote key set does not list its keys, because its keys change under the caller; `onFetch` (decision 38) gives its JWKS instead. Rejected: an `exportJwks(set)` helper, which would have to decide what to do with secret keys and with the six keys an RSA JWK without `alg` becomes, choices the caller makes better with `filter` and `exportPublicJwk`.
40. **`jwkThumbprint` takes a private key too, and `importPrivateKey` proves the key's halves match.** A signer that names its key by thumbprint holds a private key, usually not extractable, and had to keep the public key around only to compute its `kid`. Each private key now carries its public half, which `generateKeyPair` and `importKeyPair` already had. `importPrivateKey` runs `importKeyPair`'s probe signature, so a JWK whose public members belong to another key is `invalid_key` there too; without it, the thumbprint of such a key would name a key other than the one that signs. The cost is one signature and one verification per import. Rejected: thumbprints only for extractable private keys, which leaves out the default; storing the public half unproven, which gives the wrong `kid` for a mixed JWK.
41. **`importPublicKey` takes a PEM `CERTIFICATE` and imports its public key, checking nothing else in it.** Firebase Authentication publishes the keys for its ID tokens as PEM certificates, and Auth0 offers its signing certificate for download, and converting one with `openssl x509 -pubkey` was a step every such consumer had to know. The key is found by a bounded walk of the fields before `subjectPublicKeyInfo` (RFC 5280 §4.1), at most 16384 characters of PEM, and Web Crypto then parses the key as it does any SPKI. Validity, chain, extensions and signature are not checked: path validation is a large, separate job, and a certificate given out of band is trusted the way a bare key would be. Rejected: an `importX509` function, a second name for the same import; reading `x5c` in a JWKS, which would invite trusting a chain this package does not validate.
42. **A remote key set takes a `waitUntil` hook, and a `select` that joins a fetch waits only until its deadline.** Decision 37's background fetch outlives the request that starts it, and Cloudflare Workers cancels a request's unfinished I/O once it responds. A probe in production Workers (2026-11-19, compatibility date 2026-06-01) showed a second request awaiting such a fetch rejected at once with "This promise was created by a request that has since ended"; the Miniflare 5 beta the workerd test runs hangs instead. Either way a token with a new `kid` failed, and the cache was replaced only when `maxStale` ran out, so a removed key was routinely trusted for `cacheTtl` plus `maxStale`. `waitUntil` takes `waitUntil` from `cloudflare:workers`, which the probe showed keeps the fetch alive. A joining `select` that sees the fetch reject, or pass a second after its `timeout`, fetches again once from its own request, which covers Workers code that does not pass the hook. Rejected: detecting Workers and changing behavior by runtime, which guesses; making background refresh opt-in, which takes the latency win from every other runtime to fix one; a per-`select` hook, which would change the `KeySet` contract every key set implements.
43. **A key set can bind its keys to an issuer, and a verifier requires a bound key's issuer as `iss`.** `createKeySet(keys, { issuer })`, `importKeySet(jwks, { issuer })` and `createRemoteKeySet({ issuer })` hand out keys whose `issuer` member names it; `createKeySet` binds frozen copies, which share the original's material. When the selected key has an `issuer`, the token's `iss` must equal it, with or without the verifier's `issuer` option: a missing `iss` is `missing_claim` and another is `wrong_issuer`, each reported once. The 0.1 full audit found that a verifier holding several issuers' keys, as the multi-tenant recipe in key-sets.md did and any multi-tenant verifier would, accepted a token signed with tenant A's key that claimed tenant B's `iss`: the `issuer` option says which issuers are accepted, never which issuer a key speaks for, so anyone holding one tenant's key could impersonate every other. Binding the key rather than the set makes the check survive a key set built from other key sets, which is how several issuers reach one verifier. Rejected: a set-level issuer the verifier reads from the key set, which a composite set loses; documenting one verifier per issuer, which leaves the default recipe unsafe and needs the caller to route by an unverified `iss`; a callback from key to issuer on the verifier, which is a second place to configure what the key set already knows.
44. **Issue codes and `params.reason` values may gain members in a minor release.** Their meaning never changes; a new failure that needs its own name gets a new code rather than reusing one that means something else. Freezing the union at 0.1.0 would have forced each new check, such as one a future RFC adds, either into a major release or into an existing code that names the wrong thing, and decision 27 already widens the algorithm unions the same way. Callers handle an unknown code as a failure, which every caller must already do for an unverified token. Rejected: freezing the codes, for that reason; a catch-all code such as `other`, which callers cannot act on.
45. **`sign` refuses an `exp`, `nbf` or `iat` above 253402300799, the last second of year 9999.** Such a value is almost always `Date.now()` in milliseconds, which signs a token that expires some 55,000 years later and that every verifier accepts. RFC 7519 sets no upper bound, so the verifier still accepts any finite number another issuer signs. Rejected: a relative-time helper such as `expiresIn`, which adds surface for something one expression does and still leaves the mistake open to anyone writing `exp` by hand, until decision 55 added one; a verifier-side bound, which would refuse tokens other issuers legitimately sign.
46. **`generateKeyPair` retries Ed25519 generation that fails with `OperationError`, up to three times.** Linux WebKit's libgcrypt backend rejects about 1 Ed25519 generation in 128, when the new key's `d` or `x` starts with a zero byte, and the WebKit fix had not reached released builds when this was recorded; WebKitGTK and WPE browsers are real consumers, not only Playwright. Each attempt draws a new key, so the retry makes the failure about 1 in 270 million calls and costs nothing on other runtimes. Only `OperationError` from an OKP generation is retried; anything else propagates as before. The package AGENTS.md trap says when the retry can go. Rejected: telling consumers to retry, which every browser consumer of `EdDSA` or `Ed25519` had to learn from a failure in production; retrying every algorithm, which would hide real failures elsewhere.
47. **`createVerifier({ keys })` also takes a function from the claimed `iss` to a key set.** The verifier decodes the payload under the usual rules before the signature, reads `iss`, and calls the function with it and the header; `undefined` is `wrong_issuer`, a missing `iss` `missing_claim`, a non-string one `invalid_claim`, and an `iss` the `issuer` option does not list is refused before the function runs. Anything else the function does, throwing or returning a non-key-set, is `key_fetch_failed` with `key_set_error`, as for a custom key set (decision 16). This amends invariant 3, which did not weigh that `iss` is the only signal a multi-issuer verifier has to pick keys by when issuers choose their own `kid` values, as third-party identity providers and multi-tenant issuers do (Symbolon's scope leaves tenants for after its 0.1): the kid-prefix recipe in key-sets.md needs every issuer to encode its tenant in `kid`, and otherwise callers decoded the payload with a second library, with none of this package's strict parsing, to route the token themselves. The `iss` read is bounded as before (invariant 5), is handed to nothing but the function, and is checked again after the signature, where decision 43's binding refuses a key of another issuer. Rejected: a `decode()` export, which reopens invariant 3 for every claim; trying each issuer's key set in turn, whose cost grows with the tenants and whose unknown `kid` triggers a refetch in every remote set; passing the whole payload to the function, which hands it unverified claims routing does not need; documenting the custom key set only, which cannot see `iss`.
48. **A PEM block may hold whitespace anywhere inside it.** Whitespace is removed before the base64 is decoded, which RFC 7468 §3 calls lax parsing; the base64 must still be canonical, and nothing but whitespace may surround the block. Decision 31 did not weigh that PEMs kept in environment variables and secret stores often lose their line breaks or have them turned into spaces, and the 0.1 full audit found such a key refused as `invalid_key` with nothing to say why. Line breaks written as the escapes `\n` and `\r`, as a `.env` file or a JSON-encoded secret leaves them, count as line breaks, which the same audit found refused next; a backslash never occurs in a PEM, so the escapes cannot be mistaken for anything else, and any other backslash is still `invalid_key`. Rejected: asking callers to restore the line breaks, which each one had to discover; accepting text around the block, which would let a label or comment slip through unread.
49. **The import functions also take a Web Crypto `CryptoKey`, and `importPrivateKey` and `importKeyPair` a `CryptoKeyPair`.** A public `CryptoKey` must be extractable, and is exported and checked as a JWK. A pair's private `CryptoKey` is kept as given and never exported, so a non-extractable key stays so: the JWK checks run on its public half, and the probe signature proves the halves match and that the private key fits `alg`, hash and padding included. An extractable private `CryptoKey` alone is read as a JWK; a non-extractable one alone is `invalid_key`. An HMAC `CryptoKey` is kept as given after its hash, usages and length are checked. `extractable: true` needs an extractable `CryptoKey`. The import functions took only JWK and PEM, which both need the private material in hand, so no key could be imported non-extractable from storage, and this package's own key objects cannot be kept in IndexedDB, since their material sits in a registry the structured clone does not see. A browser that must sign across page loads without being able to read its key, such as a DPoP client, had no way to do it. Rejected: separate `importCryptoKey`-style functions, for decision 31's reason; exposing a key object's `CryptoKey`, which breaks the opacity every key relies on; a signer callback for keys held in a KMS or HSM, which needs `sign` to take an asynchronous signer and which no consumer has asked for yet; decision 54 adds one.
50. **`getPublicKey(privateKey)` returns a private key's public half.** Every private key already holds it, proven to match when generated or imported, for thumbprints (decision 40) and `embedKey` (decision 30); the function hands it out as a public key with the same `alg` and `kid`, the same object on every call. A key loaded with `importPrivateKey` alone otherwise had no way to publish its JWK or verify its own tokens, and `exportPublicJwk` given the private key threw "Expected a public key" with no pointer; it now names `getPublicKey`. Rejected: letting `exportPublicJwk` take a private key, which helps only the export and not `createKeySet` or a verifier; removing `importPrivateKey` in favor of `importKeyPair`, which breaks the common case of loading one signing key.
51. **The `kid` option of every import function also names a JWK, and `generateKeyPair` takes `kid: "thumbprint"`.** A JWK without a `kid` takes the option; a JWK whose own `kid` differs is `invalid_key` at `["kid"]`, and the same `kid` in both is accepted. `kid: "thumbprint"` gives both generated keys the public key's RFC 7638 thumbprint, so that literal string is reserved there. Key objects are frozen and their `kid` cannot be set after creation, so decisions 15 and 31, which ignored the option for a JWK, left a JWK stored without a `kid` (as many key stores and `exportPrivateJwk` of an unnamed key produce) with no way to be named but rebuilding the JWK by hand, and dropped a conflicting option silently; and a signer naming its key by thumbprint had to generate, compute the thumbprint, export and re-import. The 0.1 full audit found both. Rejected: the JWK's `kid` silently winning, which hides a configuration mistake; the option silently winning, which renames a key its JWKS publishes under another `kid`; a `withKid(key, kid)` function, which adds a second way to name keys and a copy of every key kind; a separate `thumbprintKid: true` option, which adds surface for one value the `kid` string can carry.
52. **JWK import refuses a `key_ops` with a repeated operation as `invalid_key`, and one with an operation other than `sign` and `verify` as `wrong_use`, for every key kind.** RFC 7517 §4.3 forbids duplicates and says unrelated operations SHOULD NOT share a key; a JWK with `["verify", "encrypt"]` names a key also used for encryption, and signing with key material that also encrypts is the cross-protocol use that rule exists to prevent. Import checked only that the required operation was present. The 0.1 full audit found both. The cost: a JWKS that lists such a key, which no common issuer publishes, loses that key. Rejected: refusing only on asymmetric keys, which leaves the same mistake accepted for a secret; ignoring unknown operation values, which RFC 7517 allows to exist but which say nothing a signature key needs.
53. **A verifier takes `onKeySetError`, and a `keys` function may return a route, `{ keys, audience, type }`.** Decision 16 keeps a key set's exception out of the result, which is right for the issue but left the cause with nowhere to go: a tenant lookup that failed on a database error showed only `key_set_error`. `onKeySetError` receives the thrown value, or a `TypeError` naming what came back instead of a result, and its own errors are swallowed as `onFetch`'s are (decision 38). Decision 47 routed only keys, so a multi-tenant verifier whose tenants each have their own client ID had to set `audience: false` and recheck `aud` in a schema, or build one verifier per tenant. A route's `audience` and `type` replace the verifier's for that issuer and are validated as the options are, each time, with an invalid one `key_set_error`. A key set is recognized first by its `select` function, so a `LocalKeySet`, which also has `keys`, is never read as a route. The 0.1 full audit found both. Rejected: putting the error in the issue's params, which decision 16 rejected because it can quote anything; a per-issuer map of options on the verifier, which duplicates what the resolver already knows; letting a route override other options such as `clockTolerance` or `maxAge`, which no consumer has asked for.
54. **`createExternalSigningKey({ publicKey, sign, signatureFormat? })` makes a private key whose signatures come from a function, for a key held by a cloud KMS or an HSM.** `alg` and `kid` come from the public key, `signatureFormat: "der"` converts a strict DER ECDSA signature to JWS form, and `sign` verifies every external signature with the public key before returning the token, throwing a `TypeError` when it fails. The key is never extractable. Decision 49 rejected a signer because no consumer had asked for one; the 0.1 full audit weighed that an issuer whose policy keeps signing keys in a KMS, as Symbolon may for its own tokens, otherwise has no way to use this package to sign at all, and that the change is additive and touches only `sign`. Rejected: `sign` taking a signer in place of `key`, which leaves `getPublicKey`, `jwkThumbprint` and `embedKey` without a key object; a probe signature at creation, which costs a KMS call, and money, at every start, while verifying each signature catches the same mistakes on first use; detecting DER by length, which collides with raw signatures for some lengths; skipping the per-token verification, which would hand out tokens no one can verify when the service key rotates under a fixed public key.
55. **`sign` takes `issuedAt`, `notBefore`, `expiresIn` and `jti` options that add those claims, and a `now` clock.** `issuedAt: true` writes `iat` as the current time, `notBefore` and `expiresIn` write `nbf` and `exp` that many seconds after it, and `jti: true` a `crypto.randomUUID()`; times are whole seconds, the clock is read once, and `now` returns milliseconds as a verifier's does. An option whose claim the payload also sets throws rather than picking one. This partially reverses decision 45, which rejected `expiresIn` as surface for one expression. It did not weigh that the maintainer wants the conveniences, or that the milliseconds risk it guarded against is handled here by names that say seconds and by bounds: `notBefore` and `expiresIn` must be whole numbers from 0 to 315360000, ten years, so `Date.now()` and any millisecond duration of four days or more throws, and decision 45's bound on the claims themselves still holds for a payload written by hand. The cost: a duration in milliseconds under four days, such as `expiresIn: 300_000`, still signs, as a token that lives a thousand times longer than meant. Rejected: leaving every claim to the caller, decision 45's choice, which the maintainer's request outweighs now that the options cannot take milliseconds from four days up; absolute-time options such as `expiresAt`, which are the payload's `exp` under another name; accepting time strings such as `"5m"`, which adds a parser and a unit grammar; basing `exp` on a payload's own `iat`, which would make the result depend on a claim the option does not name.
56. **The schema failure code is `schema_failed`.** A `claims` schema's issue was `invalid_claims`, one letter from `invalid_claim`, the code for a registered claim of the wrong type: the two were easy to confuse in a `switch` and in logs, and nothing flagged the typo, since both are members of `JwtIssueCode`. Issue codes freeze with 0.1.0 (decision 44 only adds members), so the name had to change before the release. Rejected: keeping `invalid_claims`, which keeps the near-collision forever.
57. **A verifier takes `subject`, the accepted `sub` values, and fails any other with the new code `wrong_subject`.** It works as `issuer` does: when set, `sub` is required (`missing_claim`) and must equal one value exactly. A verifier of RFC 7523 client assertions, or of tokens about one known service account, otherwise had to check `sub` after verification, where forgetting it accepts every subject the issuer signs for. A new code rather than `invalid_claim`, which means a wrong type (decision 44 allows adding one). `jti` needs no option: `requiredClaims: ["jti"]` already requires it, and its value is the caller's replay store's business. Rejected: a `claims` schema for it, which reports `schema_failed` without saying which claim check failed; checking `sub` in a route, which no consumer has asked for.
58. **A JWKS fetch that imports no usable key fails with `reason: "no_usable_keys"`.** A JWKS of no keys, of keys only for algorithms outside `algorithms`, or of keys that all fail to import, is a failed fetch (decision 44 allows the new reason): the cache stays as it was, `onFetchError` is called, and the cooldown applies as after any failure. A seed whose `jwks` imports no usable key is ignored. Before, such a response replaced keys that worked with none, so every token failed with `unknown_kid` or `no_matching_key` until the next fetch, and `maxStale`, which exists to ride out an issuer's outage, never covered it: an issuer that publishes `{"keys":[]}` while misconfigured is an outage, not a rotation. The cost: an issuer that empties its JWKS on purpose, to revoke every key, has its old keys trusted until the cache stops being usable, at most `cacheTtl` plus `maxStale` after the last fetch that succeeded, the bound of decision 5. Rejected: accepting the empty set, for the outage above; an option to choose, which no consumer has asked for.
59. **A remote key set records its URL in each snapshot, asks for `cache: "no-cache"`, and shortens its TTL to the response's `max-age`.** A snapshot held only `{ jwks, fetchedAt }`, so a set seeded from a store key another set also wrote, such as staging and production sharing `"jwks"`, bound the other issuer's keys to its own `issuer` for up to `cacheTtl` plus `maxStale`; a seed is now used only when its `url` normalizes to the set's own, and one without `url` is ignored, which costs nothing because no released version wrote snapshots. A browser's HTTP cache honours the issuer's `Cache-Control`, so a refetch for a rotated-in `kid` could be answered with the old document and a removed key outlive the `maxStale` bound of decision 5; `cache: "no-cache"` revalidates instead, and a runtime that refuses the member, as Workers before compatibility date 2025-08-07 do, is retried without it only when its rejection names `cache`, so a network failure still costs one request. A `max-age` shorter than `cacheTtl` shortens the TTL, never below `cooldown`, and `no-store` or `no-cache` gives `cooldown`; `cacheTtl` stays the upper bound, so an issuer cannot make keys live longer than the caller allows. Rejected: a `Cache-Control` request header, which is not CORS-safelisted and makes every cross-origin JWKS fetch need a preflight; retrying every rejected fetch without `cache`, which doubled the requests a failing issuer receives; and recording the `max-age` in the snapshot, since a seed taking the full `cacheTtl` is bounded by the caller's own setting.
60. **Every import function takes `kid: "thumbprint"`, as `generateKeyPair` does.** It names the key by the RFC 7638 thumbprint of its public key, or of the secret for `importSecretKey` (RFC 7638 §3.2 defines one for `oct`), whatever form the key arrives in. A JWK with its own `kid` keeps decision 51's rule: accepted when it equals the thumbprint, `invalid_key` at `["kid"]` otherwise. A non-extractable secret `CryptoKey` is `invalid_key`, since its secret cannot be hashed. Decision 51 reserved the literal for generated pairs only, so a key stored as PEM or held as a `CryptoKey` had to be imported, hashed with `jwkThumbprint` and imported again to carry its thumbprint as `kid`, and `"thumbprint"` given to an import named a key `"thumbprint"`. The 0.1 key audit found it. Rejected: leaving imports as they were, which gives one option two meanings across functions; the option winning over a JWK's own `kid`, which decision 51 rejected for any `kid`.
61. **`createKeyRing({ keys, publishAhead, publishAfter, issuer?, now? })` schedules an issuer's signing keys.** Each entry is `{ key, activeFrom, retiredAt? }` with a private key that has a `kid`; a key signs from its `activeFrom` until the next key's `activeFrom` or its own `retiredAt`, whichever comes first, and is published from `publishAhead` seconds before it signs until `publishAfter` seconds after it stops. `signingKey()` returns the key whose `activeFrom` came last, unless it is retired, and throws a `TypeError` when no key signs, never falling back to a key a later one replaced; `jwks()` resolves to the frozen public JWKS of the keys published now, in `activeFrom` order; and the ring is itself a `KeySet` over those same keys, bound to `issuer` when given (decision 43). An issuer, Symbolon among them, had to hand-roll the order a rotation needs: publish a key before it signs, so verifiers caching the JWKS (decision 5) have it, and keep it published until its tokens expire; getting it wrong fails tokens with `unknown_kid`, and the JWKS and the verifying set could disagree, which decision 39 already worked to prevent. The ring stores nothing and reads `now` at each call, so a caller keeps keys and times in its own storage and rebuilds the ring, as a serverless issuer must anyway. Times are whole seconds since the epoch, bounded as decision 45 bounds claims, so `Date.now()` in their place throws, and durations are seconds (decision 19); a record holding plain numbers survives JSON storage, which a `Date` does not. Validation is strict: 1 to 100 keys (the JWKS key limit), unique `kid`s and `activeFrom`s, `retiredAt` after `activeFrom`, `publishAhead` and `publishAfter` required whole numbers up to ten years, and unknown options and entry members throw (decision 28). Keys of different algorithms are accepted, since changing algorithm is a reason to rotate. `sign({ key: ring.signingKey() })` is the signing path; no signing convenience was added, because it would duplicate every `sign` option for one argument. Rejected: a ring that only computes the current key and leaves publishing to `createKeySet`, which keeps the two lists that can disagree; separate `keySet()` and `jwks()` objects, more surface for the same keys; a `signingKey()` result instead of a throw, since no key to sign with is a configuration mistake no request recovers from; checking for a signing key when the ring is created, which would also take down verification and the JWKS endpoint of an issuer whose newest key retired; letting a retired newest key fall back to the key it replaced, which would resume signing with a key the issuer chose to stop; `Date` or millisecond times, for the storage reason above; a `Cache-Control` helper, since the right `max-age` depends on the caller's verifiers and is documented in rotation.md instead; secret keys, which are never published in a JWKS.
62. **`createDpopProof` creates RFC 9449 proofs, and `createDpopVerifier(options)` returns `verify(proof, request)`, which checks them per §4.3.** The proof is signed with `embedKey` (decision 30), without the key's `kid`, and refuses a secret key. The verifier trusts the key the proof carries, which is what a proof proves, so this amends decision 30, which left that to a recipe of `readHeader`, `importPublicKey` and a one-key verifier: that recipe stopped at the signature and left `htm`, `htu`, `ath`, `nonce`, `jti` replay and the `cnf.jkt` binding to every server, each a check whose omission accepts a replayed or stolen proof without a visible failure. Invariant 1 holds in the form that matters: the key is imported for the header's `alg` only when `algorithms` lists it, and never for a symmetric one, so the proof's key and `alg` cannot disagree and there is no secret to confuse with a public key. The verifier is a factory, as `createVerifier` is, so its options are checked once at startup (decision 22); the request is the caller's own data, so a malformed one rejects with a `TypeError` rather than becoming an issue. `typ` must be exactly `dpop+jwt`, without the RFC 7515 normalization `createVerifier` applies, since RFC 9449 names that value. `htm` is compared exactly, as methods are case-sensitive. `htu` is compared after the WHATWG URL parser's normalization, with query and fragment removed, and without percent-decoding. `maxAge` defaults to 60 seconds, and `iat` keeps decision 26's future leeway. The new codes are `wrong_method`, `wrong_url`, `wrong_access_token_hash`, `wrong_nonce`, `wrong_key`, `replayed` and `callback_failed` (decision 44 allows adding them). A missing nonce is `wrong_nonce` rather than `missing_claim`, so a server maps one code to `use_dpop_nonce`. `request.accessTokenClaims` binds the access token: the proof's thumbprint must equal its `cnf.jkt`, and claims without one fail closed with `wrong_key`, so an unbound token cannot pass as a bound one; an introspection response works the same. A `nonce` function and `acceptJti` run last, only for a proof that passed every other check, so a refused proof consumes no `jti`; what they throw is `callback_failed` and goes to `onCallbackError`, as decisions 16 and 53 keep a key set's error out of the issue. Rejected: a `verifyDpopProof(proof, options)` function, which validates options on every request; an option on `createVerifier` that trusts the embedded key, which decision 30 rejected for every caller who sets it by mistake; `missing_claim` for a missing nonce, which splits one server answer across two codes; a `jkt` member on the request, which leaves reading `cnf.jkt` safely from the claims to each caller; replay tracking inside the package, which needs storage shared across instances that only the caller has.
63. **Compact JWE is in 0.1, with `dir`, `A128KW`, `A256KW`, `ECDH-ES` and `ECDH-ES+A128KW`/`A256KW` on P-256, P-384, P-521 and X25519, `RSA-OAEP-256` and `RSA-OAEP`, and `A128GCM`, `A256GCM`, `A128CBC-HS256` and `A256CBC-HS512`.** It gives `@codenhub/oidc` encrypted ID tokens, userinfo and request objects, which providers and clients require by registration. The roadmap had deferred it to the next minor release because no consumer received encrypted tokens yet; the maintainer brought it into 0.1.0. `RSA-OAEP` (SHA-1) is supported because providers still list it, often alone, and SHA-1's collision weaknesses do not reach OAEP's mask generation. Refused with a result, never a throw: `RSA1_5`, whose padding oracle RFC 8725 §3.2 warns against; `PBES2-*`, whose iteration count the token sets, so a hostile token chooses the recipient's cost, and which no OIDC flow uses; any `zip`, since compression before encryption leaks the plaintext through the length and a small token can inflate to an unbounded plaintext; and any `crit`, as for JWS. The 192-bit algorithms are omitted because Chromium's Web Crypto has no 192-bit AES, so a token using one would decrypt in Node.js and Firefox and fail in every Chromium browser and Chromium-based runtime; they are `unsupported_alg` or `unsupported_enc` everywhere instead. Rejected: JWE JSON serialization and multiple recipients, which no OIDC flow uses; `RSA1_5` behind an opt-in, since an opt-in oracle is still an oracle on the server that enables it.
64. **Encryption keys are three separate kinds, `JwePublicKey`, `JwePrivateKey` and `JweSecretKey`, in a registry of their own, each bound to one key management algorithm, and a `dir` secret also to one `enc`.** Invariant 1 applies unchanged: a decrypter fails a token whose `alg` is not its key's, and a `dir` token whose `enc` is not its key's, with `alg_mismatch`; the decrypter's `enc` option lists the content algorithms it accepts, checked before any key is selected. No JWS function can see a JWE key and no JWE function a JWS key, so the same key object never both signs and encrypts, which RFC 7517 §4.3 advises against and which `use` and `key_ops` (decision 52) only state. A JWK's `alg` must name the key's own algorithm, so a `dir` JWK whose `alg` names the content algorithm, as RFC 7520 §5.6 writes one, is `alg_mismatch`, and imports once its `alg` is removed. Rejected: one key kind with a `use` flag, which every function would have to check and one forgotten check would break; letting a `dir` key take whatever `enc` the header names, which lets the header choose how the key is used; reading a `dir` JWK's `alg` as its `enc`, which gives one JWK member two meanings.
65. **Every failure after key selection is one code, `decryption_failed`, with no path, and a failed unwrap continues with a random content key.** A failed AES unwrap, RSA-OAEP decryption or ECDH unwrap, a wrong tag, and a tampered header, IV or ciphertext are indistinguishable in the result, and the random content key (RFC 7516 §11.5) carries a failed unwrap on to the tag check like any other token. The CBC-HMAC tag is compared in constant time before AES-CBC runs, so a padding error is never observable. Failures before selection, such as an IV of the wrong length or an `epk` off the curve, keep their own codes, because they describe only the token's shape, which its sender already knows. Rejected: distinct codes for unwrap and tag failures, which is the oracle Bleichenbacher's and Manger's attacks need; one code for every JWE failure, which hides configuration mistakes, such as an `enc` the decrypter does not accept, that cost an attacker nothing to learn.
66. **A decrypter returns the plaintext as bytes and reads no claims; signed claims inside a JWE come only from `createNestedVerifier`, and `encryptJwt` signs before it encrypts.** Encrypting to a public key needs only the public key, so a decrypted payload says nothing about its author, and a `decryptJwt` that validated claims would present them as trustworthy when anyone could have written them. The nested verifier requires a `cty` of `JWT` or none, and passes the plaintext to an ordinary verifier, which runs every check a bare token gets. `decodeJsonObject` reads a JSON plaintext with the strict parser, for callers who encrypt JSON of their own. Rejected: a claims-validating `decryptJwt`, for the reason above; encrypt-then-sign, which RFC 7519 §11.2 advises against for nested tokens.
67. **`importKeySet` and `createRemoteKeySet` take `use: "enc"`, and return an `EncryptionKeySet` of JWE public keys that a sender selects by `alg` and `kid`.** A JWK is imported only when it says it encrypts, by `use: "enc"` or, without `use`, a `key_ops` holding an encryption operation; a JWK without `alg` is bound to each listed algorithm its key type fits, and `algorithms` defaults to every asymmetric key management algorithm. `issuer` is refused with `use: "enc"`, since issuer binding (decision 43) concerns who signs, not who receives. An OpenID Provider encrypts a client's tokens to the client's `jwks_uri`, and the remote key set's cache, cooldown and limits apply to it unchanged. Rejected: importing JWKs that say neither, as signing import does, since a JWKS mixing signing and encryption keys would then lend a signing key to encryption; separate `importEncryptionKeySet` functions, which duplicate every option and limit of the two readers.
68. **A decrypter's `maxLength` defaults to 16384 characters, twice a verifier's, with the same range of 1 through 65536.** A nested token is a signed token grown by about a third in base64url, plus its header, tag and, for RSA, an encrypted key as long as the modulus, so the verifier's 8192 would refuse JWEs holding tokens the inner verifier accepts. The cap still bounds the ciphertext, and so the work and memory one token costs, before any decoding. Rejected: the verifier's 8192, for the reason above; no default, which makes every caller pick a number.
69. **`encrypt` refuses header members that change how a token is decrypted or ask the recipient to trust a key, and never writes `apu` or `apv`; a decrypter validates `epk` by importing it.** `crit`, `zip`, `epk`, `apu`, `apv`, `iv`, `tag`, `p2s`, `p2c`, `b64`, `jwk`, `jku`, `x5u` and `x5c` throw, since a caller setting one either breaks the token or asks the recipient for something this package's own decrypter refuses. A decrypter reads `apu` and `apv` when a sender wrote them, since RFC 7518 §4.6.2 binds them into the derived key. An `epk` is imported on the private key's curve, with only the members a public key has, and an X25519 point of low order or an all-zero shared secret is `malformed` at `["header", "epk"]`, since not every runtime refuses them itself. Rejected: an option to write `apu` and `apv`, which no consumer has asked for and which adds nothing to a fresh ephemeral key; leaving low-order points to Web Crypto, which RFC 7748 §6.1 leaves to the caller.
