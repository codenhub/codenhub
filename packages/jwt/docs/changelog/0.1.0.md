# 0.1.0

0.1.0 is the release `@codenhub/oidc` and the applications built on it are meant to build on. It adds the remaining JWS algorithms, PEM and certificate import, DPoP proofs, JWK thumbprints, `tokenHash` and `importKeyPair`, lets a remote key set answer from stale keys while it refetches, closes what three audits found, and raises the Node.js floor to 26. Each breaking change is marked below with what to do.

## Added

- `generateKeyPair({ alg, kid: "thumbprint" })` names both keys by the public key's RFC 7638 thumbprint, a `kid` derived from the key alone. [Keys](../keys.md#thumbprints) covers it.
- `ES384`, `ES512`, `RS384`, `RS512`, `PS384`, `PS512`, `HS384` and `HS512`, for generating, importing, signing and verifying. An HMAC secret must be at least as long as its hash: 48 bytes for `HS384` and 64 for `HS512`. The [algorithm table](../index.md#keys-are-bound-to-one-algorithm) lists them all. From this release, an algorithm may be added in a minor version, which widens `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm` and the JWK and header types: give a `switch` over an `alg` a default branch.
- PEM import: `importPublicKey` takes a `PUBLIC KEY` block (SPKI), and `importPrivateKey` and `importKeyPair` a `PRIVATE KEY` block (PKCS#8), with a new `kid` option to name the key. Every JWK check runs on the key read. Whitespace inside the block is ignored, so a PEM flattened onto one line, as environment variables often hold it, imports too, and so does one whose line breaks are written as `\n` escapes. [Keys](../keys.md#importing-a-pem-key) covers it.
- `sign({ ..., embedKey })` writes a public key as the `jwk` header, for DPoP proofs (RFC 9449), and `jwkThumbprint(publicKey)` computes the RFC 7638 thumbprint a `cnf.jkt` claim carries. [Signing tokens](../signing.md#dpop-proofs) shows a proof signed and verified.
- `createRemoteKeySet` accepts an `http:` URL on `localhost`, `127.0.0.0/8` or `[::1]`, for an identity provider running locally.
- `importKeyPair(privateJwk, { alg, extractable? })`, which loads a signing key stored with `exportPrivateJwk` as `{ privateKey, publicKey }`, like `generateKeyPair`'s result, so the public JWK no longer has to be stored beside it. It proves the two halves belong together by signing and verifying a fixed message, so a JWK whose public members belong to another key is `invalid_key`. [Keys](../keys.md#importing-a-key-pair) covers it.
- `importPublicKey` takes a PEM `CERTIFICATE` block and imports the key inside it. Nothing else in the certificate is checked: not its dates, issuer or signature. [Keys](../keys.md#importing-a-pem-key) covers it.
- `jwkThumbprint` accepts a private key too, extractable or not, and gives the thumbprint of its public half, so a signer can name its key without keeping the public key around.
- `tokenHash(value, alg)` computes the OpenID Connect `at_hash` and `c_hash` claims for every algorithm the package signs with, `EdDSA` included. [Signing tokens](../signing.md#token-hashes-in-id-tokens) shows it.
- `JWS_ALGORITHMS`, `ASYMMETRIC_ALGORITHMS` and `SYMMETRIC_ALGORITHMS`, with the guards `isJwsAlgorithm`, `isAsymmetricAlgorithm` and `isSymmetricAlgorithm`, and `encodeBase64Url` and `decodeBase64Url`, so a caller no longer copies them. [Keys](../keys.md#algorithms) lists them.
- An `issuer` option on `createKeySet`, `importKeySet` and `createRemoteKeySet` binds each key to the issuer whose key it is, and a verifier then requires that `iss` for a token the key verifies. Without it, a verifier holding several issuers' keys accepted a token signed with one issuer's key that claimed another's `iss`. Give it to every key set when one verifier serves several tenants; [Key sets](../key-sets.md#keys-of-several-issuers) shows how. A key's new `issuer` member says what it is bound to, and `CreateKeySetOptions` is exported.
- `createVerifier({ keys })` also takes a function from the issuer a token claims to that issuer's key set, so one verifier serves several issuers or tenants without a custom key set. The verifier reads `iss` before the signature only to route the token, and a token without one fails. `KeySetResolver` is exported. [Key sets](../key-sets.md#choosing-the-key-set-by-issuer) shows it, and why the `iss` must be looked up rather than fetched from.
- The import functions take a Web Crypto `CryptoKey`, and `importPrivateKey` and `importKeyPair` a `CryptoKeyPair`, whose private key is kept as given, so a browser can sign with a non-extractable key it keeps in IndexedDB. A `CryptoKey` made for another Web Crypto algorithm or hash than `alg` signs with, such as an `RSA-OAEP` or `ECDH` key, is `alg_mismatch`. [Keys](../keys.md#importing-a-web-crypto-key) covers it.
- `getPublicKey(privateKey)` gives the public half of any private key, extractable or not, for a key imported alone with `importPrivateKey`. `exportPublicJwk` given a private key now says to use it.
- `createKeySet` and `importKeySet` return a `LocalKeySet`, whose `keys` lists the set's keys, so an issuer can publish its JWKS from the set it verifies with.
- `createVerifier` options: `allowExpired`, which accepts an expired token whose other checks pass, for an OpenID Connect `id_token_hint`; `audience: false` and `requireExpiration: false`, which waive the new defaults below; and `type` as an array, where `null` accepts a token without `typ`. [Verifying tokens](../verifying.md) covers them.
- `createRemoteKeySet` options: `seed`, to start from a JWKS saved earlier instead of fetching on the first token; `onFetch` and `onFetchError`, to save each fetched JWKS and log failures; and `waitUntil`, which on Cloudflare Workers keeps a fetch running after the request that started it has responded. [Key sets](../key-sets.md#persisting-the-cache) shows a cache saved between requests.
- `sign` is generic over the payload type, so claims declared as an `interface` compile, while a member that is not a JSON value, such as a `Date`, no longer does. `JwtRegisteredClaims` and `JsonCompatible` are exported for it.
- An [API reference](../reference/index.md) generated from the package's TSDoc.

## Changed

- **Breaking.** The `kid` option of `importPublicKey`, `importPrivateKey`, `importKeyPair` and `importSecretKey` also applies to a JWK: a JWK without a `kid` takes it, and a JWK whose own `kid` differs is `invalid_key` at `["kid"]`. In 0.0.1 the option was ignored for a JWK, so a JWK stored without a `kid` could not be named, and a conflicting option was dropped without a word.
- **Breaking.** A verifier without `audience` refuses a token that has an `aud` claim with `wrong_audience`, as RFC 7519 §4.1.3 requires; in 0.0.1 it accepted a token meant for any other service of the same issuer. Set `audience` to your own, or pass `audience: false` to accept any audience on purpose.
- **Breaking.** A token without `exp` is `missing_claim` with `{ claim: "exp" }`, unless `maxAge` is set; in 0.0.1 such a token never expired. Pass `requireExpiration: false` for tokens that carry no `exp` by design.
- **Breaking.** `importPrivateKey` proves a JWK's public members belong to its private key, as `importKeyPair` does, by signing and verifying a fixed message. A JWK mixing two keys is `invalid_key`, and each import costs one signature and one verification.
- When no key in a set has the token's `kid`, the one key without a `kid` that has the token's `alg` is selected, instead of `unknown_kid`. A PEM key has no `kid`, and issuers such as Clerk and Supabase name one in every token, so a set holding just that key refused every token. A remote set refetches its JWKS first, within its cooldown, so a key rotated in under that `kid` is still found.
- Within `maxStale` after `cacheTtl`, a remote key set answers from the expired JWKS at once and refetches in the background; only a `kid` the cache lacks waits for the fetch. A token waits for a running fetch at most until a second past its `timeout`, and, unless the cooldown is running and the cache is still usable, fetches again itself when that fetch misses the deadline or was cancelled with the Cloudflare Workers request that started it; pass `waitUntil` on Workers so the fetch is not cancelled. A key removed from the JWKS stays trusted until the background fetch replaces the cache.
- **Breaking.** `engines.node` is `>=26`, so Yarn 1, and npm with `engine-strict`, refuse the install on Node.js 24 or 25. Upgrade Node.js to 26. Browsers, Deno, Bun and Cloudflare Workers are unaffected. ([#553](https://github.com/codenhub/codenhub/issues/553))
- **Breaking.** Every function that takes options, and `sign`'s input, throws a `TypeError` naming any member it does not know, even one set to `undefined`. In 0.0.1 a typo such as `audiance` was ignored, which turned the audience check off without a sign, and one such as `extractible` silently gave a key that could not be exported. Fix the name the error gives.
- `nbf` and `iat` allow at least 60 seconds of clock skew whatever `clockTolerance` says, so a token checked the moment it is issued no longer fails on a verifier whose clock is slightly behind the issuer's. `exp` and `maxAge` still use `clockTolerance` alone. A token whose `nbf` or `iat` is less than 60 seconds ahead now verifies.
- **Breaking.** `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm` and the key, JWK and header types built on them gain the new algorithms, so code that checks at compile time that it handles every algorithm, such as a `switch` ending in a `never` assignment, fails to compile. Handle the new ones or add a default branch.
- `importKeySet` and `createRemoteKeySet` bind a JWK without `alg` to the new algorithms too, under the default `algorithms`: an `RSA` key also answers to `RS384`, `RS512`, `PS384` and `PS512`, and `P-384` and `P-521` keys are imported instead of skipped. Pass `algorithms` to keep the old set.
- **Breaking.** When `now` returns anything but a finite number, the verifier's promise rejects with a `TypeError`, and so does a remote key set's `select`, which a verifier reports as `key_fetch_failed` with `{ reason: "key_set_error" }`. In 0.0.1, `now: () => NaN` passed expired tokens and kept a remote key set's cache from ever expiring. Return milliseconds, as `Date.now` does.
- **Breaking.** `importSecretKey` takes `Uint8Array | object`, so passing a string is a compile error. At run time a string still returns `invalid_key`. Encode the secret to bytes first, such as with `new TextEncoder().encode(secret)` when it is text.
- **Breaking.** `sign` rejects `-0`, which JSON writes as `0`; an array whose prototype is not `Array.prototype`; and a value with a `toJSON` method anywhere on its prototype chain, a polluted `Object.prototype` or `Array.prototype` included. Each would have signed a different value than the one given. Pass plain data.
- **Breaking.** A custom key set's failure is passed through only when every issue is an object with a string `code` of its own; a list with a hole, or an issue without such a `code`, gives `key_fetch_failed` with `{ reason: "key_set_error" }`, as other key set mistakes already did. Return issues built as `{ code: "unknown_kid" }`.
- **Breaking.** `sign` throws a `TypeError` for an `exp`, `nbf` or `iat` above 253402300799, the last second of year 9999, which is almost always `Date.now()` in milliseconds and signed a token valid for some 55,000 years. Write seconds: `Math.floor(Date.now() / 1000)`. Verifiers still accept such values from other issuers.
- `generateKeyPair` retries an `EdDSA` or `Ed25519` generation that Web Crypto rejects with `OperationError`, up to three times. Linux builds of WebKit fail about 1 in 128 such generations at random; drop any retry of your own.
- Issue codes and `params.reason` values may gain members in a minor release, and an existing one never changes meaning. Give a `switch` over codes a default branch.
- `typ` compares ASCII letters without regard to case, and drops a leading `application/` only when no other `/` follows, as RFC 7515 §4.1.9 says. 0.0.1 used `toLowerCase`, which also folded some letters beyond ASCII, such as the Kelvin sign (U+212A) to `k`, and dropped `application/` from values such as `application/a/b`. A `typ` spelled that way no longer matches.

## Fixed

- `exportPrivateJwk` writes an EC or Ed25519 `d` at its full length on WebKit, which drops its leading zero bytes on export. 0.0.1 exported about 1 `ES256` key in 200 in a form `importPrivateKey` then refused as `invalid_key`; an `ES512` key would have failed about half the time.
- Key options are read as own properties, so a polluted `Object.prototype` can no longer make a generated or imported key extractable.
- `importSecretKey` and JWK import accept a `Uint8Array` or a plain object from another realm, as Jest and jsdom give, which 0.0.1 refused as `invalid_key`.
- A remote key set treats a clock that steps back more than a minute as an expired cache, and any step back as an ended cooldown, so a removed key stops being trusted at most a minute past `cacheTtl` plus `maxStale` after the last successful fetch. A smaller step, or a seed saved on a host whose clock runs up to a minute ahead, counts as just fetched instead of expiring the cache.
- A promise `onFetch` or `onFetchError` returns is handed to `waitUntil`, so on Cloudflare Workers saving a snapshot is no longer cancelled with the request.
- A remote key set cancels a response body still streaming when its `timeout` passes, even from a `fetch` option that ignores the abort signal.
