# 0.1.0

0.1.0 is the release `@codenhub/oidc` and the applications built on it are meant to build on. It adds the remaining JWS algorithms, PEM import, DPoP proofs, JWK thumbprints and `importKeyPair`, closes what two audits found, and raises the Node.js floor to 26. Each breaking change is marked below with what to do.

## Added

- `ES384`, `ES512`, `RS384`, `RS512`, `PS384`, `PS512`, `HS384` and `HS512`, for generating, importing, signing and verifying. An HMAC secret must be at least as long as its hash: 48 bytes for `HS384` and 64 for `HS512`. The [algorithm table](../index.md#keys-are-bound-to-one-algorithm) lists them all. From this release, an algorithm may be added in a minor version, which widens `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm` and the JWK and header types: give a `switch` over an `alg` a default branch.
- PEM import: `importPublicKey` takes a `PUBLIC KEY` block (SPKI), and `importPrivateKey` and `importKeyPair` a `PRIVATE KEY` block (PKCS#8), with a new `kid` option to name the key. Every JWK check runs on the key read. [Keys](../keys.md#importing-a-pem-key) covers it.
- `sign({ ..., embedKey })` writes a public key as the `jwk` header, for DPoP proofs (RFC 9449), and `jwkThumbprint(publicKey)` computes the RFC 7638 thumbprint a `cnf.jkt` claim carries. [Signing tokens](../signing.md#dpop-proofs) shows a proof signed and verified.
- `createRemoteKeySet` accepts an `http:` URL on `localhost`, `127.0.0.0/8` or `[::1]`, for an identity provider running locally.
- `importKeyPair(privateJwk, { alg, extractable? })`, which loads a signing key stored with `exportPrivateJwk` as `{ privateKey, publicKey }`, like `generateKeyPair`'s result, so the public JWK no longer has to be stored beside it. It proves the two halves belong together by signing and verifying a fixed message, so a JWK whose public members belong to another key is `invalid_key`. [Keys](../keys.md#importing-a-key-pair) covers it.
- An [API reference](../reference/index.md) generated from the package's TSDoc.

## Changed

- **Breaking.** `engines.node` is `>=26`, so Yarn 1, and npm with `engine-strict`, refuse the install on Node.js 24 or 25. Upgrade Node.js to 26. Browsers, Deno, Bun and Cloudflare Workers are unaffected. ([#553](https://github.com/codenhub/codenhub/issues/553))
- **Breaking.** Every function that takes options, and `sign`'s input, throws a `TypeError` naming any member it does not know, even one set to `undefined`. In 0.0.1 a typo such as `audiance` was ignored, which turned the audience check off without a sign, and one such as `extractible` silently gave a key that could not be exported. Fix the name the error gives.
- `nbf` and `iat` allow at least 60 seconds of clock skew whatever `clockTolerance` says, so a token checked the moment it is issued no longer fails on a verifier whose clock is slightly behind the issuer's. `exp` and `maxAge` still use `clockTolerance` alone. A token whose `nbf` or `iat` is less than 60 seconds ahead now verifies.
- **Breaking.** `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm` and the key, JWK and header types built on them gain the new algorithms, so code that checks at compile time that it handles every algorithm, such as a `switch` ending in a `never` assignment, fails to compile. Handle the new ones or add a default branch.
- `importKeySet` and `createRemoteKeySet` bind a JWK without `alg` to the new algorithms too, under the default `algorithms`: an `RSA` key also answers to `RS384`, `RS512`, `PS384` and `PS512`, and `P-384` and `P-521` keys are imported instead of skipped. Pass `algorithms` to keep the old set.
- **Breaking.** When `now` returns anything but a finite number, the verifier's promise rejects with a `TypeError`, and so does a remote key set's `select`, which a verifier reports as `key_fetch_failed` with `{ reason: "key_set_error" }`. In 0.0.1, `now: () => NaN` passed expired tokens and kept a remote key set's cache from ever expiring. Return milliseconds, as `Date.now` does.
- **Breaking.** `importSecretKey` takes `Uint8Array | object`, so passing a string is a compile error. At run time a string still returns `invalid_key`. Encode the secret to bytes first, such as with `new TextEncoder().encode(secret)` when it is text.
- **Breaking.** `sign` rejects `-0`, which JSON writes as `0`; an array whose prototype is not `Array.prototype`; and a value with a `toJSON` method anywhere on its prototype chain, a polluted `Object.prototype` or `Array.prototype` included. Each would have signed a different value than the one given. Pass plain data.
- **Breaking.** A custom key set's failure is passed through only when every issue is an object with a string `code` of its own; a list with a hole, or an issue without such a `code`, gives `key_fetch_failed` with `{ reason: "key_set_error" }`, as other key set mistakes already did. Return issues built as `{ code: "unknown_kid" }`.
- `typ` compares ASCII letters without regard to case, and drops a leading `application/` only when no other `/` follows, as RFC 7515 §4.1.9 says. 0.0.1 used `toLowerCase`, which also folded some letters beyond ASCII, such as the Kelvin sign (U+212A) to `k`, and dropped `application/` from values such as `application/a/b`. A `typ` spelled that way no longer matches.

## Fixed

- `exportPrivateJwk` writes an EC or Ed25519 `d` at its full length on WebKit, which drops its leading zero bytes on export. 0.0.1 exported about 1 `ES256` key in 200 in a form `importPrivateKey` then refused as `invalid_key`; an `ES512` key would have failed about half the time.
- Key options are read as own properties, so a polluted `Object.prototype` can no longer make a generated or imported key extractable.
- `importSecretKey` and JWK import accept a `Uint8Array` or a plain object from another realm, as Jest and jsdom give, which 0.0.1 refused as `invalid_key`.
- A remote key set treats a clock that steps back as an expired cache and an ended cooldown, so a removed key stops being trusted at most `cacheTtl` plus `maxStale` after the last successful fetch, as documented.
