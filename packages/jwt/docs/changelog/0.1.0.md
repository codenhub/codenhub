# 0.1.0

0.1.0 is the release `@codenhub/oidc` and the applications built on it are meant to build on. It adds compact JWE, signed and verified JWS of any payload, DPoP proofs, a key ring for rotating signing keys, the remaining JWS algorithms, PEM import and export, certificate import, JWK thumbprints, `tokenHash` and `importKeyPair`, lets a remote key set answer from stale keys while it refetches, closes what four audits found, and raises the Node.js floor to 26. Each breaking change is marked below with what to do.

## Added

- Compact JWE: `encrypt` and `createDecrypter` for any payload, and `encryptJwt` and `createNestedVerifier` for a signed token inside an encrypted one, signed first. Key management with `dir`, `A128KW`, `A256KW`, `A128GCMKW`, `A256GCMKW`, `ECDH-ES` and `ECDH-ES+A128KW`/`A256KW` on P-256, P-384, P-521 and X25519, `RSA-OAEP-256`, `RSA-OAEP-384`, `RSA-OAEP-512` and `RSA-OAEP`; content encryption with `A128GCM`, `A256GCM`, `A128CBC-HS256` and `A256CBC-HS512`. Encryption keys are their own kinds, `JwePublicKey`, `JwePrivateKey` and `JweSecretKey`, from `generateJweKeyPair`, `generateJweSecretKey`, `importJwePublicKey`, `importJwePrivateKey`, `importJweKeyPair`, `importJweSecretKey` and `getJwePublicKey`, with `exportJwePublicJwk`, `exportJwePrivateJwk`, `exportJweSecretJwk`, `exportJwePublicPem` and `exportJwePrivatePem`; `createJweKeySet`, `importEncryptionKeySet` and `createRemoteEncryptionKeySet` give a sender a recipient's keys, and `readJweHeader` reads a JWE's protected header without decrypting it. Every failure in recovering the content key or checking the tag is `decryption_failed`, an issue from the signed token inside a nested one has `"plaintext"` first in its `path`, and a token using `RSA1_5`, `PBES2`, `zip` or `crit` is refused. A low-order X25519 key is `invalid_key` at import, an X25519 `epk` with its top bit set is `malformed`, and the empty `key_ops` Web Crypto writes on an ECDH or X25519 public JWK states no constraint. `KEY_MANAGEMENT_ALGORITHMS`, `CONTENT_ENCRYPTION_ALGORITHMS`, `isKeyManagementAlgorithm` and `isContentEncryptionAlgorithm` list them, and the issue codes `unsupported_enc` and `decryption_failed` are new. [Encrypting tokens](../encrypting.md) covers it.
- `signJws`, `signGeneralJws` and `createJwsVerifier` sign and verify a JWS of any payload, bytes or text, in the compact, flattened or general JSON serialization, with RFC 7797 unencoded and detached payloads, for webhook bodies and documents that are not claims. A general JWS holds at most 8 signatures. The issue code `missing_payload` is new. [Signing other payloads](../jws.md) covers it.
- `createDpopProof` creates an RFC 9449 DPoP proof, and `createDpopVerifier(options).verify(proof, request)` checks one as RFC 9449 §4.3 says: `htm`, `htu`, `iat`, `ath`, the nonce, the access token's `cnf.jkt` and replay, through a `jti` callback. A request gives `accessToken` and `accessTokenClaims` together or neither; one without the other throws a `TypeError`, since the token alone would accept a stolen token with another key's proof. The issue codes `wrong_method`, `wrong_url`, `wrong_access_token_hash`, `wrong_nonce`, `wrong_key`, `replayed` and `callback_failed` are new. [DPoP proofs](../dpop.md) covers it.
- `createKeyRing({ keys, publishAhead, publishAfter })` schedules an issuer's signing keys by `activeFrom` and `retiredAt`: `signingKey()` returns the key that signs now, `jwks()` the JWKS to publish now, and the ring is itself a key set. `createEncryptionKeyRing({ keys, publishAfter })` does the same for a recipient's encryption keys: it publishes only the current key, so a sender selecting by `alg` finds one, and keeps a replaced key decrypting for `publishAfter` seconds. [Rotating keys](../rotation.md) covers it.
- `sign` options `issuedAt`, `notBefore`, `expiresIn` and `jti`, which write `iat`, `nbf`, `exp` and a random `jti`, and `now`, the clock they read. Durations are whole seconds up to ten years, so `Date.now()` or a duration in milliseconds of four days or more throws, and an option whose claim the payload also sets throws. [Signing tokens](../signing.md#claims-sign-can-add) covers them.
- `createVerifier({ subject })`, the accepted `sub` values, with the new issue code `wrong_subject`; and `createVerifier<Claims>(options)`, which types the payload without a schema. Such a type is not checked at run time.
- `exportPublicPem` and `exportPrivatePem` write a key as an SPKI `PUBLIC KEY` or an unencrypted PKCS#8 `PRIVATE KEY` block. [Keys](../keys.md#exporting-keys) covers them.
- `jwkThumbprintUri` gives the RFC 9278 URI of a key's thumbprint, and `certificateThumbprint` the `x5t#S256` of a `CERTIFICATE` PEM, as RFC 8705 binds certificate-bound tokens with it. [Keys](../keys.md#thumbprints) covers them.
- Every import function takes `kid: "thumbprint"`, as `generateKeyPair` does, naming the key by its RFC 7638 thumbprint; a JWK whose own `kid` differs is `invalid_key` at `["kid"]`.
- The JWK types are a union discriminated by `kty`: `EcPublicJwk`, `EcPrivateJwk`, `OkpPublicJwk`, `OkpPrivateJwk`, `RsaPublicJwk`, `RsaPrivateJwk` and `OctJwk`, grouped as `EcJwk`, `OkpJwk`, `RsaJwk`, `PublicJwk`, `PrivateJwk` and `SecretJwk`. `Jwk` is the union of all, and the export functions return the precise group.
- `JwksFetch`, the type of a remote key set's `fetch` option, `(url, init) => Promise<Response>`, which test stubs and every runtime's `fetch` fit.
- `createExternalSigningKey({ publicKey, sign, signatureFormat? })` makes a private key whose signatures come from a function, for a key held by a cloud KMS or an HSM. `signatureFormat: "der"` converts the DER ECDSA signatures such services return, and each signature is verified with the public key before `sign` returns the token; one of the wrong length throws a `TypeError`. `ExternalSigningKeyOptions` is exported. [Keys](../keys.md#keys-held-by-a-kms-or-hsm) covers it.
- `createVerifier({ onKeySetError })`, called with the error behind a `key_set_error`: what a custom key set or `keys` function threw, or a `TypeError` naming what it returned. The issue carries nothing from it, so before this the cause was lost.
- A `keys` function may return a route, `{ keys, audience, type }`, to check an issuer's tokens for its own audience or `typ` in place of the verifier's. The new `KeySetRoute` type describes it. A route with any other member, such as a misspelled `audiance`, is `key_set_error`, so a typo cannot drop a check.
- `generateKeyPair({ alg, kid: "thumbprint" })` names both keys by the public key's RFC 7638 thumbprint, a `kid` derived from the key alone. [Keys](../keys.md#thumbprints) covers it.
- `ES384`, `ES512`, `RS384`, `RS512`, `PS384`, `PS512`, `HS384` and `HS512`, for generating, importing, signing and verifying. An HMAC secret must be at least as long as its hash: 48 bytes for `HS384` and 64 for `HS512`. The [algorithm table](../index.md#keys-are-bound-to-one-algorithm) lists them all. From this release, an algorithm may be added in a minor version, which widens `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm` and the JWK and header types: give a `switch` over an `alg` a default branch.
- PEM import: `importPublicKey` takes a `PUBLIC KEY` block (SPKI), and `importPrivateKey` and `importKeyPair` a `PRIVATE KEY` block (PKCS#8), with a new `kid` option to name the key. Every JWK check runs on the key read. Whitespace inside the block is ignored, so a PEM flattened onto one line, as environment variables often hold it, imports too, and so does one whose line breaks are written as `\n` escapes. PKCS#1 `RSA PUBLIC KEY` and `RSA PRIVATE KEY` blocks and SEC 1 `EC PRIVATE KEY` blocks are read too. A block must hold exactly one DER element with minimal lengths, refused as `invalid_key` otherwise, because runtimes disagree on trailing bytes and long-form lengths. A key of another type or curve than `alg` is `unsupported_key` at `["kty"]` or `["crv"]`, as for a JWK; an encrypted key is `invalid_key` with `{ reason: "encrypted" }`, and a block the package does not read with `{ reason: "unsupported_format" }`. [Keys](../keys.md#importing-a-pem-key) covers it.
- `sign({ ..., embedKey })` writes a public key as the `jwk` header, for DPoP proofs (RFC 9449), and `jwkThumbprint(publicKey)` computes the RFC 7638 thumbprint a `cnf.jkt` claim carries. [Signing tokens](../signing.md#dpop-proofs) shows a proof signed and verified.
- `createRemoteKeySet` accepts an `http:` URL on `localhost`, `127.0.0.0/8` or `[::1]`, for an identity provider running locally.
- `importKeyPair(privateJwk, { alg, extractable? })`, which loads a signing key stored with `exportPrivateJwk` as `{ privateKey, publicKey }`, like `generateKeyPair`'s result, so the public JWK no longer has to be stored beside it. It proves the two halves belong together by signing and verifying a fixed message, so a JWK whose public members belong to another key is `invalid_key`. [Keys](../keys.md#importing-a-key-pair) covers it.
- `importPublicKey` takes a PEM `CERTIFICATE` block and imports the key inside it. Nothing else in the certificate is checked: not its dates, issuer or signature. [Keys](../keys.md#importing-a-pem-key) covers it.
- `jwkThumbprint` accepts a private key too, extractable or not, and gives the thumbprint of its public half, and an extractable secret, whose thumbprint is that of its `oct` JWK, so a signer can name its key without keeping the public key around.
- `tokenHash(value, alg)` computes the OpenID Connect `at_hash` and `c_hash` claims for every algorithm the package signs with, `EdDSA` included. [Signing tokens](../signing.md#token-hashes-in-id-tokens) shows it.
- `JWS_ALGORITHMS`, `ASYMMETRIC_ALGORITHMS` and `SYMMETRIC_ALGORITHMS`, with the guards `isJwsAlgorithm`, `isAsymmetricAlgorithm` and `isSymmetricAlgorithm`, and `encodeBase64Url` and `decodeBase64Url`, so a caller no longer copies them. [Keys](../keys.md#algorithms) lists them.
- An `issuer` option on `createKeySet`, `importKeySet` and `createRemoteKeySet` binds each key to the issuer whose key it is, and a verifier then requires that `iss` for a token the key verifies. Without it, a verifier holding several issuers' keys accepted a token signed with one issuer's key that claimed another's `iss`. Give it to every key set when one verifier serves several tenants; [Key sets](../key-sets.md#keys-of-several-issuers) shows how. A key's new `issuer` member says what it is bound to, and `CreateKeySetOptions` is exported.
- `createVerifier({ keys })` also takes a function from the issuer a token claims to that issuer's key set, so one verifier serves several issuers or tenants without a custom key set. The verifier reads `iss` before the signature only to route the token, and a token without one fails. `KeySetResolver` is exported. [Key sets](../key-sets.md#choosing-the-key-set-by-issuer) shows it, and why the `iss` must be looked up rather than fetched from.
- The import functions take a Web Crypto `CryptoKey`, and `importPrivateKey` and `importKeyPair` a `CryptoKeyPair`, whose private key is kept as given, so a browser can sign with a non-extractable key it keeps in IndexedDB. A `CryptoKey` made for another Web Crypto algorithm or hash than `alg` signs with, such as an `RSA-OAEP` or `ECDH` key, is `alg_mismatch`. [Keys](../keys.md#importing-a-web-crypto-key) covers it.
- `getPublicKey(privateKey)` gives the public half of any private key, extractable or not, for a key imported alone with `importPrivateKey`. `exportPublicJwk` given a private key now says to use it.
- `createKeySet` and `importKeySet` return a `LocalKeySet`, whose `keys` lists the set's keys, so an issuer can publish its JWKS from the set it verifies with.
- `createVerifier` options: `allowExpired`, which accepts an expired token whose other checks pass, for an OpenID Connect `id_token_hint`; `audience: false` and `requireExpiration: false`, which waive the new defaults below; and `type` as an array, where `null` accepts a token without `typ`. [Verifying tokens](../verifying.md) covers them.
- `createRemoteKeySet` options: `seed`, to start from a JWKS saved earlier instead of fetching on the first token, used only when its `url` is the set's own and ignored when it holds no usable key; `onFetch` and `onFetchError`, to save each fetched JWKS and log failures; and `waitUntil`, which on Cloudflare Workers keeps a fetch running after the request that started it has responded. [Key sets](../key-sets.md#persisting-the-cache) shows a cache saved between requests.
- `sign` is generic over the payload type, so claims declared as an `interface` compile, while a member that is not a JSON value, such as a `Date`, no longer does. `JwtRegisteredClaims` and `JsonCompatible` are exported for it.
- An [API reference](../reference/index.md) generated from the package's TSDoc.

## Changed

- **Breaking.** A `claims` schema's failure is `schema_failed`, not `invalid_claims`, which was one letter from `invalid_claim`, the code for a registered claim of the wrong type. Rename the code in any `switch` or log filter.
- **Breaking.** A JWKS fetch that imports no usable key, such as `{"keys":[]}` or a JWKS of keys only for other algorithms, fails with `{ reason: "no_usable_keys" }` and keeps the cached keys, instead of replacing them with none. An issuer that empties its JWKS to revoke every key has its old keys trusted until the cache stops being usable, at most `cacheTtl` plus `maxStale` after the last fetch that succeeded.
- A remote key set fetches with `cache: "no-cache"`, so a browser's HTTP cache revalidates the JWKS instead of answering a refetch for a new `kid` with the old document; a runtime that refuses the member, as Cloudflare Workers before compatibility date 2025-08-07 do, is retried without it. A response's `Cache-Control: max-age` shorter than `cacheTtl` shortens the TTL, never below `cooldown`, and `no-store` or `no-cache` gives `cooldown`. One leading UTF-8 byte order mark is dropped from a JWKS response.
- `onFetchError` is also called for a failed fetch that a newer fetch replaced.
- `SignHeader` types `crit`, `b64`, `jwk`, `jku`, `x5u` and `x5c` as `never`, so passing them, which `sign` throws for at run time, is a compile error too.
- Type-checking the declarations needs TypeScript 5.7 or newer, for the generic typed arrays such as `Uint8Array<ArrayBuffer>` they use.
- `importSecretKey` takes any `ArrayBufferView` or `ArrayBuffer`, from any realm.
- **Breaking.** JWK import refuses a `key_ops` that repeats an operation as `invalid_key`, as RFC 7517 §4.3 forbids, and one that also allows an operation other than `sign` and `verify`, such as `encrypt`, as `wrong_use`. A key meant for encryption as well as signatures was imported as a signing key.
- **Breaking.** The `kid` option of `importPublicKey`, `importPrivateKey`, `importKeyPair` and `importSecretKey` also applies to a JWK: a JWK without a `kid` takes it, and a JWK whose own `kid` differs is `invalid_key` at `["kid"]`. In 0.0.1 the option was ignored for a JWK, so a JWK stored without a `kid` could not be named, and a conflicting option was dropped without a word.
- **Breaking.** A verifier without `audience` refuses a token that has an `aud` claim with `wrong_audience`, as RFC 7519 §4.1.3 requires; in 0.0.1 it accepted a token meant for any other service of the same issuer. Set `audience` to your own, or pass `audience: false` to accept any audience on purpose.
- **Breaking.** A token without `exp` is `missing_claim` with `{ claim: "exp" }`, unless `maxAge` is set; in 0.0.1 such a token never expired. Pass `requireExpiration: false` for tokens that carry no `exp` by design.
- **Breaking.** `importPrivateKey` proves a JWK's public members belong to its private key, as `importKeyPair` does, by signing and verifying a fixed message. A JWK mixing two keys is `invalid_key`, and each import costs one signature and one verification.
- When no key in a set has the token's `kid`, the one key without a `kid` that has the token's `alg` is selected, instead of `unknown_kid`. A PEM key has no `kid`, and issuers such as Clerk and Supabase name one in every token, so a set holding just that key refused every token. A remote set refetches its JWKS first, within its cooldown, so a key rotated in under that `kid` is still found.
- Within `maxStale` after `cacheTtl`, a remote key set answers from the expired JWKS at once and refetches in the background; only a `kid` the cache lacks waits for the fetch. A token waits for a running fetch at most until a second past its `timeout`, and, unless the cooldown is running and the cache is still usable, fetches again itself when that fetch misses the deadline or was cancelled with the Cloudflare Workers request that started it; pass `waitUntil` on Workers so the fetch is not cancelled. A key removed from the JWKS stays trusted until the background fetch replaces the cache.
- **Breaking.** `engines.node` is `>=26`, so Yarn 1, and npm with `engine-strict`, refuse the install on Node.js 24 or 25. Upgrade Node.js to 26. Browsers, Deno, Bun and Cloudflare Workers are unaffected. ([#553](https://github.com/codenhub/codenhub/issues/553))
- **Breaking.** Every function that takes options, and `sign`'s input, throws a `TypeError` naming any member it does not know, even one set to `undefined`. In 0.0.1 a typo such as `audiance` was ignored, which turned the audience check off without a sign, and one such as `extractible` silently gave a key that could not be exported. Fix the name the error gives.
- `nbf` and `iat` allow at least 60 seconds of clock skew whatever `clockTolerance` says, so a token checked the moment it is issued no longer fails on a verifier whose clock is slightly behind the issuer's. `exp` and `maxAge` still use `clockTolerance` alone. A token whose `nbf` or `iat` is less than 60 seconds ahead now verifies.
- **Breaking.** `JwsAlgorithm`, `AsymmetricAlgorithm`, `SymmetricAlgorithm` and the key, JWK and header types built on them gain the new algorithms, so code that checks at compile time that it handles every algorithm, such as a `switch` ending in a `never` assignment, fails to compile. Handle the new ones or add a default branch.
- `importKeySet` and `createRemoteKeySet` bind a JWK without `alg` to the new algorithms too, under the default `algorithms`: an `RSA` key also answers to `RS384`, `RS512`, `PS384` and `PS512`, and `P-384` and `P-521` keys are imported instead of skipped. Pass `algorithms` to keep the old set.
- **Breaking.** When `now` returns anything but a finite number, the verifier's promise rejects with a `TypeError`, and so does a remote key set's `select`, which a verifier reports as `key_fetch_failed` with `{ reason: "key_set_error" }`. In 0.0.1, `now: () => NaN` passed expired tokens and kept a remote key set's cache from ever expiring. Return milliseconds, as `Date.now` does.
- **Breaking.** `importSecretKey` takes `Uint8Array | object`, so passing a string is a compile error. At run time a string still returns `invalid_key`. Encode the secret to bytes first, such as with `new TextEncoder().encode(secret)` when it is text.
- **Breaking.** `sign` rejects `-0`, which JSON writes as `0`; an array whose prototype is not `Array.prototype`; and a value with a `toJSON` method anywhere on its prototype chain, a polluted `Object.prototype` or `Array.prototype` included. Each would have signed a different value than the one given. Pass plain data.
- **Breaking.** A custom key set's failure is passed through only when every issue is an object with a string `code` of its own; a list with a hole, or an issue without such a `code`, gives `key_fetch_failed` with `{ reason: "key_set_error" }`, as other key set mistakes already did. Return issues built as `{ code: "unknown_kid" }`.
- **Breaking.** `sign` throws a `TypeError` for an `exp`, `nbf` or `iat` above 253402300799, the last second of year 9999, which is almost always `Date.now()` in milliseconds and signed a token valid for some 55,000 years. Write seconds: `Math.floor(Date.now() / 1000)`. Verifiers still accept such values from other issuers.
- `generateKeyPair` retries an `EdDSA` or `Ed25519` generation that Web Crypto rejects with `OperationError`, up to three times. Linux builds of WebKit fail about 1 in 128 such generations at random; drop any retry of your own.
- Issue codes and `params.reason` values may gain members in a minor release, and an existing one never changes meaning. Give a `switch` over codes a default branch.
- `typ` compares ASCII letters without regard to case, and drops a leading `application/` only when no other `/` follows, as RFC 7515 §4.1.9 says. 0.0.1 used `toLowerCase`, which also folded some letters beyond ASCII, such as the Kelvin sign (U+212A) to `k`, and dropped `application/` from values such as `application/a/b`. A `typ` spelled that way no longer matches.

## Fixed

- A callback's rejected promise from another realm, such as a `vm` context or an iframe, is handled like one from this realm. `onKeySetError`, a remote key set's callbacks and `waitUntil`, and the DPoP `nonce` and `acceptJti` callbacks tested `instanceof Promise`, so such a rejection went unhandled, which Node.js's default turns into a crash.
- A custom key set's issue is passed through only when its `path` is an array of strings and finite numbers; any other `path` is `key_set_error`. A string `path` was split into characters, and a number made the verifier reject instead of returning a result.
- A remote key set whose clock steps back while a fetch is running keeps that fetch instead of starting a second one, and answers from the newest completed fetch, so the callers waiting on the first no longer fail with `key_fetch_failed`.
- An RSA private JWK member longer than `n` is `invalid_key` at that member before any arithmetic, so a multi-megabyte member no longer costs seconds, and one whose `p` times `q` is not `n` is `invalid_key` at `["n"]`.
- An `OKP` JWK with a `y` member is `invalid_key` at `["y"]`, as RFC 8037 defines no such member.
- The build keeps each module in its own file, so a bundler drops what an application does not import: `createVerifier` alone, a remote-JWKS verifier and the DPoP verifier no longer carry module setup, PEM or JWE key code they never run.
- `sign` copies the header and payload as it checks them, reading each member once, and writes the token from that copy. A `Proxy` or getter could show the checks one value and the token another, such as `exp` in seconds to the checks and in milliseconds to the token.
- An RSA private JWK whose `qi` is not the inverse of `q` modulo `p` is `invalid_key` at `["qi"]`. Node's Web Crypto signs again with `d` when the CRT result is wrong, so the probe signature passed such a key, and its exported JWK carried the wrong `qi` to libraries that sign with the CRT members.
- `Verifier<T>` and `VerifiedJwt<T>` take an `interface` payload type, as `sign` does, instead of failing with TS2344 for its missing index signature.
- A verified token is frozen once, not walked three times, which in a verifier with a `keys` function happened before the signature was checked.
- An RSA private JWK whose `d` does not agree with its `p`, `q`, `dp` and `dq` is `invalid_key` at `["d"]`. Web Crypto signs with the CRT members alone, so such a key imported and signed, and its exported JWK carried the wrong `d` to whatever read it next.
- `exportPrivateJwk` writes an EC or Ed25519 `d` at its full length on WebKit, which drops its leading zero bytes on export. 0.0.1 exported about 1 `ES256` key in 200 in a form `importPrivateKey` then refused as `invalid_key`; an `ES512` key would have failed about half the time.
- Key options are read as own properties, so a polluted `Object.prototype` can no longer make a generated or imported key extractable.
- `importSecretKey` and JWK import accept a `Uint8Array` or a plain object from another realm, as Jest and jsdom give, which 0.0.1 refused as `invalid_key`.
- A remote key set treats a clock that steps back more than a minute as an expired cache, and any step back as an ended cooldown, so a removed key stops being trusted at most a minute past `cacheTtl` plus `maxStale` after the last successful fetch. A smaller step, or a seed saved on a host whose clock runs up to a minute ahead, counts as just fetched instead of expiring the cache.
- A promise `onFetch` or `onFetchError` returns is handed to `waitUntil`, so on Cloudflare Workers saving a snapshot is no longer cancelled with the request.
- A remote key set cancels a response body still streaming when its `timeout` passes, even from a `fetch` option that ignores the abort signal.
