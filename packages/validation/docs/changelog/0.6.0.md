# 0.6.0

0.6.0 rewrites the core as one pass over the input, so a schema carries the code of what it uses and nothing else: a lone `boolean()` is 1.54 kB gzipped, from 2.07 kB in 0.5.1, and a lone `object()` 2.31 kB, from 3.61 kB. Getting there changed the API in six ways, each marked below with what to do. A function written by hand goes through `validator()` or `check()`, the `unknownKeys` option of `object` is replaced by a factory for each way, `email()` reads a domain written in ASCII, an object reads its properties in one order, a validator of another installed copy of the package is refused, and `describe` says how an object treats unlisted keys in a part of its own. Most schemas run faster; a `union` that accepts a later option and a `record` run slower, as below says.

## Added

- `strictObject(shape)`, `looseObject(shape)` and `objectWithRest(shape, rest)`, which read a plain object as `object` does and reject, copy unchecked, or validate with `rest` the keys the shape does not list. A program carries the code of the ones it uses and of no other. [Getting started](../getting-started.md#keys-the-shape-does-not-list) covers them.
- `internationalEmail(options?, ...checks)`, which accepts what `email()` accepted in 0.5.1, a domain in another script included, and produces it in punycode: `Ada@München.DE` produces `Ada@xn--mnchen-3ya.de`. [Formats](../formats.md#internationalemail) covers it.
- The test of a `check` may return the list of issues it found, and an empty list for a value it accepts, so one check can report several issues or choose a path for each. [Custom validators](../custom-validators.md#a-check-that-reports-several-issues) covers it.

## Changed

- **Breaking.** A composer takes a function written by hand only once `validator()` made it a validator, and a validator takes a check only from `check`, `checkFields` or a built-in check such as `nonBlank()`. A bare function given as a child or as a check is a `TypeError` when the schema is created, naming the argument, such as `shape.name`. The code that calls such a function, checks what it returned and waits for it now comes with `validator` and `check`, so a schema without one carries none of it. Wrap each function: `object({ id: validator(myId) })`, `string(check((s) => s !== "admin"))`. [Custom validators](../custom-validators.md#a-function-that-is-no-validator) covers it.
- **Breaking.** `object` drops the keys its shape does not list, and has no other way: the `unknownKeys` option is a `TypeError`, in `object` and in the options of `pick`, `omit`, `partial`, `required` and `extend`, and the types `ObjectOptions` and `UnknownKeys` are removed. Replace `object(shape, { unknownKeys: "strict" })` with `strictObject(shape)`, `"passthrough"` with `looseObject(shape)`, and a validator with `objectWithRest(shape, validator)`; `"strip"` is `object(shape)`. `pick` and its kin keep the way of the object they are given, so a `strictObject` picked from stays strict; for another way, give its factory the shape. [Shaping values](../shaping-values.md#pick-omit-required-partial-and-extend) covers it.
- **Breaking.** `email()` accepts a domain written in ASCII only, and rejects one with a letter beyond ASCII, such as `ada@münchen.de`, and one with a punycode label, such as `ada@xn--mnchen-3ya.de`, which 0.5.1 accepted. Telling a valid internationalized domain apart takes the URL parser, a punycode decoder and the rule for right-to-left labels, which only `internationalEmail()` now carries. Data that passed before may fail when validated again; where internationalized domains are accepted, use `internationalEmail()`. [Formats](../formats.md#email) covers it.
- **Breaking.** An `object` reads each property as its validator runs, and every property before anything waits, where 0.5.1 read them in one of two orders depending on whether the input passed. Only input whose own code changes it while it is read, such as a getter that changes another property, can see the difference. Input that changes while a validation waits is still not seen changed.
- **Breaking.** A validator or a check made by another installed copy of the package is refused as a child, with the same `TypeError`, since each copy reports issues to itself. This happens when a program installs two copies, as when two packages depend on versions of `@codenhub/validation` that do not overlap, and one is given a schema of the other, so packages that share schemas move to 0.6.0 together. Install one copy for both, or give the validator to `validator()`, which runs it as a function written by hand and keeps its issues, though no longer what `describe` and `toJsonSchema` read of it.
- **Breaking.** `describe` gives how an object treats the keys its shape does not list in a part of its own, `unknownKeys`: absent for `object`, `"strict"`, `"passthrough"`, or the validator `objectWithRest` was given. 0.5.1 gave it among the object's `options`. Code that reads `options.unknownKeys` of a description reads `unknownKeys`. [JSON Schema](../json-schema.md#reading-a-schema) covers `describe`.
- A schema carries the code of what it uses. A lone `boolean()` is 1.54 kB gzipped, from 2.07 kB in 0.5.1, a lone `string()` 2.24 kB, from 2.54 kB, a lone `object()` 2.31 kB, from 3.61 kB, `email()` 3.27 kB, from 4.21 kB, and `union` 1.95 kB, from 2.61 kB, as `size.json` in the package records each export imported alone. What runs a check is now carried whole by the schemas that use one, so a lone `check` is 1.68 kB, from 0.68 kB, and a lone `string` with a check grows; a schema of more than one validator still comes out smaller. The bundle of every export is 32.38 kB, from 31.54 kB.
- Most validation is faster, and some cases are slower. A `string()` validates about 2.7 times as fast, a `number()` about 1.5 times, an `object` with a `transform` property about 1.4 times, and input that fails, such as an invalid signup form, more than twice as fast. A `union` that accepts its second option runs at about half its earlier speed, since each option that fails reports its issue before the next is tried, and a `record` of ten numbers at about two thirds. An `object` with a `startsWith` property, a nested `object`, a strict one and an empty one are 5 to 10% slower. All measured with `pnpm bench` on Node.js 24.22.1.
