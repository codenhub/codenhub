# 0.4.0

0.4.0 adds what a comparison with valibot, zod and yup found missing: a schema another program can read, a type for what a validator accepts, and a rule across fields that a form sees at once. It also makes objects and collections about three times faster on valid input. Every call that 0.3.0 accepted is accepted, and returns what it returned, with one exception in wording: a message map that has an entry named `default` now words unknown codes with it. The two breaking changes are in the types.

## Added

- `describe(validator)`, which returns what a validator is made of as plain, frozen data: its `kind`, the `options` it was given, its `checks`, and the validators inside it. Every factory and every built-in check of the package records it; a validator or a check written by hand gives `undefined`. [Reading a schema](../validators.md#reading-a-schema) lists what each kind holds.
- `toJsonSchema(validator, { io, unrepresentable })`, which writes a validator as a JSON Schema, draft 2020-12, for an OpenAPI document, the tools of a language model or a form generator. It writes what the validator accepts, or what it produces with `io: "output"`. A part JSON Schema cannot say, such as a custom check, a `date` or what a `transform` returns, which only `io: "output"` asks for, throws a `TypeError` naming where it is, or is written as accepting anything with `unrepresentable: "any"`. [JSON Schema](../json-schema.md) covers it.
- `pick(validator, keys)`, `omit(validator, keys)` and `required(validator)`, which make a new object validator from one `object` made, and `partial(validator)`, which `partial` accepts beside a shape. The new validator keeps the options of the one it was made from. One that carries checks is refused with a `TypeError`, since a check was written for the whole object.
- `InferInput<typeof validator>`, the type of input that can pass, beside `Infer`, the type produced. They differ for `optional` with a default, the `coerce` validators, `transform`, `pipe`, `json`, `searchParams` and `fallback`. `Validator<T, TInput>` and `AsyncValidator<T, TInput>` take it as a second type, `unknown` when left out, so a validator written by hand is unchanged. A validator is still called with any value: the type says what can pass and limits no argument.
- `checkFields(keys, test, issue?)`, a check for `object` and `objectLike` that names the properties it needs and runs as soon as those have passed, whatever the others did. A form with an empty name now shows "Passwords must match" beside the name's own issue, where a `check` waits until every property is valid. Its test is given the named properties alone, typed so, and a name the object lacks is a `TypeError` when the object is created.
- `brand(validator, name)`, which marks the type a validator produces, leaving `null` and `undefined` unmarked, so only a value that went through the validator is accepted where that type is asked for. It returns the validator it was given and changes nothing at run time. `Branded<T, "Name">` is the marked type.
- `readonly(validator)`, which makes what a validator produces read-only: in its type, a `Map` and a `Set` as `ReadonlyMap` and `ReadonlySet`, and by freezing the object or array the validator produced. It freezes one level, and never a value that is the input itself, such as what `instanceOf` or `unknown` produces.
- `portugueseMessages`, the built-in wording in Portuguese as written in Brazil, used wherever `englishMessages` is: "Deve ser no mínimo 18", "Endereço de e-mail inválido". It is a separate value, so a program bundles only the languages it imports.
- The entry `default` of a message map, which words an issue whose code has no entry of its own, such as the code of a custom check, where `formatIssue` said "Invalid value" in English whatever the language of the map. `portugueseMessages` has one, "Valor inválido"; a map of your own may give text or a function of the issue.
- The types a consumer may need to name for the above: `Description`, `JsonSchema`, `JsonSchemaOptions`, `Picked`, `Omitted`, `AllRequired`, `AllOptional`, `Reshaped`, `InferShapeInput`, `InferTupleInput`, `InferTaggedInput`, `InferRecordInput`, `Branded` and `ReadonlyOutput`.
- [Compared with valibot, zod and yup](../comparison.md), a page that says where the package differs, what was measured, and when to choose one of the others.

## Changed

- **Breaking.** `is(validator, input)` is a type guard: it narrows `input` to the type the validator accepts, `InferInput`, where 0.3.0 returned `boolean` and narrowed nothing. Inside `if (is(string(), value))`, `value` is a `string`. Code that compiled may stop compiling where the `else` branch is now narrowed too: with `value` typed `string | number`, the branch after a failed `is(string(), value)` sees a `number`, so code there that used it as text is a compile error. A validator written by hand that does not declare its input narrows nothing, as before.
- **Breaking.** `standard(validator, messages)` reports the validator's input type to the library that takes it, where 0.3.0 reported `unknown`. A form library that types a field from a Standard Schema now types one for `coerceNumber()` as `string | number` and one for `optional(string(), "")` as `string | undefined`, so code that relied on the field being `unknown` may need the narrower type.
- `Validator` and `AsyncValidator` are interfaces with a call signature, where they were function types, so that they can carry the input type. A function of the right shape is still a validator, and nothing a caller writes changes.
- Every validator and check the package makes has a property named `~description`, which `describe` reads. The record it holds is frozen, and holds no input.
- A message map with an entry named `default` words every code it has no entry for with it, as above. A map that used `default` as the code of one of its own issues now words other unknown codes with that text too.
- The package description, the README and the documentation overview lead with what the package is for, validating input nobody you trust controls, and state its size as a measurement.

## Performance

Measured on Node.js 24.19 on one machine, valid input, in millions of validations a second, the published 0.3.0 against this release with every result kept. `pnpm bench` in the package runs them.

| Validator                         | 0.3.0 | 0.4.0 |
| --------------------------------- | ----- | ----- |
| `string()`                        | 39    | 72    |
| `object` of three strings         | 1.25  | 4.2   |
| `array` of 100 strings            | 0.20  | 0.65  |
| `email()`                         | 1.1   | 1.5   |
| `{ name, email, age }`, as a form | 0.53  | 0.93  |

- `object`, `objectLike`, `array`, `set`, `tuple` and `record` no longer make a path, a list or a closure for a child that passes without waiting. What they guarantee is unchanged: the input is read before any child runs, results keep the order of the children, and a pending result of a sibling is handled when a child throws.
- `email()` and `url()` parse the text once, with `URL.parse` where the runtime has it, where they asked whether it parses and then parsed it.

## Size

A program that reads no schema pays for the description every validator now carries: a lone `boolean()` is 1.24 kB gzipped, from 1.19 kB, and an object with a string, an email and an optional integer 5.79 kB, from 5.37 kB. `toJsonSchema` with an object of one string is 5.1 kB, and `portugueseMessages` with `formatIssue` 2.5 kB.

## Migrating from 0.3.0

- Where an `else` branch after `is` stops compiling, the compiler now knows the value is not of the validator's input type there. Remove the code that treated it as one, or call the validator and read `result.ok` where no narrowing is wanted.
- Where a form library's field type changed, type the field as `InferInput<typeof validator>`, which is what the library now reads.
- A check that compares fields of a form, such as a password and its confirmation, is better written with `checkFields`. `check` still works and still waits for every property.
- A translation that worded custom codes one by one to avoid "Invalid value" can give one `default` entry.
