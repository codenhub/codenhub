# Validation architecture

This records the invariants of `@codenhub/validation` and the reasoning behind decisions that are not obvious from the code. Public behavior lives in the package docs; this is for changing the package without breaking what it relies on. The release conditions of the next release live in [roadmap.md](roadmap.md), and [0.4.0.md](0.4.0.md) is the approved design of what follows 0.3.0: where it reverses a section here, this document describes the code until the change that implements it. Each step of it says where it stands, and a step is described here once it is built. The core was rewritten after 0.5.1 as one pass over the input: [One pass](#one-pass) says what it replaced and what that cost, and the sections below describe the code as it is now.

## What the package is for

The package answers one question, "is this value what I need it to be?", for any package or app that has to ask it and does not want validation to become its business. The unit is a **value**: a URL, an email, a number, a port. A schema for an object or a form is a composition of value validators, never a different kind of thing.

Two consequences shape every decision below:

- **A consumer pays only for what it imports.** Whatever a consumer imports lands in the bundle of the application that uses it, and a package that validates a few options brings the core with its first validator. Anything that makes every validator heavier is a regression, and the size budgets in `tests/integration/bundle-size.test.ts` enforce that.
- **The contract is ours.** Results, issues and paths are plain data defined here. Nothing depends on another validator's shape or on another workspace package, which is what lets any workspace package depend on this one.

## What the package defends against

A validator is a boundary check on data a program did not make. This section says which input that covers, so a finding can be sorted before anyone writes a fix. It changes only by decision, and a change to it comes before the code that follows from it.

In scope, and the package must get right:

- **Any value JSON can hold, of any shape.** Wrong types, missing and extra keys, `__proto__` and other keys named like prototype members, and nesting of any depth reached through `lazy`. For this input, bad input is a failure and never an exception.
- **An output whose copy takes a prototype the sender chose.** `record`, the unlisted keys `looseObject` and `objectWithRest` keep and the object `intersection` merges are the places where the sender names a key of an object the package builds, and there `__proto__` is reported as `invalid_key` with one `invalid_value` issue of `{ reserved: true }`. Until 2026-10-09 both kept it as an own property, which writes to no prototype and was taken to settle it. What that did not weigh is the next line of the consumer: `Object.assign({}, output)` and a `for...in` copy assign each key, so the copy's prototype became the sender's object and `JSON.parse('{"__proto__":{"admin":true}}')` gave it `admin`, measured against the built package. Rejected: dropping the key, as zod 4.6.5 and valibot 1.5.0 do, which hides what the sender tried from the program it tried it on; and keeping it with a warning in the docs, which leaves the default unsafe for the code most often written after a validation. A shape that lists `__proto__` keeps it as data, since there the developer named it. What stays outside this: a value passed on unchecked, by `unknown()`, a key `looseObject` keeps or `json()` with no validator, is the input's own object and holds whatever keys it came with. That covers only the input's own object, passed on whole: `intersection` merging two outputs builds a new object, and reports an own `__proto__` there unless a shape of either side lists it at that place, looked for in the descriptions only when the key is met. A shape lists it only if it produced the value there: of a `pipe` the last step, and the step before each that gives back what it was given, such as `unknown()`; not the validator a `transform` runs before its function, nor the key of a map entry for its value; and a `lazy` is read as the validator its getter returned, without calling the getter again, which `lazy` documents as called once. Each pair is checked at every place it is reached, including a pair merged before. Until review of that fix, any step of a `pipe`, the inner of a `transform` and the key of a map entry counted, so `intersection(pipe(object({ __proto__: unknown(), a: string() }), transform(unknown(), () => JSON.parse(text))), object({ a: string() }))` kept a `__proto__` the transform parsed, and a pair reached first where a shape listed the key kept it unreported at a second place. Until the release audit after 0.4.1 the carve-out was read to cover what `intersection` copied from an unchecked side, which the merge did without asking; what that did not weigh is that the merged object is the package's, not the input's: `intersection(unknown(), object({ a: string() }))` passed `JSON.parse('{"__proto__":{"admin":true},"a":"x"}')`, and `Object.assign({}, output).admin` was `true`, while `record` and an `object` that kept its unlisted keys refused the same key.
- **Text crafted to be read one way by the validator and another by what uses it.** A format either describes its text completely with a pattern or grammar, or, where a standard parser decides what the text means, returns what that parser read (see [Formats are allowlists](#formats-are-allowlists)). A value that passes means the same thing to the validator and to its consumer.
- **The input leaking through issues.** An issue holds type names and constraint values, never the value under test.
- **Work that grows faster than the input.** A schema whose work multiplies with each level of nesting, such as a recursive `union` of objects, where every option recurses into the children even after it has failed, turns a few hundred bytes into hours. Capping the input cannot help. `lazy` keeps, for one validation, the result it found for each object, keyed by the object and then by the number of `lazy` levels open when it was reached, and gives it again when the same object is reached with as many levels open, so the options of a recursive `union` share the children's result and its work grows with the input. The levels are part of the key since two options may reach an object through different numbers of levels and a result found nearer `maxDepth` may have failed for that alone: kept without them, `union([lazy(() => lazy(() => node)), node])`, with `node` limited to `maxDepth: 2`, rejected an object `node` accepts, found in review of the audit fixes. Results found for one object at different depths are rare, since the levels an object is reached through are mostly fixed by the schema, so the sharing a recursive `union` relies on is kept. Until [One pass](#one-pass) the path was part of the key too, because an issue was written with its full path when it was made, so a result found at one path could not be given at another: each path a `lazy` met was a node of a tree of segments, and until 0.3.0 a result was kept by the object and the last segment of its place and found by comparing places, which with `maxCalls` raised took 7.8 seconds for 80,000 rows sharing ten objects, found by the audit of 0.3.0. An issue is now written from its own value outwards ([Issues](#issues)), so what was found for an object holds wherever it is reached, and rows that point at a shared category validate it once. A primitive is not kept, since it has no children, and keeping every one would cost a map entry for each. What was kept is given again as a copy of each issue as it stood at the object, since each composer above writes its own key onto the issues reported under it. A schema that makes a new object at every level, such as a `transform` that copies its value, defeats the sharing, so `lazy` also bounds the calls one validation makes (`maxCalls`), as it bounds the depth. A validation is the call of a composer from outside, such as `schema(input)`, and everything it reaches until its result settles: the first `lazy` reached opens one when none is running (`scopeNow` in `core/run.ts`), since only a `lazy` counts anything, the call from outside ends it, and a result that waits carries it into every continuation after an await (`context`), so waiting never restarts the count and an asynchronous recursive schema is bounded too. Only the awaits the package makes are carried: a function the consumer wrote for `validator()` that awaits and then calls a composer reaches it with no validation current, so that call starts one with fresh counts. Carrying a context through code the package does not control takes `AsyncLocalStorage`, which is Node.js only, and the package runs anywhere, so the docs state the limit and point asynchronous work at checks, whose awaits the package does carry. So a root that fans out before any `lazy` is open, such as an `array` of recursive items, is held to one count per `lazy`, which a count per outermost `lazy` call was not: fifty items of 150 bytes each made fifty counts, and the issues they kept ran the process out of memory. Validations run one after another in a loop each open their own, so they never share a count; so does a validation made from a callback the consumer wrote, such as a check's test, a `transform`'s function, a `guard`, a `format`'s test, a default or a `lazy` getter, which `detached` runs with no validation current, where it would otherwise spend, and be held to, the counts of the validation running the callback; and concurrent asynchronous validations each keep their own, since each continuation restores the validation it belongs to. Each `lazy` counts its own calls in the validation against its own `maxCalls`, keyed by the `lazy`, so a schema's limit holds wherever it is composed: one shared count read from the first `lazy` reached let an unrelated `lazy` listed earlier in an `object` replace a limit raised for a large tree, and reject the tree. A `lazy` made while another's getter runs counts its calls with that one, and holds the shared count to its own `maxCalls`. A schema built anew at every level, by a getter that calls the function that builds it, as `const node = () => union([object({ kids: array(lazy(node)) }), …])` does, makes new `lazy` validators at every level, and with a count of their own each, nothing bounded it: 240 bytes took a second, and 450 ran the process out of memory. The results a `lazy` keeps stay its own, since two validators one getter made may reach the same object at the same path and must not give each other's answer, so such a schema shares no work, doubles to the limit and rejects deep valid input; the docs say to build a recursive schema once and refer to it. The work of a validation is then bounded by the sum of the limits of the `lazy` validators it reaches outside a getter, a number fixed by the schema. The count bounds the issues kept as well as the time: each call can keep about 1 to 2 KB of issues, whose paths `maxDepth` bounds, so the default, 10,000, holds each `lazy` of a validation the limit stops to about 20 MB and a few tenths of a second. Measured on 2026-11-04, on Node.js 24, 10,000 calls each near 128 levels deep, a chain ending in a binary tree with a bad field at every node, kept 12 MB in 0.1 s, and 19 MB in 0.3 s when each level waits; before [Depth across awaits](#depth-across-awaits), a level that waited was not held to `maxDepth`, and a chain of 10,000 levels that waited at each, the same count of calls, kept 402 MB. At 100,000 it held about 100 MB, a cost a public endpoint would pay for each hostile request of a few kilobytes; recursive data of more than 10,000 nodes in one validation is rarer than that, and it raises the limit where it is set. Until 0.3.0 every value that reached a `lazy` was a call, a primitive included, so a schema for any JSON value rejected a valid list of 10,001 numbers, 60 kB. That did not weigh that a primitive which ends the recursion multiplies nothing: its work is its own, once. So a primitive during whose call no other `lazy` call started, of any `lazy`, and whose result is not pending, is given its call back. A primitive the recursion goes on through, as text a `json` or a `transform` reads the next level from, starts such a call and stays counted, which is what still bounds a recursive `union` whose options each decode the next level from text; a pending one stays counted because calls made while it waits cannot be told from its own. The calls not counted are then leaves under a counted call or under the root, so the bound is loosened by the widest value a call holds, which the input's size and a collection's `max` bound, and no further. Exempting every primitive was rejected for the decoding schema above, whose calls are all primitives. One primitive past the limit is let through to learn whether it ends the recursion, since refused on arrival, the last number of a tree with exactly `maxCalls` objects failed it, found in review of the change; its call is given back only if it does, so a second finds the count two past the limit and is refused, after an await too. The work of a flat input, which grows with it, is a matter of size, below.
- **Issues that cost far more than the input that caused them.** Each collection stops at 1,000 issues (see [The limit of issues](#the-limit-of-issues)).

Out of scope, and documented rather than defended:

- **Code inside the input.** A getter, a `Proxy` trap or a `then` method runs when read, and its exception propagates, as a callback's does.
- **Size.** Time and memory that grow with the input. The caller caps untrusted input and gives collections a `max`. The issues a failing input produces are not part of this any more: see [The limit of issues](#the-limit-of-issues).
- **The world behind a value.** Whether a domain resolves, where it points, whether a mailbox exists, and which IP ranges are private. A host that looks like another, such as `exаmple.com` with a Cyrillic `а`, is a host of its own and passes as its punycode.
- **Issues the package did not make.** `formatIssue` and `flatten` word the issues validators return, whose shape the types state; an issue received from elsewhere, such as JSON from a server, is input, and a malformed one, such as one with `params: null`, may throw. Validate it before wording it.

### When a finding is a blocker

A finding blocks a release when, for input in scope, a value that should fail passes or one that should pass fails, a passing value means something different to its consumer than to the validator, bad input throws, or an issue holds the input. Anything else is recorded in the roadmap's backlog and does not reopen a release. A finding about input out of scope is a question about this section, not a bug: it becomes a fix only after this section is changed to take it in. Documentation that disagrees with the code is fixed when found, and blocks nothing on its own.

The JSON Schema `toJsonSchema` writes is covered as the validator is: a reader that refuses a value the validator accepts blocks a release, as the validator refusing it would. A schema is handed to another program, the gateway of an API or the caller of a tool, which refuses the value before the validator sees it, so for the user the two failures are one. A schema that accepts what the validator refuses is not a finding, since [JSON Schema](#json-schema) promises only the one direction. Decided by the owner in the audit after 0.4.1, on `multipleOf(0.1)`, whose schema Ajv refused `0.3` with. Covering the validator alone, and taking the schema as advice, was rejected for that case.

### The limit of issues

Until 0.3.0 the issues of a failing input were the caller's to bound, with the size of the input: "the caller caps untrusted input and gives collections a `max`". That decision had no measurement behind it. Measured on 2026-10-05, on Node.js 24, `object({ events: array(union([five objects])) })` given `{"events":[{},{},…]}`:

| Input  | Before                                  | With the limit |
| ------ | --------------------------------------- | -------------- |
| 100 kB | 575 ms, 152 MB                          | 39 ms, 13 MB   |
| 1 MB   | 5.9 s, 1.07 GB; a 512 MB process aborts | 71 ms, 25 MB   |

A plain `array(string())` given 1 MB of `0`s took 189 MB, and takes 6 MB. So the 100 kB cap the documentation suggested still cost half a second of a blocked event loop for each request, and the default body limit of several frameworks ended a small container. It also left every adopter to remember `max` on every collection, which is the kind of care the package exists to take once.

A collection (`array`, `tuple`, `set`, `map`, `record`) stops running its items once the results that are not pending hold `MAX_ISSUES` issues, 1,000, cuts its list there, and adds `too_big` with `{ maximum: 1000, type: "issues" }` at its own place. The lists a single validator makes from input of any size are cut the same way: the unknown keys of a `strictObject`, the repeats of `unique` and `set`, the keys a query string repeats, and the conflicts of an `intersection`. The count is each collection's own, of the issues its items returned, which already include everything below them, so a collection around one that stopped stops too, and the whole result holds about a thousand issues for each collection the schema names, not for each the input holds.

- An issue counts with the issues it holds in `params.issues`, as the issue of a `union` holds every option's. Counted as one, the limit was never reached by `array(union([array(string()), array(boolean())]))`: a thousand lists of a thousand bad items, 2 MB, took 1.8 s and 331 MB, each item one issue holding two thousand. So a list of items that fail a union of five objects stops after about sixty items and not a thousand, which is the price of bounding what is held and not only what is listed.
- Only issues are counted, so the limit is never reached by input that passes, and input that fails still fails. It changes how much is listed, never the answer.
- It is not an issue of `lazy`'s kind, which stands in for the `union` it was found under: there is nothing to raise, and the input is invalid whatever was left out.
- A pending result cannot be counted, so a collection whose items wait starts them all, and only its list is cut. Running them one after another to count them would change when an asynchronous schema does its work, and the work of such an item, a request for each, needs a `max` whatever it reports.
- The limit is a constant, with no option. A program that must report every bad row of a long list calls the item validator on each row, which is also where it would page them. An option on five validators is surface to add when someone needs it.

Rejected: one count for the whole validation, kept beside `lazy`'s counts. The options of a `union` that then passes would have counted, so a long valid list of such items would have reached the limit, and taking them back out after an await, with other items running between, cannot be done by remembering a number. Rejected too: shrinking only what `union` keeps for each option, which leaves the plain array at 189 MB.

## A validator is a function

```ts
type Validator<T> = (input: unknown) => ValidationResult<T>;
type ValidationResult<T> = { ok: true; value: T } | { ok: false; error: { issues: ValidationIssue[] } };
```

There are no classes, no base type, no registry and no method chains. A validator a factory of this package made carries three things beside the call: its run, under a key of its own copy of the package ([One pass](#one-pass)), its `~description` and its `~standard`. A function of that shape written by hand is a validator to whoever calls it, to `assert`, `is` and `standard`, and to the types, and a composer takes it once `validator()` made it one. Until [One pass](#one-pass) anything with the shape was taken anywhere, so a custom validator needed no helper and no import. What that did not weigh is what every composer carried for it: the code that calls a function it knows nothing of, tests what it returned, moves its issues under the child's place and waits for its promise, in every schema, most of which hold no such function. That code now arrives with `validator`, 1.6 kB gzipped for a schema of nothing else, and a child that carries no run is refused when the composer is created, by the name of its argument ([Results, not exceptions](#results-not-exceptions)). Rejected: wrapping a bare function inside each composer, which keeps the import away and the code in every composer. Composers take validators and return validators.

The reasons, in order of weight:

- **Tree-shaking.** Each validator is a function in its own module. A bundler keeps exactly the ones a consumer references. A class hierarchy, or a `val` namespace object, drags the shared base and every method along, which is what the previous design did: 4 kB gzipped for one string rule, 19.8 kB for the package.
- **No hidden state.** A function of `unknown` has nothing to configure after construction, so there is nothing to share, mutate or clone. Immutability is free.
- **It is the contract.** `(input: unknown) => result` is small enough to state in one line and to implement in a hand-written check.

### Factories, always

Every pre-made validator is created by calling a function, options optional: `email()`, `string({ min: 2 })`, `url({ host: hostname() })`. There is no validator that is used bare, because a bare validator cannot grow an option without a breaking change, and because one rule with no exceptions is easier to remember than two. A single value therefore reads `email()(input)`.

Every factory has the same signature: `validator(options?, ...checks)`, where a composer's own arguments, such as the shape of `object` or the item of `array`, come first. Options are an object and checks are functions, so the factory tells them apart with `typeof` and `string(startsWith("a"))` needs no empty options. An option given as `undefined` is no option, and every options interface types it so, `min?: number | undefined`: a limit read from configuration that may lack it is passed as it is. Typed `min?: number`, that call was a compile error under `exactOptionalPropertyTypes`, which the package's own consumer test compiles with, found by the audit before the release. Leaving it and telling callers to omit the option was rejected: the validator already reads `undefined` as absent, and a caller would spread a conditional object to say the same. Every factory that reports an issue of its own accepts a `message` option, so its validators have an options object that can grow without a breaking change. Each factory names the options it reads to `split`, which throws a `TypeError` for any other name: a misspelled limit, `array(item, { maxx: 3 })`, would otherwise leave the limit unset and accept what it was written to reject. This was first left to TypeScript, to keep the names out of every validator, but TypeScript does not see options passed through a loosely typed variable, read from configuration or written in JavaScript, and the options 0.1.0 removed already threw for the same reason. Measured, the check costs 68 bytes gzipped on `boolean()`, about 7%, and the error names only the option, not the ones there are, which the types list.

The wrappers are the exception: `optional`, `nullable`, `nullish`, `fallback`, `transform`, `pipe` and `partial` report no issue of their own, only their child's, so they take neither options nor checks. `optional` could not take checks in any case, since its second argument is a default, which may itself be a function. `json` takes the validator of the parsed value first and optionally, so its checks follow options and need the validator: `json(object(shape), {}, check(...))`.

### Options, checks, formats and composition

- **Options** carry the common constraints and the clean-up of one type: `string({ min, max, length, trim, case })`, `number({ min, max, gt, lt, int, safeInt, clamp })`, and `min`, `max` and `length` on collections. They are the short way to say the usual thing, and each costs one small branch in its validator.
- **Checks** carry the rarer constraints, each in its own module: `pattern`, `startsWith`, `endsWith`, `includes`, `lowercase`, `uppercase`, `multipleOf`, `nonZero`, `unique`. Each takes its message last; `unique(by?, message?)` takes what to compare first, since a function in first place is what to compare, not a message. A consumer that never requires a prefix does not bundle the code that checks one. See [Checks](#checks).
- **Formats** are separate validators: `email()`, `url()`, `uuid()`. Each is its own module, so a consumer that wants `email` does not pay for `uuid`.
- **Composition** carries everything else, by function: `object`, `optional`, `pipe`, `transform`. Cleaning a string before checking a format is `pipe(string({ trim: true }), email())`, not an option on `email`.

Which constraints are options is a judgment of how often they are used, weighed against what they add to every use of their validator. A constraint moves between the two only in a breaking release.

Options that change the value are named as changes, and checks never change it: `string({ case: "lower" })` lowercases, where the `lowercase()` check requires lowercase and changes nothing. Clean-up (`trim`, `case`, `clamp`) runs first, then every option constraint and every check on the cleaned value. Every failing constraint reports its own issue.

### Checks

A check is a rule about a value that already has its type. It is not a validator: it receives the typed value, and returns nothing when the value passes, or the issues it found.

```ts
type Check<T> = (value: T) => readonly ValidationIssue[] | undefined;
type AsyncCheck<T> = (value: T) => readonly ValidationIssue[] | undefined | PromiseLike<readonly ValidationIssue[] | undefined>;
```

The two mirror `Validator` and `AsyncValidator`: a check a consumer writes and types as `Check` keeps its validator synchronous, where one typed as the broader `AsyncCheck` would make every validator given it asynchronous.

A check is given to a validator after its options: `string({ min: 3 }, startsWith("ab"))`, `object(shape, check((data) => data.password === data.confirm, { path: ["confirm"] }))`. It runs once the value has its type: for a leaf, once the input has passed the type test and every option constraint, so a bound such as `max` keeps a long value from a costly check and an invalid one from an asynchronous lookup; for a format, once the input is of the format, since the format is what its value is; for a composer, once every child has passed, since before that there is no value of the type to check. A check on an object therefore reports nothing while a property fails, which is the price of giving it a typed value, and a check on `ip()` never sees text that is not an address, so it can parse the value without guarding against that.

Every check of a validator runs and every issue is reported, as for options. A check that returns a promise makes its validator asynchronous, and the types say so: each factory has overloads for synchronous checks, which return `Validator<T>`, and for any checks, which return `AsyncValidator<T>`. Overloads, not a generic list of checks, because a generic rest parameter loses the contextual type that lets `check((data) => …)` infer `data`. What runs the checks comes with the checks and not with the validator: each check holds a runner (`carry` in `core/rule.ts`), a validator asks its checks for one (`runnerOf` in `core/finish.ts`), and a validator given no check carries no code for them. A built-in rule, which answers at once and runs no code of the consumer, brings a loop of a few lines. `check`, `checkFields` and `contentType` bring the runner of `core/check-run.ts`, which runs each check with no validation current, tests what it returned and waits for those that wait, and which runs the built-in rules given beside them too. A function that is not a check of this copy of the package is refused when the validator is created, as a child that is no validator is. Until [One pass](#one-pass) one shared helper ran the checks of every validator, so a `string()` with none carried what waits for a promise.

`checkFields(keys, test, issue?)` is the one check that does not wait for every child. A form with a name, a password and its confirmation showed the price above at its worst: with the name empty, a check that the two match reported nothing, and the user learned of it only after fixing every other field. It names the properties its test reads, and `object` and `objectLike` run it once those have passed, whatever the rest did, on an object of the properties that passed; its test is given the named ones alone, so it is still given a value of its type.

- **A check like any other, described.** It is a function of the whole object, made by `check`, that takes the named properties out and tests them, so given to any validator it runs as a check does. It carries a description, `{ kind: "check", fields }`, which names the properties it waits for. No second kind of argument, and no new signature for a factory.
- **What runs it is bundled only by `checkFields`.** `checkFields` registers each check it makes, in a `WeakMap` in `core/field-hook.ts`, with the function in `core/field-checks.ts` that reads where each named property is in the shape and runs the field checks whose properties passed. `object` and `objectLike` ask that map when they are made, and a program that never calls `checkFields` carries only the lookup: measured on 2026-10-08, an `object` of one string went from 3366 to 3206 bytes gzipped, the object of three fields from 6207 to 6052, `objectLike` from 2931 to 2759, and an `object` with a `checkFields` grew 69, as did the bundle of every export. Importing the runner from `object`, as before, was the rejected alternative: every object paid for it, and most have no `checkFields`.
- **Run after the children, with the object's own checks when all passed.** When every property passed and the object found nothing of its own, it runs with the other checks, in the order given. When a property failed, or a strict object met a key it does not know, the other checks do not run; the field checks whose properties all passed do, and their issues follow the properties' issues. A property it names that failed keeps it silent: its test would be given a value that is not valid.
- **A name the shape lacks is a `TypeError` when the object is made**, as a key `pick` is given, since the check would never run. A list of no names is one when the check is made: it would wait for nothing, and so run its test on every object that failed.
- **What it costs.** `object` asks each check once, when it is made, whether it names properties, and looks at a list that is usually empty when a property fails. No size budget moved, and an `object` of three strings validates as fast as before.

Rejected: running every `check` on a partly valid object, which gives a test a value that is not of its type; and an option of `check`, `{ fields }`, which could not type the test's argument as the named properties, since an option does not change the type of an argument beside it.

Checks replace `refine`, which wrapped a validator to add one rule. A check attaches to the validator instead, reports every issue with the others, and needs no second concept.

### Builders

Four public helpers make validators and checks on the same internals as the built-in ones, `leaf` in `core/leaf.ts`, `split` in `core/split.ts` and `toValidator` in `core/make.ts`, so a custom one behaves exactly as a built-in does, with the same issue shapes, the same `message` option and the same checks. A built-in made by a call when its module loads, such as `export const hex = /* @__PURE__ */ formatFactory(...)`, carries the pure annotation, without which a bundler keeps the call and every consumer carries the validator (see [Tree-shaking is a contract](#tree-shaking-is-a-contract)):

- `check(predicate, issue?)` makes a check of any type. The issue is an issue to report, or a string as its message, and defaults to code `custom`. The test answers with a boolean, or with the list of the issues it found, empty for a value it accepts. Any other answer throws a `TypeError`, `undefined` included, since a test that forgot its `return` would otherwise accept every value.
- `format(name, predicate)` makes a factory for a string format, such as `slug()`: a non-string fails with `invalid_type`, and a string the predicate rejects with `invalid_format` and `params.format` set to `name`.
- `guard(expected, typeGuard)` makes a factory for a validator of any type from a type guard: `const file = guard("File", (value): value is File => value instanceof File)`, used as `file()`. A value the guard rejects fails with `invalid_type` and `params.expected` set to `expected`.

- `validator(validate)` makes a validator of a function written by hand, one that returns `pass(value)` or `fail(issue)`, or a promise of one, so a composer takes it ([A validator is a function](#a-validator-is-a-function)). It is built on none of those internals. It has one signature, which reads the types from what the function returns, and the input type from a function typed as a validator. It says nothing of itself, as a function a reader of the schema cannot see into: `describe` gives `undefined`, `audit` reports a rule it cannot read, and `toJsonSchema` and `encode` throw at its place.

A validator with options of its own is a function that checks its options and returns one of these. No further helper exists for it, because a function already does it.

### Formats are allowlists

A format accepts text that matches a complete, positive description of it, a pattern or a grammar, and rejects everything else. It never accepts text for avoiding a list of known problems: such a list is finished only when nobody finds the next problem, and every finding adds to it.

Where a standard parser decides what the text means, the parser is the description. `url` hands the text to the URL parser, checks what it read (the scheme against a list, the absence of credentials unless a `credentials` validator accepts them, the host against the public-host rule), and returns that reading serialized, never the text it was given. `internationalEmail` does the same for its domain, and a `mailto` URL gives each recipient as `internationalEmail` does. `email` reads a domain written in ASCII without the parser, and returns it in lowercase, which is what the parser gives for such a domain ([Two readers of an email address](#two-readers-of-an-email-address)). The value then cannot mean one thing to the validator and another to the request or mail server that uses it, whatever spelling the text used: dot segments, fullwidth or invisible characters, IPv4 shorthand, escapes in a host. That holds for what the URL Standard defines. A path is the parser's too, and a server may still route it as another: it may decode an escape such as `%61` for `a`, merge `//` into `/`, or drop `;` and the parameters after it from every segment, as Tomcat and Jetty do. So a `path` part is an allowlist, a description of the paths that may pass, which every such reading of a path it accepts still satisfies; a denylist such as "not under `/admin`" passes `/;/admin`, `//admin` and `/%61dmin`. Where a reading would carry a path an allowlist accepts outside it, the path fails before the part runs, below. The rules these validators apply to raw text are positive descriptions too: a written URL holds no whitespace and no control characters, and a domain is written with letters, marks, digits, the zero-width non-joiner and joiner, dots and hyphens, none of which can end a host. The joiners are there because Persian and the Indic scripts write them inside a word, and IDNA allows them where those scripts do, after a virama or between letters that join (RFC 5892, CONTEXTJ), which the parser checks itself: it refuses `a\u200Cb.com`, a non-joiner between Latin letters, in Node.js and every browser. Until the release audit after 0.4.1 they were left out, which did not weigh CONTEXTJ: `domain()` and `email()` refused `می‌خواهم.com`, `क्‌ष.com` and `ශ්‍රී.lk`, which `url` and Chromium, Firefox and WebKit read, while their punycode passed, so one host had two answers. Text a format checks without a parser, such as a UUID, is described completely by its pattern and is returned as written.

The parser is the runtime's own, and runtimes read some hosts differently, while a schema often runs in two of them, on a form and on a server, and must give one answer. Where they differ, the package checks what the parser read itself, by the rule browsers apply, so every runtime gives the browsers' answer: a punycode label must decode to the label it spells, which Node.js and Firefox require and Chromium and WebKit do not, and a name with a right-to-left label must keep the bidi rule of RFC 5893, which every browser applies and Node.js 24 does not. Both are in `formats/punycode.ts` and `formats/bidi.ts`. `tests/browser/agreement.spec.ts` runs generated text through the built package in Node.js and in Chromium, Firefox and WebKit, and fails on any difference, so a new difference is found rather than shipped. A host validator replaces the rule of which hosts are public and none of this: for a scheme the URL Standard has rules for, `url` gives it only a host of lowercase letters, digits, `.`, `-` and `_`, an IPv4 address not written with a bare `0x` part, or an IPv6 address without a leading zero in its IPv4 tail, and none written with a Hangul filler, as it is or percent-encoded, which the parser decodes first, since Chromium writes `a*b.com` as `a%2Ab.com`, Firefox refuses it and `0x`, Chromium reads `a%20.com` and `[::01.2.3.4]`, which Node.js refuses, and Node.js, Chromium and Firefox drop a Hangul filler that WebKit on Linux refuses, found when a new piece of the generated hosts in 2026-11 made `𞤀ㅤ`. No DNS name holds the characters left out. The spec runs `url({ host: unknown() })` too, so the rule is tested against the engines it exists for.

The parser's time is the package's to bound too, where it grows faster than the text. The parser of Node.js 24.19 decodes a punycode label in time that grows with the square of its length: measured on 2026-10-05, `email()` took 0.3 s to reject `a@xn--` and 100,000 letters, 1.3 s for 200,000 and 5 s for 400,000, and `url` the same with `xn--` in capitals, in fullwidth letters or written `%78n--`, found by the audit of 0.3.0. So `internationalEmail`, `domain` and a `mailto` recipient refuse a host written with more than 759 characters, and `url` the host of a scheme the parser has rules for, before the parser is given it (`HOST_TEXT_MAX_LENGTH` in `formats/patterns.ts`). 759 is three for each of the 253 characters a host can have, every one as an escape, the longest a host is written with nothing the parser drops. It is not 253, the limit of the host itself: text spells a host with more characters than the host has, as letters written with their accents apart do, and five labels of thirty such letters are 308 characters for a host of 188. What it refuses that passed before is a host padded past the limit with characters the parser drops, such as variation selectors, which nobody writes. Rejected: refusing only a written `xn--` label longer than the 63 characters a label can have, which the fullwidth and escaped spellings pass; and leaving the length to the caller, as `pipe(string({ max: 254 }), email())`, which is the care the package exists to take once. A host of a scheme the parser has no rules for is kept as written and takes no such time, so `url` measures none. `src/formats/linear-time.test.ts` holds each spelling to the bound.

A format whose meaning has more than one spelling returns one canonical spelling, so a later comparison or lookup on the value treats one meaning as one value:

- `url`, `internationalEmail` and `domain` return what the URL parser read, and `email` the same text for the domains it accepts. For a scheme the parser has no rules for, such as `ssh`, it reads the host as written, so `url` normalizes that host as RFC 3986 does, letters in lowercase and escapes in uppercase.
- `ip` returns an IPv4 address as written, which has one spelling, and an IPv6 address as the URL parser writes it, lowercase with the longest run of zero groups shortened (RFC 5952), its IPv4 part dotted when it is IPv4-mapped or NAT64, as RFC 5952 section 5 recommends, and its zone as written. `cidr` returns its address as `ip` does. `url` gives a `host` validator an IPv6 host in that spelling, so `host: ip()` and a list of addresses `ip()` produced agree, but its value keeps the hex groups the parser writes, since a URL is the URL Standard's to spell, and `new URL(value).href` must give the value back.
- `mac` returns lowercase pairs separated by colons.
- `hostname` and `uuid` return lowercase, and `ulid` uppercase, the spelling each one's specification writes. An absolute name ending in a dot, `example.com.`, names the same host as `example.com`, so `hostname`, `domain`, `email`, `internationalEmail` and `url`, whatever its host validator, reject it rather than produce a second value for one host, which a list of blocked hosts or a uniqueness check comparing strings would miss. It was accepted and kept during 0.2.0's development, as the parser keeps it, and rejected before release for that reason, found in the pre-release audit; an option to accept it can be added without breaking anyone.
- `phone` returns E.164, `+` and the digits (`+5511987654321`), and `creditCard` the digits alone, however either was grouped.

### Formats are made of parts

A composite format is built from parts that are validators on their own. `hostname()`, `domain()` (a public domain name), `ip()` and `port()` each validate a value alone, and `url`, `email` and `internationalEmail` take them as options that check what was read:

```ts
url({ protocols, host, path, port, query, repeated });
email({ domain, local, allowPlus });
internationalEmail({ domain, local, allowPlus });
```

- Without a part option the format applies its own default rule: `url`, `email` and `internationalEmail` require a public domain name, and a URL with no port or path passes those. The default rule is the shared predicate, never the public validator, so a default `url()` builds no issue it throws away and costs what it did without parts.
- A part given as an option replaces the default rule, never the syntax: `url({ host: hostname() })` accepts any hostname, `localhost` included, `url({ host: unknown() })` accepts any host the parser reads, which is what `allowLocal` did, and `url({ host: union([domain(), ip()]) })` accepts IP addresses but not `localhost`. `email({ domain })` still requires a hostname. The protocol is not a part: a list, `protocols`, says it better than a validator would.
- The parts apply to a URL with a host. A `mailto`, `tel` or `urn` URL keeps its own rules, and a `mailto` recipient's domain must be public, as for `internationalEmail()`: `host` checks a URL's host, and a `mailto` has none.
- The port is given as a number, or as `undefined` when the URL names none or names its scheme's default, which the parser drops. `port()` accepts 1 to 65535: 0 asks a system for any port and cannot be connected to.
- A repeated query key is structure, checked before content: it fails before any part runs, as a failure of the query part whose `issues` hold `invalid_key` at `[key]`. `searchParams`, which is the reader itself, reports it at `[key]` as its own.
- An encoded path separator is structure too: with a `path` part, a path holding `%2F` or `%5C` fails before any part runs, as a failure of the path part whose `issues` hold `invalid_value` with `{ encodedSeparator: true }`. The parser keeps it encoded, so a check on the path reads one segment where a server that decodes it before routing reads two, and `/api/..%2fadmin` would pass a check for `/api/` and reach `/admin`. A segment `.` or `..` followed by `;`, such as `/api/..;/admin`, or by `%3B`, which a proxy that decodes the path, such as nginx, hands on as `;`, fails the same way with `{ dotSegment: true }`: the parser reads one segment named `..;`, and a server that drops path parameters before resolving dot segments, as Tomcat and Jetty do, reads `..`. Only a dot segment is rejected, since that is the one place parameters turn a path an allowlist accepts into one outside it: dropping them from any other segment, as in `/api/a;v=1` or `/;/api`, leaves a path under the same prefix, and rejecting every `;` would reject paths that are valid and in use. Without a `path` part nothing checks the path, so the URL is accepted.
- A part validator receives what the parser read, not the text: the host in its ASCII form, the path after dot segments are resolved, the port as a number.
- A part that fails is the format's own issue, not a child's: one `invalid_format` at the place of the URL or address, `{ format, part, issues }`, with what the part validator found in `issues`, its paths relative to the part. The value is text, so a path into it, such as `["email", "domain"]`, would name a field no form has, and the error would show nowhere; at the format's place it shows beside the field. Being the format's own, it is worded by the format's `message`, which is what makes `email({ domain: oneOf(["company.com"]), message: "Use your company address" })` say that sentence. `englishMessages` words it with the part and what the part found first.
- A part validator only decides; the format still returns the URL or address as the parser writes it, and a part that transforms its value changes nothing in the output. To read typed values out of a URL, validate the part itself.
- An asynchronous part makes the format asynchronous, as a child makes a composer asynchronous.

`query` is given an object built from the decoded search parameters, the values a server reading them with `URLSearchParams` sees. A key that appears more than once fails, as a failure of the query part, unless `repeated` is set, in which case every value of every key is given as an array. The default is the defense against parameter pollution: a validator that saw one of two values while the server read the other would pass a value nobody checked. `repeated` is an option, so the type a validator receives is one or the other and never depends on the input. `searchParams(validator, { repeated })` is the same reading on its own: it takes a query string or a `URLSearchParams` and returns what the validator produces, so `searchParams(object({ page: coerceNumber() }))` reads a typed query.

`email` has no `query`: the `+tag` of `me+tag@example.com` is part of the local part, and `allowPlus: false` rejects it, since refusing `+` aliases is the one common restriction on a local part and is clumsy to write as a `local` validator.

### Two readers of an email address

`email()` and `internationalEmail()` are one format with two readers of the domain, each given to `emailOf` in `formats/email.ts`. Both are described as `format: "email"`, take the same parts and report the same issues.

- **`internationalEmail` reads the domain with the URL parser**, as `domain` does, so a domain written in another script is accepted and returned as the parser read it. A `mailto` recipient is read the same way.
- **`email` reads a domain written in ASCII, without the parser** (`toPlainHost` in `formats/patterns.ts`), and returns it in lowercase. It refuses a domain with a character outside ASCII, and one with a label that starts with `xn--`: telling a label that decodes to a valid name from one that does not takes the parser, and passing it unread would accept as an address what `internationalEmail` and `url` refuse.
- **For an address both accept, both return the same value**, so a schema moved from one to the other compares its stored addresses as before.

Until [One pass](#one-pass) there was one `email`, which read every domain with the parser, and [The bar for size](#the-bar-for-size) recorded what that cost as a gap left open. What that did not weigh is who pays it: every form with an email field carried the reading of punycode and of the joiners, about 1.2 kB gzipped (4429 bytes for a lone `internationalEmail()` against 3216 for `email()`, bundled from source on 2026-11-14), while most forms take addresses whose domains are written in ASCII. The owner decided the split, and that the short name is the light one, since it is the one a form reaches for. Rejected: an option, `email({ international: true })`, which no bundler can drop, since every `email` would reach the reader; a name of its own for the light one, `asciiEmail`, which leaves the heavy one as what a form picks; and passing an `xn--` label unread, above.

### Compatibility of a format

A format is a contract with three parts, and changing any of them breaks a caller even when the module around it is untouched:

- **Its issue.** `invalid_format` with `params.format` set to its name. The name is frozen once released; params may be added.
- **What it returns.** As written or canonical, and which canonical form. Changing it changes values callers have stored and compare.
- **What it accepts.** Accepting more can let through a value a caller relied on being rejected, and accepting less rejects values that were valid. The accepted set changes only to fix a bug by the rules of [When a finding is a blocker](#when-a-finding-is-a-blocker). New leniency comes behind an option that is off by default, such as a `country` for national phone numbers.

A new format, and a new option on one, are additive. A format that needs data too large for every consumer, such as per-country phone rules, keeps it in a module of its own, so plain use never bundles it.

### Forms with files

`formData`, `file` and `contentType` are each a module of their own, so a program bundles only the ones it imports, and what they share with the rest is two readers in `core/objects.ts` and the unit of a size in bytes, a word in each message map.

- **A `FormData` is read as a query is.** `formData` gives its entries to `readEntries` in `formats/parts.ts`, the reading `searchParams` and `url`'s `query` part use, renamed from `readQuery` when it began to read entries of any kind, so a key given twice is refused the same way and for the same reason. The entries are read with the built-in iterator of `FormData.prototype`, which checks the value's own slot, so a `FormData` from another realm is read and an object that only claims the prototype is not.
- **A `File` is told by its slot, after its tag.** `fileOf` asks `Object.prototype.toString` first, so most values that are not a file are refused without a throw, which costs about 10 µs, and then reads `name` from `File.prototype` and `size` and `type` from `Blob.prototype`, whose getters throw for a value that only claims the tag. A `Blob` has no `name`, so it is no file. A `File` whose prototype was swapped for one without the tag is refused, and one swapped for one that claims the tag again is read, since its slot is a file's; one from another realm keeps its tag.
- **The content is read by a check.** `contentType` reads the first twelve bytes with the built-in `slice` and `arrayBuffer` of `Blob.prototype`, so the bytes read are those of the file `file` checked. A check runs once the options of its validator passed, so `maxSize` refuses a large file before it is read. A read that fails is `{ unreadable: true }`, the wording `invalidValueMessage` already had. The signatures are a table in its module, and a type it does not know throws when the check is made, since a type without a signature cannot be checked against the content: the check would either pass it unchecked or refuse every file.
- **The runtime's `File`, without naming it.** [Types](#types) records that a public signature names no global of the runtime, which a consumer compiling without the DOM's or Node.js's types could not resolve. `file` produces `GlobalFile`, `typeof globalThis extends { File: { prototype: infer TFile } } ? TFile : FileLike`, which is the DOM's or Node.js's `File` where the consumer has it, and otherwise the members every runtime's has; `formData` takes `GlobalFormData` the same way. Both are internal types. A structural type alone was rejected: a consumer would have to cast what `file` produces to pass it where a `File` is asked for.

## Results, not exceptions

Invalid input is a normal outcome, so it is a return value: `{ ok: true, value }` or `{ ok: false, error: { issues } }`. The shape matches the `Result<T>` used elsewhere in the repository on purpose, and is defined locally so the package depends on nothing. `docs/specs/errors.md` asks packages without an error dependency to return a package-local result, and asks that throwing and returning not be mixed for the same failure, which is why no validator throws for its input.

`assert(validator, input, { subject, messages })` is the one entry point that does: it returns the value or throws a `TypeError` naming the subject, the path of the first issue and its wording, with the failure as its `cause`. It is for input whose being invalid is a programmer error, such as a configuration object, which the same spec says must throw. Until 0.3.0 it was left out, on the reasoning that a caller who wants to throw writes `if (!result.ok) throw …`. That did not weigh what the first adopter showed: every package that validates configuration writes the same dozen lines, with its own choice of which issue to name and how to write its path, which is the duplication this package exists to end. It is not a second way to read a form or a request: it names one issue and throws, where the result lists all of them. Its `messages` are optional, unlike those of `formatIssue`, because the path still says which option is wrong when the wording is the generic one. Its options are checked as a factory checks its own, before the validator runs: `null` is no options, anything else that is not a plain object is a `TypeError`, and so is a name it does not read, since `message`, which every validator takes, is the likely slip for `messages` and would otherwise word every problem "Invalid value". A validator written by hand that returns no result, or a failure without an issue, is named as the fault rather than left to fail on a property read.

Two things do throw, and both are programmer errors: an invalid option when a validator is created (`string({ min: -1 })` is a `RangeError`, `objectWithRest(shape)` without the validator of the rest is a `TypeError`, and so is an option of the wrong type, such as `number({ int: "yes" })`, an option name the factory does not read, a part validator that is not a function, an empty `protocols`, or checks passed as a list, every one of which would otherwise be ignored or read as something else), and a callback the consumer wrote that throws, which propagates as the bug it is, or that returns what it may not, a message function anything but text or a check anything but issue objects, which throws a `TypeError` saying so rather than letting a form show `undefined`. A child that is no validator of this package is the same mistake, and is refused when the composer is created (`runOf` in `core/child.ts`), by the name of its argument: `shape.name`, `item`, `options[1]` of a `union`, and `getter()` of a `lazy` when its getter is first read. That covers a factory given where its validator belongs, `object({ name: string })`, a function written by hand that `validator()` was not given, and a validator another copy of the package made ([Dependency model](#dependency-model)). Until [One pass](#one-pass) a factory could only be told when the schema ran: it is a function too, called with the input as its options it returned a validator, and telling it from a validator when the schema was made was taken to need a mark on every factory, set when its module loads, the side effect [Tree-shaking is a contract](#tree-shaking-is-a-contract) forbids. What that did not weigh is that the mark belongs on the validator, which a factory sets when it is called and not when its module loads: the run a validator carries is that mark. So the test of what a child returned, about 125 bytes gzipped in each composer, is gone from them. TypeScript rejects a factory given as a child, so this is for schemas written in JavaScript or through a loose type. What is still tested when it is read is what a function given to `validator()` returns: a result is an object that passed or one that holds a list of at least one issue, so nothing, a value given back as it is and a failure without its issues throw a `TypeError` that says to return `pass(value)` or `fail(issue)`. It no longer names the place of the child in the input, as the composers' test did, since `validator` is not told where its value sits. An empty list was taken as a result until the audit after 0.4.1 found that `object` and `array`, which gather their children's issues, then found none and passed: `object({ password: bad })` gave `{ ok: true, value: {} }` for a `bad` that returned `{ ok: false, error: { issues: [] } }`, while `assert` and `is` already named it; `ok` is read as true or false and not compared, since a result written by hand with `ok: 1` passed before and `is` already allows for it, and no issue is inspected, which is what `fail()` is for. When a callback throws while the result of a sibling is pending, as a child of `object` may after an asynchronous one, the rejection of that result is handled before the exception propagates (`wait` in `core/wait.ts`, and for the checks of one validator `core/check-run.ts`): nothing waits for it any more, and unhandled it is reported apart from the exception and ends a Node.js process by default. That code arrives only with what can wait, so a leaf carries none of it. Code inside the input is treated as a callback too: reading a property runs a getter, and a `Proxy` runs a trap, and an exception from either propagates rather than being reported, which would take a `try` around every read in `object`, `record` and `tagged`. `objectLike` is the exception, since it exists for values that carry code: it reads each listed property as `input[key]`, so an inherited one, a non-enumerable one or a getter counts, and a read that throws is an `invalid_value` issue with `params.unreadable`. It is a validator of its own and not an option of `object`, so `object` carries none of it, and there is no strict or loose `objectLike`, since the keys of an instance and its prototypes are not a list a schema can be strict about. Data parsed from JSON carries no code, so validation never throws for it. The one place it could is recursion, since each level of nesting is a level of the JavaScript stack: `lazy` is the only way a schema refers to itself, so `lazy` alone counts. It keeps one module-level count of the `lazy` levels open, in `core/run.ts`, incremented on entry and decremented in a `finally`, which a result that waits carries into each continuation as it carries the validation (`context`), and fails with `too_big` and `{ type: "depth" }` past `maxDepth` ([Depth across awaits](#depth-across-awaits)). A second, kept in the validation, counts the calls of each `lazy` in it, keyed by the `lazy`, from the call from outside until its result settles, the continuations after its awaits included; `context` captures the validation running when a result starts to wait and restores it in the continuation, so the count lasts the whole validation, whether or not a `lazy` call is open, and fails with `too_big` and `{ type: "calls" }` past that `lazy`'s `maxCalls`, so work that multiplies with each level, as in a recursive `union` of objects, stops after a bounded number of calls. The levels open are never fewer than the `lazy` calls on the stack, since a continuation starts from a shallow stack with only the levels that were open at its await, so the count bounds what can overflow as a count of the calls on the stack did. It bounds the stack only while a level costs a number of frames the input does not choose, so `union` tries its options in a loop: tried by one call inside another, every option that failed stayed on the stack while the next ran, and a recursive union of twenty options overflowed it at 120 levels, inside the default of 128, on 3 kB of valid input, found by the audit of 0.3.0. What a level costs is still the schema's, and what a stack holds the runtime's, so the default is a margin and not a guarantee. Measured on 2026-10-05 with the lazy limits lifted, a recursive `union` of objects overflowed near 730 levels on a page in Chromium, 660 in Firefox and 2,600 in WebKit, and in a worker near 260, 330 and 2,600: twice the default at the least. A schema of seven composers and three checks at each level threw for valid input 126 levels deep on its first call in a Chromium and a Firefox worker. Lowering the default to 64 was weighed and rejected: it would refuse valid deep data in every runtime for a schema nobody has written. The docs say a worker has half the stack and such a schema lowers `maxDepth` there, and `tests/browser/recursion.spec.ts` holds the default in each engine, on a page and in a worker, so a change that adds frames to a level fails there first. It bounds asynchronous recursion too, cyclic input included, and with it the length of every issue's path. No composer takes a depth parameter or holds state. Size is a separate matter that the docs leave to the consumer: nothing here caps how much flat input is checked. That rests on the work of a flat input growing with its bytes, which holds for JSON and not for a value received by structured clone, such as `event.data` from `postMessage`: it keeps a sparse array's length and the same array at many places, so a 28-byte message held an array of 10 million holes that `array` took 14 seconds over, and 5 KB held 10 million items through shared arrays. A collection's `max` bounds both, since it is checked before any item, so the docs say a structured-clone value needs it whatever its size. Rejecting a hole was weighed and left out: it would change the documented treatment of holes, which JSON never produces, and it would not bound the shared arrays, which only `max` does.

`is(validator, input)` is the boolean projection, and does not narrow. A guard typed `input is T`, with `T` what the validator produces, would be false for every validator that produces another value than it was given, a coercion, a `transform` or `json`, which can say a string is an object. A guard typed by what the validator accepts, `input is InferInput<typeof validator>`, was built for 0.4.0 and taken out before the release. It is true of a value that passes, and a predicate is read both ways: TypeScript also takes a value that fails to be not of the type. `string({ min: 3 })` refuses `"ab"`, so after a failed `is` a `string` was narrowed to `never` and a `string | number` to `number` while it held text, which compiled and was wrong when run. A one-sided guard is not something the language has.

### Depth across awaits

`maxDepth` counts the `lazy` levels open where a value is validated, whether or not they are still on the stack: `context` in `core/run.ts` captures the count when a result starts to wait and restores it in the continuation, beside the validation, so a level opened before an await is still open after it, and an asynchronous recursive schema stops at `maxDepth` as a synchronous one does. Each branch carries its own count, so the siblings of an `object` and validations that run at the same time do not add up. A validation made from a callback the consumer wrote starts with the levels open where the callback runs, as it always did on the stack, and a validator written by hand that awaits on its own is not seen, as for the counts of calls.

The reason is the issues. Each issue holds its full path, a segment for each composer above it, so a failing value with a bad field at each of n levels holds n issues whose paths add up to about n²/2 segments. The collection limit does not help, since it cuts a list after its issues were built with their paths, which a pending result cannot avoid. Measured on 2026-11-04, on Node.js 24, `lazy(() => object({ bad: string(), next: optional(pipe(unknown(check(async () => true)), schema)) }))` and its shapes in other composers, given 10,000 levels with a bad field at each:

| Shape              | Input  | Before: kept, peak RSS | Now: kept, peak RSS |
| ------------------ | ------ | ---------------------- | ------------------- |
| `object`           | 166 kB | 402 MB, 1,143 MB       | 0 MB, 61 MB         |
| `tagged`           | 244 kB | 402 MB, 1,150 MB       | 0 MB, 61 MB         |
| `tuple`            | 39 kB  | 4 MB, 1,003 MB         | 0 MB, 63 MB         |
| `array` of objects | 186 kB | 9 MB, 1,954 MB         | 0 MB, 65 MB         |

Before, the `object` held about 50 million path segments, and each validation took 2 to 10 seconds; now each stops at 128 levels with 129 issues, in under 20 ms. The cost is that valid asynchronous data deeper than 128 levels fails, as a chain of 5,000 levels with an asynchronous check at each now does, and needs `maxDepth` raised, which takes no stack when each level waits. That is the same rule a synchronous schema already had, and the docs say it.

Rejected:

- Counting only the `lazy` calls on the stack, the rule until this change, which held that `maxDepth` "is not a bound on asynchronous recursion… the count of calls is what bounds it". It did not weigh that issue paths cost memory quadratic in the depth, nor that the collection limit applies only after paths are built: under the default `maxCalls`, 166 kB of input kept 402 MB and peaked at 1.1 GB, and an `array` of objects peaked at 2 GB while it kept 9 MB, measured above. Found by the release audit of 2026-11-04.
- One limit of issues for the whole validation. It was rejected in [The limit of issues](#the-limit-of-issues), since the options of a `union` that then passes would count toward it, and it would not bound the peak either: the issues of pending results are built with their full paths before anything can count them.
- A lower default `maxCalls`. It only scales the quadratic down, 51 MB at 2,000 levels, and it refuses wide valid input, a tree of more nodes than the new default in one validation, which the count of calls exists to allow.
- Changing nothing and documenting the cost. A few hundred kilobytes of hostile input would still end a 512 MB process, which is what the limits of `lazy` exist to prevent, and the docs promised about 10 MB.

## Issues

An issue is `{ code, path, params?, message? }` and nothing else.

- `code` is an open set of strings. The built-in codes are `invalid_type`, `invalid_value`, `invalid_format`, `too_small`, `too_big`, `unrecognized_key`, `invalid_key`, `invalid_union` and `invalid_intersection`; a custom validator adds its own, such as `username_taken`, and callers branch on them.
- `path` is absolute: from the root of what was validated down to the offending value. A validator called on its own reports an issue at its own location (an empty path, or a path relative to its value). Each composer above it pushes the key of the child the issue came from onto the paths reported under that child (`under` in `core/run.ts`), so a path is written from the value outwards, one push for each level, and is turned round once, when the call from outside builds its result (`straighten`). Prefixing every issue's path at every level, as composers once did, copied each path once per level, which cost the square of the depth for each issue, and recursive input chooses the depth: 400 KB took eight seconds. Until [One pass](#one-pass) a composer passed its children the place of the value instead, a chain of segments one link per level, and the inner one wrote each path in full once, which took every composer knowing two ways to be called. So a validator called directly, by a consumer or by a function given to `validator()`, returns paths relative to its input, and `validator()` reports those issues into the validation it runs in, where the composers above place them as any other. No issue is changed after the result is returned. Nothing else edits paths, which is what keeps them predictable.
- `params` holds the facts behind the failure (`{ minimum: 3, type: "string" }`, `{ expected: "string", received: "number" }`), enough to build a message and to branch on.
- An issue held in another's `params.issues`, as `invalid_union`, `invalid_key` and a failed part hold them, keeps the issues behind it only when none of them carries issues of its own (`nested` in `core/result.ts`). Every issue a composer holds passes through it, so issues nest at most three deep. Holding them in full nested them once per level of a recursive schema, which an asynchronous one does 10,000 times, past what a serializer can write, and where levels share a result, as the options of a recursive `union` share the children's through `lazy`, the serialized result doubled with each level: 430 bytes of input, 350 MB of JSON. The cache keeps the work linear; this keeps the result so. A limit of `lazy` found behind such an issue takes its place, so `too_big` with its `maximum` is never hidden.
- `message` is optional. A built-in validator sets it only when the consumer passed a `message` option, and a check only when it was given one. A custom validator can set it when it wants fixed text.
- `params.received` of `invalid_type` names the kind of value, from `typeof` plus `null`, `array`, `date`, `invalid date`, `nan` and `infinity`, and never a class name: naming a class takes reading the prototype's constructor, which every validator would pay for, for a message that tells the reader little. Whether a value is a `Date`, a `Map` or a `Set` is asked by running a built-in method on it, which reads the value's own slot, so one from another realm or without its prototype is recognized, and which throws for a value that is not one. A throw costs far more than the validation around it, so a value that cannot be one is never asked: anything that is not an object, an array, and, when naming a value, an object whose prototype is this realm's `Object.prototype`, as `{}` and `JSON.parse` make it, or that has none, as `querystring.parse` and `Object.groupBy` make it. Until 0.3.0 every value was asked, which did not weigh input that passes, where no limit of issues stops the work: measured on 2026-10-05, on Node.js 24.19, 100 kB of valid `{}` under a `union` of four options took 0.9 s and 1 MB 8.7 s, each option before the matching one naming the object it refused, and `coerceDate` took 1.3 s to read 100,000 dates from text, found by the audit of 0.3.0. They take 30 ms, 0.2 s and 0.2 s. The time was linear, so by [Size](#what-the-package-defends-against) it was the caller's to bound; it was fixed because the constant was about thirty times what the work needs, on ordinary schemas. A `Date` whose prototype was replaced by `Object.prototype` itself, or removed, is therefore named `object`; `date` still accepts it, since only the name skips the question. An object with no prototype was still asked while 0.3.0 was built, to name such a `Date`. That did not weigh that an object with no prototype is ordinary data: 100,000 rows as `querystring.parse` makes them took 1.7 s under a `union` of three options against 77 ms for the same rows as `{}`, found by the audit before the release. An object of a class or of another realm is still asked, which `src/core/result.test.ts` holds, and so is any object given to `map` or `set`, since refusing to ask a plain one there would reject a `Map` or `Set` whose prototype was replaced or removed, which `Object.prototype.toString` tags `[object Object]`: it stays linear, about 15 µs for each value. `date` and `coerceDate` first skip a value that `Object.prototype.toString` tags `[object Object]`, since a `Date` of any realm or prototype is tagged `[object Date]` by its slot unless its class names itself otherwise; a tag can be claimed, so it only ever refuses, and `getTime` decides the rest. The audit after 0.4.1 found 100,000 `{}` under a `union` with `date` took a second; it takes under a tenth of that. `src/core/probes.test.ts` counts the questions that threw.

**Issues never contain an input value.** No `input` field exists, and `params` carries type names and constraint values, never the value under test. Keys are the exception by necessity: a path is made of the input's keys, and `unrecognized_key` names the key in `params.key` as well. This is a privacy invariant, not a default: inputs are passwords and tokens, and an issue is something callers log. Any new rule must keep it, and the unit tests check it per validator.

### Messages are on demand, and the English is separate

Text is not built when an issue is created. `formatIssue(issue, messages?)` builds it from a message map, taking the first of: the issue's own `message`, an entry for its `code` in the map, the map's `default` entry, then the generic "Invalid value". The map defaults to `englishMessages` for `formatIssue`, `flatten` and `standard`, and to none for `assert`, as below. `flatten` groups formatted messages by path for forms. An entry of the map must be text or a function that returns text: anything else, such as a translation lookup that missed or an entry that is a group of translations, throws a `TypeError`, as a validator's own `message` function does, rather than reaching a form as `undefined` or `[object Object]`. That costs `formatIssue` 45 bytes gzipped, for the test every validator already carries.

The built-in English wording is `englishMessages`, a map in its own module, which makes rewording and localization the same operation: spread `englishMessages` and override some codes, or write a whole map. Until 0.4.0 `formatIssue` and `flatten` required it, so that a forgotten map could not word every issue "Invalid value", and a program that words its own issues did not bundle about 1.7 kB gzipped of English it never shows. That did not weigh that a default of the whole English map does not do the first, and that the import of a map was the one thing the first example of the README had to explain; [0.4.0.md](0.4.0.md#14-words-without-a-map) has the step. So both now default to it, as `standard` did first, and a program that calls either bundles the English even when it passes another map, since the default is referenced: measured with rolldown, `formatIssue` with a map of one entry went from 377 bytes gzipped to 2366, and with `portugueseMessages` from 2542 to 3391. A separate export for each default was rejected, as it was for `standard`: one more name each, for a saving only a program that never shows the English sees.

The default of `formatIssue` and `flatten` is kept out of everything else. The wording itself is `wordIssue` in `messages/word.ts`, which takes the map it is given and no other; `formatIssue` and `flatten` in `messages/format-issue.ts` are it with the default. `assert`, `standard` and the wording of an issue quoted inside another call `wordIssue`, `standard` with a default of its own, so `assert` keeps its empty map and bundles no English through the default, and `messages/word.ts` imports nothing of the English, which would otherwise import it back through `messages/wording.ts`. `assert` was left without the default, as the owner chose on 2026-10-07: its callers are the packages that check a caller's options, which pay most for each byte, as [Who gains from adopting](#who-gains-from-adopting) found.

The wording of each code is also an export of its own, `invalidTypeMessage`, `tooSmallMessage` and the rest, and `englishMessages` is the map of them. A program that can report three codes builds a map of those three and bundles no other wording, where before 0.3.0 the first adopter rewrote them by hand to avoid the whole map, and so kept wording of its own to maintain. They are constants of one module, not a module each: a bundler drops the ones nothing references, and the tables they share stay in one place. The three that quote the issue behind another, `invalidFormatMessage`, `invalidKeyMessage` and `invalidUnionMessage`, take the map in use as a second argument, and the others take the issue alone, so a program can call one directly. Every one is a function, `invalidIntersectionMessage` included, though it reads nothing from its issue: it was text while 0.3.0 was built, which made it the one export a program could not call as the rest, found by the audit of 0.3.0, and changing text to a function after the release would have broken whoever used it as text. Leaving it as text and saying so in the docs was rejected for that reason. Typing all of them with the map, as an entry of a map is typed, made `invalidTypeMessage(issue)` a compile error. Making the map optional on all was rejected: a quoted issue would then read "Invalid value" without a word. `tooSmallMessage` and `tooBigMessage` each word their own direction whatever code the issue has, so a check that reports a code of its own can reuse one.

That split is what keeps validators small (no string per rule) and makes localization a data problem: a map keyed by code. A consumer that never asks for text bundles none of the map, and only the short English of a validator's own Standard Schema, in [Standard Schema](#standard-schema).

### Other languages

A map in another language is a module and an export of its own, as the English is: `portugueseMessages`, in `messages/portuguese-messages.ts`, is the first, in Portuguese as written in Brazil. One is added when someone will maintain it, since wording nobody reads goes stale with every new param. `spanishMessages`, in `messages/spanish-messages.ts`, was added on 2026-11-05, when the docs began to ship in Spanish, by the owner's decision. It follows the Portuguese in every convention, and writes a bound or a step with a decimal comma, as Spain and most of South America do; Mexico and part of Central America write a point, and a program for them overrides `too_small`, `too_big` and `invalid_value`. Rejected: a point, which Spain and most of South America read as a thousands separator, and a map for each region, which would double the upkeep for one character.

- **What every language reads the same is shared.** `messages/wording.ts` holds what is not words: reading a param, quoting the issue behind another, the moment of a date limit, the first ten of a list, and which option of a union the input was meant for. It was inside the English module until there was a second language, and moving it changed no bundle: the English scenario measures what it did.
- **A language words whole sentences.** The English builds "Invalid" and the name of the format; Portuguese cannot, since the adjective agrees with the noun, "URL inválida" and "Endereço de e-mail inválido", so its table holds the sentence for each format. A format it does not know is "Formato cpf inválido".
- **Only the map is exported.** The English also exports the wording of each code, for a program that reports two or three. A second language would add nine names each, and nobody has asked for a part of one, so a program that wants less than the map builds its own from `portugueseMessages.too_small` and the like, which bundles the whole module. The exports are added when an adopter shows the need.
- **What stays English.** The names of types and of parts are data of the issue, the same in every language so a program can test them. A code the map lacks is another matter, below.

- **A map words the codes it lacks, with its `default` entry.** `formatIssue`'s last wording, "Invalid value", was the one text no map could change, so a program in Portuguese showed English for a custom check that carried no message. An entry of the map is the only place that reaches `flatten`, `assert` and `standard` without a new argument on each, and it is text or a function of the issue as every entry is. Its name can be the code of an issue, and that is harmless: an issue coded `default` with no entry of its own is worded by it either way. `portugueseMessages` has one and `englishMessages` does not, since the last wording is English already and its map stays the nine codes its tests and adopters count. It cost no budget.

It measures 2.53 kB gzipped with `formatIssue`, where the English measures 2.33: the sentence for each format costs what the English saves by building it.

### One validator's own wording

A map words every issue of a code alike, which is wrong for a form where one field needs its own sentence. So every validator takes a `message` option, a string or a function of the issue returning one, and every built-in check takes a message as its last argument:

```ts
string({ min: 3, message: "Pick a longer name" });
email({ message: (issue) => t("errors.email") });
startsWith("ab", "Must start with ab");
```

The option words every issue the validator reports itself, every issue one of its checks reports without a message of its own, and none a child reports, so `object({...}, { message })` words an object that is not an object and leaves each property's issues to that property. A check takes its validator's wording because a field's sentence is meant for the field: `string({ message: "Invalid username" }, pattern(/^\w+$/))` would otherwise show a user the regular expression. A check that needs a sentence of its own is given one, and keeps it. A function is called when the issue is reported, so the issue carries text and stays plain data. It is given the issue as its validator reports it, with a path relative to that validator's value: a validator runs without knowing where its value sits, and the composers above write their keys onto its issues afterwards, so the full path does not exist yet. Passing it would take telling every validator where its value sits, a cost every validator pays, for a sentence that is written where the field is already known. The order of [`formatIssue`](#messages-are-on-demand-and-the-english-is-separate) is unchanged, since an issue that carries a message is worded by it first. There is no message per option, such as `min: [3, "Too short"]`: it would make every option a union and every validator heavier, and a constraint that needs its own wording can be written as a check, which takes one.

## Sync until proven async

There is one implementation of every composer, not a sync one and an async one. A validator is synchronous exactly when everything it runs is.

A run returns its value, the mark of a failure, or a `Pending`, a value that waits (`core/wait.ts`), and stays synchronous while nothing is a promise. A composer is written once: it runs its children, and if any gave a value that waits the whole result waits, otherwise it is returned directly. The composers do not import the code that waits (`wait`, `after`, `join` and `settle`). It arrives with what can wait, which is `check`, `checkFields`, `contentType`, `validator`, `transform`, `lazy` and `encode`, as `w` on the run or the runner that brings it, and a composer asks its children and its checks for it (`toolsOf` in `core/child.ts`), so a schema in which nothing can wait carries none of it. A value that waits is told by a private field and not by a `then` method, so an input that is a thenable is never taken for one. Nothing is exported under the name `then`: a module namespace with an export called `then` is a thenable, and importing it can hang in some loaders.

### The types say which

`Validator<T>` returns a result directly. `AsyncValidator<T>` returns a result or a promise of one. A composer's return type is computed from its children by `Composed`: `Validator` when every child is a `Validator`, `AsyncValidator` as soon as one is not. So `object({ name: string(), taken: asyncRule })` is an `AsyncValidator`, and the compiler makes the caller `await` it, while `object({ name: string() })` stays directly readable.

`AsyncValidator` is honestly a result or a promise, not always a promise, because a composer holding an async child can still answer at once for input it can reject without running it: `optional(asyncRule)` given `undefined`, or `object(...)` given a non-object. Promising a `Promise` there would be a lie, and code that chains `.then` on it would break. `await` handles both, so that is the documented contract.

Results keep the order of the children, never the order in which promises settled, so issue order is deterministic. Any callback that returns a thenable counts as async; nothing inspects the function itself, because guessing from `fn.constructor.name` fails silently when a function is wrapped.

`is` accepts only `Validator<T>`, and throws a `TypeError` naming the fix if a validator turns out to return a promise anyway (the type system prevents this unless the type was cast away). It abandons that promise so a later rejection is not reported as unhandled.

## What a function cannot do

To the composers of this package a validator is opaque: a combinator runs it and reads what it produced, and nothing else. Three things the previous, class-based design did follow from that, and are done differently here. A validator can be read since [A validator can be described](#a-validator-can-be-described), and none of these was changed to read one: each is still the shorter thing to write, and [0.4.0.md](0.4.0.md) leaves open whether `tagged` also takes a list.

- **Tagged unions take a record.** `tagged(key, { click: object(...), key: object(...) })` reads the tag from the input and routes by it, because a variant cannot be asked which tag it accepts. The tag is added back to the output so the type is a proper tagged union, and the variants do not repeat it.
- **Shapes are plain objects.** Extending is spread and omitting is destructuring, and `extend` and the others of [Objects made from an object](#objects-made-from-an-object) do the same for a validator. `partial(shape)` wraps each property in `optional` and returns a new shape. There is no `required`, since it would have to unwrap `optional`.
- **Defaults belong to `optional`.** `optional(validator, value)` replaces `undefined` with the value, and the output type loses `undefined`. There is no separate `withDefault`: a default is what an optional value is when it is absent.
- **Recursion names its own type.** `lazy` looks a validator up on first use, and the variable that holds a recursive validator carries an explicit type annotation, because TypeScript cannot infer a type that refers to itself.

Structure is checked before content. A collection whose size is wrong fails at once without validating its items, and a tagged union with a missing tag fails without running any variant, so hostile input is rejected before it is worked through. Every other check still reports every problem it can find.

## A validator can be described

Until 0.4.0 a validator could only be called. The roadmap had JSON Schema generation and `pick`, `omit` and `required` under Not Planned, because "functions cannot be introspected" and a class hierarchy cannot be tree-shaken. That compared two designs and did not weigh a third, a function that carries a description of itself as plain data, read by a function imported on its own; nor that the tools of a language model and the body of an HTTP API are declared as JSON Schema, so a library that cannot produce one is not chosen for either. [0.4.0.md](0.4.0.md#2-a-validator-can-be-described) has the comparison that showed it.

Every factory records what it made with `toValidator` in `core/make.ts`, and `describe(validator)` in `core/describe.ts` reads it:

- **One property on the function, `~description`.** Not a `WeakMap`, and not a key of one copy as the run is kept under: two minors of this package can be installed at once before 1.0, as [Dependency model](#dependency-model) says, and either would make a validator of the other copy unreadable, where a property named by text is read by any copy. So a copy reads what another made, writes it as a JSON Schema and calls it; what it does not do is run it as a child, which [Dependency model](#dependency-model) explains. The name starts with `~` as Standard Schema's does, so it sorts after a function's own members and is not taken for one. It is set when a validator is made, never when a module loads, so [Tree-shaking is a contract](#tree-shaking-is-a-contract) holds.
- **Plain, frozen data: `kind`, `options`, `checks`, and the parts of that kind.** `options` is the copy `split` makes, frozen there, so it is what the validator reads and no second copy is made. The freeze is shallow: a value nested in an option is the caller's. The one exception is the range of a `clamp`, which `number` copies and freezes when it is made, so the description gives the range that runs. A wrapper that takes no options and no checks, such as `optional`, has neither key.
- **A child is the validator, not its description.** Described on demand, a recursive schema is read one level at a time, and nothing is built for a consumer that describes nothing. `lazy` gives its getter and does not call it.
- **A shape is recorded as it was read.** `object` and `objectLike` read each validator of a shape once and run the one they checked; spreading the shape again for the record read a getter twice, which the test of that promise caught. `tagged` records the table it made. An object says how it treats the keys its shape does not list in a part, `unknownKeys`: absent for `object`, which drops them, `"strict"`, `"passthrough"`, or the validator `objectWithRest` was given. Beside it, `way` holds the code that does it, which a reader does not interpret: it is what lets the reshapers and `encode` make an object of the same kind, while `object` imports none of the three. Until [One pass](#one-pass) `unknownKeys` was an option of `object`, read among `options`.
- **Every format is kind `"format"` with its name in `format`**, `email`, `url`, `port` and a factory made by `format` included, as every one reports `invalid_format` with `params.format`. A kind for each would let a format a consumer names `string` be taken for the built-in. `guard` is `"guard"` with `expected` for the same reason.
- **A built-in check is described too**, by `rule`, or by `unique` itself, which adds the function it compares by as `by`, with the `code` and `params` of its issue, which already say what it requires: `{ format: "regex", pattern }`, `{ format: "startsWith", value }`. So a reader finds a pattern or a multiple without a table of checks. A check made by `check` has none: its test is a function, and to a reader a rule that cannot be read is what matters. A validator made by `validator` has none either, for the same reason.
- **What `standard` returns carries the description of the validator it wraps**, since it behaves as that one.
- **What `meta` returns carries that description with a `meta` part added**, a frozen record of the keys it was given over those of a `meta` already there, or `{ kind: "meta", inner, meta }` for a validator that has none. It is a new function, made by `sameAs` in `core/make.ts`, which carries the run of the validator it is given, so a composer around it runs that validator as it would without the `meta`. A reader that does not know `meta` reads the object, the string or the `lazy` it describes as before, which is why it is a part and not a kind of its own. It keeps a `~standard` the validator had, so a Standard Schema stays one. Rejected: a `description` option on every factory, which every validator would carry for the few that are described; and writing to the record of the validator given, which would change a validator its caller may share.
- **The parts are typed `unknown`.** A union of one interface for each kind would say more, and would make every part's name and type a signature the moment it ships. They are named in the validator reference, and typing them is additive.

Measured with rolldown, minified and gzipped: a lone `boolean()` went from 1199 to 1238 bytes, 3.3%, and the object of three fields from 5477 to 5596, 2.2%, under the 5% the spec allowed, and no size budget was reset. The committed build and this one, run in turn, validate at the same speed: the record is made once, with the validator.

`src/core/describe.test.ts` holds a case for every export of the package and fails when an export has none, so a factory added later cannot go undescribed.

Rejected: a registry, above; describing children when the parent is made, which builds a tree nobody may read and cannot end for a recursive schema; and a method on the validator, which is the class the package does not have.

### Objects made from an object

`pick`, `omit`, `required` and `partial` given a validator read the `shape`, the `options`, and the `unknownKeys` and `way` an object describes itself with, change the shape, and make the object again with `objectOf` (`composition/reshape.ts`). What they return is therefore an object of the kind they were given, like any other, described and derived from again, and none of them is a second implementation of one.

- **Only a validator `object`, `strictObject`, `looseObject` or `objectWithRest` made, in this copy of the package.** `objectLike`, a wrapper around an object, a validator written by hand and an object another copy made are a `TypeError`. Reading through a wrapper would have to decide what a `transform` around an object means once a property is gone.
- **An object with checks is refused.** A check reads the whole object, so it may read a property the new shape lacks or holds otherwise. Kept, it fails every value or throws; dropped, the new object accepts what the first was written to refuse, and nothing says so. So each takes a `message` and then checks, and the caller gives the new object the checks it needs. Without a `message` of its own it keeps that of the object it came from. How it treats unlisted keys is not theirs to change: a strict object picked from stays strict, and an object that must treat them otherwise is made from the shape.
- **A key the object does not have is a `TypeError`**, as an option a factory does not read is: it is a misspelling, and would otherwise pick nothing.
- **`required` undoes `optional` and `nullish`, and nothing else.** `optional` becomes what it wrapped, default gone, and `nullish` becomes `nullable`. A property that accepts `undefined` another way, `unknown()` or a `union` with `literal(undefined)`, is kept, and for the second the type `AllRequired` says more than is true. Wrapping every such property in a rule against `undefined` was weighed and left out: it would add a validator around properties that need none, for a shape nobody has asked about.
- **`extend` spreads the shape.** `extend(validator, shape)` makes an `object` of `{ ...old, ...shape }`, so a property of the same name replaces the old one in its place, as spreading two shapes does. It was under Not Planned as spreading a shape; what that did not weigh is what `pick` and `omit` were built for, that a module exports the validator and not its shape.
- **What they make has no `meta`.** They read through it to the object, and a title or description written for that object is rarely right for the new one.
- **The types work on the output**, `Pick`, `Omit` and the two mapped types of `Infer<typeof validator>`, since the shape's type is gone from a validator's. `Reshaped` keeps a synchronous validator synchronous; one that was asynchronous stays typed so even when the property that waited is left out.

### JSON Schema

`toJsonSchema` (`interop/json-schema.ts`) walks a schema with `describe` and writes draft 2020-12. It is one module and one export, so only a consumer that asks for a schema bundles it: 5060 bytes gzipped with an `object` of one string, about 2.2 kB above that object alone.

- **One promise: a value the validator accepts passes the schema.** A schema says less than a validator checks, so it may accept what the validator refuses, never the reverse. On the output side a default of `optional` and a value of `fallback` are taken to pass the validator they are given to, which neither is checked for: `optional(string({ min: 3 }), "")` produces text its output schema refuses. Writing the default beside the schema was rejected, since one that comes from a function, as every array or object does, cannot be read without calling it; a default its own validator refuses is a mistake in the schema. The other exceptions are stated in the public page and are all clean-up: `trim`, `case` and `clamp` are written as the value is after cleaning, and a length counts UTF-16 units where JSON Schema counts characters. Writing clean-up options loosely, without `maxLength` under `trim`, was rejected: a form or a tool would lose the limit for the sake of text padded with spaces.
- **The input side by default.** What a request body or a tool call must satisfy is what the validator accepts. `io: "output"` writes what it produces. They differ at `optional` with a default, the `coerce` validators, `transform`, `pipe`, `json`, `searchParams` and `fallback`.
- **What cannot be written throws**, naming the part and its place, and `unrepresentable: "any"` writes `{}` there and leaves a check out. Writing it loosely by default was rejected: a schema would be weaker than its author believed with nothing to say so.
- **A format is written under JSON Schema's name where it has one, and with none otherwise.** A format is never a reason to throw. Until the audit after 0.4.1 a format JSON Schema has no name for was written under its own, `"format": "phone"`, on the reasoning that `format` is an open vocabulary and a reader ignores a name it does not know, so the name was honest and harmless. That did not weigh that Ajv, the most used reader, does not ignore it: in its default strict mode `new Ajv()` with ajv-formats threw "unknown format" for `phone`, `slug`, `hex`, `ulid`, `semver`, `cidr`, `mac`, `jwt`, `cuid2`, `nanoid`, `creditCard` and every `format()`, so a schema with any of them could not be used at all there. Leaving the name out only accepts more, which the promise allows; writing a `pattern` where one describes a format whole was weighed and left for when someone asks, since it would be a second definition of each format to keep in step with the first. The input of `email` and `domain` is written with none: it may be internationalized, which `email` and `hostname` refuse, and `idn-email` and `idn-hostname`, written there until the audit after 0.4.1, are not in ajv-formats, so Ajv in its default strict mode refused to compile any schema holding an `email`. Writing them anyway was rejected because a schema that fails to compile in the most used reader is worse than one that checks less; the output, always ASCII, keeps `email` and `hostname`.
- **A step of `multipleOf` is written only when binary floating point holds it exactly**, an integer it holds as written or a fraction whose denominator is a power of two, such as `0.25`; `1e23` is held as `99999999999999991611392`, so a reader found `3e23 / 1e23` to be `3.0000000000000004` and refused `3e23`, which the check accepts, found in review of the audit fixes. The check compares decimals, so `0.3` is a multiple of `0.1`; a reader divides in binary, where `0.3 / 0.1` is `2.9999999999999996`, and Ajv refused `0.3` and `0.7` with a step of `0.1`, and `1.13` with `0.01`, in both drafts, found by the audit after 0.4.1. Leaving the step out accepts more, which the promise allows. Writing every step, as before, was rejected by the rule of [When a finding is a blocker](#when-a-finding-is-a-blocker). One gap is left, by the owner's decision of 2026-11-04: above 2^53 a number is not the integer its decimal spells, so with an integer step a reader can still refuse what the check accepts, as it does `20054952883093950` with `multipleOf(5)`, finding a quotient of `4010990576618790.5`. It is documented on the public page, beside Ajv's misreading of a quotient of `1e21` or more. Rejected: writing only `1` and the fractions binary holds, which cannot disagree and drops steps such as `5` and `100` from every schema for integers JSON already cannot carry exactly.
- **A definition for each `lazy`, keyed by its getter.** The getter is the one thing that stays the same in a schema built anew at each level, `lazy(build)` inside `build`, which is written as one definition. The two other keys tried, the `lazy` itself and what its getter returns, are new at each level there and never met twice. A getter written where the schema is built, `lazy(() => build())`, is new each time as well, and no key is left: it is told as `audit` tells it, by its getter, called a second time, making `lazy` parts the first call did not, and more than 64 such definitions open one inside another throws, where it would run out of stack. Until the audit after 0.4.1 any 64 open definitions counted, so a finite chain of 65 distinct `lazy` parts built once threw for a schema that validates.
- **What `meta` says is written on the part it is given to**, spread over the schema of that part under JSON Schema's own keywords, `title`, `description`, `examples` and `deprecated`, so beside a `$ref` or an `anyOf`, which draft 2020-12 allows. Draft-07 ignores every keyword beside a `$ref`, so there a reference is wrapped in an `allOf` before anything is written beside it, a default of `optional` too, found in review. It is written on both sides, since the input and the output of a value are the same value. With an `object` of one string whose property has a description it is 5782 bytes gzipped, 423 above `toJsonSchema` alone. Each example must be a JSON value, and `meta` copies it as it checks it: a JSON Schema is JSON, and a `bigint` in one made `JSON.stringify` of the schema throw, found in review.
- **Two drafts.** `target: "draft-07"` writes a tuple's items under `items` and its rest under `additionalItems`, definitions under `definitions`, and no `contentSchema` for `json`, which that draft does not have, so what `json` parses is not written and cannot make it throw. Leaving it out only accepts more, which the promise allows. `title`, `description` and `examples` are the same in both, `deprecated` is a word draft-07 does not know and a reader ignores, and a keyword beside a `$ref` is ignored by a reader of draft-07. Another target, such as `"openapi-3.0"`, throws, as Standard JSON Schema asks of a draft a library does not write. Draft-07 is what the AI SDK asks for.
- **A `codec` is written as its `input`**, what is sent, and as its `output` with `io: "output"`.
- **`literal(undefined)` in a `union`, and `undefined` in `oneOf`, are left out**, since they say a value may be absent, which an object says by not requiring the property.

Checked once against Ajv 8 in draft 2020-12 mode, outside the suite since it is a dependency the package does not have: 17 schemas and 68 values, objects, bounds, checks, tuples, records, unions, a tagged union with a strict variant, a recursive tree and formats, and the schema and the validator gave the same answer for every one.

Adding the two grew the bundle of every export past its budget, 19810 to 21191 bytes, so every scenario was measured again and every budget reset by the rule of [Tree-shaking is a contract](#tree-shaking-is-a-contract), with a scenario for `toJsonSchema` and one for `pick`.

### Bounds a schema leaves open

Input that passes is validated in full, which [The limit of issues](#the-limit-of-issues) leaves to the caller to bound with a `max` on each collection and a cap on the input. `audit` (`core/audit.ts`) checks that a schema does, by walking its description: none of valibot, zod or yup checks it, and it is a step further along what the package is for rather than a gap it closes.

- **Four rules, each a place where the size of what passes is open, or cannot be told closed**: a collection without `max` or `length`, text without one, a `lazy` whose limits were raised, and a part that cannot be read. The last is a place the audit cannot certify, since a validator written by hand may bound its input or not; it is reported rather than passed, since a check that says nothing of what it could not see reads as a clean bill.
- **A bound before a part counts.** A `pipe` step reads what the steps before it produced, so after a step that bounds its own value, a `string` or a collection with `max` or `length`, a format below, or a wrapper or a `pipe` of one, nothing is reported. That is how `json` and `searchParams`, which read text, are bounded, and with them everything parsed from that text. A collection's `max` or `length` bounds how many items it has and not what each holds, so after it a collection is not reported for its count, while what its items hold still is, unless the first collection bounds its items too or its items are of a fixed size, such as a `number`, a `boolean`, a `date`, a `literal` or a `oneOf`, alone or in `optional`, `nullable`, `nullish`, `readonly` or `meta`. Counting only a bound on the items, as the fix first did, reported `pipe(array(array(number(), { max: 5 }), { max: 5 }), array(array(number())))` as unbounded, found in review of that fix; a fixed-size value counts only as an item, not as a step, so `pipe(number(), transform(…), string())` is still reported. Until the audit after 0.4.1 any bound counted for everything after it, which did not tell a collection's count from the size of what it holds: `pipe(array(unknown(), { max: 1 }), array(string()))` audited clean and accepted a string of 100,000 characters. Keeping that and documenting the blind spot was rejected, since a clean audit is read as every bound being there.
- **Formats are listed by name as bounding their text** where what they accept has a length limit: `email`, `uuid`, `ulid`, `cuid2`, `nanoid`, `ip`, `cidr`, `mac`, `port`, `phone`, `creditCard`, `isoDate`, `hostname` and `domain`. The others, `url`, `hex`, `base64`, `jwt`, `slug`, `semver`, `duration`, `datetime` and `time`, accept text of any length. One made with `format` is reported too, even when its rule limits the length, since the rule is a function the audit cannot read, and even under a built-in name. Until the audit after 0.4.1 the name alone decided, so `format("email", test)` was taken as bounded while it accepted 100 KB of text. `format` records the options of what it makes in a set of the module's own, kept by `meta` and `standard`, which copy a description with its options, so `describe` gives what it gave; a mark in the description was rejected, since it would change what `describe` gives for every format. A new format is added to the list when it bounds its text.
- **A `lazy` is walked at each place it is used**, and not again inside itself, so the same recursive schema under a bounded `pipe` and under an open one is reported at the open one; its raised limits are reported once. A schema built anew at every level, as `lazy(() => build())` builds it, never comes back to a `lazy` already walked, so `audit` throws for it rather than overflow the stack. It is told by its getter, called a second time, making `lazy` parts the first call did not, and it throws when 64 such parts are open one inside another. Until the audit after 0.4.1 any 64 open `lazy` parts counted, which took a finite chain of 65 distinct ones built once, as a schema generator writes, for one built anew, and threw for a schema that validates. A getter that makes new `lazy` parts only on its first call, by keeping what it built, is not told, and overflows the stack as before the throw was added.
- **The path is written as in the errors of `toJsonSchema`**, as text, since the items of an array have no index to write.
- **Not judged:** whether a `max` is small enough. Any number says someone decided, and a default would be a number this package chose for every schema.

Measured with rolldown, an `object` with an `array` of strings audited is 4363 bytes gzipped, and no other budget moved.

### Writing a value back

`codec(input, output, { decode, encode })` (`composition/codec.ts`) is a composer like `pipe` with a function between its two validators, and keeps both functions in its description, so `encode` (`composition/encode.ts`) can run it the other way. A `transform` cannot: its function was written for one direction, and most have no inverse, so a pair is written by whoever knows both. zod 4.1 has codecs for the same reason.

- **`encode` builds a validator the other way and runs it.** It walks the description and rebuilds each composer from its own factory over the encoders of its children, with the options it was made with, so writing back reports issues, bounds them and waits as validating does, with no second implementation of any composer. Two wrappers produce a value their inner part may refuse, and differ: `optional` with a default writes the default back as `undefined` when its inner part refuses it, since only `undefined` produced it, comparing a primitive default and not one a function makes; a `fallback` value its inner part refuses fails, since every input its inner part refuses produces it, and which one was given is not known. A part that produces what it accepts, a leaf, a format, a `guard` or a coercion, is its own encoder: validating the value gives what it produced, which is what it accepts.
- **Checks run on the value as it was given.** A check is written for what its validator produces, which is what `encode` is given, so a composer's checks run on the value once its encoded parts passed, and not on what they wrote.
- **What cannot go back throws**, naming its place, as `toJsonSchema` does for what it cannot write: a `transform` and a validator written by hand. Encoding it as it is would hand a value of the wrong type to whoever reads it next. A codec writes the value back through its `output` first, so a codec inside it writes its own part. An `output` written by hand, with no description, is used as a check only and its `encode` is given the value as it was given, since a codec around such a part is the remedy this rule names and run forward the part may change the value. Any other `output` that cannot be written back, such as a `transform` or an object holding one, throws naming its place, as it does everywhere else. Until the audit after 0.4.1 the value was checked with `output` in the reading direction, which refused what a codec inside `output` produced. The fix for that, falling back to running `output` forward whenever writing it back threw, was rejected in the release audit of the same cycle: `codec(string(), transform(number(), (n) => n * 2), { decode: Number, encode: String })` encoded `42` as `"84"`, which decodes to `168`, with no error, and a `transform` inside an object `output` failed with `invalid_type` instead of the `TypeError` naming it.
- **`json` and `searchParams` read back the text they wrote**, with the validator it came from, so text it would refuse fails rather than going out: a list written as a repeated key that `searchParams` reads only with `repeated`, and JSON of `undefined`, which `JSON.stringify` writes as no text at all. A codec checks its input accepts what `encode` wrote for the same reason. What JSON cannot hold and `JSON.stringify` changes, `NaN` written as `null`, is not refused: it is how JSON is written.
- **Conversions are synchronous.** A `decode` or an `encode` that returns a promise throws a `TypeError`, as the test of a `guard` does: a promise passed on to `output` would be validated as a value, or make the codec wait while its type says it does not. Typing a waiting codec, as `transform` is typed, was weighed and left out: a conversion of a representation does not wait, and a rule that does belongs in a check.
- **The encoders are built on each call**, one for each validator met, cached by validator, so a recursive schema that refers to itself through one `lazy` reuses its encoder at every level, and only a getter that makes a new validator at each level builds one there. Keeping them between calls would take a `WeakMap` at module level, which [Tree-shaking is a contract](#tree-shaking-is-a-contract) admits only where composers need it; building them costs about what making the schema did, and is measured if a caller writes back in a hot path.
- **It bundles every composer**: 8401 bytes gzipped with an object and a codec, against 2598 for the codec alone. Importing each composer only where its kind is met would need a registry, which the package does not have.

### Wrappers that change the type

`brand(validator, name)` and `readonly(validator)` exist for the type they give, and each does as little at run time as that type allows.

- **`brand` returns the validator it was given.** A wrapper would cost a call for every validation and hide the description, so a branded `object` could not be picked from or written as a JSON Schema. The name is read by the types alone. The mark is a property that no value has, `"~brand"`, keyed by the name so two brands add up, and it is a text key and not a `unique symbol` so two copies of the package agree on it, as [Dependency model](#dependency-model) needs. The input type is left unmarked: what is given to a validator has not passed it. `null` and `undefined` are left unmarked too: intersected with the mark they would be `never`, and `brand(optional(string()), "Id")` was first typed as always producing text, where it produces `undefined` for a missing value.
- **`readonly` freezes what was produced and never what was given.** A validator such as `instanceOf`, `guard` or `unknown` produces the input itself, and freezing it would change an object the caller owns, far from where the schema is written, so there the type alone is read-only. It tells the two apart by identity, `value !== input`, which costs nothing. It freezes one level, which is what `Readonly` says, and leaves a typed array, which throws when frozen. A `Map` and a `Set` are typed as the read-only kind, since freezing them stops nothing.
- **`readonly` is described, as `{ kind: "readonly", inner }`**, and `toJsonSchema` writes what is inside it. `pick` and the others refuse it, as they refuse any validator that is not an `object`: reshaping first and wrapping after says the same, and unwrapping it would have to decide whether the result is still frozen.

## Tree-shaking is a contract

The package is `sideEffects: false`, every module is side-effect free at load, and nothing registers itself anywhere. To keep it that way:

- One validator or check per module; a module imports only `core/` helpers and other validators it truly composes.
- No shared mutable state, no module-level registries, no `Object.assign`-style attachment of properties to functions at load. A factory does attach one to the validator it makes, its description, when it is called: see [A validator can be described](#a-validator-can-be-described). The only module-level state is, in `core/run.ts`, the issues reported so far, the validation running now and the count of `lazy` levels open, described under [Results, not exceptions](#results-not-exceptions) and [One pass](#one-pass); in `composition/lazy.ts`, the count a `lazy` made while a getter runs shares, and a count of the `lazy` calls started, which tells a primitive that ends the recursion; the `WeakMap` in `core/field-hook`, from each check `checkFields` made to what runs it; the `WeakMap` in `core/lazy`, from each `lazy` to the validator its getter returned; and the `WeakSet` in `core/describe`, of the options of the formats `format` made. All are created at load without a side effect. No issue is held, the depth is back at zero, no getter is running and no validation is current whenever no validator is running, each validation has counts of its own, so none sees what an earlier one counted, and the maps and the set hold their validators, checks and options weakly, are written only when a factory is called or a `lazy` first runs, and change no function. The two symbols a run and a check's runner are kept under, in `core/run.ts`, are made at load too, by a call marked pure.
- Options are read once when a validator is created, not per call, and defaults are resolved there.
- An export made by a call at load, such as `export const hex = /* @__PURE__ */ formatFactory(...)`, carries the pure annotation on the outermost call, and its arguments make no call of their own: a bundler keeps a call it cannot prove pure, so every consumer would carry it. Rolldown and esbuild both drop an annotated call nothing uses, and the size budgets would catch one that stayed. Any other export is a function or a constant.
- The English wording lives in `messages/english-messages.ts` and is reachable only through `englishMessages`, the export of each code's wording, and the default map of `formatIssue`, `flatten` and `standard`, so a validator and `assert` carry none of it. A validator carries only the pieces of `core/words.ts` that word the issues it can report, the short English of its own Standard Schema ([Standard Schema](#standard-schema)).

`tests/integration/bundle-size.test.ts` bundles small consumer-shaped modules against the built `dist/` and asserts a gzip ceiling for each: one leaf validator, an object of a few fields, messages alone, and everything. A budget that fails means something made a validator a tenth heavier. The shared core, the code every validator carries, is where a byte costs most: it is paid once per validator family a consumer uses, so a helper there earns its place only if nearly every validator needs it. Each budget is what its scenario measured plus 10%, rounded up to ten bytes, so a fix that adds a few bytes passes without touching the test. When one fails on purpose, every scenario is measured again, the budget of each one whose size the change altered is reset by the same rule, the others keep theirs, and the commit says what grew and why. Until 2026-11-06 every budget was reset, which did not weigh that a scenario the change left alone gains the headroom of a new tenth it never measured: resetting them all for the size work of 0.5.1 raised the budget of a lone `boolean` from 2140 to 2290 bytes while its bundle stayed at 2080, so a later change could make it 150 bytes heavier unnoticed.

## Speed

This section is in order of time: what was measured and changed up to 0.5.1, then [One pass](#one-pass), which replaced the core those changes were made in. The names in the first part, such as `call`, `childOf`, `runEach`, `collect`, `chain` and `pathAt`, are of that earlier core, and are kept for what they measured.

Measured against valibot, zod and yup on 2026-10-07, the leaves were within a small factor of theirs and the composers about ten times slower: an `object` of three strings ran 1.1 million times a second where its three leaves alone allow about ten. [0.4.0.md](0.4.0.md#what-the-comparison-measured) has the comparison. Nothing had measured time before, only size, so each of these had been paid on every call without anyone seeing it:

- **Defining every property of an output.** `setOwn` used `Object.defineProperty` for each, so that `__proto__` is data and no setter of a prototype runs: 45% of the time of an `object` of three strings. It now assigns a key the target does not have, its prototypes included, which nothing can intercept, and defines any other. Rejected: deciding it for each key of a shape when the validator is made, which a property added to `Object.prototype` afterwards would defeat.
- **Two maps for each validation**, for the counts and results of `lazy`, which most validations never reach. Each is now made by the first `lazy` that needs it.
- **Asking what a child is, and making it a place, for each value.** `call` looked the child up in the `WeakMap` of composers and was given a new `Place` on every call. `childOf` asks once, when the composer is made, and makes a place for a composer, which needs one, and for any other child only when its result is not one that passed. `object`, `objectLike`, `array`, `tuple`, `set` and `record` use it; the composers of one child, and `map`, `union` and `intersection`, still use `call`.
- **Running checks there are none of.** `finish` returns the value at once without them, where it gathered an empty list through `runEach`, `collect` and `chain`.
- **A list of every result, read a second time.** `settle`, behind `array`, `tuple` and `set`, reads each result as it is returned while none is pending, and from the first pending one starts the rest and waits for them together, as before. The limit of issues counts what was found on both sides of it.
- **A path built with `Array.from` and a length**, 46% of the time of a list of bad items. `pathAt` now makes it with `new Array` of that length.
- **The paths of every object a `lazy` reached.** A `lazy` keeps what it found for each object at each path, so the options of a `union` that reach the same object share it, and it walked each place to its path and made up to three maps for every object, about a fifth of the time of a recursive tree. Since 2026-11-05 it records where it first found each object, in one map for the validation, and makes the paths only for an object found again, which is what they are for; an object found again at the very same place is answered from that record. Measured with `pnpm bench` on Node.js 24.22, three whole runs alternated, a `lazy` tree of 127 nodes went from 0.0095–0.0100 to 0.0132–0.0137 million validations a second, and no other scenario moved. What is left of its time is the full work of each `object` and `array` in it, which have no fast test under a `lazy`; [roadmap.md](roadmap.md#later--possible) has the next step.

[0.4.0.md](0.4.0.md#16-an-ascii-domain-without-the-parser) has why `url()` keeps asking the parser for everything, and why the step was built short of the three times it first asked for.

### One pass

Until 0.5.1 a composer answered input in two ways. A fast test was a validator's answer for input that passes, the value it would produce or a miss, made from the validator's own test. A composer whose children all had one asked those first, and ran its full work, which made a result, a place and a list for each child, only on a miss. It was built from 2026-10-07 for what it measured: an `object` of three strings went from 3.8 to 8.7 million validations a second, an `array` of 100 strings from 0.55 to 2.0, and `tuple`, `record`, `union` and `tagged` by two to five times. [0.4.0.md](0.4.0.md#11-valid-input-without-the-full-work) has the prototype, and why code generated with `Function` was dropped: a Content Security Policy without `unsafe-eval` and Cloudflare Workers refuse it.

What that did not weigh is what it cost everything else, which showed only once all of it was built:

- **Every validator was written twice, in bytes.** A leaf carried its fast test beside its full work, and a composer both ways of running its children and the switch between them. Each later step added its own: the run for an object some of whose properties had no fast test, the lookup of a child's work, the place a composer passed its children. An `object` of three fields was 7260 bytes gzipped, and [The bar for size](#the-bar-for-size) was missed by 1.33 kB.
- **Two answers had to agree**, and where they did not was found one case at a time in review: the test of a `format` and a custom `Symbol.hasInstance` run twice, a getter read twice on a miss, the properties of an object read in two orders, a `union` under a `lazy` that would have counted its calls differently. Each was closed by taking the fast test away from something, so the rules for what had one grew to a page of this document.
- **Invalid input paid for both**, since a miss ran the fast attempt and then the full work from the root.

The owner decided after 0.5.1 to replace both with one pass, and accepted before it was built that valid input through some composers would be slower, for the size.

- **A validator has one run** (`core/run.ts`), which a composer reaches under a key of its own copy of the package. It is given the value and returns what the validator produces, the mark of a failure once it has reported why, or a value that waits. No result, list or place is made for a child that passes.
- **Issues are reported, not returned.** A run that refuses a value reports its issues into the list of the validation running, module-level state that the first issue makes, so valid input makes none. A composer reads how many were reported before and after a child: that tells it the child failed, counts toward [The limit of issues](#the-limit-of-issues), says which issues take the child's key ([Issues](#issues)), and lets a `union` take back what an option reported when a later one passes. The call from outside (`call`) owns the list, builds the result from it and puts back what was there, so a validation made from a callback, or one started while another waits, has its own.
- **What a validator does not use, it does not carry.** The code for checks arrives with the checks ([Checks](#checks)), the code that waits with what can wait ([Sync until proven async](#sync-until-proven-async)), the code that calls a function written by hand with `validator` ([A validator is a function](#a-validator-is-a-function)), the wording of an issue with the validator that reports it ([Standard Schema](#standard-schema)), and each way of treating the keys a shape does not list with the factory named for it: `object` drops them, and `strictObject`, `looseObject` and `objectWithRest(shape, rest)` are factories of their own, where `object` took an `unknownKeys` option until then. Recorded with that option was the rejection of "a separate `objectWithRest`, which repeats `object`". What it did not weigh is that an option is read when the schema runs, so every `object` carried the ways it was not asked for; and the four factories share one implementation, `objectOf`, so nothing is repeated.
- **A run belongs to the copy of the package that made it.** [Dependency model](#dependency-model) has what follows from that.
- **An `object` reads each property as its validator runs, and every property before anything waits.** A way of treating unlisted keys reads them before any property is validated. Until then the full work read every value before any child ran and the fast test read as it went, so the two differed for input whose own code changes it while it is read. There is now one order, the one the fast test had, which the owner chose on 2026-10-07 for its speed and kept for the one pass. Reading before a wait is what is still promised: input that changes while a validation waits is not seen changed. `src/composition/object.test.ts` holds both.
- **Consumer code runs once.** Nothing is run again on a miss, so a check, a `guard`, the test of a `format`, a `transform`, a default and a getter of the input each run once for a value, whether it passes or not. The rules about what had a fast test are gone, with `fast-path.test.ts` and `mixed.test.ts`, which compared the two answers.
- **`lazy` keeps a result by the object and the levels open**, no longer by the path ([What the package defends against](#what-the-package-defends-against)).

## Types

A validator has two types: what it produces, `Infer`, and what can pass, `InferInput`. Until 0.4.0 there was only the first, on the reasoning that every validator accepts `unknown`, which is the honest type of the argument of a function that exists to check unknown data. That is true of the call and was taken to settle the type, and it did not weigh who else asks: a form library does not ask what a validator may be called with, it asks what a value that passes looked like before validation, to type the field that holds it. `optional(number(), 0)` produces `number` from `number | undefined`, and `coerceNumber()` produces `number` from text, and both told Standard Schema their input was `unknown`.

- **The call is unchanged.** `Validator<T, TInput = unknown>` is still called with `unknown`. `TInput` is the type of input that can pass and never a limit on the argument, so nothing a consumer wrote stops compiling and a validator still checks data nobody trusts.
- **A phantom property carries it.** `Validator` and `AsyncValidator` are interfaces with the call signature and `readonly "~types"?: { readonly input: TInput }`, which is never set. Being optional, it leaves any function of the right shape a validator, which an intersection with an object type would not: a function has no property in common with one whose every property is optional, and TypeScript refuses that. The type sits inside an object because read straight from an optional property, `infer` drops `undefined`, and an input type that includes `undefined` is the case that matters most: `optional` with a default was typed as required until the fixture caught it.
- **Every built-in declares it.** A leaf and a format accept what they produce, which `Factory` assumes; the `coerce` validators name what they convert from; a composer computes it from its children, as `InferShapeInput`, `InferTupleInput` and `InferTaggedInput` do. `fallback` accepts `unknown`, since it never fails. `searchParams` accepts text or a `URLSearchParams`, typed `string | Iterable<[string, string]>`: naming `URLSearchParams` would put a global of the runtime in a public signature, which a consumer compiling without the DOM or Node.js types could not resolve, and `hub check` refuses it. The type is wider than what passes, which a type of input may be. Clean-up is not a difference in type.
- **A validator written by hand has `unknown`** unless it says otherwise, so no existing one changes meaning, and `Validator<number, string>` is how one says it. `validator()` reads it from a function typed so.
- **`standard` reports it.** `is` does not narrow to it: see [Results, not exceptions](#results-not-exceptions).

It is types only: no validator grew a byte. `Infer<typeof validator>` reads the output type from either flavor, and `InferInput` the input type.

The types that compute a composer's return type and that a consumer may need to name, such as `Composed`, `AnyValidator` and `InferShape`, are exported, so a library that exports a validator can name its type. A helper type that only shapes a signature, such as `Simplify` or `UrlParts`, may stay internal: `hub check` allows it, the reference lists it under its internal types, and TypeScript writes it out in a consumer's declarations, which a generic wrapper around `url`, `optional`, `tagged` or `object` emitted without an error. The ones a consumer is expected to write are `Validator`, `AsyncValidator`, `Check`, `AsyncCheck`, `Message`, `Infer`, `ValidationResult`, `ValidationIssue`, `Messages` and the options interface of each validator; the docs present the rest as the machinery of signatures, and a change to them is still a change to the API.

An `object` output type is built with `Simplify`, so hover text shows one object, and a property whose validator can produce `undefined` becomes optional in it.

`tests/integration/consumer-types.test.ts` compiles `tests/integration/fixtures/consumer.ts` against `dist/index.d.ts` with `skipLibCheck: false`. The fixture uses `@ts-expect-error` for lines that must fail, so a declaration that becomes too permissive breaks the test as surely as one that becomes too strict. Unit tests import from source and cannot see what a consumer sees; this is the test that can. It needs `dist/`, which `hub test` builds first. `tests/integration/doc-examples.test.ts` holds the public docs to the same declarations: every TypeScript block of `README.md` and the pages directly under `docs/` is compiled as a module of its own, with the same settings, so an example that stops compiling fails the suite. A fragment that uses a name from the text around it, such as `input`, finds it in a short list of global declarations in the test, and a block that imports nothing is given an import of every export.

The runtime code is checked against the runtimes it promises, not against Node.js alone. `tsconfig.json` is a solution file that `tsc -b` follows to two projects: `tsconfig.src.json` checks `src` with the ECMAScript library and `src/runtime-globals.d.ts` only, which declares the members of `URL`, `URLSearchParams`, `TextDecoder`, `atob`, `Blob`, `File` and `FormData` the code uses, so a global one runtime lacks, such as `Buffer` or `document`, fails to compile; `tsconfig.test.json` checks the tests and `src/test-utils.ts` with Node's types. The two share `src` without referencing each other, since a reference would want the shared files from the other project's output, which `noEmit` never writes. The build reads `tsconfig.src.json`, since `tsdown` refuses a config with references.

### What the types cost a compiler

Nothing had measured what a schema costs to type-check, only what it costs to bundle and to run. Measured on 2026-10-09 with TypeScript 7.0.2 on Node.js 24.14.1, `--extendedDiagnostics`, the median of three runs: a file of 100 and of 400 distinct schemas, each an `object` of ten properties holding a nested `object`, an `array`, a `tagged`, a `record` and an `optional`, with its `Infer` and `InferInput`, a `pick`, a `partial` and a function that reads the inferred value. Each further schema costs 2,069 type instantiations and 5.7 ms of checking, and 400 of them check in 2.1 s. The same shapes written for zod 4.6.5 cost 993 instantiations and 3.7 ms each, for zod/mini 1,247 and 4.1 ms, and for valibot 1.5.0 2,100 and 7.1 ms. The cost grows in a straight line with the number of schemas, so there is no shape among these that the checker struggles with, and nothing was changed for it. It is one machine and one shape of schema, and the ratios are what to read. A change to `Composed`, to the overloads of a composer or to `InferShape` is measured the same way before and after; the harness is not in the repository, since it installs the other libraries.

## Dependency model

The package has no dependencies, and it must never depend on another workspace package: workspace packages depend on it, and a cycle has no build order.

A package that validates with it declares it as a regular `dependency`, installed from its release as `docs/specs/packages-lifecycle.md` asks of any public package that depends on another.

Until 0.3.0 the recorded choice was the opposite: a `devDependency` that the adopter's build inlined, declared in `codenhub.bundled`, so its consumers never saw this package or its version. That bought isolation from an API that was still changing. It did not weigh the package's purpose, which is to be the one place validation's edge cases are handled, once more than one package relies on it:

- **A fix did not reach anyone by itself.** Inlined code is a copy. A fix here reached an application only after every package that inlined it was rebuilt and released, where a dependency range delivers it with one update.
- **The core was paid once per package.** An application using several such packages carried a copy of the shared core in each, about 1.2 kB gzipped per copy at 0.2.0, and more for each validator they had in common. As a dependency the application's bundler keeps one.

The cost of the reversal is that this package's version is now visible to an adopter's consumers. Before 1.0 a caret range spans one minor, so two adopters on different minors install two copies: adopters move to a new minor together. `codenhub.bundled` remains a rule of the tooling for other libraries; this package no longer asks for it.

**Two copies do not run each other's validators.** Since [One pass](#one-pass) a validator reports its issues into a list its own copy of the package holds, and answers a value it refuses with a mark of that copy. A composer of another copy that ran it would find no issue and take the mark for the value: measured against two built copies while the run was kept under a text key, `object({ name: other.string() })` passed `{ name: 1 }` and gave a symbol back in its place. So a run, and what runs a check, are kept under symbols of the copy that made them (`RUN` and `CHECK` in `core/run.ts`), and what another copy made is refused where it is given, when the schema is created, as a function written by hand is: as a child, as a check, by `pick` and the others of [Objects made from an object](#objects-made-from-an-object), and by `encode`. Until then a composer called any function of the shape, so a schema an adopter exported from one minor could be composed in an application on another. That is given up, for what the code to call an unknown function cost every composer, and it makes the rule above firmer: adopters move to a new minor together. What still crosses copies is what reads a validator or calls it whole: `describe`, `toJsonSchema`, `meta`, `standard`, `assert`, `is`, and the call itself. `validator(theirs)` makes one a child, with its issues at their place, as it does any function, and it is then described no longer. Rejected: keys made with `Symbol.for` and a list shared on `globalThis`, which is state shared between versions whose internals differ, so each minor would have to read what any other wrote; and wrapping what another copy made without being asked, which puts the code to call an unknown function back in every composer. `src/core/copies.test.ts` holds it against a second copy of the modules.

## What adopting costs

The claim that a consumer pays only for what it uses was measured, for 0.1.0, on a real workspace package that validates its own configuration. It took the package as a bundled devDependency and replaced about 80 lines of hand-written checks with eight validators (`array`, `boolean`, `object`, `optional`, `pipe`, `refine`, `string`, `unknown`) and `formatIssue` and `formatPath`. Minified and gzipped, across every entry point and chunk, it went from 5.6 kB to 8.3 kB: +2.7 kB, about +48%. The hand-written checks were about 0.5 kB.

The claim held in the sense that matters for correctness: the built output contained none of the validators the package did not use, no coercion code and no Standard Schema adapter, and `hub check` found no leak. It did not hold in the sense of being small for a package that only checks a few options. Where the bytes went:

- **The validators, about 1.9 kB**, of which about 0.6 kB is the core every validator shares: reporting the received type, building issues, and the sync-until-async plumbing. `string` alone is close to 1 kB because its options are all in one function, so a consumer that uses `min` still carries `pattern`, `startsWith` and the rest.
- **The built-in English wording, about 1.0 kB.** In the first measurement `formatIssue` carried the wording for every issue a built-in can report, and it could not be shaken per code, so a consumer that worded its own issues still bundled it. It is now a separate import, and the same package supplying its own three lines of wording dropped to +1.9 kB (7.6 kB in total, +35%) with none of the English in its build. After the fixes of the pre-release review, which added a few hundred bytes to the shared checks, the same package measures 7.8 kB, +2.2 kB or +39%. The fixes of the second review, chiefly checking when a validator is created that every child is a function, add 0.1 kB more: 7.95 kB, +2.35 kB or about +42%.
- **The consumer's own glue, about 0.3 kB.**

Two consequences follow. First, hand-written checks are still cheaper in bytes for a handful of options, and the package earns its place through consistency and shared behavior rather than size, so "lightweight" holds per validator and not for a package that validates little. Second, inlining copies the shared core into every package that inlines it: an application that installs several such packages carries one copy per package, where a regular dependency would be deduplicated by the application's bundler. Inlining bought isolation from this package's version; 0.3.0 gave it up, as [Dependency model](#dependency-model) records.

The measurements above are of 0.1.0. The migration also exposed three gaps, which 0.2.0 closes: there was no leaf for function-valued options, which `func()` now is; a validator could not carry a fixed message of its own, which the `message` option now does; and the shared core was about 0.6 kB in every consumer. One gap remains by design: a message that needs the offending value cannot be built by a validator, since issues never hold it.

### 0.2.0, measured again

The same package, moved to checks, `func` and `unique`, measures 7.88 kB against 8.04 kB for the same package on 0.1.0, each built file minified with esbuild and gzipped, then summed. So 0.2.0 costs this adopter 0.16 kB less while adding checks, messages per validator and asynchronous checks to everything it uses: the slimmer type naming and the rare constraints leaving `string` pay for the argument handling and check running every validator now shares. That shared core is about 0.65 kB in a bundle with one leaf in it. The fixes of the third review, chiefly rejecting options that are not a plain object, which takes the same test `object` uses, add 63 bytes gzipped to it (`boolean()` alone, 797 to 860 bytes); the adopter was not measured again for them.

Measured again on 2026-10-04, the same way, before the release: 8.90 kB with the package as the fourth to sixth reviews and the pre-release audit left it, 8.98 kB after the first fixes of the final audit, and 9.26 kB after the rest, chiefly the check of option names that every validator now carries, with the names it reads and the error that lists them, and the handling of a pending result when a sibling throws. So 0.2.0 costs this adopter 1.22 kB more than 0.1.0, about 15%, for options and checks that are checked when made, issues bounded in size, recursion bounded in work, and one answer in every runtime. The fixes of the audit before the API freeze add 0.15 kB more: 9.35 kB, against 9.20 kB for `main` before them, both measured the same way on the same day, chiefly from requiring text of every message a function returns and refusing a check's result that is not an issue, which every validator carries, and from `oneOf` refusing a list with a hole or a `Set`. The budgets in `tests/integration/bundle-size.test.ts` were reset from measurement for them (`boolean()` alone, 1064 to 1127 bytes) and hold the line from here.

### 0.3.0, and what a small adopter can expect

[Issue 209](https://github.com/codenhub/codenhub/issues/209) asked for a floor low enough that inlining the package costs a small package about what hand-written checks would. Measured on 0.2.0 with esbuild, minified:

- A lone `boolean()` is 2.6 kB (1.2 kB gzipped), nearly all of it the shared core: argument handling, the check runner, wording and naming the received type.
- The eleven exports the first adopter uses are 10.1 kB (3.9 kB gzipped). The hand-written checks they replaced, rebuilt from the commit that removed them, are 2.1 kB (0.66 kB gzipped).
- Removing three of the checks the core makes of a schema, the 0.1.0 migration errors, the test of option names and the test of what a check returns, takes 7% off that adopter's 10.1 kB. The bytes are in the validators it uses, not in the floor.

So the target is out of reach by about five times, and nothing that keeps the behavior closes it. Two designs that lower the floor were considered and rejected:

- **Lean factories beside the full ones**, taking no checks and no message: 0.6 kB for a leaf and 3.4 kB for a plain object of three fields against 7.2 kB, measured on a prototype. A second family is a second implementation of the same edge cases, and the first adopter, which uses checks and messages, gains nothing.
- **Checks out of every factory, into one composer**, so the runner arrives with the import that needs it. It saves about 2 kB minified, 0.8 kB gzipped, once per application, and only in an application where nothing uses a check or a message, while every check written becomes a longer call. [One pass](#one-pass) got the saving another way, which this did not weigh: a check carries what runs it, so the call is written as before ([Checks](#checks)).

What 0.3.0 does instead is make the cost a shared one and remove what adopters wrote around the package: it becomes a regular dependency, `assert` replaces the throwing helper each adopter wrote, the wording of each code is importable alone, and `objectLike` covers the instances `object` refuses. The 0.1.0 migration errors are gone, and an option 0.1.0 had is reported as any unknown option is: `string()` alone goes from 1787 to 1606 bytes gzipped, `number()` from 1962 to 1864, `array` from 2525 to 2299, and an object of three fields from 5313 to 5076. `assert` with two wordings (2738 bytes) and `objectLike` (2332 bytes) have budgets of their own. Requiring text of what a message map holds, found by the audit of 0.3.0, grew `formatIssue` with a map of your own from 304 to 349 bytes, past its budget, so every scenario was measured again and every budget reset from measurement. Naming a validator that returns no result, found by the audit before the release, grew `array`, `set` and `tuple` past theirs, and every budget was reset the same way.

Hand-written checks stay cheaper in bytes for a handful of options. What an adopter buys is that the edge cases are handled in one place, and what it pays is shared with every other adopter in the same application.

So the cost is accepted, and issue 209 is closed without a lower floor. A package that needs every byte keeps its checks written by hand, and does not adopt this one.

### The bar for size

Recorded on 2026-11-05 by the owner's decision: the size the package holds itself to is that of zod/mini, a library of the same kind, with checks, messages and Standard Schema, not that of valibot. Measured that day with esbuild, minified and gzipped at level 9, on a typical form, a name with `min` and `max`, an email, an optional integer and an array with `max`:

| Bundle                              | This package | zod/mini | valibot |
| ----------------------------------- | ------------ | -------- | ------- |
| The form                            | 7.79 kB      | 6.54 kB  | 1.82 kB |
| With English messages and `flatten` | 9.87 kB      | 6.68 kB  | 2.00 kB |
| A lone `boolean()`                  | 2.08 kB      | 3.08 kB  | 0.76 kB |

- **Valibot is out of reach without dropping guarantees.** Even the lean factories rejected above, 3.4 kB for an `object` of three fields, would be about twice its form, and they keep fewer guarantees than the package does.

### Who gains from adopting

Recorded on 2026-10-05, after 0.3.0 was built, from reading how the workspace packages check their input. It is a finding about fit, and it names no package, as the roadmap does not.

- **A package that checks a developer's options gains little.** Its input is wrong only by mistake, so the realms, prototypes and hostile text this package handles hardly reach it, and its checks are a few `typeof` tests whose review is short. The first adopter's eleven exports are 3.9 kB gzipped against 0.66 kB written by hand. A second package was read for the same move, four fields of an object that may be an instance and about ten one-line argument checks: `objectLike` and `assert` would shorten it, and would give a package with no dependencies its first one, for an estimated 3.5 to 4 kB gzipped. That estimate was not measured.
- **Data from outside the program is where it pays.** Stored state read back with `JSON.parse` and returned as its declared type, and the parameters of a URL, are both in the workspace and both unchecked. Neither package should depend on this one: each should accept a validator from its caller, since the caller knows the shape and only a caller that validates then pays.
- **A structure that is validated and converted in one walk does not fit.** A nested dictionary that is flattened as it is checked, with its own counts and its own refusal of accessors and symbol keys, is a different algorithm and not a composition of validators.

What this changed: `nonBlank()` was added, since requiring text that is not blank without trimming it is what such option checks do and `trim` with `min: 1` changes the value; the errors page shows `assert` keeping an adopter's own wording, with no message map; and the roadmap's direction says who the package is for. What it did not change: the dependency model, and the adopter the package already has.

## Coercion

A coercing validator is a strict validator behind a converter: `coerceNumber(options)` builds `number(options)` once, converts the input, and hands the converted value to it. So the strict validator owns every constraint and every option check, and the coercing one adds only the conversion. Each is its own module and its own export, so a consumer that never coerces does not bundle the conversion code, which is why coercion is not an option on the strict validators.

The conversions are narrow on purpose, because a conversion that guesses turns a bug into a plausible value: no booleans as numbers, no empty string as zero, no free-form dates, no typo read as `false`. What cannot be converted fails with `invalid_type` and `coerced: true` in `params`, and never the value.

## Standard Schema

Every validator a factory makes is a Standard Schema v1 as it is. `toValidator` in `core/make.ts`, which every factory calls on what it makes, gives it a `~standard` (`standardOf`). A check has none: it is given a value already validated and is not a schema. Its `validate` runs the validator and words each issue in a short English: the issue's own `message`, or one sentence for its code with the limit it names, such as "Must be at least 2 characters", and "Invalid value" for what it does not word. Since [One pass](#one-pass) the sentences are not one module that every validator carries. Each is a function in `core/words.ts`, a validator holds those of the issues it reports itself, in `~words`, and adds those of its checks and its children when it is made, so a `boolean` carries the wording of a wrong type and not that of a size or a format. Until then `brief` (`messages/brief.ts`) worded every code in every program, the 1.15 kB of [The bar for size](#the-bar-for-size). A function written by hand has no `~standard`, since no factory made it, and `validator()` gives it one, which words an issue that has no message "Invalid value". A wrapper that makes a new function for a validator (`sameAs`) keeps the `~standard` it had, which is how `meta` keeps the one of a validator `standard` or `standardJsonSchema` made, with its wording and JSON Schema: found in review, where it was replaced.

`standard(validator, messages?)` is the adapter for the rest: it returns a new function that calls the validator and carries a `~standard` of its own, which words each issue with `wordIssue` and a message map, the full English by default, and leaves the validator you gave untouched. It is how a program gets the full English, another language, or a Standard Schema from a validator written by hand.

The types say which is which. A factory returns `Schema<T, TInput>`, or `AsyncSchema<T, TInput>`, which extend `Validator` or `AsyncValidator` and `StandardSchemaV1<TInput, T>`, through `Composed`, `Factory` and `Reshaped`, so a schema is accepted wherever a validator is. `Validator` is still what a validator written by hand is, and asks for no `~standard`; what `validator()` makes of it is a `Schema`. `brand` returns the validator it is given, so it is a `Schema` only when that one is.

- **What step 18 did not weigh.** It measured two wordings for a `~standard` on every validator, the whole English, 2.2 kB in every program, and the issue's code, which a form would show as `too_small`, and dropped both, so every hand-off to a form library, a router or a tool took a `standard` call. A third, a short English that names the limit, was not measured. Measured on 2026-10-08 against the code before it, gzipped: a lone `boolean` grew 507 bytes, the object of three fields 423, `assert` 414 and the bundle of every export 413, as predicted before it was built, and the owner accepted it on that measurement. A fuller short English, with singular units, the units of a limit of `lazy`, the value a `literal` expects and the factor of `multipleOf`, measured 672 bytes on a lone `boolean` and was cut back to the predicted wording.
- **No code identifier in the wording.** `0527af6f` took the checks' wording out of `brief`, which had cost every validator about 400 bytes gzipped, and named a check by its format instead, "Invalid startsWith". That weighed size and not that the name is a code identifier, which reaches a form's user as it is when the validator is passed to a form library, as [the public page](../standard-schema.md) advises: "Invalid regex", "Invalid nonBlank", "Invalid creditCard", found by the audit after 0.4.1. So a check, `regex`, `includes`, `lowercase`, `uppercase` or any name in camelCase, is worded "Invalid value", the brief's own fallback; a format named in one word, "Invalid email", keeps its name. Measured with rolldown on 2026-11-04, gzipped: a lone `boolean` grew 56 bytes, from 1957 to 2013, every scenario that makes a validator 43 to 60, and the bundle of every export 51, inside every budget. Rejected: keeping the names and pointing to `standard` for text a user reads, which leaves the default hand-off showing identifiers; and wording each check in full again, the 400 bytes `0527af6f` saved.
- **Rejected for the types:** `~standard` required on `Validator`, which every validator written by hand, and every function typed to take one, would stop compiling against; the intersection written out at every factory, with no name, which makes every hover longer; and the runtime alone, which leaves a TypeScript caller still calling `standard` to satisfy a library's types, for the same bytes.

The map defaults to `englishMessages`. Until 0.4.0 it was required, as it was by `formatIssue`, so that a forgotten one could not word every issue "Invalid value". That did not weigh that a default of the whole English map does not do that, nor that `standard` is the call made at every hand-off to another library, where valibot, zod and yup ask for no argument at all. The cost is the English in every program that calls `standard`, about 1.7 kB gzipped, even one that passes another map, since the default is referenced: measured with rolldown, an `object` of one string exposed with no map is 5221 bytes gzipped. A second export that defaults the map, leaving `standard` as it was, was rejected: one more name, for a saving only a program in another language that also uses Standard Schema sees. `formatIssue` and `flatten` took the same default in step 14 of 0.4.0, and `assert` keeps its reason, above. Input type and output type are the validator's `InferInput` and `Infer`.

`standardJsonSchema(validator, messages?)` (`interop/standard-json-schema.ts`) is the same adapter with `~standard.jsonSchema` added, from the Standard JSON Schema part of the specification, which `@standard-schema/spec` 1.1 published: `input({ target })` and `output({ target })` call `toJsonSchema` with that side and draft, and pass `libraryOptions.unrepresentable` on. The AI SDK takes any Standard Schema that has it as the input of a tool, and asks for draft-07. It is an export of its own, and not part of `standard`, so a form in the browser, which calls `standard`, does not bundle the code that writes a schema: with an `object` of one string the first measures 7929 bytes gzipped and the second 5513, both with step 11 built; the second was 5221 when step 7 added it, before the steps between grew every `object`. Leaving it to an adapter on the AI SDK's side, `jsonSchema(toJsonSchema(validator), { validate })`, was rejected: every caller would write it again. `meta` given to what it returns keeps its `~standard`, which writes the validator it was given, so `meta` goes on first.

`~standard.validate` is synchronous for a synchronous validator and returns a promise for an asynchronous one. The interface types are vendored in `src/interop/standard-schema.ts` so the package needs no dependency for them.

## Adding a validator

1. One module, one exported factory, options in one interface, all with TSDoc per `docs/guidelines/code.md`. Throw `RangeError` or `TypeError` from the factory for options that make no sense.
2. Build it with the [builders](#builders) where one fits: `format` for a string format, `guard` for a type, `check` for a rule on a typed value. One built on `toValidator` itself gives it the wordings of the issues it reports, from `core/words.ts`, so its `~standard` words them. The signature is `validator(options?, ...checks)`, and the options include `message`.
3. Decide whether a constraint is an option or a check by [how often it is used](#options-checks-formats-and-composition).
4. Describe what is accepted, never what is rejected, per [Formats are allowlists](#formats-are-allowlists). When a standard parser gives the input its meaning, check what the parser read and return it. Decide whether it returns the text as written or a canonical form before it is released, since that is [part of its contract](#compatibility-of-a-format).
5. Non-matching type: `invalid_type`. Failed constraint: `invalid_format`, `invalid_value`, `too_small` or `too_big` with `params` that name the facts and never the value.
6. Report every failing constraint, not the first.
7. Tests beside it: accepted values, rejected values, edge cases, the exact issue shape, the `message` option, and that no issue contains the input. A format that returns a parser's reading also gets a case in `src/formats/parser-agreement.test.ts`.
8. Add it to the size budgets if it adds a scenario a consumer would plausibly bundle alone.
9. Document it on the public page that covers its kind, such as `docs/formats.md` for a format or `docs/getting-started.md` for a primitive or a check, and the wording for its issue shape in `messages/english-messages.ts`.
