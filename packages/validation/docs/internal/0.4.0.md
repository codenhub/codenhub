# 0.4.0 spec

This is the design of the work that follows 0.3.0, all of it released together as 0.4.0. It came from comparing the package with valibot, zod and yup on 2026-10-07, three times: steps 1 to 6 from the first comparison, the [second pass](#the-second-pass), steps 7 to 13, from the second, and the [third pass](#the-third-pass), steps 14 to 18, from the third. Each step is a condition of the release, which [roadmap.md](roadmap.md#current-focus) holds back until nothing left would significantly improve the package. [architecture.md](architecture.md) still describes the code as it is; each step updates the sections it changes in the change that implements it, and until then this document says where the code is going. [roadmap.md](roadmap.md) points here for its current focus.

## What the comparison measured

The same schema in each library, `{ name: string of at least 2, email, age: optional integer }`, bundled with rolldown 1.2.12, minified and gzipped at level 9, and run on Node.js 24.19 on one machine. `ours` is `src` at 0.3.0, bundled the same way.

| Library        | Object, gzipped | Lone `boolean`, gzipped | Valid input, M ops/s | Invalid input, M ops/s |
| -------------- | --------------- | ----------------------- | -------------------- | ---------------------- |
| ours 0.3.0     | 5.37 kB         | 1.19 kB                 | 0.48                 | 0.70                   |
| valibot 1.5.0  | 1.58 kB         | 0.76 kB                 | 5.42                 | 2.88                   |
| zod/mini 4.6.5 | 5.76 kB         | 3.04 kB                 | 4.30                 | 0.55                   |
| zod 4.6.5      | 23.8 kB         | 14.7 kB                 | 7.85                 | 0.88                   |
| yup 1.7.1      | 12.8 kB         | 12.7 kB                 | 0.35                 | 0.01                   |

Where our time goes, each alone, valid input, M ops/s: `string()` 32.7, `number({ int: true })` 29.6, `email()` 0.99, `object({})` 6.1, `object({ a: string() })` 2.3, an `object` of three strings 1.19. Valibot's `object` of three strings ran 12.5 and its `string` 79.7. So the leaves are within a small factor, `email()` costs what the URL parser costs, which [Formats are allowlists](architecture.md#formats-are-allowlists) chose, and the composers are about ten times slower than they need to be.

The speed figures are one schema on one machine and the ratios are what to read. What the other libraries can do, below, is from their documentation and was not run.

What they have that this package lacks, and a consumer would choose them for:

- **Schemas that can be read.** JSON Schema and OpenAPI output, structured output for language models, `pick`, `omit` and `required`, and forms generated from a schema.
- **An input type.** A form library types the state of a field from it when a default, a coercion or a `transform` makes the input differ from the output.
- **A rule across fields that runs while another field fails.** Our `check` on an object runs once every property has passed, so "Passwords must match" is not shown until the rest of the form is valid.
- **Speed**, as measured.
- `brand`, `readonly`, a narrowing `is`, which was built and taken out, and message maps in other languages.

What this package has that they lack is the reason to keep building it: formats that return what a standard parser read, tested for one answer across runtimes; work and issues bounded for hostile input; issues that never hold the input; validation that is synchronous until a rule waits, with types that say so; and options checked when a validator is made.

## Steps

Every step is part of 0.4.0. They were first planned as releases of their own, the first as a 0.3.x; none was cut, and the package stays unpublished until the release bar of the roadmap is met.

### 1. Composers as fast as their leaves allow

No signature, issue or result changes.

- **The cause.** Every call of `object` makes three arrays the size of its shape, a `Place` for each child, a `WeakMap` lookup for each child and the closures of `runEach`, `collect` and `chain`, whether or not anything waits or fails. The other composers do the same.
- **The change.** A composer does the work of the usual case, where no child waits and no issue is found, without what only the other cases need: a `Place` is made when an issue is written, what a composer learns of a child when it is created is not looked up again on each call, and a list is not made to be read once. What a composer guarantees is unchanged and stays tested: the input is read before any child runs, results keep the order of the children, a pending result of a sibling is handled when a child throws, and a validation carries each `lazy`'s counts.
- **Held by a benchmark.** `pnpm bench` in the package runs the scenarios above against the built `dist/` and prints operations per second. It is not a test: time measured in CI fails for reasons that are not the code's. The measurements before and after are recorded in [architecture.md](architecture.md), as sizes are.
- **Done when** an `object` of three strings and an `array` of 100 strings are each at least three times faster on valid input than before the step, no test changed to pass, and every size budget holds or is reset by its own rule with the growth named. This first also named the schema of the table, which was a mistake of the spec: `email()` alone runs about a million times a second, so no composer makes that schema four times faster.
- **Where it stands.** [Speed](architecture.md#speed) has the measurements, with no test changed to pass and every budget holding. The condition is met as the owner lowered it on 2026-10-07, from four times to three: measured with every result kept, an `object` of three strings is 3.4 times faster and an `array` of 100 strings 3.3 times. This first said 3.7 and 4.0, from a benchmark that discarded results and so flattered both, and four was not reached. What is left in an `object` is the lists and the output an `object` makes for each call, not something only the rarer cases need.

Not part of this step: `email()` and `url()`. Their time is the parser's, and returning what it read is the point of them.

### 2. A validator can be described

Reverses "JSON Schema generation and code generation" and "`required` and the `extend`, `pick`, `omit` and `keyof` object methods" of the roadmap's Not Planned, and [What a function cannot do](architecture.md#what-a-function-cannot-do).

- **What the decision did not weigh.** It compared a plain function with a class hierarchy, and found that classes cannot be tree-shaken. It did not weigh the third design, a function or object that carries a description of itself as plain data, read by functions imported on their own. Valibot is that design and is the smallest of the five, so being readable and being small are not in tension. Nor did it weigh what reading a schema is for now: the tools of a language model and the body of an HTTP API are both declared as JSON Schema, and a validation library that cannot produce one is not chosen for either, whatever else it does well.
- **The design.** A validator stays `(input: unknown) => result`, and one written by hand stays valid. Each factory of this package also records, when it makes a validator, what it made: its kind, the options it read, and its children. `describe(validator)` returns that record, or `undefined` for a validator that carries none. The record is plain, frozen data; a check, a `transform`'s function, a `guard` and a `format`'s test appear in it as present and opaque.
- **Kept on the validator, not in a registry.** Two minors of this package can be installed at once before 1.0, as [Dependency model](architecture.md#dependency-model) notes, and a module-level map would make a validator from one copy unreadable by the other. It is set when the validator is created, never when a module loads, so [Tree-shaking is a contract](architecture.md#tree-shaking-is-a-contract) holds.
- **Built on it, each an export of its own**, so a consumer that describes nothing bundles only the record:
  - `toJsonSchema(validator, options?)`, draft 2020-12. A part with no JSON Schema, such as a `transform`, a custom check or a `date`, throws by default naming its path, and is written as accepting anything when the caller asks for that.
  - `pick(validator, keys)`, `omit(validator, keys)` and `required(validator)` for a validator `object` made. `partial` accepts a validator as well as a shape.
- **Budget.** The record is the one cost every consumer pays. It is measured on `boolean()` and the object of three fields before the design is fixed, and the step is redesigned if it adds more than 5% to either.

- **Where it stands.** The record and `describe` are built, for every factory and every built-in check, with two differences from the design above. `brand` returns the validator it was given, so it adds no record of its own. The test of a `guard` and of a format are not in the record, where the design had them as present and opaque: nothing reads them, and a `guard` gives its `expected` and a format its name. [A validator can be described](architecture.md#a-validator-can-be-described) has the design and its measurements, 3.3% on `boolean()` and 2.2% on the object of three fields. The property is `~description`. `toJsonSchema`, `pick`, `omit`, `required` and `partial` for a validator are built on it: [Objects made from an object](architecture.md#objects-made-from-an-object) and [JSON Schema](architecture.md#json-schema) have their designs. Three choices were confirmed before they were built: a part with no JSON Schema throws by default, the input side is written by default, and an object with checks is refused by `pick`, `omit`, `required` and `partial`. A `union` is `anyOf` and a `lazy` a `$ref` to a definition.

Open: whether `tagged` also accepts a list of described objects and reads each one's tag. Nothing built so far needed it.

### 3. An input type

Reverses "`InferInput`" of the roadmap's Not Planned and [Types](architecture.md#types).

- **What the decision did not weigh.** "Every validator accepts `unknown`" is true of the call and was taken to settle the type. A form library does not ask what a validator accepts; it asks what a value that passes looked like before validation, to type the field that holds it. `optional(number(), 0)` produces `number` from `number | undefined`, and `coerceNumber()` produces `number` from text, and today both tell Standard Schema their input is `unknown`.
- **The design.** `Validator<TOutput, TInput = unknown>` and `AsyncValidator` the same, with `InferInput<typeof validator>` beside `Infer`. The call signature stays `(input: unknown)`: the parameter is the type of input that can pass, not a constraint on the argument. Every built-in declares it, a validator written by hand has `unknown`, and `standard` reports it.
- **`is` narrows to it.** `is(validator, input)` becomes `input is InferInput<typeof validator>`. Whatever a validator does to a value it accepts, the value it was given was of its input type, so the guard is sound for coercions, `transform` and `json`, which is what kept `is` from narrowing in [Results, not exceptions](architecture.md#results-not-exceptions).

This is the first change to a signature, so it is 0.4.0.

- **Where it stands.** Built, without the narrowing `is`: [Types](architecture.md#types) has the design. The owner reversed that part on 2026-10-07, after review. What it did not weigh is that a type predicate is read both ways: the reasoning above holds for a value that passes, and TypeScript also takes one that fails to be not of the input type, which is false whenever a validator refuses a value of that type, as `string({ min: 3 })` refuses `"ab"`. `is` returns `boolean`, as in 0.3.0, and [Results, not exceptions](architecture.md#results-not-exceptions) has the cases. `Validator` and `AsyncValidator` became interfaces to carry the type, which no caller sees, and `standard` reports the input type where it reported `unknown`, which changes the field types a form library reads. Nothing else that compiled before stops compiling.

### 4. A rule across fields that does not wait for the others

- **The case.** A signup form with a name, a password and its confirmation. With the name empty, `check((data) => data.password === data.confirm, …)` on the object reports nothing, since a check is given a typed value and there is none while a property fails.
- **The design.** `checkFields(keys, predicate, issue?)`, a check for `object` and `objectLike`. It runs when every property it names has passed, whatever the others did, and its predicate is given an object of those properties alone, typed so. It reports with the properties' own issues. `check` is unchanged.
- **Rejected:** running every `check` on a partly valid object, which would give a predicate a value that is not of its type.
- **Where it stands.** Built: [Checks](architecture.md#checks) has the design.

### 5. Say what the package is for

The README, the package description and `docs/index.md` lead with what the comparison shows is its own: validating data nobody controls, with formats that mean what the parser reads and work that is bounded. "Each validator is small" stays as a fact with its measurement, and is no longer the first claim: valibot is a third of the size, and closing that takes moving checks out of every factory, which [What adopting costs](architecture.md#what-adopting-costs) measured and rejected and this spec does not reopen. A page compares the package with the other three, with the table above measured again on the release.

- **Where it stands.** Built: [comparison.md](../comparison.md) is the page. Measured again the same day, the object is 5.79 kB, up from 5.37 kB at 0.3.0 by what steps 2 and 4 added to every `object`, a lone `boolean` 1.24 kB, and the schema runs 0.9 million times a second on valid input and 2.0 on invalid, from 0.48 and 0.70. zod/mini is now the same size as this package for that object, where it was larger. The page also records what was run for each claim of what is this package's own: what a format produces, the issues of 200,000 bad items, input nested 100,000 deep, and whether an issue holds the input. Measured once more with step 6 built and the version at 0.4.0: the sizes are the same, and the schema runs 1.0 million times a second on valid input and 2.0 on invalid.

### 6. Smaller additions

Each additive.

- `brand(validator, name)` and `readonly(validator)`, which change the output type and nothing at run time but freezing, for `readonly`.
- Message maps in other languages, each a module and an export of its own as `englishMessages` is, starting with `portugueseMessages`. One is added when someone will maintain it.
- **Where it stands.** Built. [Wrappers that change the type](architecture.md#wrappers-that-change-the-type) has the design of `brand` and `readonly`, and [Other languages](architecture.md#other-languages) that of `portugueseMessages`, which the owner of the package maintains.

## The second pass

The six steps above closed what the first comparison found. The second asked again what valibot, zod and yup have that a consumer would choose them for, and found these, each grounded in a case:

- **Handing a validator to another library takes a wrapper and a message map.** valibot, zod and yup are each a Standard Schema as they are; here every form library, router or SDK is given `standard(validator, englishMessages)`.
- **A JSON Schema says nothing a model or a reader can use beyond the types and their constraints.** A language model chooses a tool and fills its arguments from the `description` of each, and an OpenAPI document shows `title`, `description` and `examples`; `toJsonSchema` writes types, bounds, formats and structure, but none of these annotations, where zod has `.meta()` and valibot has metadata actions.
- **An exported object cannot be extended.** A shape is extended by spreading it, but a module that exports `user`, the validator, has no shape to spread, and `extend` is among the most used methods of zod.
- **Nothing checks the bounds the README asks for.** The package's case is input nobody controls, and it tells the caller to give each collection a `max` and to cap text; whether a schema does is left to review. None of the others checks it either, so this is the one item that is not a gap but a step further along what the package is for.
- **Data cannot be written back.** A `Date` read from an ISO string, or a `bigint` from text, has no way back to what a request carries; zod 4.1 has codecs, with `encode` and `decode`.
- **Valid input is the weakest figure.** Step 1 made composers about three times faster, and what is left in an `object` is the lists and the output each call makes: an `object` of three strings validates about 3.8 million times a second here, and about 12.5 million in valibot. zod generates a function for each object at run time.
- **Adopting it means finding out how to plug it in.** Most adoption starts from an integration snippet, and the package has none.
- **A tool of a language model cannot take one.** Found while step 13 ran its examples against the AI SDK 7.0.131: Standard Schema 1.1 added Standard JSON Schema, `~standard.jsonSchema.input` and `output`, and the AI SDK takes any Standard Schema that has it as a tool's input, and throws "does not support JSON Schema conversion" for one that has not, as `standard` returned. It asks for draft-07, which `toJsonSchema` did not write.

What the second comparison weighed and left out, with the reason: moving checks out of the factories to close the gap in size, which [What adopting costs](architecture.md#what-adopting-costs) measured and rejected and no new measurement reopens; method chains, which cannot be tree-shaken; and a lower Node.js floor, which [issue 203](https://github.com/codenhub/codenhub/issues/203) decided with that cost weighed.

Each step below is a pull request of its own, in this order: a later step builds on, or is only worth it after, the ones before it.

### 7. A Standard Schema without a message map

Reverses, for `standard` alone, "the map is required, by `formatIssue`, `flatten` and `standard` alike" of [Messages are on demand](architecture.md#messages-are-on-demand-and-the-english-is-separate).

- **What the decision did not weigh.** It was taken so that a forgotten map could not word every issue "Invalid value" without a word. A default of the whole English map does not do that, and `standard` is the call made at every hand-off to another library, where the import of a map is the one argument the others do not ask for.
- **The design.** `standard(validator, messages?)`, with `messages` defaulting to `englishMessages`. `formatIssue`, `flatten` and `assert` are unchanged: their caller words issues the program shows itself, and chooses the language each time.
- **The cost, accepted.** A program that calls `standard` bundles the English, about 1.7 kB gzipped, even when it passes another map, since the default is referenced. A separate export for the default was weighed and rejected: one more name, for a saving only a program in another language that also uses Standard Schema sees.
- **Done when** `standard(validator)` types and runs, a size scenario measures `standard` with an `object` and no map, and the docs show it without one.
- **Where it stands.** Built: [Standard Schema](architecture.md#standard-schema) has the design. The new scenario measures 5221 bytes gzipped, and no other budget moved.

### 8. Schemas that say what they are for

Two additions on the description record that step 2 built.

- **`meta(validator, { title, description, examples, deprecated })`** returns a validator that behaves as the one given and whose description is that one's plus `meta`. A `meta` given to a validator that has one replaces the keys it names. `toJsonSchema` writes each key on the part it is given to, under JSON Schema's own name. `pick`, `omit`, `required`, `partial` and `extend` read through it, since its description is the object's. Rejected: a `description` option on every factory, which every validator would carry for the few that are described; and writing to the record of the validator given, which would change a validator its caller may share. Examples are written as given and not validated: they may be of the input or of the output, and a validator may be asynchronous. Each must be a JSON value, `null`, a boolean, a finite number, text, or a list or plain object of them, or `meta` throws a `TypeError`: a JSON Schema is JSON, and a `bigint`, a `Date` or `undefined` in it would make `JSON.stringify` throw or change the example without a word.
- **`extend(validator, shape, ...rest)`** makes an `object` of the shape of an `object` validator with the properties given added or replaced, as spreading the shape does. It takes what follows a shape in `object`, keeps the options of the object it came from when given none, as `pick` does, and refuses an object with checks for the same reason. This reverses "`extend` and `keyof` object methods" of the roadmap's Not Planned. What that did not weigh is what step 2 found for `pick` and `omit`: a module exports the validator, not its shape, so the shape is not there to spread.
- **Done when** both are exported with their types, `toJsonSchema` writes every key of `meta`, the reshaping functions read through it, and each has a size scenario.
- **Where it stands.** Built: [A validator can be described](architecture.md#a-validator-can-be-described), [Objects made from an object](architecture.md#objects-made-from-an-object) and [JSON Schema](architecture.md#json-schema) have the design. `meta` wraps a composer without an extra call, by sharing its work, and a validator written by hand given a `meta` is described as `{ kind: "meta", inner, meta }`, which this spec did not say. `extend` of an `object` of one string measures 3320 bytes gzipped, and `toJsonSchema` with a `meta` 5782. Checking that each example is a JSON value, added in review, took the bundle of every export past its budget, so every scenario was measured again and every budget reset by the rule of [Tree-shaking is a contract](architecture.md#tree-shaking-is-a-contract). Against the code before step 7, the bundle of every export grew 496 bytes, for `meta`, `extend` and the default map of `standard`, a lone `boolean` 9 bytes and `standard` 14; the budgets had been set before earlier steps of 0.4.0 grew them within their tenth, so most rose more than that.

### 9. A schema checked for the bounds it needs

- **The case.** `object({ tags: array(string()) })` validates a body of a million tags of a megabyte each in full, since input that passes is checked in full. The README tells the caller to give the array and the text a `max`, and nothing tells them they did not.
- **The design.** `audit(validator)` walks the description and returns a list of findings, each a `rule` and the `path` in the schema where it applies, and an empty list for a schema that bounds what it accepts. A test asserts it is empty. The rules: a collection, `array`, `set`, `map`, `record` and a `tuple` with `rest`, without a `max`; text, `string` and `coerceString`, without a `max`, and `json` or `searchParams` not reached through one; a `lazy` whose `maxDepth` or `maxCalls` is above its default; and a part it cannot read, such as a validator written by hand, which it names rather than passing in silence. A format that bounds its own text is not reported.
- **Not part of it.** Whether a `max` is small enough: that is the caller's to decide, and any number says the caller decided.
- **Done when** `audit` is exported, every rule has tests of a schema that breaks it and one that does not, and the validator reference says how to use it in a test.
- **Where it stands.** Built: [Bounds a schema leaves open](architecture.md#bounds-a-schema-leaves-open) has the design. Each finding also gives the `kind` of the part, and the path is text, as in the errors of `toJsonSchema`. A bound before a part in a `pipe` counts for it, which is what bounds `json` and `searchParams`; the formats that bound their own text are listed by name. Its size scenario measures 4363 bytes gzipped, and no other budget moved. In review, a `lazy` used at two places was walked only at the first, and a bound inside a wrapper or a nested `pipe` was not seen, so both were fixed: a `lazy` is walked at each place, and a wrapper bounds what it produces when what it holds does.

### 10. Data written back: codecs

- **The design.** `codec(input, output, { decode, encode })` is a validator that validates with `input`, decodes what it produced, and validates that with `output`. `encode(validator, value)` writes a value back to what the validator accepts: it walks the description, rebuilds each composer over the encoding of its children, runs `encode` at a codec, and returns a result as a validator does, so a value the validator could not have produced fails with its issues. A part that produces what it accepts, such as a leaf, a format, a `guard` or a coercion whose output is one of its inputs, encodes by validating. `json` and `searchParams` encode by writing the text, which is then read back through them, so text they would refuse, such as a list written as a repeated key that `searchParams` reads only with `repeated`, fails. Two wrappers produce a value their inner part may refuse: `optional(string({ min: 3 }), "x")` produces `"x"` from `undefined`. When the inner part refuses the value and it is the default, `Object.is` the primitive the `optional` was given, it is written back as `undefined`, the input that produced it; a default from a function cannot be compared and fails. A `fallback` value the inner part refuses fails too, since every input its inner part refuses produces it, and which one was given is not known. `decode` and `encode` are synchronous: a promise returned by either throws a `TypeError`, as one from the test of a `guard` does, since the validator would wait while its type says it does not. A part that cannot be written back, such as a `transform` or a validator written by hand, throws a `TypeError` naming its place, as `toJsonSchema` does.
- **Why a codec and not an inverse on `transform`.** A `transform` is a function written for one direction, and most have no inverse; a codec is written as a pair by whoever knows both.
- **Done when** `codec` and `encode` are exported with their types, `encode` of every composer and of each coercion is tested, and a size scenario measures them.
- **Where it stands.** Built: [Writing a value back](architecture.md#writing-a-value-back) has the design. Two things this spec did not say: a composer's checks run on the value as it was given, once its parts passed, since they are written for what it produces; and `encode` bundles every composer, 8401 bytes gzipped with an object and a codec, since it rebuilds each from its factory. `toJsonSchema` writes a codec as its input by default, and as its output with `io: "output"`, and `audit` reads it by its input. In review, four were fixed: the checks of a composer lost its `message` on the way back; text `json` and `searchParams` wrote is now read back; a default `optional` produced from `undefined` is written back as `undefined`; and a conversion that returns a promise throws.

### 11. Valid input without the full work

This was first designed as `compile(validator)`, an export that would generate a function with `Function`, and reversed "code generation" of the roadmap's Not Planned for it. A prototype measured on 2026-10-07 replaced it before it was built, and the owner chose the replacement the same day.

- **What the prototype measured.** On Node.js 24.19, each alone, valid input: an `object` of three strings ran 4.5 million times a second as built, 11.7 with a path that calls each child directly and falls back to the full work on any failure, 13.6 with that path given each leaf's test instead of its call, so no result is made for a value that passes, and 15.0 with code generated by `Function`. An `array` of 100 strings ran 1.1, 1.4 with direct calls and 9.9 with the leaves' tests. So almost all of the gain is in not making a result, a place and a list for each child, and generated code adds a tenth.
- **Why not `compile`.** A Content Security Policy without `unsafe-eval`, and Cloudflare Workers, refuse `Function`, so the users it would serve least are those on the edge runtimes the package runs in; it is a second path of every composer to test; and an export of its own would leave everyone who does not know to call it at the old speed. The fast path below has none of these costs, and pays bytes instead.
- **The design.** A validator that can answer valid input without the full work has a fast test: a function that gives the value it would produce, or a miss. Each leaf without checks has one, made from its own test and clean-up, and so has each format without checks whose parts all have one; `object`, `array`, `optional`, `nullable` and `nullish` have one when every child has one and they have no checks. On a miss the validator does its full work, which reports the same issues as before, so a failing input costs the fast attempt and then what it cost before.
- **What calls a consumer's code has none**, since a miss would run it a second time: a check, a `guard`, a `format`'s test, a class's custom `Symbol.hasInstance`, own or inherited, a default made by a function, and a `transform`, a `pipe` or a `lazy`, whose functions or getters may. A getter or a `Proxy` trap in the input is read once for input that passes; on a miss, what the fast attempt read before it stopped is read again, and what comes after it only by the full work. An `object`'s fast test reads each property as it asks its child, so a getter that changes a later property of its parent can give a result the full work would not; the owner kept that over a fifth of the speed, as [Valid input without the full work](architecture.md#valid-input-without-the-full-work) records.
- **Done when** an `object` of three strings and an `array` of 100 strings are each at least twice as fast as before the step, measured with `pnpm bench` in a whole run, every test of the composers passes unchanged, and every size budget holds or is reset with what grew named.
- **Where it stands.** Built: [Valid input without the full work](architecture.md#valid-input-without-the-full-work) has the design and the measurements. In a whole run, an `object` of three strings went from 3.8 to 8.7 million validations a second and an `array` of 100 strings from 0.55 to 2.0; no test of the composers changed. A lone `boolean()` grew 86 bytes gzipped and an `object` of three fields 398; with what review added to `audit` in steps 9 and 10, that took `audit` past its budget, so every budget was reset.

### 12. A Standard Schema that carries its JSON Schema

- **The design.** `standardJsonSchema(validator, messages?)` returns what `standard` returns with `~standard.jsonSchema` added, whose `input` and `output` write the validator with `toJsonSchema`, the target as asked and `libraryOptions.unrepresentable` passed on. `toJsonSchema` takes `target: "draft-2020-12" | "draft-07"`; any other target throws, as the specification asks.
- **An export of its own**, chosen by the owner on 2026-10-07 over carrying it in `standard`: a form in the browser calls `standard` and would bundle the code that writes a schema, about 2.5 kB gzipped, for a reader it never has. Rejected too: leaving it to an adapter of the AI SDK, `jsonSchema(toJsonSchema(validator), { validate })`, which every caller would write again.
- **Done when** `standardJsonSchema` is exported and typed as both specifications, `toJsonSchema` writes draft-07, a tool of the AI SDK takes it as its input, and a size scenario measures it.
- **Where it stands.** Built: [Standard Schema](architecture.md#standard-schema) and [JSON Schema](architecture.md#json-schema) have the design. A tool of the AI SDK 7.0.131 took it as its input, wrote its draft-07 schema with each description and reported issues worded in English. With an `object` of one string it measures 7929 bytes gzipped.

### 13. How to plug it in

- **The design.** A public page, `docs/integrations.md`, with what each of the common places a validator goes needs: a form library through Standard Schema, an RPC or HTTP framework, the tools of a language model through `standardJsonSchema` or `toJsonSchema`, with `meta`, and an OpenAPI document. Each example names the version of the library it was checked against.
- **Done when** the page exists, every example in it was run against the library it names, and the README and the overview link it.
- **Where it stands.** Built: [integrations.md](../integrations.md). Each example was type-checked with the package's strictest settings and run, against react-hook-form 7.89.0 with @hookform/resolvers 5.9.1, @tanstack/form-core 1.33.5, @trpc/server 11.19.0, hono 4.13.13 with @hono/standard-validator 0.4.0, ai 7.0.131 and @modelcontextprotocol/sdk 1.32.1, in a folder outside the repository, since none is a dependency. `tests/integration/doc-examples.test.ts` skips a block that imports another library for that reason. Running them found step 12, and that Hono's validator answers a failing body by sending it back, which the page's example replaces with the issues alone. The MCP server's `registerTool` takes zod schemas only, so the page declares the tool on its lower-level `Server` with `toJsonSchema`.

## The third pass

The thirteen steps above closed the gaps in what the package can do. The third comparison, on 2026-10-07, asked when a consumer would still choose valibot, zod or yup, and found that what decides it is mostly reach, not features: a team picks zod for its ecosystem and valibot for its size, and nobody looks for a library that is safe by default until something goes wrong. Each finding is grounded in a case:

- **What the package does best is hard to have without the rest of it.** A team on zod that stores emails or fetches URLs can call `email()` and `url()` from a transform of its own schemas, but nothing shows it how, so it moves every schema to this package or does without them. Neither zod nor valibot takes a Standard Schema as a part of its own schemas, so there is no shared protocol to lean on, only a wrapper written by hand: checked against zod 4.6.5 and valibot 1.5.0.
- **Valid input is still the weakest figure, and most of it is one format.** The signup schema of the comparison validates about a million times a second here and six to nine million in valibot and zod, and [Speed](architecture.md#speed) says the time is `email()`'s, which asks the URL parser for the domain. For an ASCII domain, which is most of them, what the parser returns can be known without asking it.
- **Text takes a map.** The first example of the README imports `englishMessages` to show one sentence, and every form passes it to `flatten` again. Two languages ship, where zod and valibot each have a set of ready-made ones.
- **A validator is handed to another library through `standard`.** Step 7 took away the map; the call is still one the others do not ask for. Whether it can go too depends on what it costs, which nobody has measured.
- **A form with a file has nothing to read it with.** The package is for "a form, a request", and a `FormData` or an uploaded `File` is what a form sends. zod has `z.file()` and valibot `file()` with `maxSize` and `mimeType`; neither reads a `FormData`, which is left to other packages. The type a `File` declares is whatever the client said, so a check on it alone checks nothing.

What the third comparison weighed and left out, with the reason:

- **A lower Node.js floor.** This package declares `>=24` by a repository rule, which [issue 203](https://github.com/codenhub/codenhub/issues/203) settled with the cost to Node.js 22 weighed. Revisiting it belongs to the repository, not to this spec.
- **Recursive types read from the schema**, as zod 4 does with a getter in the shape. A recursive schema here is written with an `interface` and `Validator<T>`, as in valibot, which is a few lines once per recursive type, and a getter in `object` would be a second way to write a shape for every composer, `describe`, `audit` and `encode` to read. Not measured, since the gain did not justify the prototype.
- **Method chains, a smaller core and a throwing `parse`**, for the reasons of [roadmap.md](roadmap.md#not-planned), which no new case reopens.

Each step below is a pull request of its own, in this order: the words come first because the recipes of step 15 and the measurement of step 18 use them.

### 14. Words without a map

Reverses, for `formatIssue` and `flatten`, "the map is required by `formatIssue` and `flatten`" of [Messages are on demand](architecture.md#messages-are-on-demand-and-the-english-is-separate).

- **What the decision did not weigh.** It was taken so that a forgotten map could not word every issue "Invalid value". A default of the whole English map does not do that, as step 7 found for `standard`, and the import of a map is the one thing the first example of the README has to explain.
- **The design.** `formatIssue(issue, messages?)` and `flatten(failure, messages?)`, the map defaulting to `englishMessages`, as `standard` does. The wording of each code stays as it is: the three that quote another issue still take the map, for the reason recorded there.
- **`assert` is left as it is**, with its empty map, as the owner chose on 2026-10-07: its callers are the packages that check a caller's options, which [Who gains from adopting](architecture.md#who-gains-from-adopting) found pay most for every byte, and a default English would add about 1.7 kB to each.
- **The cost, accepted.** A program that calls `formatIssue` or `flatten` bundles the English, about 1.7 kB gzipped, even when it passes a map of its own, since the default is referenced. The scenario "formatIssue with your own wording", 420 bytes, grows by that. A separate export for each default was rejected as it was for `standard`.
- **No new language.** The owner chose on 2026-10-07 to ship none in 0.4.0: [Other languages](architecture.md#other-languages) adds one only when someone will maintain it, and nobody has offered to. zod and valibot keep that lead.
- **Done when** both take no map, the README and the docs show them without one, and every size budget holds or is reset with what grew named.
- **Where it stands.** Built: [Messages are on demand](architecture.md#messages-are-on-demand-and-the-english-is-separate) has the design. The wording that takes no default is `wordIssue`, in a module of its own. `assert`, `standard` and the quoting of a nested issue call it, which this spec did not say: with the default inside one function, `assert` would have bundled the English through it, and the module that holds it would have imported the English back. `formatIssue` with a map of its own went from 377 bytes gzipped to 2366 and with `portugueseMessages` from 2542 to 3391; `assert` and `standard` did not move, and every budget was reset by the rule of [Tree-shaking is a contract](architecture.md#tree-shaking-is-a-contract).

### 15. Our formats inside zod and valibot

- **The case.** A team on zod that fetches a URL a user gave has `z.url()`, which accepts `http://169.254.169.254/latest`. It can have `url()` without moving its schemas, if it is shown how.
- **The design.** A section of [integrations.md](../integrations.md) that wraps any validator of this package as a part of a zod schema, through `.transform`, and of a valibot one, through `rawTransform`: the value it produces is the one the wrapper returns, and each issue is reported with its path and its wording from `formatIssue`. No export is added, as the owner chose on 2026-10-07 over `toZod` and `toValibot` adapters: an adapter is a few lines, and an export would tie this package's API to the context each library gives a transform, which zod changed between its versions 3 and 4.
- **What it does not carry.** An issue reported this way becomes the other library's issue, which in valibot holds the input, so what [An issue never holds a value of the input](../comparison.md#an-issue-never-holds-a-value-of-the-input) says no longer holds for it. The page says so.
- **Done when** the section exists, each recipe is type-checked and run against the version of the library it names, as step 13's were, and the comparison names it under "When to choose another".
- **Where it stands.** Built: [Inside a zod or valibot schema](../integrations.md#inside-a-zod-or-valibot-schema). Both recipes were type-checked with the package's strictest settings and run against zod 4.6.5 and valibot 1.5.0, outside the repository: `url()` and `email()` produced what they produce alone, and refused `http://169.254.169.254/latest` and `ada@localhost` with their English wording. Two things this spec did not say: valibot's `pipe` needs the transform's input type to be what the schema before it produces, so its recipe takes it from the validator's input type; and valibot's `addIssue` takes a path only as its own records of each step, so an issue below the field, such as one from an `object`, lands on the field there, where zod keeps its path. zod's issues held no input, as the comparison says; valibot's held it.

### 16. An ASCII domain without the parser

- **The case.** `email()` asks the URL parser to read the domain, which is what makes `Ada@EXAMPLE.com` `Ada@example.com` and an internationalized domain its punycode. For a domain of ASCII letters, digits, hyphens and dots, with no `xn--` label and a last label the parser does not read as a number, what the parser returns is the text in lowercase.
- **Measured before it is built.** A prototype of `toAsciiHost` that answers such a domain without the parser is measured with `pnpm bench`, `email()` alone and the signup schema, and checked against the parser over generated hosts. It is built only if `email()` is at least three times faster for such an address, and dropped otherwise, with the measurement recorded here.
- **The design, if built.** `toAsciiHost` in `formats/patterns.ts`, which `email`, `domain` and `hostname` share, returns the lowercase text for such a host and asks the parser for any other. A test in `parser-agreement.test.ts` compares the two over generated hosts of every class the condition names, its edges included, so a host the shortcut and the parser read differently fails a test. No signature changes.
- **Not part of it: `url()`.** The parser normalizes the whole URL, its path, escapes and port included, and writing that again is a second URL parser, the risk [Formats are allowlists](architecture.md#formats-are-allowlists) exists to avoid.
- **Done when** the measurement is recorded and the step is built or dropped by it.
- **What the prototype measured.** On Node.js 24.14.1, in whole runs of `pnpm bench` against the code before it, `email()` went from 0.76 to 1.64 million validations a second, 2.15 times, and the signup schema from 0.58 to 1.06, both steady across two runs. These are lower than the figures of [Speed](architecture.md#speed) for the same code, since whole runs differ from one session to the next by more than the tenth they differ by within one: a whole run on Node.js 24.19 on 2026-10-08 gave `email()` 1.14 and the signup schema 0.74. Only figures of one session are compared. Asking the shortcut before the test for Unicode text gained a tenth over asking it after. What is left of `email()`'s time is the rest of its reading, about eight patterns and the lists and objects of `partsFormat`, spread so that no one of them is worth a step: three times would take writing that reading again.
- **The bar, lowered.** The owner chose on 2026-10-07 to build it at 2.15 times over dropping it or writing the reading again: the shortcut is a few lines with no change to any signature, and the agreement test bounds its risk.
- **Where it stands.** Measured; to be built.

### 17. Forms with files

- **The design.** Two validators, each in a module of its own, so neither reaches a program that does not import it:
  - **`formData(validator, options?, ...checks)`** reads a `FormData`, from this realm or another, into an object of its entries, each a string or a `File`, and produces what `validator` makes of it, as `searchParams` does for a query string, including its `repeated` option and its refusal of a key given twice without it.
  - **`file(options?, ...checks)`** accepts a `File`, with `minSize`, `maxSize` and `types`, the media types it may declare. A size is the most data the program will go on to hold, so `audit` reports a `file` without a `maxSize` as it reports text without a `max`. It does not bound what was read to make the `File`, which is the size of the body, as `formData` below says.
- **The declared type is not the content.** `types` checks what the client declared, which it chooses freely. A check, in a module of its own with its table of signatures, reads the first bytes of the file and compares them with the types it is given; reading is asynchronous, so a `file` given it is an `AsyncValidator`. Which types it knows is set when it is built, and starts small.
- **Done when** both are exported with their types, a size scenario measures each, every other size budget holds unchanged, the realm, repeated-key and size limits are tested, and the validator reference has a section on forms with files.
- **The check is `contentType(types)`**, and starts with `image/png`, `image/jpeg`, `image/gif`, `image/webp` and `application/pdf`. The owner approved the names and options on 2026-10-07.
- **Not reported by `audit`: `formData`.** A program receives a `FormData` already read, by `request.formData()` or the like, so the bound on it is the size of the body, which is set where the request is read and which nothing in the schema can express.
- **Where it stands.** Not started.

### 18. A validator that is a Standard Schema as it is

- **The question.** Whether every validator can carry `~standard` itself, so a form library or a router takes it with no `standard` call, cheaply enough to be worth it. The owner decides with the measurement.
- **What is measured.** A prototype, which is not merged, that gives every validator a `~standard`, measured against the code before it: the size of a lone `boolean`, of the object of three fields and of the bundle of every export, and `pnpm bench` in a whole run. The Standard Schema needs a message on every issue, so the prototype is measured both with the English referenced, which every program would then bundle, and with the wording left to `standard`, the `~standard` of a bare validator giving the issue's own message or its code.
- **Done when** the measurement is recorded here and the owner has chosen to build it or to drop it.
- **What the prototype measured.** On 2026-10-07, `~standard` set by `described` on every validator, against the code before it, gzipped. With the English referenced, a lone `boolean` went from 1336 bytes to 3534, the object of three fields from 6179 to 8219 and the bundle of every export from 25668 to 26295. With the issue's own message or its code, the first two grew 130 and 119 bytes and the bundle 118. `pnpm bench` in a whole run moved by less than its runs differ by, either way.
- **Dropped**, as the owner chose on 2026-10-07. The English is 2.2 kB in every program, including the many that never hand a validator to another library; with codes, a form library shows its user `too_small`, so a program calls `standard` anyway to get words, and the step saves nothing.
- **Where it stands.** Dropped.

## What this does not change

- A validator is a function, and a factory is `validator(options?, ...checks)`.
- No dependencies, results and issues as plain data, and no issue holding the input.
- No method chains, no `abortEarly`, no message per option, and no checks as steps of `pipe`. The comparison found no case their reasons in the roadmap did not weigh.
