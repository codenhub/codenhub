# Coding

Code fails at its edges: values that pass a check and then break the thing that uses them, inputs that are missing, writes that fail, paths nobody updated, and tests that pass against broken code. These rules close those edges. They are part of building the feature, not extras on top of it: the smallest correct change includes them.

Follow the project's own conventions, checks, and instructions where they exist. Where the project is silent, this skill is the standard. When the code is TypeScript or JavaScript, read [references/languages/typescript.md](references/languages/typescript.md) before writing it.

## Before Changing Code

Read the code the change touches and the code around it: how it is split into modules, how similar features were built, and which names and patterns it uses. Decide where the change belongs before deciding how to write it.

When the existing structure would make the change worse, stop and propose a refactor before writing the change. Signs: a function that already does several jobs and would gain another, logic duplicated in places the change must also update, a file that mixes unrelated features, state shared through globals, or I/O wired into logic so that it cannot be tested. Describe the problem, the refactor, and its size, and ask whether to refactor first, make the change as asked, or both. Do not refactor without that answer. When nobody can answer during the session, end with the proposal and the question instead of writing the change. Before a refactor moves existing behavior, such as a validation check or an error, add a test that pins it, so the refactor cannot drop it unnoticed; name any behavior the refactor does change, such as a new error case, in the final report. Do not copy a bad pattern because nearby code uses it; when the change goes ahead as asked, name the problem in the final report. Sharing one piece of duplicated code does not settle the rest: report the duplication that remains.

When the task starts a project, adds a module, service, data model, storage, public API, or dependency, or asks how to structure something, read [references/design.md](references/design.md) first.

Assume the person asking may not be able to judge code. Ask them about what they will notice: behavior, data that changes or is deleted, cost, security, and anything hard to undo. When you ask, give the options in plain words, what each one costs, and which you recommend. Decide technical internals yourself with the defaults in this skill, and name each one in the final report.

## Design Defaults

Where the project sets no convention, use these, and apply each the same way across the whole change:

- **Names:** follow the language's own conventions, such as `snake_case` functions in Python and `camelCase` in JavaScript, and keep one style throughout. Name by domain meaning, `unpaidInvoices` rather than `data` or `list2`. Functions are verb phrases, booleans read as questions (`isExpired`, `hasAccess`), and collections are plural.
- **Functions:** one job each, describable without "and". Extract a step when it has its own name. Take at most two or three parameters; past that, take one named options object or record. Return early instead of nesting. Replace a boolean parameter that switches between two behaviors with two functions.
- **Values:** give a literal a named constant when it has domain meaning or appears in more than one place: `MAX_RETRIES`, not `3` in several files. Protocol strings, one-off messages, and test fixtures stay inline.
- **Dependencies:** pass I/O, clocks, randomness, and configuration into the code that uses them, as parameters or constructor arguments, instead of reading globals or creating a concrete client deep inside logic. A plain parameter is enough; do not add an interface or container for a single implementation.
- **Modules:** keep code that changes together in one place and unrelated code apart. Once a module needs a second file, give it a folder with one entry point (`index.ts`, `__init__.py`, `mod.rs`) that exposes its public surface, and keep the rest private. Dependencies point one way: shared code never imports feature code, and imports never form a cycle.
- **Objects:** split a class or module that owns unrelated state and behavior. Move a function that mostly reads another object's data onto that object. Prefer composition to inheritance, and immutable values to shared mutable state.
- **Duplication:** reuse what the codebase already has before writing a helper. Extract shared logic once a second real copy exists and both copies change for the same reason; leave coincidental similarity alone.
- **Async:** await or explicitly handle every promise, future, or task; never start work whose failure matters without observing it. Run independent work concurrently, bound concurrency over input-sized collections, and pass cancellation (abort signals, contexts, deadlines) through to every call that can block.
- **Errors:** handle an error where the code can act on it; otherwise let it propagate, adding context about what was being done. Catch only the errors you expect, never everything around a block. Use the language's usual mechanism (exceptions, `Result`, error returns) consistently, and never use errors for normal control flow.
- **Types:** in typed languages, type public functions explicitly, avoid escape hatches such as `any` and unchecked casts, and model state so invalid combinations cannot be built.
- **Public surface:** export only what callers need and keep the rest private. Constants and helpers a change adds stay private unless code outside the module uses them. Add no compatibility layer, alias, or deprecated path unless a real caller, stored data, or shipped behavior needs it.
- **Messages to people:** an error a person sees says what happened, why when that is known, and what to do next, in plain words. It never shows raw error text, stack traces, or internal names; those go to logs. Advise "try again" only when retrying is safe, and when the action may already have taken effect, say so.
- **Logging:** log what someone running the program would act on, with enough context to find the cause. Never log secrets, tokens, credentials, or personal data. Logging an error is not handling it.
- **Documentation:** give every public function or type a doc comment in the language's standard format that says what the signature does not: what it does for the caller, units and ranges, what empty or missing results mean, side effects, and each error it raises and when. Do not restate the types. Update the README, help text, and docs the change affects in the same change.
- **Tests:** test observable behavior through the public interface, not internals. One behavior per test, named for it. Assert the whole result, not one field of it, so an extra or missing key fails. Place tests where the project does, or next to the code they test. Replace only external boundaries (network, storage, file system, clock, randomness) with fakes. Keep tests fast and deterministic, cover error paths next to the normal path, run any test that writes files in its own directory under the system temporary directory (`os.tmpdir()`, `tempfile`), never under the project or the current directory, and remove it afterwards. A test that asserts something is absent, such as a password hash missing from output, must use input that would produce it if the protection were removed. Work out expected values by hand from the requirement or a worked example, never by running the code's own formula.
- **Readability:** prefer plain code over clever code, and immutable bindings over reassigned ones. Name intermediate values instead of chaining long expressions. Given the same input and state, code returns the same result: sort any output built from a directory listing, a hash map, a database query without `ORDER BY`, or concurrent results by a defined key with a tie-breaker, and pass the clock, randomness, and locale in rather than reading them. Use only APIs that exist in every environment the code runs in, such as no Node modules in browser code. Comments explain why, never what; delete commented-out code and comments the change made stale.

## Hard Rules

1. **When input from outside the code's control is converted before use, validate the converted value against the limits of what consumes it.** Converted means parsed, scaled, unit-converted, merged, or decoded. Check the value the timer, array, allocator, library, or protocol receives, against that consumer's maximum and minimum. A check on the raw input is not enough: `--timeout 1e308` passes "positive number" and becomes Infinity milliseconds. Test the exact edge values on both sides of each limit, and state the limit in messages and docs from the same constant the check uses. Reject degenerate raw values too: empty, whitespace-only, NaN, Infinity, partial numbers such as `10s`, unknown enum values, and ranges such as `min > max`.
2. **When required input is missing, unreadable, or matches nothing, fail with a message naming it, unless the task says empty is valid.** This covers a directory that does not exist, a glob or filter that selects zero items, a command that is not found, and a required field or key that is absent. Exit non-zero or throw. Treat only the specific error that means absence, such as `ENOENT` or HTTP 404, as absence, and only where absence is legitimate; rethrow every other error. A run whose required input was missing never reports success. A run whose job is to remove or process what exists, such as a cleanup with nothing left to clean, reports that and succeeds. A run whose output replaces earlier output or gates a deploy fails on zero items unless the task says empty is valid, and the final report names that choice so the user can reverse it. A sitemap build that gates a deploy must fail when its content directory is missing, not write an empty sitemap and exit 0.
3. **Give every behavior decision a test that fails if the decision is reversed, then break the code once to watch it fail.** A decision is each edge case the code handles and each behavior it chooses that the task did not spell out: what an explicit `undefined` or `None` means, which values are rejected, what happens when a read or write fails, that a child's whole process tree is stopped, that output is escaped, and that timers, listeners, and child processes are cleaned up when the work ends normally. Test cleanup by its effect, such as the program exiting promptly after fast work under a long timeout, not by inspecting the cleanup code. Name each test after the exact claim and assert that claim, not something near it. Pick input and expected values that differ from the defaults and from each other, so broken code gives a different result: a test that sets a field to `undefined` and expects the default value cannot tell "kept" from "reset", a sort test whose input is already in the expected order passes with the sort removed, and a money test whose amounts all come out to exact cents passes with the rounding removed. Give each test an input that breaks only the rule under test, so no other check can make it pass: a test for unknown keys uses a key whose value would otherwise be valid. A rejection test asserts which rule rejected the input, such as the error type or the field and reason the message names, not only that it failed or which file it named, since any other check firing would pass that. Test each check on every source that feeds it, such as arguments, query string, stored data, and files, and an edge case such as `undefined` on every field it applies to; a check tested in one place can vanish from another unnoticed. Before writing these tests, list every pair of check and source, and give each pair a test or a reason it cannot occur. Keep at least one test that runs the real entry point, such as the CLI or exported function with its default paths, on realistic input, in a temporary copy of the project so its output never lands in the real one, and assert the output file, what it prints, and its exit code, on success and on each error. Then, for each decision, break the line that implements it (delete the check, flip the branch), run the tests, see a failure, and undo that edit. This includes cleanup decisions such as clearing a timer. Make the break by editing the file in place and undo it with the reverse edit; never undo it with `git checkout` or `git restore`, which also discard your unsaved work, and never copy files to a shared temporary directory, where another process can overwrite them. When no test fails, or only an unrelated assertion fails, the decision is unproven: fix its test until its own assertion fails. A break you did not run is reported as unverified, not skipped silently.
4. **When a hand-written parser meets syntax it does not support, reject the input with an error naming the file and line.** Never read unsupported syntax as data. First support every construct the real input already uses, such as full-line comments, quoted values, and the date spellings in the existing files; rejecting valid existing content blocks every run. A frontmatter scanner that supports `key: value` must reject `slug: x # comment`, a multi-line value, an unknown key, or a key that differs only in case such as `Draft: true`, rather than store `x # comment` as the slug or ignore the draft flag. Use the format's real parser, or a machine-readable output mode such as `-z` or `--json`, when one is available without a new dependency.
5. **When you add an option or fix a path, list every sibling path and cover each one, or say why not.** Siblings are every place the same input or behavior flows: each source of the same value (arguments, query string, stored data, files), setup and main commands, sync and async variants, create and update, each overload, mode, output format, and event source, and every caller of a patched function. Apply the change to each and test each. A sibling you leave out is named, with the reason, in the final report.
6. **When a write can fail, commit state after it succeeds or surface the error, and never swallow it.** A write is any step that persists or sends: storage, files, network, cache, a consumed token. Validate and compute first, perform the write, then update in-memory state. If in-memory state must change first, throw or return the error and document that the change stays applied. Never catch a write error and carry on silently, and never cache a failure. A call that changes nothing, such as an empty or all-invalid query, makes no write; test it with a write that throws.
7. **Report every change to public API or shared process behavior, and ask before one the task did not ask for.** This covers an exported signature (including sync to async), a default, a thrown error type, a CLI flag, an exit code, a file format, signal handling, process groups, global state, and environment variables. Prefer a design that avoids the change, and limit it to when the new feature is in use. When the task needs it, keep it and list it in the final report. Example: putting a child in its own process group to kill its tree also stops the terminal's Ctrl+C from reaching it; do it only when the timeout is set, forward the same signal to the group so the command can clean up, and then stop the whole run as the signal would have. When a fix or improvement would change public surface the task did not name, such as a new export, option, or limit, or a sync function turned async, present the options, who is affected, and your recommendation, and ask before making it.
8. **Never make a check pass by weakening it, and never present unfinished work as done.** When a test, type check, or lint rule fails, fix the code. Do not delete, skip, or loosen the test or assertion, add ignore comments or casts, or catch and discard the error to get a green run. When the check itself is wrong, change it as a separate step and say why in the final report. Never deliver a stub, placeholder, hard-coded result, or mocked behavior as working code; when part of the task is not done, say which part.

## Judgment

### Who controls the input

The hard rules apply where input comes from outside the code's control: users, CLI arguments, URLs and shared links, files, network responses, environment variables, other processes, and stored data that an earlier session or version wrote. Data that looks internal often crosses one of these: a preference read back from storage came from a URL last week. Find that boundary before writing the code; the failures this skill prevents happened where input was not obviously untrusted.

Trust developer-only configuration, values an earlier step already validated, and the return values of your own code. Do not add validation, limits, or snapshots there.

Match the response to who supplied the bad value. When the caller or the person running the command supplied it, fail with a clear error. When a third party supplied optional input, such as a parameter in a shared link or a field in stored data, drop the bad value, keep the valid rest, and keep working: a malformed link must not break the page it opens. Drop a value only when leaving it out is safe; a malformed expiry, permission, price, or other restriction is rejected, because dropping it widens access or changes money.

### Scale to the code's life

A one-off script for the person asking, run locally, stays short: one file read top to bottom, no helper functions or constants used only once, no argument parsing layer, no validation layer, no output beyond what was asked, no tests unless asked, and no README section. The Design Defaults apply to code that will be kept and changed. Rule 2 still holds, in one line without a stack trace, because a script that matched nothing should say so instead of printing nothing. A script that deletes, moves, or overwrites files or data gets the full rules however short its life, and asks before a run that cannot be undone. Code that runs in CI, ships to users, or is called by other code gets the full rules.

### Edges to check while writing

- **Text placed into another language** (HTML, XML, CSS, Markdown, YAML, JSON, shell, URLs, regex replacement strings, inline scripts): use that language's serializer, or escape for that exact context, and test with its metacharacters. Match prefixes and substrings with a boundary: `/callback` must not accept `/callback.evil`.
- **Present but absent values:** decide per field whether a key set to `undefined`, `None`, or `nil` means "omitted", "clear it", or "invalid", and test that call shape. A falsy check rejects legitimate `0` and `""`.
- **Stored data that could not be read:** when the read itself throws and the code falls back to defaults, do not save over the stored data until a read succeeds, because the next save would replace everything stored with the defaults plus one change. Data that was read but is corrupt can be replaced.
- **Caller-owned input:** copy it once at the call when you keep it, return copies of internal state, do not mutate the receiver in a builder, and apply fields you control after spreading caller input.
- **Unbounded work on uncontrolled input:** bound size, depth, and time. Avoid regexes with overlapping quantifiers and recursion on input depth. Pair every listener, timer, and child process with its teardown, stop the whole process tree, and re-check that the owner still wants the result after every await.
- **Paths:** find the project's own files from the script's or module's location, not the current directory, so the program works from any folder. Resolve a configured or stored path and require it to stay inside its root. Generate output into a new location and replace the old output only after generation succeeds, so a failed run leaves the last good output in place; delete only files the program created.
- **Access:** when code reads or changes records that belong to someone, check on the server that the caller may access each record it returns or changes, and test that another user is refused.
- **Errors:** branch on error codes or types, never on message text. The message names the rule broken and the value that broke it, with secrets removed: a database URL is shown without its password. Generated output never carries secrets either: reject or strip credentials in a URL before writing it into files or pages. A failure your change adds reaches the person running the program as that one-line message with a non-zero exit code, not an unhandled-exception stack trace, even when older failures in the same path still print one. That includes the errors that library functions raise on bad input, such as a URL, date, or number parser: catch them where the input enters and report them the same way. Find each call that parses, decodes, or converts input, or creates output, and run the program once with a bad value for it, such as `http://[bad` for a URL parser, a file that is not valid UTF-8, or an output path that already exists as a file.
- **Collisions:** when inputs become names, URLs, IDs, paths, or keys, two inputs can become the same one, including after case folding or normalization. Fail naming both instead of letting one silently replace the other.
- **Platform:** pass an explicit locale and time zone, use the platform's path and process APIs, and expect case-insensitive paths on Windows and macOS. Parse dates and numbers before sorting or comparing them.
- **Contracts:** in the same change, search for the changed symbol's name in doc comments, README, help text, and comments, and update what describes the old behavior. Types describe what the code does at runtime.
- **Tests that do not flake:** poll for a condition instead of sleeping a fixed time, and leave margins far above process startup time, such as a command that sleeps 10 seconds against a 1-second timeout.

### What not to add

Leave these out unless the task or the code's real use calls for them:

- Handling for inputs no current caller, document, or file produces.
- Atomic writes or getter snapshots as a reflex. Use them when someone else's process or input can race the code, or when a failed write would destroy the only copy of data someone needs.
- Exotic type-level and engine corner cases nobody hits.
- New public API, exports, or throws as part of a fix (rule 7).
- Dependencies, schema libraries, or frameworks for what a few lines do.
- Lint norms the project does not use, and micro-optimizations on rarely reached paths.

## Verify

- Run every check the project has, not only the tests you touched: tests in every environment it uses, type checking, linting, formatting, and builds or size limits. A fix verified by unit tests alone has broken browser suites and hand-written callers.
- Run each error path the change adds through the real entry point and read what the person sees: one line, no stack trace, non-zero exit.
- Confirm claims about behavior by running the code. Do not report what you expect it to do. A claim that covers every case, such as "every error prints one line" in a report or README, needs every case run, or narrow the claim to what you ran.
- Before using a library function, option, CLI flag, or package, confirm it exists in the version the project uses: read its installed types, source, or documentation, or run it. Never write an API from memory alone.
- Keep the diff to the task: no unrelated reformatting, renames, or rewrites. Check `git status` after running the tests; a file you did not mean to create means a test writes into the project.
- Run the code on the project's real input, such as its existing content, config, or sample data. When valid existing input fails the new checks, the checks are wrong: loosen them, or ask before changing the data.
- Keep each file's existing line endings and encoding. A scripted edit that rewrites them turns a small diff into a whole-file one.

## Final Report

After the change, report in this order, omitting empty items:

- **Structure** (never omitted): problems found in the existing code, such as duplication, mixed responsibilities, or magic values, and the refactor proposed or the answer given; or "none found".
- **Decisions:** each behavior decision and the test that proves it.
- **Siblings:** paths covered, and any left out with the reason.
- **Public API and shared behavior changes**, each on its own line, quoting the words of the task or answer that asked for it, or marked "not asked".
- **Checks:** each command run and its result. Name failures and skipped checks plainly.
