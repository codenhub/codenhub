# `@codenhub/oidc`: package scope

> **How to read this document.** This is not a final spec. Section 4 lists the **invariants**: security and design commitments that hold unless there's a strong, explained reason to break them. Sections 1 to 3, 5 and 7 are the agreed scope of 0.1. The API sketch in section 6 was a **proposal**; the shipped API answers it differently in places, and section 8 records how. Section 8 also records the decisions taken while building the package, marked by who settled them. If you find a better API shape, better behavior, or a better-established practice, propose it and explain why, as `docs/guidelines/documentation.md` asks for reversing a decision. The goal is the best possible package, not faithfulness to this document.
>
> The invariants and every decision in section 8 are approved by the maintainer.
>
> The display name is `OidcKit`. How the package is built, and why, is in [architecture.md](architecture.md). What remains before 0.1 is in [roadmap.md](roadmap.md).

---

## 1. Context

This is the second building block:

1. **`@codenhub/jwt`**: JWS/JWK primitives on Web Crypto. It's published as 0.0.1.
2. **`@codenhub/oidc`** (this package): OpenID Connect for **both sides**, the client (Relying Party) and the provider (OpenID Provider).
3. **The SSO application**: a self-hosted, 100% free and open-source identity provider with an admin dashboard for users, roles, and registered apps. Its differentiator is that user data belongs to the user's account, not to individual apps. This app is the first real consumer of the provider side.
4. Later, and only if needed: SAML.

The package covers both sides on purpose. It isn't "a package built for one project": it's a general OIDC toolkit. Apps integrating with the SSO get a client written by the same people who wrote the provider. Both sides also share a lot: metadata types, error codes, PKCE, and token validation rules.

### Relationship with `@codenhub/jwt`

- Use `@codenhub/jwt` for all JWS/JWK work. **Read its current public API and docs in `packages/jwt` first.** Don't rely on the sketch from its scope document, because some decisions changed before publishing.
- If `oidc` needs something `jwt` lacks, propose the change to `jwt` instead of working around it. A hashing helper for `at_hash` is one likely example, and a claim-check hook is another.
- Don't reimplement anything `jwt` already does.

## 2. Scope

### Shared (root export)

- Types for discovery metadata (OpenID Connect Discovery, RFC 8414), for authorization/token/error responses, and for standard claims.
- OAuth/OIDC error codes (RFC 6749 §4.1.2.1 and §5.2, OIDC Core §3.1.2.6) as typed values.
- PKCE (RFC 7636), `S256` only, and `at_hash` computation. Both ship as internal shared modules rather than root exports (decision 6).

### Client (`@codenhub/oidc/client`)

- **Discovery**: fetch and validate `/.well-known/openid-configuration`. The `issuer` must match exactly. Results are cached, and the client can also be configured without discovery. As shipped, `discover` fetches on every call, and the app caches by keeping the metadata or the client (decision 5).
- **Authorization request**: build the URL with `state`, `nonce`, and PKCE `S256`. Return a serializable "pending" object that the app stores. The client itself holds no state.
- **Callback**: check `state` and handle error responses. Validate the `iss` parameter (RFC 9207) when the provider advertises it. Exchange the code.
- **ID token validation**:
  - signature, through `jwt` and the provider's JWKS
  - `iss` and `aud`
  - `azp` when `aud` has multiple values
  - `exp` and `iat`
  - `nonce`
  - `auth_time` when `max_age` was requested
  - `at_hash` when present
- **Refresh** (`refresh_token` grant).
- **Userinfo**. The `sub` must equal the ID token's `sub`.
- **Client authentication**: `client_secret_basic`, `client_secret_post`, `private_key_jwt`, `client_secret_jwt` (HS256 is available in `jwt`), and `none` for public clients with PKCE.

### Provider (`@codenhub/oidc/provider`)

- **Endpoints**: discovery, JWKS, authorization, token, userinfo, revocation (RFC 7009), and end-session (RP-initiated logout, decision 37).
- **Authorization** is split into begin and complete steps, because login and consent UI belong to the app (see section 6).
- **Grants**: `authorization_code`, `refresh_token`, and `client_credentials` (decision 35).
- **Client authentication verification** for the same methods the client supports.
- **Request handling**:
  - `prompt`: `none` must return `login_required` / `consent_required`; `login` and `consent` must force those steps. As shipped, the app performs these steps, since sessions and consent are its own (decision 3): it answers `prompt=none` with a denial, and the provider checks the outcome it reports, such as an `authTime` no older than the request under `prompt=login` (decision 16).
  - `max_age`, with `auth_time` in the ID token.
  - Scopes mapped to claims.
- **`iss` in the authorization response** (RFC 9207), advertised in discovery.
- **RP-initiated logout** (RP-Initiated Logout 1.0): the end-session request is validated by the provider and the session ended by the app (decision 37).
- **Refresh tokens** rotate on every use. Reuse detection revokes the whole token family.
- **Code replay** revokes every token issued from that code.
- **Store interface**: the adapters the app implements (section 5).
- **An in-memory reference store** under a testing subpath (for example `@codenhub/oidc/testing`). It's clearly marked as not for production, and it's used by tests and examples.

### Candidates (in if cheap and clean, otherwise later)

- Token revocation (RFC 7009). It's useful for logout and for the SSO dashboard. Shipped in 0.0.1 (decision 27).
- JWT access tokens (RFC 9068, `typ: at+jwt`) as an option alongside opaque tokens. Shipped in 0.0.1 (decision 36).

### Out of scope (0.1)

These are left out to keep the surface small, not because they're bad:

- **Never supported:** implicit and hybrid flows, the password grant (ROPC), and PKCE `plain`.
- **Out of scope for 0.1:**
  - Device flow, CIBA, and PAR (RFC 9126). PAR is not planned (decision 38).
  - DPoP and mTLS.
  - Dynamic client registration.
  - Request objects (JAR) and JWE-encrypted tokens.
  - Front-channel logout and session management. RP-initiated logout is in (decision 37), and so is back-channel logout (decision 53).
  - Token introspection.
  - Deriving pairwise subject identifiers in the provider. The app derives them, and `subjectTypes` advertises them (decision 60).

## 3. Design direction

- **Fetch API everywhere.** The provider takes a `Request` and returns a `Response`. The client uses an injectable `fetch`. This one choice makes it run unchanged on Workers, Node 26+, Deno, Bun, and inside any framework (Hono, plain Workers, Node adapters).
- **The package owns the protocol; the app owns everything else**: users, passwords, MFA, sessions and cookies, login and consent pages, persistence. The provider renders no HTML other than the `form_post` response page (decision 85), and never decides how a user authenticates.
- **Opinionated.** Secure choices are defaults or the only option, and rejected options are rejected loudly.
- **The client stays small.** Importing `oidc/client` must not pull in provider code.

## 4. Invariants

1. **PKCE `S256` is required for every client by default**, confidential ones included. A missing or `plain` challenge is rejected. Decision 52 lets a confidential client go without PKCE when it sends a `nonce`; a public client never can, and a challenge that is sent is always enforced.
2. **`redirect_uri` matches exactly.** It's a byte-for-byte comparison against a registered value, with no normalization, wildcards, or prefix matching. Loopback redirects with variable ports (RFC 8252) are not planned (decision 38), so the match is exact in every case.
3. **No open redirects.** The provider only redirects to a redirect URI it has verified for that client. The types make the difference between "send this error back to the client" and "render an error yourself" impossible to miss.
4. **Authorization codes:**
   - single-use
   - short-lived, with a bounded default (around 60s or less)
   - bound to the client, `redirect_uri`, PKCE challenge, `nonce`, scopes, and the authenticated session. As shipped, the code carries the subject, `auth_time`, `amr` and `acr` the app reports; tying the interaction to the browser's session is the app's job, by keeping the interaction identifier in that session.
   - consumed atomically
5. **Exact issuer matching** everywhere: discovery, ID tokens, and the RFC 9207 `iss` parameter. Decision 79 makes one opt-in exception, for a multi-tenant issuer written as a `{tenantid}` template.
6. **No token type confusion.** An ID token is never accepted as an access token or the reverse; use `typ`/`aud` distinctions through `jwt`. A refresh token is never accepted anywhere else.
7. **Client secrets.** The store interface must allow verifying a secret without the provider ever seeing it in plaintext, so storing hashes is possible and recommended. Secret comparisons are constant-time.
8. **Untrusted input never throws.** Requests, callbacks, discovery documents, token responses, and JWKS all produce results. Programmer errors (bad options, an invalid store) throw `TypeError`, ideally when the client or provider is created.
9. **Bounded cost.**
   - Cap request body sizes, parameter counts, and parameter lengths before parsing.
   - Reject duplicate parameters (OAuth forbids them), except `resource`, which RFC 8707 repeats (decision 59).
   - Cap outbound fetches (discovery, JWKS, token, userinfo) for response size and time.
10. **Nothing secret leaks.** Codes, tokens, secrets, verifiers, and claim values never appear in issues, logs, or `error_description`. Error responses to clients are generic.
11. **HTTP hygiene.**
    - Token and userinfo responses carry `Cache-Control: no-store`.
    - The token endpoint accepts only `POST` with `application/x-www-form-urlencoded`.
    - The CORS policy is decided and documented. Public browser clients need it on the token endpoint; the authorization endpoint must never have it.
12. **Randomness** comes from `crypto.getRandomValues` only, with enough entropy (at least 128 bits) for `state`, `nonce`, codes, verifiers, and tokens.
13. **Codenhub conventions**, as in `jwt`:
    - result shape `{ ok: true, value } | { ok: false, error: { issues } }`
    - frozen results
    - ESM only, `sideEffects: false`, subpath exports
    - follow `AGENTS.md` and `docs/`
14. **Dependencies.** The only runtime dependency is `@codenhub/jwt`, plus another `@codenhub/*` package only when it's clearly justified. No third-party runtime dependencies. Runtime-agnostic, with an injectable `fetch` and clock.

## 5. The store interface

The store is where most real-world bugs live. Its contract should be precise and documented, including what each method must guarantee.

The provider needs, at minimum:

- **Clients**: look up by `client_id`. This returns registered redirect URIs, allowed scopes, the authentication method, and either a secret verifier or a JWKS. As shipped, a record also lists its grants and its post-logout redirect URIs (decisions 35 and 37).
- **Authorization codes**: `save` with a TTL, and `consume`. `consume` **must be atomic**. Decision 10 makes it an atomic mark-as-used rather than a get-and-delete, so a replay can be recognized. Document what that rules out: plain Cloudflare KV is not atomic, so it needs D1 or Durable Objects.
- **Refresh tokens**: `save`, `rotate` (atomic), `revokeFamily`.
- **Grants or sessions**, if needed, for code-replay revocation and refresh-family tracking.

As shipped, `OidcStore` (`src/provider/types.ts`) answers this list: refresh tokens are consumed like codes, by an atomic mark-as-used, and rotation saves a new token; a family is a grant, revoked with `revokeGrant`, which must also hide tokens of that grant saved after it (decision 10). The TSDoc on `OidcStore` is the contract.

Tokens and codes should be stored hashed, so a leaked database doesn't leak usable tokens. Decide whether the provider hashes before calling the store; it probably should.

The in-memory testing store must implement these guarantees faithfully. It's also the reference other adapters are tested against. A reusable **store conformance test suite** checks the SSO app's D1 or Postgres adapters against the same rules: as shipped, `storeConformanceCases` in `@codenhub/oidc/testing` (decision 29).

## 6. API sketch (a proposal, change freely)

```ts
// ── Client ─────────────────────────────────────────────
import { createClient } from "@codenhub/oidc/client";

const client = await createClient({
  issuer: "https://sso.example", // discovery runs here; issuer must match exactly
  clientId: "app123",
  auth: { method: "client_secret_basic", secret: "..." }, // or private_key_jwt, none, ...
  redirectUri: "https://app.example/callback",
  fetch, // optional
});

const { url, pending } = await client.authorize({ scope: ["openid", "email"] });
// pending: serializable { state, nonce, codeVerifier, ... }, stored by the app

const result = await client.callback(request, pending);
// ok    → { claims, tokens: { accessToken, refreshToken, idToken, expiresAt } }
// error → state_mismatch | provider_error | invalid_id_token | nonce_mismatch | ...

await client.refresh(refreshToken);
await client.userinfo(accessToken);

// ── Provider ───────────────────────────────────────────
import { createProvider } from "@codenhub/oidc/provider";

const provider = createProvider({
  issuer: "https://sso.example",
  keys, // @codenhub/jwt key set
  store,
  claims: (subject, scopes) => ({ email: "...", name: "..." }),
  ttl: { code: 60, accessToken: 600, idToken: 600, refreshToken: 2_592_000 },
});

// Discovery, JWKS, token, userinfo
const response = await provider.handle(request); // Response | null (not an OIDC route)

// Authorization: two steps, because the login UI belongs to the app
const begin = await provider.beginAuthorization(request);
if (begin.ok) {
  // begin.value.interaction: validated and serializable; the app stores it and renders login/consent
} else if (begin.error.redirect) {
  return begin.error.redirect; // safe: the error goes to the verified redirect_uri
} else {
  // unknown client / bad redirect_uri: must NOT redirect; the app renders its error page
}

return provider.completeAuthorization(interaction, {
  subject,
  authTime,
  amr: ["pwd"],
  grantedScopes,
});
```

### Open questions

- **The interaction handle.** If the app stores the interaction client-side, in a cookie or a hidden form, it must be tamper-proof. Should the package sign it with `jwt`, or always store it server-side through the store and return an opaque ID? The second is probably simpler and safer.
- **Consent persistence.** Does "remember consent" belong to the provider (through the store) or to the app?
- **Default access token format.** Opaque is simpler to revoke. A JWT (RFC 9068) lets resource servers verify offline. Pick one default and make the other an option.
- **Loopback redirects** for native and CLI apps: in 0.1, or later?
- **Customization hooks.** Custom scopes and claims, extra ID token claims, and per-client policy (allowed scopes, token TTLs). Design these so the SSO's user-data scopes fit later without breaking changes.
- **Error-to-response mapping.** How much of it the package does automatically, versus handing the app a typed error.

## 7. Testing and acceptance

- **Cross-implementation interop**, devDependencies only:
  - this client against panva's `oidc-provider`
  - this provider against panva's `openid-client`
  - this client against this provider, end to end
- **OpenID conformance suite.** Run the provider against the official Basic OP and Config OP test plans, and the client against the RP tests where practical. Required for 0.1; 0.0.1 does not run it (decision 30).
- **Hostile-input suite**, in the style of `jwt` and `validation`. Each case asserts the exact result:
  - missing or `plain` PKCE
  - wrong `code_verifier`
  - code reuse, which must also revoke the tokens issued from that code
  - an expired code
  - a code used by a different client, or with a different `redirect_uri`
  - `redirect_uri` variants: trailing slash, case change, extra query parameter, fragment, encoded characters, different port, `http` instead of `https`
  - unknown `client_id`, which must not redirect
  - duplicate parameters, other than `resource`
  - oversized bodies and parameters
  - wrong content type, or `GET` on the token endpoint
  - refresh token reuse, which must revoke the whole family
  - an ID token presented as an access token
  - a discovery document with a mismatched issuer
  - an ID token with a wrong `nonce`, `aud`, `azp`, or `iss`
  - an `iss` mismatch in the callback (mix-up attack)
  - a `state` mismatch
  - slow, huge, or malformed provider responses on the client side
- **Leak tests.** No token, code, secret, or verifier appears in issues, logs, or error responses.
- **Concurrency tests for the store contract.** Two simultaneous redemptions of one code means exactly one succeeds. The same holds for refresh token rotation.
- **Runtime matrix.** Node and workerd/Miniflare, as in `jwt`.
- **Docs.** README and `docs/` to codenhub standards, with a "what hostile input gets" section and a short guide for each side: integrating a client, and building a provider on top of the store interface.

**0.0.1 is done when:**

- The authorization code flow works end to end, this client against this provider, on Node and workerd.
- All invariants hold and have tests.
- The hostile-input and leak suites pass.

**0.1 is done when:**

- Everything in scope works.
- The provider passes the OpenID conformance Basic and Config OP plans.
- The client interoperates with `oidc-provider`.
- The public API is stable enough to build the SSO application on.

## 8. Decisions

Decisions bind work while they stand; reversing one follows "Recording decisions" in `docs/guidelines/documentation.md`.

### Approved by the maintainer

1. **The interaction handle is an opaque identifier, kept server-side through the store.** `beginAuthorization` saves the validated request with `saveInteraction` and returns a random 256-bit `id`; `completeAuthorization` consumes it atomically, so an interaction completes at most once. The store key is the identifier's SHA-256 digest, like every other secret value. Rejected: a signed JWT handle kept by the app in a cookie or form, which needs a signing key, can be replayed until it expires unless the app tracks it, and grows with the request.
2. **Access tokens are opaque by default.** A random 256-bit value, stored hashed; revoking a family is a store revocation (`revokeGrant`, which must also hide tokens of that grant saved after it, decision 10). RFC 9068 JWT access tokens became an option in the release audit (decision 36). Rejected at first: shipping `at+jwt` alongside, which adds surface and tests to 0.0.1 and gives tokens that cannot be revoked before they expire; decision 36 reversed this with opaque kept the default.
3. **Consent belongs to the app, and `redirect_uri` matching is exact only.** The app decides whether to show consent and passes the granted scopes to `completeAuthorization`; the store has no consent table. Loopback redirects with variable ports (RFC 8252 §7.3) are not planned (decision 38). Rejected for now: a provider-side consent store, which adds a table and a policy the SSO app must own anyway.
4. **0.0.1 targets the "0.0.1 is done when" criteria of section 7.** Interop against panva's `oidc-provider` and `openid-client`, the OpenID conformance runs, and token revocation (RFC 7009) were left for later; the audit brought interop and revocation into 0.0.1 (decisions 27 and 30).

### Taken while building, approved in the pre-release audit

5. **The shipped API.** `discover(issuer)` returns the metadata as a result, and `createClient({ metadata, ... })` is synchronous and holds the metadata, so a discovery failure is a result rather than a rejected constructor (invariant 8) and an app caches discovery by keeping the client. `createProvider` returns `{ metadata, handle, beginAuthorization, completeAuthorization }`; `handle` returns `null` for any URL that is not discovery, JWKS, token or userinfo, including the authorization endpoint, which the app routes to `beginAuthorization` itself. Rejected: an async `createClient` that discovers, as in the sketch, which must either throw for untrusted input or return a result in place of a client.
6. **The root export is types only.** PKCE and `at_hash` live in internal shared modules both sides import; no consumer needs them once the client and the provider compute them. Exporting them later is additive.
7. **Every URL is `https`.** Issuer, endpoints and `jwks_uri` must be `https` URLs, on both sides, with no exception for `localhost`: `@codenhub/jwt` refuses a non-`https` JWKS URL, and the client verifies ID tokens through it. Redirect URIs may use any scheme but `javascript:`, `data:`, `vbscript:` and `file:`, so native apps can register custom schemes.
8. **The provider hashes before it calls the store.** Codes, tokens and interaction identifiers reach the store only as base64url SHA-256 digests (section 5).
9. **Client secrets are random and stored as a SHA-256 digest.** `generateClientSecret` makes a 256-bit secret and `hashClientSecret` its digest, which is what a client record holds; the provider compares digests in constant time. A fast hash is sound for a 256-bit random value, which cannot be guessed. Rejected: a password hash such as PBKDF2, which costs every token request a deliberate delay to protect secrets the package never lets a human choose. `client_secret_jwt` is the exception: an HMAC is checked with the secret itself, so a client using it has its secret in the record as an `HS256` `SecretKey`, and the documentation says so (invariant 7).
10. **Code replay and refresh reuse revoke one grant.** A code exchange starts a grant (`grantId`); every access and refresh token issued from that code, and from refreshes after it, belongs to it. A replayed code or a reused refresh token makes the provider call `revokeGrant`, and the store contract requires that tokens saved after the revocation by a request already in flight are revoked too. Consumption is atomic mark-as-used, not delete, so a replay can be recognized and the grant named.
11. **A refresh token family keeps the expiry of the code exchange.** Rotation issues a new token with the same `expiresAt`, so a family lives at most `ttl.refreshToken` (30 days by default) and the user signs in again after it. A refresh token is issued only when `offline_access` is granted.
12. **ID tokens carry only protocol claims; scope claims are released at the userinfo endpoint.** The code flow always yields an access token, and OpenID Connect Core §5.4 releases scope claims through userinfo in that case. ID tokens are signed with the first signing key (decision 51 changed which key) and carry `typ: JWT`, `auth_time`, `nonce` when the request had one, `amr` and `acr` when the app gave them, and `at_hash`.
13. **CORS.** Discovery, JWKS, token and userinfo answer any origin (`Access-Control-Allow-Origin: *`) and their preflights; the authorization endpoint never has CORS headers. None of the cross-origin endpoints reads cookies or other ambient credentials, so a page on another origin can do nothing through them it could not do from a server.
14. **Error responses never carry `error_description`.** Token errors are `{ "error": code }`, userinfo errors a `WWW-Authenticate` challenge, authorization errors a redirect with `error`, `state` and `iss`.
15. **`private_key_jwt` and `client_secret_jwt` need `client_id` in the body.** The provider finds the client before it verifies the assertion and never decodes an unverified payload, which `@codenhub/jwt` deliberately does not offer. The assertion's `aud` may be the issuer or the token endpoint URL. Its `jti` is required but not tracked, and its lifetime is capped (decision 23).
16. **`completeAuthorization` throws `TypeError` when the app's outcome contradicts the request**: scopes that were not requested or no `openid`, an `authTime` before the interaction under `prompt=login`, or more than `max_age` before the request (decision 32). These are bugs in the app's login flow, and answering them with a code would silently log a user in without the step the client asked for.
17. **Store failures propagate.** A store that throws or rejects makes `handle`, `beginAuthorization` or `completeAuthorization` reject. Answering `invalid_grant` for a database outage would hide it and log users out. The `claims` callback is treated the same way.
18. **The client's clock tolerance defaults to 0 seconds**, following `@codenhub/jwt` decision 6; an app whose clock may drift from the provider's sets `clockTolerance`. Decision 44 reversed this: the default is 60 seconds.
19. **`@codenhub/jwt` is a peer dependency.** Its keys are recognized only by the copy that created them, so the app and this package must share one copy. It is installed from its release through the catalog, as `docs/specs/packages-lifecycle.md` asks.
20. **A code or refresh token is consumed before any check that needs its record.** The store offers only atomic consumption, so a refresh request that asks for a scope outside the family's grant, or a token presented by another client, burns the token: the first answers `invalid_scope`, and the legitimate client's next use of the token is a replay that revokes the family. A well-behaved client never sends either. Checks that need only the request run first: the shape of the `code_verifier`, and a refresh `scope` naming a scope the client's record does not list or that is not a scope token (decision 56), or leaving out `openid` (decision 31), are refused before the value is consumed. Checks against the record (expiry, client, `redirect_uri`, the verifier against the challenge, the scope against the family) run after, so they burn it. Rejected: a non-consuming lookup before consumption, which adds a store method and a read-then-write window the atomic path closes. The audit dropped it from the roadmap: reopen it only with a real client that sends such requests, which is the evidence it lacks.

### Approved by the maintainer during review

21. **A refresh whose new ID token fails validation returns no tokens.** The client reports the ID token's issues and drops the access and refresh tokens of that response, although the provider has already spent the refresh token that was sent, so the user must sign in again. An ID token that fails validation means the response cannot be trusted, and handing its tokens to the app would invite it to use them. Rejected: returning the tokens alongside the issues, which changes the failure shape of `refresh` and makes an untrusted response usable.

### Taken during review, approved in the pre-release audit

22. **Client-side caps match what the provider accepts, and URLs are visible ASCII.** Added in response to PR review: `authorize` refuses `scope`, `prompt` and `uiLocales` lists of more than 100 entries, a `maxAge` above 999999999, and a joined `scope`, a `loginHint` or a joined `ui_locales` longer than 4096 characters; `refresh` refuses a `scope` list of more than 100 entries or longer than 4096 characters joined; each is a `TypeError`. Issuers, endpoint URLs and redirect URIs, on both sides, must be visible ASCII (`!` to `~`) other than `\`, which the URL parser rewrites to `/` in special schemes (added in the audit). A client token response whose `access_token` is not printable ASCII is `invalid_token_response`. The caps mirror what this package's provider accepts (`\d{1,9}` for `max_age`, 4096 characters per parameter, and 8192 characters of URL, decision 24), so the client fails at the call rather than sending a request the provider would answer with an error page instead of a redirect; 100 entries is far above any real request and bounds the copy each list goes through. The URL rule exists because the URL parser rewrites spaces, controls and non-ASCII host characters (IDNA maps `example。com` to `example.com`), so a stored string would differ from the URL it serializes to; internationalized URLs are written as punycode and percent-encoding. The access token rule follows RFC 6749 §A.12, and `at_hash` is defined over ASCII octets. Rejected: leaving the caps to the provider, which turns a caller mistake into an unredirected provider error page; accepting non-ASCII URLs and comparing their serialized form, which breaks the byte-for-byte issuer and redirect URI matching of invariants 2 and 5.

### Taken in the pre-release audit, approved by the maintainer

23. **Client assertions get 60 seconds of clock tolerance and at most 300 seconds of lifetime, and `jti` replay is accepted by design.** The provider verified assertions with no tolerance, so a client whose clock ran one second ahead sent an `iat` in the future and failed every token request; clients such as openid-client and this package's set `iat` to their own clock. An assertion whose `exp` is more than 300 seconds after the provider's now, plus the tolerance, is refused, as RFC 7523 §3 allows. Replay within that window is accepted: a replayed assertion only authenticates the client, and a token request also needs a code with its PKCE verifier or a single-use refresh token. Rejected: tracking `jti` through a store method, which costs every adapter a table and a write on every token request for no token an attacker could not already get; no tolerance, which fails honest clients.
24. **`authorize` refuses an encoded authorization URL longer than 8192 characters**, the provider's URL limit. Decision 22's per-value caps count characters before percent-encoding, so a `loginHint` of 2048 emoji passed its cap and made a URL of about 25,000 characters, which the provider answers with an error page instead of a redirect: the outcome decision 22 exists to prevent. Rejected: lowering the per-value caps to cover the worst encoding, which refuses legitimate ASCII values to bound a rare case.
25. **`OidcIssueCode` lists only codes an operation returns.** It included every `OAuthErrorCode`, so an exhaustive `switch` had to handle fifteen codes that never occur as issues; it now holds the client codes, the three provider codes, and the six OAuth codes `beginAuthorization` redirects with (seven since `unauthorized_client` joined in decision 35). An OAuth code a provider sends stays in `provider_error`'s `params.error`. Rejected: keeping the wide union as reserved, since narrowing it after publishing is a breaking change and widening it later is not.
26. **The in-memory store keeps every record, has no clock, and saves and returns copies.** It purged expired records by its own `Date.now` on every write, so a provider on a test clock lost live codes, a late replay's answer depended on unrelated writes, and each write scanned every map. It is a testing store, so memory growing with use is acceptable, and the provider checks expiry itself. Rejected: documenting that its clock must match the provider's, a trap for every test; a `purgeExpired` method, surface for a store that is not for production.
27. **Token revocation (RFC 7009) ships without a store change.** The provider's revocation endpoint finds an access token with `findAccessToken` and spends a refresh token with `consumeRefreshToken`, and either revokes its whole grant with `revokeGrant`, as RFC 7009 §2.1 allows. Unknown tokens get `200` (§2.2), `token_type_hint` is ignored (§2.1 permits it), and another client's token is refused with `invalid_request`; a refresh token spent by that lookup still has its grant revoked, since it has leaked and its next use would revoke the grant as a replay anyway. The client gains `revoke`. Rejected: the revoke-by-token store method the roadmap assumed, which the existing methods make unnecessary; a non-consuming refresh lookup (decision 20).
28. **`onDiagnostic` reports why the token, userinfo and revocation endpoints refused a request.** (Decision 61 passes it the request too.) Decision 14 sends clients a bare OAuth code, which left an operator unable to tell an expired code from a wrong verifier. The callback receives a frozen `{ endpoint, reason, status, clientId? }` with a fixed vocabulary of reasons; `clientId` appears only when it comes from the store, never from an unverified request. It is awaited before `handle` resolves, so a throw or a rejection propagates, as decision 17 has the store and `claims` do; its type returns `void`, so a callback that returns another value still fits. Authorization failures are not reported, since `beginAuthorization` and `completeAuthorization` already return issues. Rejected: logging inside the package, which has no logger and runs on every runtime; reasons in `error_description`, which decision 14 refuses.
29. **`storeConformanceCases` checks an adapter against the `OidcStore` contract with any test runner.** Each case is a name and a `run(createStore)` that rejects with an `Error` naming the broken rule. The audit also wrote down rules the contract left unsaid: saves never overwrite, the revocation check is atomic with consumption, and adapters purge expired rows themselves, keeping replay and revocation markers as long as they matter. Rejected: a suite bound to one runner, such as Vitest's `describe`.
30. **Interop runs now; OpenID conformance certification stays a 0.1 item.** Dev-only suites run openid-client against this provider and this client against oidc-provider. The OpenID conformance plans need a provider reachable from the OpenID Foundation's runner, so they wait for a deployable host. Rejected: documenting "how far it gets" for 0.0.1 without running it, which would be a guess.
31. **Behaviors settled in the audit.** A refresh `scope` must include `openid`, checked before the token is spent, and userinfo answers `insufficient_scope` (403) for a token without `openid` (OpenID Connect Core §5.3). A failing `Authorization` header at the token or revocation endpoint always gets the Basic challenge (RFC 6749 §5.2). A registered redirect URI's query is kept byte for byte (§3.1.2). Invalid percent-encoded UTF-8 is refused as `malformed` rather than decoded to U+FFFD. Empty `ui_locales` entries are dropped, since it is a hint. The client strips a JSON byte order mark (RFC 8259 §8.1), accepts hand-written metadata that reuses an object, type-checks every claim `IdTokenClaims` types, and refuses at creation an assertion key whose algorithm the provider does not advertise.

### Taken in the release audit, approved by the maintainer

32. **`max_age` is measured at the request, on both sides.** OpenID Connect Core §3.1.2.1 asks for re-authentication when the time since the last login is more than `max_age`, which is judged when the request arrives. Measured at the callback, against a millisecond clock and a whole-second `auth_time`, `authorize({ maxAge: 0 })`, the spec's equivalent of `prompt=login`, would fail every sign-in with `auth_too_old`, and small values would fail whenever the login took longer than `max_age`. Measured in `completeAuthorization`, a user who spent longer on the consent page than `max_age` allows would make it throw `TypeError`. The provider compares `authTime` with the interaction's `createdAt`, and `PendingAuthorization` carries `requestedAt` beside `maxAge` for the client to compare with. Rejected: fixing only the provider and refusing `maxAge: 0`, which drops a value the spec defines and still fails small values; a clock tolerance as the remedy, which loosens every other time check to fix one.
33. **`storeConformanceCases` seeds clients.** `createStore` receives `{ clients }`, the shape `createMemoryStore` already takes, and a case checks that `findClient` returns a registered client with its values. The suite passed an adapter whose `findClient` never found anything, the one read every request starts with, because `OidcStore` has no method that saves a client. A refresh-token twin of the duplicate-save case was added beside it. Rejected: narrowing the documentation to say the suite does not check `findClient`, which leaves that read untested in every adapter.
34. **Behaviors settled in the release audit.** `userinfo` throws `TypeError` for an access token that is not printable ASCII, rather than reporting the header `fetch` refuses as a network failure that invites a retry. The hostile parameter check runs in workerd against the built package as well, since the bundler had deleted it from `dist/` (`AGENTS.md` records the trap).
35. **Client credentials (RFC 6749 §4.4) ships, gated per client.** A client record lists `grantTypes`, `authorization_code` by default, or `client_credentials`; the refresh grant comes with `authorization_code`. Only a client that authenticates may use `client_credentials`, and a record that gives it to a `none` client is a `TypeError`. A request without `scope` gets every scope of the client but `openid` and `offline_access`, which mean nothing without a user, and it is `invalid_scope` when that leaves no scope, as for a client registered with none beyond those two. Asking for either is `invalid_scope`. The token's subject is the client, as RFC 9068 §2.2 has it, no ID token or refresh token is issued, and each token is its own grant, so revoking one leaves the client's others. A client not allowed a grant gets `unauthorized_client`, which joins `OidcIssueCode` for the authorization redirect. On the client, `clientCredentials` sends the grant and drops an `id_token` nothing would check and a `refresh_token` RFC 6749 §4.4.3 says SHOULD NOT be included, and `redirectUri` becomes optional, since a service client signs no user in; `authorize` and `callback` throw `TypeError` without it. The SSO application's user-data API is the consumer section 2 anticipated. Rejected: `refresh_token` as its own grant type, as RFC 7591 lists it, since `offline_access` already decides whether a sign-in may refresh; a separate record type for service clients, which every adapter would have to store twice.
36. **JWT access tokens (RFC 9068) ship as an option; opaque stays the default.** `accessToken: { format: "jwt", audience }` signs access tokens with the first signing key, with `typ: at+jwt`, `iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti`, `scope`, and, for a user's grant, `auth_time`, `amr` and `acr`. They are stored by digest like opaque tokens, so userinfo and revocation work alike; a resource server verifies them offline with `@codenhub/jwt`'s `createVerifier({ type: "at+jwt" })` and sees a revocation only when the token expires, which the documentation states and `ttl.accessToken` bounds. This reverses decision 2's "later": the maintainer settled deferred items before 0.0.1, and decision 2's reason, tokens that outlive their revocation, is answered by keeping opaque the default. Rejected: per-client or per-scope audiences through resource indicators (RFC 8707), which wait for a second resource server; a verifier helper in this package, which `@codenhub/jwt` already is; leaving JWT access tokens out of the store, which would break userinfo and revocation for them.
37. **RP-initiated logout ships as a stateless validation step, like authorization.** The app routes the end-session endpoint (`endpoints.endSession`, `${issuer}/logout` by default, advertised as `end_session_endpoint`) and calls `endSession(request)`, which reads `GET` or a `POST` form and returns who asked and a `redirect`, or a failure the app renders: a logout request never redirects to anything unverified. An `id_token_hint` is verified as this provider's ID token, typed `JWT` so a JWT access token signed by the same keys does not pass, and naming its client through `azp` when it has several audiences; one that does not verify is ignored, because `@codenhub/jwt` returns no payload for a token that fails and an expired hint is normal, so the result names no user and the app asks the user to confirm (an expired hint is accepted since decision 45). A verified hint issued to another client than `client_id` is `invalid_request` (RP-Initiated Logout 1.0 §2). A `post_logout_redirect_uri` must match one of the client's `postLogoutRedirectUris` byte for byte, which needs a known client from `client_id` or the hint. The client gains `endSessionUrl`, which always sends `client_id`, so the redirect works after the hint expires. Rejected: accepting expired hints, which needs a decoded unverified payload, refused for the reason decision 15 gives (decision 45 reversed this, without decoding an unverified payload); a store-backed logout interaction, which keeps state the request does not need; front-channel and back-channel logout, which need session identifiers (`sid`) and calls from the provider (decision 38).
38. **Not planned, each until a consumer needs it:** loopback redirect URIs with variable ports (RFC 8252 §7.3), since the SSO application's clients are web apps and the exact match of invariant 2 is simpler to keep; PAR (RFC 9126), since its gain is keeping large or sensitive request parameters out of the URL, and no client of this package sends any; pairwise subject identifiers, since the app chooses the `subject` it passes to `completeAuthorization` and can derive it per client already, leaving only `subject_types_supported` to change (decision 60 changed it); front-channel and back-channel logout and session management, which need the app's sessions to carry `sid` and the provider to call clients (decision 53 brought back-channel logout in, as a request the provider builds and the app sends, with `sid` optional). Rejected: keeping them as "later", which the maintainer asked to settle before 0.0.1. Reopening one needs the consumer and its case.
39. **The OpenID conformance run stays the 0.1 release criterion.** It is a criterion of section 7, not a feature: it needs a host reachable from the OpenID Foundation's runner, and 0.0.1 is the release that puts the provider behind a real host in the SSO application. Rejected: dropping it with the deferred features, which would leave 0.1 without an outside check of the provider.

### Taken in the follow-up audit, approved by the maintainer

40. **A request whose body was already read throws `TypeError`.** `beginAuthorization`, `endSession`, and `handle` for a token or revocation request reject when a `POST` reaches them with `request.bodyUsed`, before any check; userinfo reads no body, so it is unaffected. Middleware that parses the form first, such as a framework's body parser, left the provider an empty stream, and the client got `invalid_request` for a valid request while nothing told the operator the cause was the app's own code. This follows invariant 8: a bug in the calling code throws. Rejected: keeping `invalid_request` and documenting that the request must be unread, which leaves the app with a generic refusal to debug; accepting already-parsed parameters as an argument, which adds surface for a mistake one rule prevents.
41. **`endSessionUrl` puts no length cap on `idTokenHint`.** Decision 22's caps exist so a caller's mistake fails at the call rather than as a provider error page, and they fit values the app chooses. An ID token is not one: the provider issued it, and a third-party provider whose ID tokens carry many claims issues hints over 4096 characters, which made the app's logout handler throw. The provider that issued the token decides what it accepts, and `client_id` is always sent, so logout still works if it ignores the hint. The other `endSessionUrl` values keep their caps, and the whole URL keeps its 8192-character limit (decision 24). Rejected: omitting an over-long hint, which hides the cause and makes the provider ask the user to confirm; keeping the throw, which crashes logout on input the app does not control; raising this package's provider limit for `id_token_hint` to match, since its ID tokens carry only protocol claims (decision 12) and stay far below 4096 characters, so the exemption serves third-party providers only.
42. **Behaviors settled in the follow-up audit.** Userinfo accepts `Bearer` followed by one or more spaces (RFC 6750 §2.1, `1*SP`), as the Basic parser already did, and its challenge responses expose `WWW-Authenticate` to cross-origin readers (`Access-Control-Expose-Headers`), since they allow any origin (decision 13). The authorization and end-session `POST` forms refuse a charset other than UTF-8, as the token endpoint does, since every body is decoded as UTF-8. An `http`, `https` or other special-scheme URL must be written with `//` after the scheme: the URL parser rewrites `https:app.example/cb` to `https://app.example/cb`, and a browser resolves it as a `Location` relative to the provider's own origin, the rewriting decision 22 refuses. `createProvider`'s `scopes` option given as an array, rather than an object mapping scopes to claims, is a `TypeError`. The in-memory store copies every list of a client record (decision 26). Rejected: a conformance case for a consumption racing a revocation, which cannot tell a broken adapter from a correct one whose commit lands before its promise settles, so the contract's wording was made precise instead; conformance cases for records past their `expiresAt`, which would fail an adapter that purges expired rows or sets a database TTL from `expiresAt`, as the contract allows, to catch an adapter whose only effect is `code_unknown` where `code_expired` was due.

### Taken in the publish-readiness audit, approved by the maintainer

43. **The app keeps the whole interaction; the provider offers no lookup by `id`.** The docs told the app to keep only the interaction's `id`, but the pages between `beginAuthorization` and `completeAuthorization` need what it carries: the consent page shows `clientId` and `scopes`, the login page follows `prompt`, `maxAge` and `loginHint`, and the granted scopes must be among `scopes`. `AuthorizationInteraction` is frozen and JSON-serializable, so the docs now say to keep all of it in the server-side session. Decision 1's server-side, single-use handle stands. Rejected: a `findInteraction` store method with a `getInteraction(id)` on the provider, which adds a required method to every adapter for a value the app already receives; it is worth reopening only for a flow that reaches the consent page without the app's session, such as a link opened on another device. Should a consumer show that case, the lookup can arrive as an optional store method, which breaks no adapter.

### Taken in the audit before the SSO application, approved by the maintainer

44. **The client's clock tolerance defaults to 60 seconds.** With 0, `callback` failed with `issued_in_future` whenever the provider's clock ran ahead of the client's: at one second of skew whenever the response came back before the client's clock reached the token's second, and intermittently at 400 ms, since both sides compare whole seconds. Decision 18 followed `@codenhub/jwt` decision 6, whose reason is that a default must not extend a token's life; it did not weigh the `iat` check, which fails honest providers the way decision 23 found a zero tolerance failed honest clients. 60 seconds is the tolerance the provider already gives client assertions. An ID token is checked once, seconds after it is issued, so the minute added to `exp` costs little. The tolerance also applies to `max_age`, as it always has when set: under the default, `maxAge: 0` accepts an `auth_time` up to 60 seconds before the request, and an app that needs the exact bound sets `clockTolerance: 0`. `@codenhub/jwt` keeps its default of 0, and the resource-server example in `provider.md` sets `clockTolerance`. Rejected: keeping 0 and setting `clockTolerance` in every example, which leaves the failure to every app that starts from the types; changing `@codenhub/jwt`'s default, which widens `exp` for consumers that hold long-lived tokens.
45. **An expired `id_token_hint` is accepted when expiry is its only fault.** RP-Initiated Logout 1.0 makes `client_id` optional and says the provider should accept an expired ID token as a hint while the relying party has a current or recent session at the provider. The provider keeps no sessions (decision 37), so it accepts one whatever its age and leaves the comparison with the session to the app. Decision 37 ignored expired hints, so a relying party that sent only the hint and a `post_logout_redirect_uri` got its redirect for `ttl.idToken` (600 seconds by default) after sign-in and `invalid_redirect_uri` afterwards. This package's client always sends `client_id`, but the SSO application will serve relying parties built on other libraries. Decision 37 rejected this as needing a decoded unverified payload. It does not: when `@codenhub/jwt` reports `expired` as a hint's only issue, it has already verified the signature, the issuer, the type and the claim types. Only then does the provider read `iat` from the payload, and it verifies the hint again with the clock set to that moment, so the claims it uses still come from `@codenhub/jwt`. A hint that verifies this way is treated as an unexpired one, including the `invalid_request` for one issued to another client than `client_id`. It stays acceptable while its signing key is among the provider's keys. Rejected: an option in `@codenhub/jwt` to skip the expiry check, which adds public surface to a package this one consumes from its release (decision 19) for a need one internal caller has; a limit on how long ago the hint expired, which the specification does not ask for and key rotation already provides; keeping decision 37 and documenting that relying parties must send `client_id`, which breaks logout for libraries the SSO application cannot change.
46. **Documentation settled in the audit before the SSO application.** A remote key set in a client record must be one object per client, reused across `findClient` calls: `store.md` told stores to rebuild key objects on each read, and a rebuilt remote key set has an empty cache and no fetch limit, so 20 token requests with an assertion signed by an unrelated key made 20 JWKS fetches, against 1 with a shared object under the default 30-second `cooldown`. A resource server must not take `sub` alone for a user, since a client credentials token's `sub` is the client identifier (decision 35, RFC 9068 §5); `provider.md` says to compare it with `client_id` and to keep client identifiers distinct from subjects. Rejected: caching remote key sets inside the provider, which would key a cache on records the store owns and may change.

### Proposed in the roadmap for the SSO application, approved by the maintainer

The SSO application's scope review found what it needs before it persists records. These settle the record shapes before its store adapters exist, so none of them costs it a migration.

47. **A grant carries the app's session, and the ID token names it as `sid`.** `AuthorizationGrant.sessionId` is kept on the code, access token and refresh token records, survives refresh rotation, and is emitted as `sid` in every ID token of the grant, the claim OpenID Connect Front-Channel and Back-Channel Logout use. The provider never interprets it. The client types `sid` as an optional string of `IdTokenClaims` and refuses an ID token whose `sid` is not a string, as for the other optional claims, and discovery lists `sid` in `claims_supported`. The SSO application lets users and admins revoke one session, which should end the tokens issued during it rather than every grant of that user and client; `completeAuthorization` returned only a `Response`, so the app could not tell which grant came from which session. Rejected: returning the `grantId` from `completeAuthorization` for the app to map, which needs a second table and still leaves `sid` out of the ID token that back-channel logout (decision 53) needs.
48. **A client secret method holds several digests.** `secretHash` became `secretHashes`, a non-empty list; a presented secret authenticates when it matches any entry, and every entry is compared, so timing tells nothing about which matched. Rotation adds the new digest, moves the client to the new secret, then removes the old one, so the client never stops working. Breaking for records that hold `secretHash`; nothing has persisted one yet. Rejected: `secretHash: string | readonly string[]`, which is not breaking but makes the persisted shape an either-or for good; a separate `previousSecretHash`, which allows only one overlap at a time.
49. **Token lifetimes may be set per client.** `ClientRecord.ttl` takes `code`, `accessToken`, `idToken` and `refreshToken`, each held to the bounds of its `ProviderTtl` field and falling back to it. The interaction lifetime stays provider-wide, since it is the app's login and consent time. The SSO application registers each app with its own lifetimes. A store keeps a revoked grant's marker for the longest refresh token lifetime of any client plus the longest access token lifetime.
50. **`acr_values`, `claims_locales` and `display` reach the app** on the interaction, as `acrValues`, `claimsLocales` and `display`. They are requests the app chooses whether to honor; the `acr` it reports in the grant says what it did. The SSO application has MFA policies, and a client asking for a stronger authentication had no way to tell it. The `claims` parameter stays unsupported, as discovery says.
51. **A client may name the algorithm its ID tokens are signed with, and RS256 is preferred otherwise.** `ClientRecord.idTokenSigningAlg` signs with the first signing key of that algorithm, and a record naming one no key has is a `TypeError`. Without it, the first `RS256` key signs, or the first key when there is none. This reverses decision 12's "signed with the first signing key" for ID tokens; JWT access tokens still use the first key (decision 36). What decision 12 did not weigh: OpenID Connect Core §15.1 requires a provider to support `RS256`, and OpenID Connect Registration makes it the default for a client that registers no `id_token_signed_response_alg`, so a provider whose first key is `EdDSA` or `ES256` broke relying parties that verify only `RS256`. Rejected: signing every ID token with RS256 whatever the keys, which forbids a provider without RSA keys.
52. **A confidential client may go without PKCE when it sends a `nonce`; this reverses invariant 1.** `ClientRecord.requirePkce` is `true` by default and cannot be `false` for a client whose `auth.method` is `none`. A `code_challenge` that is sent is always enforced. A request from a client with the flag off that carries no challenge must carry a `nonce`, which the provider binds to the code and puts in the ID token. A code issued without a challenge refuses a token request that carries a `code_verifier` (RFC 9700 §2.1.1, PKCE downgrade). Turning the flag off is the operator's assurance that the client checks the `nonce`, the condition OAuth 2.1 §7.5.1.1 and RFC 9700 §2.1.1 set for going without PKCE. What invariant 1 did not weigh: the OpenID conformance plans that are its own 0.1 criterion (decision 39), whose modules send no `code_challenge` but one, and confidential clients of relying-party libraries that send none, which the SSO application will serve. The conformance module `oidcc-ensure-request-without-nonce-succeeds-for-code-flow`, which sends neither PKCE nor a `nonce`, is a known failure argued in the certification submission. Rejected: a third client setting that waives the `nonce` too, which lets an operator register a client with no defense against code injection to pass one module; keeping invariant 1, which fails most of the plan at its first request.
53. **Back-channel logout ships as a request the app sends; this reverses part of decision 38.** A client record may hold `backchannelLogout: { uri, sessionRequired? }`, an `https` URI checked like the provider's own URLs (decision 7). `backchannelLogout({ clientId, subject?, sessionId? })` returns a `POST` `Request` carrying a `logout_token` (OpenID Connect Back-Channel Logout 1.0), or `null` when the client is unknown or registered none, and throws `TypeError` without `subject` or `sessionId`, or without `sessionId` for a client that requires it. The token is signed like that client's ID tokens (decision 51), typed `logout+jwt` so it never verifies as an ID token (invariant 6), and carries `iss`, `aud`, `iat`, `exp` 120 seconds later, a random `jti`, the logout event, `sub` and `sid` as given, and never a `nonce`. The request has `redirect: "manual"`, since a redirect would forward a bearer credential to a URI the client never registered. Discovery advertises `backchannel_logout_supported` and `backchannel_logout_session_supported`. What decision 38 did not weigh: the SSO application is the consumer it waited for, and its scope asks for single sign-out that works without the browser. The provider still keeps no sessions and makes no outbound requests: the app tracks which clients it signed into during a session, sends the requests, and owns timeouts, retries and egress rules. Rejected: the provider sending the requests, which adds an outbound fetch, retries and their failure modes to a package that has none on this side; front-channel logout and session management, which stay not planned. The client receives it too: `client.readBackchannelLogout(request)` requires a `POST` form body within the provider's body limit carrying exactly one `logout_token`, and `client.verifyLogoutToken(token)` runs the checks of §2.6 with the ID token's key set and algorithms, returning `{ subject?, sessionId?, jti, issuedAt, expiresAt }` or every issue as `invalid_logout_request` or `invalid_logout_token` (`azp_mismatch` as for ID tokens). `typ` must be `logout+jwt`, so a token without it is refused, and the ID token check refuses `logout+jwt` as it refuses `at+jwt`, since a logout token carries no `nonce` and nothing else would refuse one returned on refresh; `events` must hold the logout event as an object; `sub` and `sid` must be non-empty strings when present, with at least one, and `sid` is required when `createClient` gets `backchannelLogout: { sessionRequired: true }`; a `nonce` is refused. The client stores nothing: refusing a replayed `jti` until `expiresAt` plus the clock tolerance, ending the matching sessions, and answering `200`, or `400` with an error, with `Cache-Control: no-store` (§2.8), are the app's. A token that names no live session still answers `200`, since the session is ended either way. Rejected: accepting a token without `typ` for providers that omit it, since `typ` is what keeps the same provider's ID and access tokens out and relaxing it later is compatible while tightening is not; a `jti` store in the client, which would be the package's first state on this side and needs storage that spans the app's instances; `sessionRequired` as an argument of each call, when it is a property of the client's registration; a key set of its own, which would fetch the JWKS twice; a response helper now, until apps show the response they need.
54. **`onRefresh` lets the app refuse a refresh.** The provider calls it with a frozen `{ subject, clientId, scopes, grantId, sessionId? }` after the refresh token is consumed and every record check passes, before it issues tokens. `false` answers `invalid_grant`, revokes the grant, and reports `refresh_refused` to `onDiagnostic`; a value that is not a boolean is a `TypeError`, and a throw or rejection propagates (decision 17) without revoking, since the spent token makes the client's next attempt a reuse that revokes the family anyway. Without it, a user who is disabled, loses a role an app requires, or revokes consent kept refreshing until the family expired, 30 days by default. Rejected: a rule in the SSO application that every action ending access revokes the matching grants, which one forgotten code path breaks; a store method listing grants by subject, which every adapter would carry for the same effect.
55. **Scope claims may go in the ID token, per client; this reverses part of decision 12.** `ClientRecord.idTokenClaims`, `false` by default, puts the claims the granted scopes release in every ID token issued to that client, at the code exchange and each refresh, from the same `claims` callback and filtering userinfo uses. Protocol claim names (`iss`, `sub`, `aud`, `exp`, `iat`, `auth_time`, `nonce`, `acr`, `amr`, `azp`, `at_hash`, `c_hash`, `sid`, `jti`, `nbf`, `events`, `cnf`) are dropped from what the callback returns. The claims are fetched before a refresh token is saved, at the code exchange as at each refresh, so a failing callback leaves none the client never receives; the code or refresh token it presented is spent all the same, and the retry revokes the grant as a replay or a reuse, as for `onRefresh` (decision 54). Userinfo is unchanged. What decision 12 did not weigh: relying parties that read only the ID token and never call userinfo, such as Kubernetes' API server OIDC authenticator and many "Sign in with" integrations that expect `email` there, which a general identity provider serves. Rejected: a provider-wide option, which puts personal data in the ID tokens of every client to serve a few; both a provider default and a client override, one more option for no case the per-client flag misses.
56. **Configuration changes by rebuilding the provider, and a client may hold scopes the provider does not list; this reverses part of decision 20.** `createProvider` does no I/O and keeps no state between requests, so the app rebuilds it when keys, scopes or options change, or per request on Workers; tests show a rebuilt provider honoring the codes and tokens of the one before, and key rotation by order across rebuilds. A requested scope is accepted when it is a valid scope token and the client's record lists it, whether or not the provider's `scopes` option names it; one the option does not name releases no claims, and discovery's `scopes_supported` lists only the option's. A refresh `scope` is checked the same way before the token is spent, so one the client's record lists and the family does not hold is now refused after it, where decision 20 refused a scope the provider did not define before it. What decision 20 did not weigh: a scope that lives only in the client's record, as an app-defined one does. The SSO application edits keys, apps and scopes from its dashboard, and an app-defined scope such as `data:<namespace>:read` then lives only in its database. Rejected: setters or a reload method on the provider, which add mutable state that the rebuild already avoids and that Worker isolates would not share. A refresh narrows to the scopes the client's record still lists. Without a `scope`, it issues the family's scopes the record lists; a requested `scope` is already checked against the record before the token is spent. The family's stored scopes are unchanged, so listing a scope again restores it on the next refresh. `onRefresh`, the access token record and the ID token's claims get the narrowed scopes, and the response's `scope` names them (RFC 6749 §5.1). A client that refreshes uses `authorization_code`, whose record must list `openid`; a record without it is a `TypeError` read before the token is spent, so narrowing never drops `openid` and needs no check of its own. A record that drops `offline_access` drops it from the issued scope but still rotates the refresh token, as a request that leaves it out does. Without the narrowing, a scope an admin removed from an app kept being issued on every refresh until the family expired. Rejected: refusing the refresh and revoking the family when the record lost one of its scopes, which signs the user out for an edit that only narrows their access; leaving it to `onRefresh`, which can refuse a refresh but not narrow it.

### Requested for the SSO application's resource servers, approved by the maintainer

The SSO application serves a data API beside the provider, whose app-defined `data:<namespace>:*` scopes (decision 56) gate the records it holds for each user ([its scope](https://github.com/codenhub/symbolon/blob/main/docs/scope.md), sections 3 and 4). That API needs tokens restricted to it that carry the user's roles, and a way to check them. Token introspection (RFC 7662) stays out of scope (section 2): the API runs beside the provider, over the same store, and a network round trip to its own provider would only add a credential to manage and a failure mode.

57. **`authenticate` checks a bearer token for the app's own API.** `Provider.authenticate(request, { scopes?, audience? })` reads the `Authorization: Bearer` header only, through the parser userinfo uses, finds the access token by its digest, checks its expiry, then that its `audience` includes the required one, then that it carries every required scope. The value is a frozen copy of the access token record. A failure carries a ready RFC 6750 §3 response, without CORS headers, and a `reason` for the app's logs: a missing token gets a bare `Bearer` challenge, a malformed header `400 invalid_request` as userinfo answers it, a missing scope `403 insufficient_scope` naming the required scopes, and every other refusal, an audience mismatch included, `401 invalid_token`. The audience is checked first, so a token for another API learns nothing about this one's scopes. It never throws for a request, rejects only when the store does or with a `TypeError` for malformed options, and reports nothing to `onDiagnostic`, since a refused API call is the API's to log. Without it, the SSO application's data API would repeat the digest, lookup and expiry checks against the store, and an opaque token has no other check. Rejected: a resource endpoint the provider routes itself, which would own the API's paths and CORS; returning only a boolean or the record, which leaves every API to build the challenge; reporting failures to `onDiagnostic`, which mixes a public API's traffic into the provider's diagnostics.
58. **`accessTokenClaims` adds the app's claims to JWT access tokens.** `ProviderOptions.accessTokenClaims` is called with a frozen `{ subject, clientId, scopes, audience, grantId }` for every JWT access token, at the code exchange, each refresh and `client_credentials`, and returns an object of claims or a promise of one. Claims the provider sets or could set (`iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti`, `scope`, `auth_time`, `acr`, `amr`, `nbf`, `cnf`, `azp`), and any other claim the token sets, are dropped by name, as decision 55 drops them from ID tokens, and only own enumerable data properties are read. A result that is not a plain object is a `TypeError`, and a throw propagates (decision 17). At a refresh it runs before the next refresh token is saved, as decision 55 orders the ID token's claims. Given with opaque access tokens it is a `TypeError` at creation, since nothing would carry the claims. Without it, the SSO application's data API, verifying offline, had no way to learn the user's roles but a call back to the app per request. Rejected: claims released by scope, as the ID token's are, which ties roles to consent scopes they are not; a per-client option, since the claims depend on the resource server, which `audience` already names; storing the claims on the access token record for `authenticate`, which changes the persisted format for a caller that can look the roles up itself.
59. **Resource indicators (RFC 8707) restrict a token to the resource servers it is for; this reverses part of decision 36, and invariant 9 for `resource`.** `ClientRecord.resources` lists the URIs a client may name, each absolute, without a fragment and of visible ASCII, and a record that breaks that is a `TypeError`. `resource` is the one parameter that may repeat, at authorization and at the token endpoint, and a value sent twice counts once. At authorization each must be in the client's list, or the request redirects with `invalid_target`, and the interaction carries them as `resources` for the consent page; the code and refresh token records keep them as `resources`, and rotation keeps them. At the token endpoint each must be in the client's list, checked before the code or refresh token is consumed, and within the grant's, checked after (decision 20); `client_credentials` checks only the list. The access token's audience is the token request's resources, else the grant's, else for a JWT the `accessToken.audience` option; it is saved as `AccessTokenRecord.audience`, and a JWT's `aud` is a string for one value and an array for several. Every new persisted field is optional, so existing records stay valid, and the conformance cases check that a store returns an absent field as absent. What decision 36 did not weigh: the second resource server it waited for is the SSO application's data API, and a token meant for one API that another accepts is the confused deputy an audience prevents. Rejected: letting a token request name a resource the authorization did not, which RFC 8707 permits and which grants what the user never saw on the consent page; letting `completeAuthorization` narrow the resources, which no consent page of the SSO application needs yet and which can be added later without a break. The client sends `resource` through a `resource` option of `authorize`, `refresh` and `clientCredentials`, validated as `ClientRecord.resources` is, with a `TypeError` that never repeats the value, deduplicated, and capped at 20 values, since the provider reads at most 32 parameters and an authorization request sends up to 12 others. The option takes the protocol's name, as `scope` does. `callback` sends none, so the code exchange issues for every resource of the grant; a client narrows at a refresh. Without it, a client of this package could not ask for a restricted token at all, and the SSO application's own apps are such clients. A refresh that names no resource is for the family's resources that the client's record still lists, as decision 56 has scopes narrowed: a resource an admin removes from `ClientRecord.resources` stops being issued on the next refresh, the family keeps its resources so listing it again restores it, and when none is left the token falls back as one for a grant without resources does, to `accessToken.audience` for a JWT and to no audience for an opaque token. Narrowing only drops resources, so it never widens what the family covers, and the fallback is the audience any grant of the client that names no resource gets. A named resource is checked against the record before the token is spent and against the family after, as before. Rejected: leaving the narrowing to `onRefresh`, which can only refuse the whole family rather than drop one resource, and which every app would have to write to get what the record already says.

### Requested for the SSO application's privacy and audit, approved by the maintainer

60. **`subjectTypes` advertises pairwise subjects the app derives; this reverses part of decision 38.** `ProviderOptions.subjectTypes`, `["public"]` by default, is published as discovery's `subject_types_supported`; a value that is not a non-empty array of `public` and `pairwise` without repeats is a `TypeError` at creation. The provider still never derives or checks a subject: the app passes each client's `subject` to `completeAuthorization`, as decision 38 found it could, and gets that value back wherever the provider names the user (`claims`, `onRefresh`, `accessTokenClaims`, the record `authenticate` returns) and passes it to `backchannelLogout`. `provider.md` shows a derivation by OpenID Connect Core §8.1, an HMAC of the sector identifier and the local identifier under a secret key, and says the app keeps a table back to its users, since the hash cannot be reversed. `ClientRecord` gets no `subjectType`: which clients get pairwise subjects is the app's choice, made where it computes the subject, so the provider would persist a field it never reads, and with dynamic registration out of scope (section 2) no client registers `subject_type` through it. An optional field can be added later without a break, should the provider need to see the choice. What decision 38 waited for is the consumer: the SSO application's scope (section 4) asks for pairwise subjects for privacy, and a relying party reads `subject_types_supported` to learn whether it may ask for them. Rejected: deriving subjects in the provider from a salt option, which needs a sector identifier the client record does not hold and leaves the app without the mapping back to its users; `ClientRecord.subjectType` checked against the option, which makes every adapter store a field for a check the app already makes when it picks the subject.

61. **`onDiagnostic` receives the refused request as its second argument.** `handle` calls `onDiagnostic(diagnostic, request)` with the same `Request` object it was given, at the token, userinfo and revocation endpoints alike; the diagnostic is unchanged and still holds no request value (decision 28). The parameter is additive: a callback that takes one argument keeps working, and so does its type. A token or revocation request refused after its body was read rejects a second read, one refused for its content type still has its body unread, and userinfo reads none, so the body is not part of what the callback can use. `provider.md` says to log chosen headers and the URL's path, and never the URL's query, which the client wrote, the `authorization` header or the body, which carry the client's credentials and tokens. What decision 28 did not weigh: an audit log records who was refused as well as why, and the SSO application's audit log needs the user agent and the client address, which only the request carries; without it, an app wraps `handle` and cannot match a refusal to its request. Rejected: copying chosen headers into the diagnostic, which fixes a list of headers that differs by platform and proxy, and makes the frozen diagnostic hold request values; a clone of the request with an unread body, which costs a copy of every refused body and hands the callback the very secrets it must not log.

### Taken in the 0.1 release audit, approved by the maintainer

62. **A sign-in honors the client's record as it is when it completes.** `completeAuthorization` reads the client's record for a denial as well as a grant, and answers `interaction_not_found` without a redirect when the client was removed, no longer lists the interaction's redirect URI, or no longer has the `authorization_code` grant type. A grant's code holds only the granted scopes and the interaction's resources that the record still lists, and the code exchange narrows its tokens to the record again, as a refresh does (decisions 56 and 59), while the family keeps the code's scopes and resources. Without it, an admin who removed a redirect URI or a scope while a user was signing in still saw the code sent to that URI, and the first tokens carry that scope, for up to `ttl.interaction` plus the code's lifetime, against invariant 3. Rejected: refusing the sign-in when a scope or resource was removed, which fails a user for an edit that only narrows their access.
63. **Userinfo does not check an access token's audience.** A token restricted to resource servers with `resource` (decision 59) is answered at userinfo like any other, and the docs say so. What decision 59 did not weigh is userinfo itself: a resource server that holds such a token can read the claims its scopes release. Refusing a token whose audience lacks the issuer would break this package's own sign-in, since `callback` names no resource and the code exchange's token is then for the grant's resources; refusing only a token whose audience came from a token request's `resource` needs a new persisted field on the access token record. Neither is needed while the SSO application lists in `resources` only servers it operates. The docs tell the app to list only servers it trusts with those claims. Revisit when a consumer lists a resource server it does not operate.
64. **The client accepts an ID token of up to 65536 characters.** `@codenhub/jwt`'s default of 8192 refused the ID token of a client with `idTokenClaims` and a few hundred groups (decision 55's Kubernetes case) after the code was spent, so that user could never sign in. 65536 is the verifier's ceiling and the token response's own cap, so the cost stays bounded, and no option was added. Rejected: a provider that refuses to sign an ID token over 8192 characters, which fails the same users at the other end; documenting the limit only, which leaves them unable to sign in.
65. **What the conformance cases check of a client record, and what they cannot.** The `findClient` cases check every optional field and that a `client_secret_jwt` key still verifies, so an adapter written before those fields passes no longer. No case seeds a `private_key_jwt` client: a `KeySet` cannot be exported, so a persisting adapter could not store the seed, and changing `StoreSeed` to carry JWKs is a contract change no consumer has asked for. The concurrent cases cannot prove atomicity against an adapter whose queries a single connection serializes, and `store.md` says so. `authenticate`'s `audience` stays optional, as decision 57 has it: an API that every access token may call needs none, and `provider.md` already says that leaving it out accepts a token for another resource server. A refreshed ID token is still held to the original `sub` only: `iss` and `aud` are checked on every ID token, and holding `auth_time` to the original would need a new `refresh` option for a harm no case shows.

### Taken in the 0.1 release review, approved by the maintainer

66. **A client assertion's `aud` is the issuer identifier alone; this reverses part of decision 15.** The provider verifies the assertion with the issuer as the audience and accepts it only when `aud` is that single string; the token endpoint URL, and an array even when it holds only the issuer, are `invalid_client`. The client signs `aud` as the issuer by default, and `ClientAuth`'s `audience` option, `"issuer"` or `"token_endpoint"`, names the token endpoint for a provider that refuses the issuer; another value is a `TypeError` at creation. What decision 15 did not weigh: draft-ietf-oauth-rfc7523bis, written after attacks in which a client's assertion for one authorization server is collected by another posing as it, makes the issuer the only audience, and a token endpoint URL is the very value such a server can claim. Rejected: keeping both audiences on the provider, which leaves this package's provider open to that replay; signing the token endpoint by default on the client, which every provider following the draft refuses.
67. **Decision 23 stands, with its reason corrected.** A captured assertion is not useless while it lives: for a client with the `client_credentials` grant it mints access tokens for up to 360 seconds. `provider.md` and `security.md` said a replay "gets nothing", and now say what it gets. Remembering `jti` values still costs every store a table and a write per token request, and decision 66 narrows where an assertion can be captured to this provider's own token endpoint, over TLS. Rejected again: a `jti` table, for the same cost decision 23 weighed.
68. **`findClient` matches the identifier byte for byte.** The contract and `store.md` say so, a conformance case checks that a different letter case or a surrounding space finds nothing, and the provider treats a record whose `clientId` differs from the one it asked for as no client, through one helper every endpoint uses. Without it, a store over a column with a case-insensitive collation answered `APP` with the record of `app`, and the provider then issued tokens naming the identifier the request sent. Rejected: normalizing identifiers in the provider, which picks one store's rules for every store.
69. **`id_token_hint` is as long as an ID token the client accepts.** At the authorization and end-session endpoints, `id_token_hint` alone is exempt from the 4096-character parameter cap, the hint is verified with a length limit of 65536 (decision 64's), and a `POST` body to those endpoints may hold 81920 bytes; a `GET` stays within the 8192-character URL. Without it, a client with `idTokenClaims` (decision 55) whose ID tokens passed 4096 characters could not log out with its hint, which RP-Initiated Logout recommends sending. Rejected: raising the cap for every parameter, which widens what every other parameter may cost to serve one.
70. **The provider verifies an `id_token_hint` at authorization and hands it to the app, without enforcing it.** `AuthorizationInteraction.idTokenHint` is a frozen `{ subject, sessionId? }` from a hint verified as at logout, expired or not; a verified hint issued to another client redirects with `invalid_request`, path `["id_token_hint"]`, and one that does not verify is ignored, as OpenID Connect Core §3.1.2.1 allows. `provider.md` shows the app answering `login_required` when its session's user differs. The hint is not saved with the interaction, so the persisted format is unchanged. What was missing: the provider ignored the parameter, so a `prompt=none` request from a client that named a user could be answered for whoever the app had signed in. Rejected: enforcing it in the provider, which keeps no sessions and cannot know who is signed in; saving it on `InteractionRecord`, a persisted field nothing reads at completion.
71. **`CodeRecord.maxAgeRequested` is removed.** The provider wrote it and nothing read it, since `auth_time` is in every ID token whatever the request asked. A store that still returns it is unaffected, and an adapter that wrote the column can drop it. Rejected: keeping it for a future reader, which every adapter pays for until one exists.
72. **A subject is 1 to 255 characters of visible ASCII, and a sparse list is refused.** `completeAuthorization` and `backchannelLogout` throw `TypeError` for a `subject` that is empty, longer than 255 characters, or holds a space, a control character or anything outside ASCII: OpenID Connect Core §2 caps `sub` at 255 ASCII characters, and a relying party compares it byte for byte, so a lookalike would name another user. Every list the provider reads from the app or a client record is read through `Array.from`, so a hole is `undefined` and refused, where `every` skipped it and an `amr` of `["pwd", <hole>]` passed. Rejected: accepting any non-empty string, which lets an app issue a `sub` a conforming relying party may refuse.
73. **Two client inputs settled.** A callback URL that is not absolute, such as a path a framework hands over, throws `TypeError`, since it is the app's mistake and no browser sends it; one over 8192 characters stays `invalid_callback`. An `expires_in` sent as a string of one to ten digits is read as the number it spells, since the code is spent when the response arrives and refusing a lifetime the client uses only to schedule a refresh fails the sign-in for good. Rejected: refusing a string `expires_in` as RFC 6749 §5.1's number, which locks out users of the providers that send one.
74. **A token whose client the store no longer finds is refused.** Userinfo and `authenticate` look the client up after the token, and refuse with `invalid_token`; `authenticate`'s reason and the diagnostic are `access_token_client_unknown`. Removing a client, or making `findClient` return `undefined` for it, which is how `store.md` now says to disable one, then cuts off its opaque tokens at once. It costs one store read per bearer request, the read every other endpoint already makes. What was missing: the SSO application disables apps, and a disabled app's access tokens kept working until they expired. Rejected: revoking the client's grants on removal, which needs a store method listing grants by client (rejected in decision 54) and still misses tokens saved meanwhile.
75. **`EndSession.sessionId` names the session of a hint that carries `sid`.** The app can end the session the client was signed in with, rather than every session of the user. Rejected: leaving the app to decode the hint itself, which `@codenhub/jwt` deliberately offers no unverified way to do.

Not added in this review, each recorded so it is not raised again without a new case: an `http` issuer for local development, since `@codenhub/jwt`'s remote key set refuses an `http` JWKS and a local certificate serves the SSO application's development mode without giving up `https` for the issuer; reading the userinfo access token from a `POST` body, which the roadmap leaves to the first conformance run.

### Taken in the full audit, approved by the maintainer

The maintainer asked for the best package, without regard to breaking changes or earlier decisions, and approved fixing every finding of the audit that does not need `@codenhub/jwt` 0.1.0.

76. **The provider reads `null` as absent in every optional field of the records it reads back from the store, and a client record stays strict.** `src/provider/records.ts` lists the optional fields of the interaction, code, access token and refresh token records as a compile-checked `Record` per type, so a new optional field fails to compile until it is listed, and `readInteractionRecord`, `readCodeRecord`, `readAccessTokenRecord` and `readRefreshTokenRecord` drop each optional member whose value is `null` before the provider uses the record. No `null` claim reaches an ID token, a `null` parameter a redirect, or a `null` member the value `authenticate` returns. A required field is left as it is, so a `null` `expiresAt` makes a token expired rather than ageless. `""`, `[]`, `0` and `false` stay values. The conformance case "a record saved without its optional fields comes back with each one absent" saves each record with none of its optional fields and passes missing, `undefined` or `null`, naming the field for anything else; it replaces the two narrower cases for `codeChallenge`, `resources` and `audience`. The earlier rule, that a store must return a missing field as missing and never as `null`, did not weigh that the obvious SQL adapter returns `NULL` for every unset column, so every such adapter had to remap each column or emit `"nonce": null` and `"acr": null` in ID tokens. Client records keep throwing `TypeError` on `null`: a client record is configuration the operator writes, read on every request, and a loud `TypeError` at the first request finds a bad row at once, while reading `null` as absent there would quietly change behavior, for example turning a `null` `requirePkce` into the default `true` or a `null` `ttl` into the provider's lifetimes. Rejected: reading `null` as absent in client records too, for that reason; refusing `null` in token records with a `TypeError`, which turns a common adapter shape into an outage; a normalization inside each handler, which would miss the next field added.
77. **`authorize` sends the remaining OpenID Connect request parameters, takes provider-specific ones through `extraParameters`, and rejects an unknown option.** New options: `acrValues` and `claimsLocales` (space lists under the `uiLocales` rules), `display` (`page`, `popup`, `touch`, `wap`), `idTokenHint` (well-formed Unicode, bounded only by the 8192-character URL), and `claims` (a plain object of JSON values at most 8 deep, sent JSON-encoded, at most 4096 characters; `claims_parameter_supported` is not checked, since providers that honour the parameter often do not advertise it). `extraParameters` is a plain object of at most 32 non-empty, well-formed strings of at most 4096 characters, sent after the client's own parameters. It refuses, naming the parameter, the 21 names the client sets or an option covers (`state`, `nonce`, `code_challenge`, `code_challenge_method`, `redirect_uri`, `client_id`, `response_type`, `response_mode`, `scope`, `prompt`, `max_age`, `login_hint`, `ui_locales`, `acr_values`, `display`, `id_token_hint`, `claims_locales`, `claims`, `resource`, `request`, `request_uri`), because overriding any of them would break PKCE, state, or the client's validation, and `request`/`request_uri` would replace the whole request with one the client never checks. The built URL may hold at most 32 parameters, counting any query the authorization endpoint already has, which matches the provider's `MAX_PARAMETERS`, so a request this client builds is one this package's provider reads. A member of the options that is not an option throws `TypeError`, quoting its name only when it looks like an identifier, so a misspelt `loginHint` is not silently dropped and a value pasted as a key never reaches the message. Rejected: passing extras through unchecked, which lets an app overwrite `state` or `redirect_uri`; letting an extra override an option, which gives two ways to send one parameter; a separate cap on extras' total length, which the URL limit already enforces; checking `claims_parameter_supported`, which would refuse requests providers accept.
78. **`responseMode: "form_post"` is supported, and `callback` takes the `Request` itself.** `authorize` accepts `responseMode` of `query` (the default, not sent) or `form_post`, refused with `TypeError` when the metadata lists `response_modes_supported` without `form_post`; when the list is absent, the mode is allowed. `pending.responseMode` records `form_post`, so the callback knows how the response must arrive. `callback` now takes a string, a `URL`, or a Fetch API `Request`. The method must match `pending`: a query sign-in takes a string, a `URL` or a `GET` request, and a `form_post` one takes a `POST` request; anything else is `invalid_callback` at `["callback", "method"]`, checked before any body is read. A posted body is read with the shared `readBody` and `parseParameters`, under the same limits as a back-channel logout request (16384 bytes, the form content type, 32 parameters, 4096 characters each), with `invalid_callback` at `["callback", "headers", "content-type"]` or `["callback", "body"]` and a `reason`. A `Request` whose body was already used throws `TypeError` (`assertBodyUnread`), since that is the app's mistake. `SignIn` gains `parameters`, the response's parameters other than `state`, `code` and `iss`, frozen, which carries Apple's `user` and Entra's `session_state`; the docs say none of them is vouched for and that `pending` needs a `SameSite=None` cookie or a store for this mode, since the post is cross-site. Rejected: accepting a POST for a query sign-in, or the reverse, which lets an attacker choose the channel; a `parameters` that includes `code`, which puts a credential in an object apps log; parsing `user` for the app, which would present unsigned data as verified.
79. **A multi-tenant Microsoft Entra ID issuer is accepted through a `{tenantid}` template, as an explicit exception to invariant 5.** Invariant 5 requires exact issuer matching everywhere. Entra's multi-tenant endpoints (`common`, `organizations`, `consumers`) publish `issuer` as `https://login.microsoftonline.com/{tenantid}/v2.0`, and each token names its tenant's own issuer, so no exact match can succeed and every app had to either skip the issuer check or not use this package. The exception is opt-in and narrow. `discover(issuer, { tenantIssuer: true })` accepts a document whose `issuer` is the template with `{tenantid}` once, as a whole path segment, when the requested issuer is that template with one segment in its place; without the option the document is `issuer_mismatch` as before. `createClient` requires `tenantIssuer` (`true` or `{ tenants }`, at most 100 identifiers) exactly when `metadata.issuer` is a template, and throws otherwise. For ID tokens, logout tokens and signed userinfo responses, the verifier's exact issuer check is dropped and `iss` is required instead; after the signature, the `tid` claim must match `[A-Za-z0-9-]+` and be listed in `tenants` when they are given, and `iss` must equal the template with that `tid` substituted. Failures report `wrong_issuer` at `payload.tid` or `payload.iss`. The callback's `iss` parameter is held to the same rule. A tenant client must address its assertion to `token_endpoint`, since the template names no single issuer. The exception does not widen exact matching anywhere else: a template is never accepted by default, a token is bound to the tenant it names, and the substitution is a fixed string, never a pattern. What invariant 5 did not weigh: the most widely deployed enterprise provider cannot be used with it, and apps that work around it disable the issuer check entirely, which is worse than a checked template. Rejected: a caller-supplied issuer predicate, which hands the check to every app; accepting any issuer whose JWKS verified, as some libraries do, which lets one tenant's token pass as another's; a wildcard or regular expression issuer, which is easy to write too broadly; requiring `tenants`, which would make the option useless for the multi-tenant apps it exists for.
80. **`RefreshCheck` carries the sign-in's authentication context, the family's resources, and the times an idle-timeout or age policy needs.** `onRefresh` now receives `authTime`, `amr?`, `acr?`, `resources?`, `issuedAt?` and `expiresAt`, beside `subject`, `clientId`, `scopes`, `grantId` and `sessionId?`, frozen with its arrays. `issuedAt` is a new optional field of `RefreshTokenRecord`, set to the time of the code exchange and anew at each rotation, so `now - issuedAt` is how long the family has been idle; it is optional so rows saved before 0.1.0 still read, and those rows report no `issuedAt`. `expiresAt` was added beyond the brief, since an absolute-lifetime policy otherwise has to re-read the store. `docs/provider.md` shows an idle-timeout example, falling back to `authTime` for an old row, and an MFA policy that keeps `payments:write` only for a second-factor sign-in under 12 hours old. Decision 54 chose `{ subject, clientId, scopes, grantId, sessionId? }` as enough for entitlement checks; it did not weigh idle timeouts or step-up policies, which need the time of the last refresh and how the user signed in, and which the app cannot look up because the provider holds those values only in the refresh token record. Rejected: a separate `idleTimeout` option, which fixes one policy in the package where a callback serves all of them.
81. **An opaque access token's record carries how it was issued, and the claims callbacks learn the session and grant.** `AccessTokenRecord` gains optional `grantType`, `authTime`, `amr` and `acr`. `grantType` is optional when read, for rows saved before 0.1.0, and always written: `authorization_code` for a code exchange and each refresh, `client_credentials` for a client's own token. `authTime`, `amr` and `acr` are copied from the grant for a user's token and absent for a client's. `authenticate` returns all four when the record has them, and `docs/provider.md` warns that an API requiring them must refuse a token that lacks them rather than read the lack as a weak sign-in. `AccessTokenClaimsRequest` gains `sessionId?`, and `ClaimsRequest` gains `grantId` and `sessionId?`. The memory store copies the new fields, and the conformance fixtures carry them. Decision 57 returned the record as stored; it did not weigh that an API beside the provider has no other way to tell a client's token from a user's, or a step-up sign-in from a password one, when the token is opaque. Rejected: deriving `grantType` from `subject === clientId`, which breaks for a user whose subject equals a client identifier.
82. **A `client_secret_jwt` client registers a non-empty list of keys, and any of them authenticates it.** `ClientAuthentication` for `client_secret_jwt` is now `{ method: "client_secret_jwt"; keys: readonly SecretKey[] }`. The record check throws `TypeError` for a missing, non-array or empty `keys`, or an entry that is not a secret key, including the old single `key`. Client authentication verifies the assertion with every key, each through its own `createKeySet([key])`, and ORs the results without stopping at the first, as `secretHashes` does, so the time does not show which key matched. Each key needs its own key set because `@codenhub/jwt` 0.0.1 picks one key per `alg` when the assertion has no `kid` and does not try keys in turn, and the peer stays at 0.0.1. The memory store copies the list, so a caller that mutates it later does not change the next find, and keeps the key objects by identity. The conformance case "findClient returns a client_secret_jwt client whose keys still verify" registers two extractable keys and checks the count and that each key, in order, verifies what its original signed. This is a breaking change to the record shape. Decision 9 put the secret in the record as one `SecretKey`; it did not weigh rotation, which `secretHashes` already supports for the other secret methods, so a `client_secret_jwt` client could only change its secret with downtime. Rejected: `key | keys` accepted side by side, which keeps two shapes in every adapter for a package not yet at 1.0; a `kid` on each key, which asks every client to send one.
83. **`createClient({ openid: false })` makes a plain OAuth 2.0 client for providers without ID tokens, and a token endpoint error is an error at any status.** With `openid: false`, the metadata's OpenID members (`jwks_uri`, `response_types_supported`, `subject_types_supported`, `id_token_signing_alg_values_supported`) become optional but are still checked when present; the issuer stays required, as the client's name for the provider. No key set is created. `authorize` sends no `nonce`, no default scope, and no `openid` requirement, and rejects the OpenID-only options with `TypeError`; `callback` returns `{ tokens, parameters }`, ignoring any `id_token`; `refresh` takes no `previous`; `userinfo` takes no `subject` and returns the provider's JSON as is, frozen, accepting JSON only. `backchannelLogout` and `tenantIssuer` throw, and the returned `OAuthClient` type has no logout methods, so the overloads keep claims out of its types. Separately, a token response with an `error` member is `provider_error` even at HTTP 200 (GitHub answers that way), with `params.error` the code when it is a string and `unknown` otherwise; and every token, userinfo and revocation request sends `Accept: application/json`, without which GitHub answers with a form body. GitHub's comma-separated `scope` is kept unsplit, and the docs say to split it. Rejected: a separate `createOAuthClient` export, which duplicates the whole surface; inferring the mode from missing metadata, which would turn an incomplete OpenID document into a silently weaker client; splitting `scope` on commas, which RFC 6749 does not allow and would mis-split a scope that contains one.
84. **Verification keys are published and accepted but never sign, and a rotation moves a key through them.** `ProviderOptions.verificationKeys`, at most 16 `@codenhub/jwt` public keys, each with a `kid` unique among them and the signing keys, is published at the JWKS endpoint after the signing keys' public halves and accepted wherever the provider verifies a token it issued (today the `id_token_hint` at authorization and logout). Its algorithms are not added to `id_token_signing_alg_values_supported`, since no ID token is signed with them, and `ResolvedOptions.publicKeys` stays the signing halves so `idTokenSigningAlg` still resolves against signing keys only. "Rotating a signing key" now pre-publishes the new key as a verification key, swaps it into `signingKeys` with the old key moved to `verificationKeys`, then drops it once its tokens expire, and warns that adding the first `RS256` pair or reordering `signingKeys` changes which key signs ID tokens (decision 51) and JWT access tokens (decision 36) at once. What the earlier rotation (`[old, new]`, then `[new, old]`) did not weigh: under decision 51 a new `RS256` pair placed second already signs every ID token of the clients that name no algorithm, so step 1 published and started signing in the same rebuild, and the retired key's private half had to stay loaded. Rejected: a per-key `use: "verify"` flag inside `signingKeys`, which mixes two shapes in one list and still needs a private key; advertising verification algorithms, which would tell relying parties to expect ID tokens nothing signs.
85. **The provider answers `response_mode=form_post`, and its page is the one HTML it renders; this reverses section 3's "the provider never renders HTML".** `beginAuthorization` accepts `query` and `form_post`; the fragment mode and JARM stay `invalid_request` with path `["response_mode"]`, answered in the query. The mode is read once the redirect URI is verified, so every response to that URI honors it: the grant and denial of `completeAuthorization` and every redirecting failure of `beginAuthorization`, including those found before `response_mode` itself is checked. It is saved as the optional `InteractionRecord.responseMode`, set only for `form_post`, so absent (or `null` from a SQL column) means the query and older records complete as before. The page is fixed: hidden fields with every name and value HTML-escaped, an auto-submit script, and a `noscript` Continue button; headers `Content-Security-Policy: default-src 'none'; script-src '<sha256 of the script>'; form-action <redirect origin>; frame-ancestors 'none'; base-uri 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, no CORS. A redirect origin a CSP source cannot express (a host holding `;` or other characters outside a host's syntax) leaves `form-action` out rather than write it into the policy. Discovery advertises `response_modes_supported: ["query", "form_post"]`. What the earlier rule did not weigh: relying parties such as ASP.NET's OpenID Connect middleware default to `form_post`, and the query leaks the code into history, logs and `Referer`, while the page carries nothing the app could style and needs no template from it. Rejected: returning the parameters for the app to render, which hands every app an XSS-prone template; supporting the fragment mode, which the code flow never needs; JARM, which signs responses the client does not verify today.
86. **`prompt=create` reaches the app, and unrecognized parameters reach it as `extensions`.** `Prompt` gains `create` (Initiating User Registration via OpenID Connect 1.0); `none` still stands alone, so `create none` is `invalid_request`; discovery advertises `prompt_values_supported: ["none", "login", "consent", "select_account", "create"]`. `AuthorizationInteraction.extensions` is a frozen record of every parameter outside the set the provider reads, refuses or ignores by design (the OAuth and OpenID Connect authorization parameters, `claims` among them), built with `Object.fromEntries` so `__proto__` is an own member, bounded by the existing front-channel limits (32 parameters, 4096 characters, no repeats), absent when empty, and saved as the optional `InteractionRecord.extensions`. The client's `authorize` accepts `create` too. What was missing: an app could not tell a sign-up request (`prompt=create`, or Auth0-style `screen_hint=signup`) from a login, and an unknown `prompt` failed the request. Rejected: an always-present `extensions: {}`, which differs from every other optional interaction member; passing `claims` through, which would suggest the claims parameter is honored; a configurable allow-list, which adds an option for what the app can filter itself.
87. **The app can deny with `temporarily_unavailable`, `server_error` or `unmet_authentication_requirements`.** `AuthorizationDenial` and `completeAuthorization`'s shape check accept the three, and `OAuthErrorCode` gains `unmet_authentication_requirements` (OpenID Connect Core Unmet Authentication Requirements 1.0; the other two were already there), so the client reports it as `provider_error` with that code rather than `unknown`. `provider.md` has a table of when to send each denial and `errors.md` a summary. What was missing: an app whose user store was down, or that could not meet an essential `acr`, had no denial that said so, and either sent `access_denied`, which tells the client the user refused, or left the user on its own error page with the client waiting. Rejected: letting the app send any string, which lets a typo reach the client as a code no library knows.
88. **`metadata` adds discovery members the provider does not compute.** `ProviderOptions.metadata` is copied, deep-frozen and appended after the computed members. `createProvider` throws `TypeError` for a member the provider computes (`createProvider: metadata.<name> is a member the provider computes`), for a value that is not JSON data (only strings that are well-formed Unicode, finite numbers, booleans, `null`, dense arrays and plain objects, with no accessor), for an empty top-level name, for nesting deeper than 16, and for more than 16384 characters of JSON or as many visited values. `provider.md` shows `acr_values_supported`, `ui_locales_supported`, `op_policy_uri` and `service_documentation`. What was missing: those members describe what the app implements, so the provider cannot compute them, and a relying party that reads `ui_locales_supported` or `acr_values_supported` had no way to see them. Rejected: letting `metadata` override computed members, which lets the document drift from what the endpoints enforce (the reason the document is computed); typed options per member, which grows the option surface for values the provider never reads.
89. **A diagnostic names the grant and subject of record, and a successful revocation is reported as `token_revoked`.** `ProviderDiagnostic` gains `grantId?` and `subject?`, both taken only from a record the store returned, never from the request. A token endpoint refusal after the code or refresh token was consumed carries both, a code or refresh replay carries the `grantId` the store reported and no `subject`, since the store returns only the grant then, and userinfo carries both for an expired token, a token of an unknown client and a token without `openid`. The revocation endpoint now calls `onDiagnostic` for a revocation that revoked a grant, with reason `token_revoked`, status `200`, and the grant and subject; `token_of_another_client` carries the grant too. A `200` for a token the store did not find revoked nothing and is not reported. The diagnostic stays frozen, and the hostile and leak suites check that no diagnostic holds a token, code, verifier or secret, and that the grant fields appear. `docs/provider.md` and `docs/security.md` say that a subject identifies a person, so a diagnostic log holds personal data. Decision 28 limited the callback to refusals and the payload to `{ endpoint, reason, status, clientId? }`; it did not weigh that an operator investigating a replay, which revokes a grant, could not tell which grant or user was affected, nor that a revocation is the security event an audit log most needs. Rejected: a separate `onEvent` callback, which doubles the option surface for one event; omitting `subject`, which makes a replay report useless to a support desk.
90. **Ending a user's, a session's or a client's grants is the adapter's sweep plus `revokeGrant` per grant, documented with its race.** `docs/store.md` gains "Revoking a user's, session's or client's grants". It says to index `subject`, `clientId`, `sessionId` and `grantId` across the code, access token and refresh token tables, to include codes not yet exchanged, and to call `revokeGrant` once per grant. It names the window a sweep leaves, a sign-in the app completes during it, and two ways to close it: make the provider refuse from the app's own state, through `findClient`, `onRefresh`, and `claims`, whose `ClaimsRequest` now carries `sessionId` and `grantId` so userinfo stops releasing claims at once; or repeat the sweep after the longest code lifetime. No code changed. Rejected: `revokeSubject`, `revokeSession` and `revokeClient` store methods, which every adapter would have to implement and which still could not see a grant a request in flight has yet to save.
91. **A lost refresh response signs the user out, and the client docs say how to avoid causing one.** Decision 10, reuse revokes the family, stands. `docs/errors.md` gains "A lost refresh response", and the refresh section of `docs/client.md` gains two rules: persist a rotated refresh token before using the new access token, and do not retry a refresh blindly after `request_failed`, since a retry of a request that did reach the provider is a reuse and revokes the sign-in; retry at most once, and treat `invalid_grant` as the end of the session. No code changed. Rejected: a grace period in which the previous refresh token still works, which RFC 9700 §4.14.2 permits but which needs a store method or a second state per token, and reopens the replay window decision 10 closes.
92. **A refreshed ID token is checked against the previous one as OpenID Connect Core §12.2 requires; this reverses part of decision 65.** `refresh` takes `previous`, the claims of the ID token the session holds, in place of `subject`; it is required in OpenID mode and checked like `pending`, throwing `TypeError` for a malformed value. A new ID token must have the same `sub` (`subject_mismatch`), and the same `iss`, `aud` (compared as a set, so `"app"` and `["app"]` match), and `azp` (absent when it was absent), and the same `auth_time` when both carry one; otherwise the new code `id_token_mismatch` at `["id_token", "payload", <claim>]`. A `nonce` is not required, but one that is present must equal `previous.nonce`, compared in constant time, or `nonce_mismatch`. What decision 65 did not weigh: §12.2 states these checks as MUST, so a conformant relying party needs them; a provider that mixes up sessions, or an attacker who can replace a refresh response with a token issued to the same user for another client, is caught by `aud` and `azp` but not by `sub`; and the new option costs the app nothing, since it already holds the claims it got at sign-in. Rejected: keeping `subject` beside `previous`, two ways to pass one thing; requiring `auth_time` to be present on both, which would refuse providers that omit it on refresh; comparing `aud` as an ordered array, which refuses an equivalent token.
93. **A `private_key_jwt` assertion may carry `x5t` and `x5t#S256` in its header.** `auth.header` for `private_key_jwt` accepts only those two members, as base64url strings of exactly 27 and 43 characters (a SHA-1 and SHA-256 digest), and any other member or a wrong length throws `TypeError` naming the option; on another method `header` is ignored, as any other unread member of `auth` is. Microsoft Entra ID finds a certificate credential by its thumbprint, so this is what makes certificate authentication work there. The header is copied before signing, so the caller's object is not held. Rejected: an open header, which `@codenhub/jwt` 0.0.1 would partly refuse (`crit`, `jwk`, `x5c` and others) and which lets an app send a `kid` that contradicts the key; computing the thumbprint from a certificate, which needs X.509 parsing this package does not carry; accepting a hex thumbprint, which certificate tools print but no provider reads.
94. **A userinfo response of `application/jwt` is verified and accepted.** The request now accepts `application/json, application/jwt`. A 200 JWT response is read within the 65536-byte cap, decoded as strict UTF-8, and verified with the provider's keys and the ID token algorithms, with no issuer or audience in the verifier and no `exp` required, as OpenID Connect Core §5.3.2 makes `iss` and `aud` optional there. When present, `iss` must be the issuer (or the tenant rule) and `aud` must contain the client, as `wrong_issuer` or `wrong_audience` at `["userinfo", "payload", ...]`; an access or logout token's `typ` is `wrong_type`; any other verification failure is `invalid_userinfo` with `params.jwtCode`. A five-segment JWE is `invalid_userinfo` at `["userinfo"]` with `reason: "encrypted"`, since this package holds no decryption key. `sub` is then checked as for JSON. Plain OAuth clients accept JSON only. Rejected: decoding without verifying, which presents unsigned claims as the provider's; requiring `iss` and `aud`, which the specification leaves optional; adding JWE support, which needs key management this package does not have.
95. **`createProvider` refuses a member that is not an option.** At the top level and in `endpoints`, `ttl` and `accessToken` (checked against the members of the chosen `format`), a member that is not an option, even one whose value is `undefined`, throws `TypeError` naming it, as `createProvider: ttl.acessToken is not an option`; a name longer than 64 characters is cut to 64 and `...`. `ClientRecord` is not checked this way: the app's store may carry columns of its own. This matches `@codenhub/jwt` 0.1. What was missing: a misspelled `ttl.acessToken` or `endpoint` was ignored, so the provider ran with the default the operator meant to change, which for a lifetime or an endpoint is a silent security difference. Rejected: a warning through `onDiagnostic`, which is for refused requests and fires too late; checking client records, which would break stores that return whole rows.
96. **The issuer and every configured endpoint must be written as the URL parser serializes them.** `createProvider` throws `TypeError` (`... must be written as the URL parser serializes it: a lowercase scheme and host, no default port, no dot segments, and percent-encoding as the parser writes it`) unless the value equals its WHATWG serialization, with one allowance: an empty path to which the parser adds `/`, so `https://op.example` stays valid and keeps its exact form in `iss`. What invariant 5's exact matching did not weigh: the provider used the issuer byte for byte while the parser routed requests and relying parties compared `iss` against their own normalized copy, so `https://OP.example` or `https://op.example:443/` produced tokens a strict client refuses and routes that never matched, with an error far from the cause. Rejected: normalizing the value silently, which makes `iss` differ from what the operator wrote and the relying party was configured with; allowing a dot segment that the parser removes, which yields the same mismatch.
