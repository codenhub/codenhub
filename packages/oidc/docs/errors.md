# Issues

Every operation on untrusted input returns a result instead of throwing. This page describes what a failed result holds, lists every code the package can return, and says which mistakes throw.

## The failed result

```ts
// What the client returned for a callback whose ID token had expired and named another audience.
const result = {
  ok: false,
  error: {
    issues: [
      { code: "invalid_id_token", path: ["id_token", "payload", "exp"], params: { jwtCode: "expired" } },
      { code: "invalid_id_token", path: ["id_token", "payload", "aud"], params: { jwtCode: "wrong_audience" } },
    ],
  },
};
```

`error.issues` is never empty, and its type says so, so `result.error.issues[0]` is an issue and not `undefined`. Issues are listed in the order the checks ran. A check that stops at its first failure leaves one issue, and the claim checks of the ID token report every failing claim. The whole result is deeply frozen.

A failed `beginAuthorization` result also has a `redirect`: the response to return to the browser, or `null` when the app must render an error. See [Provider](provider.md#starting-beginauthorization).

## The issue

| Field    | Meaning                                                                                                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `code`   | The stable category of the failure. Branch on it. The type is a union of string literals, and the list below is complete for this version.                                                                                     |
| `path`   | Where the failure is, when it concerns one place: `["callback", "state"]`, `["id_token", "payload", "exp"]`, `["response", "access_token"]`, `["client_id"]`. Omitted when it concerns the whole input or no particular place. |
| `params` | Facts that are never input values: the endpoint, a reason, an HTTP status, a limit, a `jwtCode`, or an OAuth code the provider sent. Omitted when there are none.                                                              |

An issue never holds a value taken from the input: no token, code, secret, verifier, claim value or response body. Where a provider sent an OAuth error, the issue carries the code only when it is one of the OAuth error codes the spec defines, and `unknown` otherwise. A `params.status` is an HTTP status number, and never content.

There are no messages. A code is the whole answer. Map codes to text yourself, and prefer telling a client only "invalid request" when the client may be an attacker.

Three kinds of issue come from `@codenhub/jwt`, not this package. An `invalid_id_token` issue wraps a `@codenhub/jwt` issue: its `jwtCode` names the JWT check, and its `params` carry whatever that check reported, such as `{ limit: "length", maximum: 8192 }` for `too_large` or `{ claim: "exp" }` for `missing_claim`. The `path` is the JWT path with `"id_token"` in front.

## Client issues

These come from `discover`, the client's `callback`, `refresh` and `userinfo`, and their token and userinfo requests.

| Code                     | Where it comes from                                                                                                              | `path`                                                                                                                        | `params`                                                                                                                                                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `request_failed`         | `discover`, the token request, and the userinfo request.                                                                         | None.                                                                                                                         | `endpoint`: `discovery`, `token` or `userinfo`. `reason`: `timeout`, `network`, `status`, `too_large`, `content_type` or `malformed`. `status`, the HTTP status, for `reason` of `status`.                                                                         |
| `invalid_metadata`       | `discover`, for a discovery document.                                                                                            | `["metadata", <member>]`, or `["metadata"]` when the document is not an object or holds an accessor.                          | None.                                                                                                                                                                                                                                                              |
| `issuer_mismatch`        | `discover`, when the document's `issuer` is not the one requested.                                                               | `["metadata", "issuer"]`.                                                                                                     | None.                                                                                                                                                                                                                                                              |
| `invalid_token_response` | The token request, for a `200` response that is not a valid token response.                                                      | `["response", <member>]`, such as `["response", "access_token"]`, or `["response", "id_token"]` when the ID token is missing. | None.                                                                                                                                                                                                                                                              |
| `invalid_userinfo`       | `userinfo`, when the response has no `sub` string.                                                                               | `["userinfo", "sub"]`.                                                                                                        | None.                                                                                                                                                                                                                                                              |

| `subject_mismatch`       | `refresh`, when a new ID token's `sub` is not the subject given. `userinfo`, when the response's `sub` is not the subject given. | `["id_token", "payload", "sub"]` for refresh, `["userinfo", "sub"]` for userinfo.                                             | None.                                                                                                                                                                                                                                                              |

A `provider_error` from the token request carries one of these OAuth codes in `params.error`: `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope` and `server_error`, or any other code of the OAuth and OpenID Connect registries, such as `access_denied` at the callback. A code outside the registries is `unknown`.

## Provider issues

These come from `beginAuthorization` and `completeAuthorization`. The token and userinfo endpoints do not return issues. They answer with the OAuth error responses described in [Provider](provider.md#the-token-endpoint), which carry only the code.

| Code                                                                               | Where it comes from                                                                                                       | `path`                                                                                                                                                | `params`                                                                                  |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `invalid_request`                                                                  | `beginAuthorization`, for a URL, a body, a parameter set, or a missing or malformed parameter.                            | `["client_id"]`, `["response_type"]`, `["response_mode"]`, `["code_challenge"]`, `["code_challenge_method"]`, `["prompt"]` or `["max_age"]`, or none. | `reason`, for a parameter set that does not parse: `duplicate`, `too_many` or `too_long`. |
| `unknown_client`                                                                   | `beginAuthorization`, when no client has the `client_id`. Always rendered.                                                | None.                                                                                                                                                 | None.                                                                                     |
| `invalid_redirect_uri`                                                             | `beginAuthorization`, when `redirect_uri` is missing or not registered. Always rendered.                                  | None.                                                                                                                                                 | None.                                                                                     |
| `unsupported_response_type`                                                        | `beginAuthorization`, when `response_type` is not `code`. Redirected.                                                     | None.                                                                                                                                                 | None.                                                                                     |
| `invalid_scope`                                                                    | `beginAuthorization`, when `scope` lacks `openid`, or names a scope the provider or the client does not have. Redirected. | None.                                                                                                                                                 | None.                                                                                     |
| `request_not_supported`, `request_uri_not_supported`, `registration_not_supported` | `beginAuthorization`, for a `request`, `request_uri` or `registration` parameter. Redirected.                             | None.                                                                                                                                                 | None.                                                                                     |
| `interaction_not_found`                                                            | `completeAuthorization`, when the id is empty or unknown, was completed, or has expired. Not redirected.                  | None.                                                                                                                                                 | None.                                                                                     |

Whether a `beginAuthorization` code redirects depends on whether the client and its redirect URI were verified first. The codes checked after that verification redirect, and the others are rendered. `completeAuthorization` redirects a denial, so a denial's `error` is an OAuth code the client receives and does not produce an issue.

## What throws

Some mistakes throw instead of returning a result. They are bugs in the code that calls the package, and the message names the option or member at fault, never its value.

- **`TypeError` from a synchronous call.** `createClient` and `createProvider` throw when an option is invalid, so a misconfigured client or provider never starts. `createClient` throws, for example, for a non-`https` issuer, a `clientId` that is empty, a `redirectUri` with a fragment, or an `auth.method` the provider does not advertise.
- **`TypeError` from an asynchronous call.** Every other method that takes an options or outcome object rejects with `TypeError` rather than throwing. These are `discover` for its arguments, `client.authorize`, `client.callback`, `client.refresh`, `client.userinfo`, `provider.completeAuthorization`, and `hashClientSecret`. `client.userinfo` also rejects when the metadata has no userinfo endpoint.
- **`TypeError` from the store or the callback.** A malformed client record from `findClient` is a `TypeError`, and so is a `claims` callback that resolves to something other than an object. Both reject the request that reached them.
- **Store and callback failures.** A store method that throws or rejects, and a `claims` callback that throws or rejects, reject the call that reached them. They are not results. See [Store](store.md#errors).

Hostile input never produces a `TypeError`. A token that does not parse, a discovery document with a missing member, and a callback with no `state` each produce an issue, and no operation throws because of them.
